```drill
type: free-form
prompt: "Ручка «список заказов клиента» тормозит: p99 = 1.2 с. Проговори вслух порядок диагностики и что будешь чинить."
answer: "1) EXPLAIN (ANALYZE, BUFFERS) на реальных параметрах: seq scan или index scan, сколько строк реально прочитано против оценки. 2) Проверить индекс: есть ли (customer_id, created_at DESC), совпадает ли порядок колонок с ORDER BY, не мешает ли низкая селективность. 3) Проверить пагинацию: если OFFSET большой — переводить на курсор. 4) Посмотреть на приложение: нет ли N+1 (для каждого заказа тянем клиента и позиции) — лечится JOIN или WHERE id = ANY($1). 5) Проверить объём ответа: не тянем ли 500 полей и вложенные коллекции. 6) Проверить пул: не ждём ли соединение в очереди — тогда база не при чём. И только после этого — кэш или денормализация. Кэш поверх плохого запроса маскирует проблему и умирает при промахе."
check: manual
hint: "Сначала EXPLAIN, потом приложение, кэш — в конце."
```

```drill
type: free-form
prompt: "Объясни вслух, почему пул соединений на 500 к одной PostgreSQL — плохая идея, и как выбрать размер."
answer: "Соединение в PostgreSQL — отдельный процесс со своей памятью (work_mem, буферы). 500 процессов конкурируют за те же ядра и тот же диск: добавляются переключения контекста, конкуренция за блокировки и буферный кэш, и суммарная пропускная способность падает, а p99 растёт. Параллелизм ограничен ресурсами БД, а не желанием приложения. Как выбирать: старт 2–4 × число ядер сервера БД, дальше смотреть на реальную утилизацию и время ожидания в пуле; суммарно по всем инстансам сервиса не превышать max_connections; при десятках инстансов ставить PgBouncer в transaction pooling. Обязательно дедлайны в context, иначе очередь к пулу растёт молча и «медленная база» на деле оказывается медленной очередью."
check: manual
```

```drill
type: free-form
prompt: "Лидер PostgreSQL перестал отвечать. Опиши вслух корректную процедуру failover и три способа всё испортить."
answer: "Процедура: (1) детекция несколькими независимыми наблюдателями с кворумом, а не одним монитором, таймаут подобран так, чтобы не срабатывать на GC-паузу; (2) выбор самой свежей реплики по позиции WAL; (3) fencing старого лидера — физически запретить ему принимать запись (отозвать VIP, закрыть порт, STONITH); (4) промоушен реплики, переключение остальных реплик на нового лидера; (5) переключение приложений — через VIP, service discovery или обновление конфигурации пула, с ротацией соединений (ConnMaxLifetime); (6) разбор: сколько коммитов потеряно при async. Как испортить: не сделать fencing и получить split brain с двумя пишущими лидерами; поставить слишком маленький таймаут и переключаться на каждой паузе; забыть, что при асинхронной репликации хвост коммитов потерян, и не проверить, не пропали ли оплаченные заказы."
check: manual
hint: "Fencing, свежесть реплики, потерянный хвост."
```

```drill
type: free-form
prompt: "Сформулируй вслух ответ на вопрос «CAP: что выберете для платежей и для ленты новостей?»"
answer: "Сначала поправлю рамку: P не выбирают — сети рвутся, поэтому выбор C или A существует только во время разделения; а в обычное время работает PACELC, то есть выбор между задержкой и консистентностью. Для платежей — CP/EC: при разделении лучше отказать в операции, чем провести двойное списание; платим доступностью и задержкой синхронного подтверждения. Для ленты новостей — AP/EL: при разделении отдаём слегка устаревшую ленту, это никого не убьёт; платим тем, что пользователь может увидеть пост с задержкой. И главное: консистентность выбирается по операциям, а не по системе целиком — в одном сервисе баланс линеаризуем, а счётчик просмотров eventual."
check: manual
```

```drill
type: free-form
prompt: "Напиши дизайн-скетч из 5–10 строк: шардирование таблицы orders (500 ТБ, 20k write QPS) — ключ, роутинг, что сломается, как расширяться."
answer: "1) Ключ шардирования — customer_id: он есть почти во всех запросах («мои заказы», «заказ клиента»), распределение равномерное, данные клиента лежат вместе. 2) Не id и не created_at: монотонный ключ даст горячий шард. 3) Роутинг — 1024 логических слота, slot = hash(customer_id) % 1024, таблица «слот → физический узел» в etcd; расширение = перенос слотов без пересчёта хэшей. 4) Каждый шард — лидер плюс две реплики, semi-sync внутри зоны. 5) Сломается: поиск по order_id без customer_id — заводим глобальный индекс order_id → customer_id как отдельную маленькую таблицу; отчёты и админка — переезжают в ClickHouse через CDC. 6) Кросс-шардовые транзакции исчезают: сценарии, затрагивающие двух клиентов, переводим на saga. 7) Горячий клиент-маркетплейс — отдельный шард или салтинг ключа. 8) Переезд без простоя: двойная запись, фоновая копия, сверка, переключение чтения, удаление старого, план отката на каждом шаге."
check: manual
hint: "Ключ → роутинг → что сломается → как расширяться."
```
