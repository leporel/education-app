# Карточки

## Индексы

```card
front: "B-tree: почему поиск в миллиарде строк — это 3-4 обращения к диску?"
back: "Дерево очень широкое: один узел — страница 8 КБ, в неё влезают сотни ключей, поэтому глубина логарифмическая и мала. Листья связаны в список, поэтому индекс обслуживает и диапазоны, и ORDER BY без отдельной сортировки."
tags: [system-design, indexes]
```

```card
front: "Индекс (a, b, c) — какие запросы он ускоряет, а какие нет?"
back: "Работает для условий по a, по (a, b) и по (a, b, c) — то есть по левому префиксу. Не работает для запроса только по b: это как искать в телефонной книге по имени, когда она отсортирована по фамилии."
tags: [system-design, indexes]
```

```card
front: "Почему LIKE 'abc%' индексируется, а LIKE '%abc' — нет?"
back: "B-tree отсортирован по началу значения: с известным префиксом можно спуститься в нужную ветку. У шаблона с ведущим % начала нет, идти некуда — нужен полнотекстовый индекс или триграммы (pg_trgm)."
tags: [system-design, indexes]
```

```card
front: "Что такое covering index и чем за него платят?"
back: "Индекс, содержащий все нужные запросу колонки, — база не ходит в таблицу вообще (index-only scan). Например (customer_id, created_at) INCLUDE (status, total). Цена: индекс толще, запись дороже, места больше."
tags: [system-design, indexes]
```

```card
front: "Как индексы влияют на запись?"
back: "Каждый индекс — отдельная структура, обновляемая при INSERT/UPDATE/DELETE. Пять индексов = пять дополнительных записей на строку плюс расщепление страниц и место (индексы часто больше таблицы). Индексы ускоряют чтение за счёт записи и диска."
tags: [system-design, indexes]
```

```card
front: "Почему индекс по колонке is_active (два значения) бесполезен?"
back: "Низкая селективность: условие отсекает мало строк, и планировщику дешевле прочитать таблицу подряд, чем прыгать по индексу и таблице. Полезен вариант — частичный индекс WHERE status = 'pending' под конкретный сценарий."
tags: [system-design, indexes]
```

```card
front: "B-tree vs LSM-дерево — в чём разница и кто где?"
back: "B-tree обновляет страницы на месте: сбалансированное чтение и запись (PostgreSQL, MySQL). LSM пишет в память и последовательно сбрасывает на диск, потом сливает (compaction): очень быстрая запись, дороже чтение и нужен фоновый compaction (Cassandra, RocksDB)."
tags: [system-design, indexes, storage]
```

## Транзакции и изоляция

```card
front: "ACID — расшифровка и что за что отвечает."
back: "Atomicity — всё или ничего; Consistency — инварианты БД не нарушены; Isolation — параллельные транзакции не видят полуфабрикаты друг друга (в объёме уровня изоляции); Durability — после COMMIT переживём падение, за счёт WAL и fsync."
tags: [system-design, transactions]
```

```card
front: "Что такое WAL и почему из-за него помогает батчинг вставок?"
back: "Write-ahead log: изменения сначала последовательно пишутся в журнал и фиксируются fsync, потом лениво применяются к страницам. Стоимость коммита — это fsync, поэтому групповой коммит и вставка пачками резко повышают пропускную способность."
tags: [system-design, transactions, wal]
```

```card
front: "Четыре классические аномалии параллельного доступа."
back: "Dirty read — прочитал незакоммиченное; non-repeatable read — прочитал строку дважды и получил разное; phantom read — повторил запрос по условию и появились новые строки; lost update — двое прочитали, посчитали и записали, одно изменение потерялось."
tags: [system-design, isolation]
```

```card
front: "Какой уровень изоляции в PostgreSQL по умолчанию и что он допускает?"
back: "Read Committed. Dirty read невозможен (MVCC), но возможны non-repeatable read, phantom и lost update. Поэтому связка SELECT → расчёт в коде → UPDATE без защиты — это готовый lost update."
tags: [system-design, isolation, postgresql]
```

```card
front: "Чем Repeatable Read в PostgreSQL отличается от стандарта?"
back: "Он сильнее: это snapshot isolation, фантомов в привычном виде нет. Зато транзакция может упасть с ошибкой сериализации (could not serialize access) — значит в коде обязателен retry. Serializable реализован как SSI: не блокирует, а отслеживает конфликты и откатывает."
tags: [system-design, isolation, postgresql]
```

```card
front: "Три способа защититься от lost update при списании с баланса."
back: "1) Атомарный SQL: UPDATE ... SET balance = balance - $1 WHERE id = $2 AND balance >= $1. 2) Пессимистично: SELECT ... FOR UPDATE, строка блокируется до конца транзакции. 3) Оптимистично: колонка version и UPDATE ... WHERE version = $2; 0 затронутых строк — читаем заново и повторяем."
tags: [system-design, locking]
```

```card
front: "Пессимистичная или оптимистичная блокировка — когда что?"
back: "Пессимистичная — частые короткие конфликты (списание с одного счёта): проще и предсказуемее. Оптимистичная — редкие конфликты и длинные операции (человек редактирует карточку). На горячей строке FOR UPDATE даёт очередь, а оптимистичная — шторм повторов."
tags: [system-design, locking]
```

```card
front: "Что такое N+1 и почему он опаснее, чем выглядит?"
back: "Один запрос списка плюс по запросу на каждый элемент. Каждый запрос — round trip 0.3–1 мс, на 100 элементах 100 мс чистого ожидания при незагруженной БД: метрики базы выглядят здоровыми, а p99 ручки ужасен. Лечится JOIN, WHERE id = ANY($1) или явным eager loading."
tags: [system-design, n-plus-one]
```

```card
front: "Почему пул соединений к PostgreSQL должен быть маленьким?"
back: "Каждое соединение — отдельный процесс на сервере БД со своей памятью; сотни процессов конкурируют за CPU и диск, добавляя переключения контекста и блокировки. Пропускная способность при уменьшении пула часто растёт. Ориентир: 2–4 × число ядер БД, при многих инстансах — PgBouncer."
tags: [system-design, connection-pool]
```

## Репликация

```card
front: "Что масштабирует репликация, а что — нет?"
back: "Масштабирует чтение и даёт отказоустойчивость. Запись не масштабирует: каждая реплика применяет ВЕСЬ поток изменений лидера. Запись масштабирует только шардирование."
tags: [system-design, replication]
```

```card
front: "Async, sync и semi-sync репликация — что чем платит?"
back: "Async: минимальная задержка, но при падении лидера теряется хвост коммитов. Sync: потерь нет, но запись зависит от доступности и RTT реплики — падение реплики останавливает запись. Semi-sync: подтверждает хотя бы одна из N — компромисс, обычный выбор на практике."
tags: [system-design, replication]
```

```card
front: "Read-your-writes: в чём проблема и три способа решения."
back: "Пользователь написал коммент, перезагрузил страницу, прочитал с отстающей реплики и не увидел его. Решения: читать с лидера N секунд после его записи; запомнить LSN записи и читать с реплики, которая её применила; sticky-роутинг на лидера для страниц после записи."
tags: [system-design, replication, consistency]
```

```card
front: "Что может пойти не так при failover?"
back: "Split brain (два лидера пишут — расхождение сводить руками, защита fencing и кворум наблюдателей); потерянный хвост коммитов при async; ложное срабатывание из-за GC-паузы при малом таймауте и долгий простой при большом; повторная выдача автоинкрементных ID."
tags: [system-design, failover]
```

```card
front: "Реплика — это бэкап?"
back: "Нет. DELETE и DROP реплицируются мгновенно, ошибка приложения приезжает на все реплики за миллисекунды. Бэкап — отдельная сущность с точкой во времени, и он не считается бэкапом, пока не проверено восстановление."
tags: [system-design, replication, backup]
```

```card
front: "Кворум N, W, R — что означает W + R > N?"
back: "N — число копий, W — сколько подтверждают запись, R — из скольких читаем. При W + R > N множества узлов пересекаются, значит чтение увидит хотя бы одну свежую копию. Классика N=3, W=2, R=2. Линеаризуемости это в общем случае не даёт."
tags: [system-design, quorum]
```

```card
front: "Multi-leader: зачем берут и чем всегда платят?"
back: "Берут ради локальной записи в каждом регионе и работы при разрыве между ДЦ. Платят конфликтами: один объект изменён в двух регионах. Стратегии — LWW (теряет данные, зависит от часов), CRDT (сливаются без конфликтов), ручное разрешение. Годится, когда конфликтов почти не бывает по природе данных."
tags: [system-design, replication]
```

## Шардирование и консистентность

```card
front: "Range- и hash-шардирование: плюсы и минусы."
back: "Range (диапазоны ключей): эффективные диапазонные запросы, легко досыпать шарды, но при монотонном ключе (время, автоинкремент) весь новый трафик идёт в один горячий шард. Hash: равномерность, зато диапазонные запросы разлетаются по всем шардам (scatter-gather)."
tags: [system-design, sharding]
```

```card
front: "Три свойства хорошего ключа шардирования."
back: "1) Присутствует почти в каждом запросе (иначе scatter-gather). 2) Даёт равномерное распределение. 3) Держит вместе данные, которые читаются вместе. Примеры: chat_id для мессенджера, customer_id для магазина, (tenant_id, дата) для аналитики."
tags: [system-design, sharding]
```

```card
front: "Celebrity problem: как размазать горячий ключ?"
back: "Key salting — писать в celebrity_id:0..99 и читать со всех подключей; отдельный путь для горячих (обычным — fan-out на запись, знаменитостям — на чтение); кэш перед шардом (горячий ключ отлично кэшируется); rate limiting на уровне ключа."
tags: [system-design, sharding, hot-key]
```

```card
front: "Локальный и глобальный вторичный индекс на шардах."
back: "Локальный (document-partitioned): каждый шард индексирует своё, запись дешёвая, но запрос без ключа шардирования идёт во все шарды и его p99 равен p99 худшего шарда. Глобальный (term-partitioned): индекс шардирован по значению поля, чтение быстрое, но запись распределённая и обычно асинхронная — индекс отстаёт."
tags: [system-design, sharding, indexes]
```

```card
front: "Почему hash(key) mod N плох при добавлении узла и что вместо него?"
back: "При изменении N переезжает почти всё. Вместо: consistent hashing (кольцо 0..2^32 плюс виртуальные узлы — переезжает ~1/N ключей) или фиксированное большое число логических слотов, которые мапятся на физические узлы таблицей (Redis Cluster — 16384 слота)."
tags: [system-design, sharding, consistent-hashing]
```

```card
front: "Лестница действий ПЕРЕД шардированием."
back: "1) Индексы и запросы (половина «нам нужен шардинг» лечится одним индексом). 2) Вертикальный рост. 3) Реплики для чтения, если проблема в чтении. 4) Партиционирование по дате внутри одного сервера. 5) Архивация и TTL. 6) И только потом шардирование."
tags: [system-design, sharding]
```

```card
front: "Почему «выбери два из трёх» в CAP — вводящая в заблуждение формулировка?"
back: "P (сетевое разделение) не выбирают — сети рвутся. Реальный выбор C или A существует только ВО ВРЕМЯ разделения. Плюс C в CAP — это линеаризуемость, а A — «любой живой узел отвечает», а не 99.99 % аптайма. Поведение в обычное время CAP не описывает вовсе."
tags: [system-design, cap]
```

```card
front: "Что добавляет PACELC к CAP?"
back: "If Partition — выбор между A и C; Else — выбор между Latency и Consistency. То есть синхронная репликация платит задержкой каждый день, а не только в аварию. PostgreSQL с sync-репликацией — PC/EC; Cassandra с W=1,R=1 — PA/EL; DynamoDB даёт выбор на уровне запроса."
tags: [system-design, cap, pacelc]
```

```card
front: "Модели консистентности от сильной к слабой — одной строкой каждая."
back: "Линеаризуемая — система как одна машина. Sequential — общий порядок операций, но не обязательно свежий. Causal — причина раньше следствия. Read-your-writes — свои изменения видишь всегда. Monotonic reads — данные не едут назад. Eventual — сойдутся, если перестать писать."
tags: [system-design, consistency]
```

```card
front: "Главная мысль про консистентность для интервью."
back: "Она выбирается ПО ОПЕРАЦИЯМ, а не по системе целиком: баланс кошелька — линеаризуемо, счётчик лайков — eventual, лента — causal с read-your-writes для своих постов. Ответ «у нас strong consistency» без уточнения «где именно» звучит слабо."
tags: [system-design, consistency]
```
