# Карточки

## Основы

```card
front: "Главное свойство кэша, которое нельзя нарушать?"
back: "Кэш — не источник правды. Его потеря должна означать «стало медленно», а не «данные пропали». Если потеря кэша = потеря данных, значит это уже база, и её нужно строить как базу."
tags: [system-design, caching]
```

```card
front: "Три причины ставить кэш?"
back: "1) Латентность (мс вместо десятков мс). 2) Снять нагрузку с дорогого компонента (БД, внешний API, тяжёлый расчёт). 3) Деньги: память дешевле реплик БД и платных вызовов API."
tags: [system-design, caching]
```

```card
front: "Порядки задержек: RAM, локальный кэш в процессе, Redis в том же ДЦ, индексный SELECT в PostgreSQL, round-trip между континентами?"
back: "RAM ~100 нс; in-process кэш 0.1–1 мкс; Redis 0.2–1 мс; SELECT по индексу 1–10 мс; межконтинентальный round-trip 10–150 мс."
hint: "Каждая строка — примерно на порядок больше предыдущей."
tags: [system-design, latency, numbers]
```

```card
front: "Кэш улучшает медиану или p99?"
back: "Прежде всего медиану. p99 определяется промахами (miss + поход в БД), поэтому хвост улучшается слабее. Сильный ответ на интервью: «медиана упадёт в разы, p99 — только если разберёмся с промахами и stampede»."
tags: [system-design, caching, latency]
```

```card
front: "Перечисли уровни кэша на пути запроса."
back: "Браузер (Cache-Control/ETag) → CDN/edge → gateway/reverse proxy (nginx, Varnish) → in-process кэш сервиса → распределённый кэш (Redis/Memcached) → buffer pool БД и page cache ОС."
tags: [system-design, caching]
```

```card
front: "In-process кэш vs Redis — главный trade-off?"
back: "In-process: наносекунды, без сети, но у каждого пода своя копия (N состояний, промахи после деплоя, сложная инвалидация). Redis: общий и переживает деплой, но +сетевой hop (~0.5 мс) и ещё один компонент, который может упасть."
tags: [system-design, caching]
```

## Redis и Memcached

```card
front: "Когда Memcached, а когда Redis?"
back: "Memcached — если нужен только простой большой KV с многопоточной раздачей. Redis — почти всегда: структуры данных (hash, ZSET, stream), атомарные INCR/SETNX, Lua, pub/sub, репликация, персистентность. На интервью аргументируй нужной фичей, а не «Redis круче»."
tags: [system-design, redis, memcached]
```

```card
front: "Какие структуры Redis нужны в дизайне и зачем?"
back: "String — JSON-кэш. Hash — объект по полям (обновить одно поле). ZSET — лидерборд, «последние N», отложенные задачи, sliding window. Set — уникальные (онлайн, дедуп). Stream — лог с consumer groups. Pub/Sub — рассылка без хранения (сброс локальных кэшей). Bitmap/HyperLogLog — дешёвые счётчики уникальных."
tags: [system-design, redis]
```

```card
front: "Чем pub/sub в Redis опасен как «очередь»?"
back: "Он не хранит сообщения: подписчик офлайн — сообщение потеряно навсегда, доставка максимум at-most-once. Годится для сигналов («сбрось локальный кэш»), не годится для задач. Для задач в Redis — Streams."
tags: [system-design, redis, queues]
```

```card
front: "RDB и AOF — в чём разница, и нужны ли они кэшу?"
back: "RDB — периодический снапшот (быстрый рестарт, теряются последние минуты). AOF — журнал команд (appendfsync everysec — потеря до секунды). Для чистого кэша персистентность часто выключают: прогреться проще, чем поднимать устаревший дамп."
tags: [system-design, redis]
```

```card
front: "Как Redis Cluster распределяет ключи?"
back: "16384 хеш-слота: ключ → слот (CRC16) → узел, отвечающий за слот. При решардинге переезжают слоты, а не все ключи. Репликация асинхронная, поэтому подтверждённая запись может потеряться при failover — ещё причина не делать Redis источником правды."
tags: [system-design, redis, cluster]
```

## Стратегии

```card
front: "Cache-aside — как работает и почему это дефолт?"
back: "Приложение смотрит в кэш; miss → читает БД → кладёт в кэш с TTL. Дефолт потому, что просто, кэшируется только реально запрашиваемое, и кэш опционален (упал — просто медленнее). Минусы: код кэша размазан, первый запрос всегда miss, есть окно рассогласования."
tags: [system-design, caching]
```

```card
front: "Write-through: что даёт и чем платим?"
back: "Запись идёт в кэш, кэш синхронно пишет в БД, потом ответ клиенту. Кэш всегда согласован и горячий, чтения почти всегда hit. Платим латентностью записи (два хранилища) и памятью на данные, которые могут никому не понадобиться."
tags: [system-design, caching]
```

```card
front: "Write-behind (write-back) — где уместен и где категорически нет?"
back: "Пишем в кэш, клиенту сразу ok, в БД — асинхронно пачками. Уместен для счётчиков просмотров, лайков, «last seen» — тысячи INCR склеиваются в один UPDATE. Категорически нет для денег и заказов: падение кэша до flush = потеря данных."
tags: [system-design, caching]
```

```card
front: "Read-through чем отличается от cache-aside?"
back: "Логика «miss → сходить в источник» живёт не в приложении, а в слое/библиотеке за кэшем. Приложение только просит ключ. Плюс — единая логика на все сервисы; минус — этот слой становится обязательным компонентом и точкой отказа."
tags: [system-design, caching]
```

## TTL, expiration, eviction

```card
front: "Зачем TTL, если есть явная инвалидация?"
back: "TTL — страховка: он не гарантирует свежесть, но ограничивает возраст лжи. Явную инвалидацию легко забыть (новый код, новый агрегат, ошибка при DEL), а TTL сработает всегда. Правило: TTL ставится всегда."
tags: [system-design, caching, ttl]
```

```card
front: "Expiration и eviction — в чём разница?"
back: "Expiration — удаление по истечении TTL (по времени). Eviction — принудительное вытеснение, потому что кончилась память (maxmemory). Разные причины, разные метрики: expired_keys vs evicted_keys."
tags: [system-design, redis]
```

```card
front: "maxmemory-policy: какие варианты и что выбрать для кэша?"
back: "noeviction (ошибка на запись — для Redis как БД/очереди), allkeys-lru (дефолт для кэша), allkeys-lfu (защита от вытеснения горячего ядра холодным сканом), volatile-lru/volatile-ttl (вытеснять только ключи с TTL), allkeys-random (все ключи равноценны). Для кэша: allkeys-lru или allkeys-lfu."
tags: [system-design, redis, eviction]
```

```card
front: "LRU vs LFU на пальцах?"
back: "LRU смотрит «когда трогали последний раз», LFU — «как часто трогают». Ночной аналитический скан миллиона холодных ключей вытеснит горячее ядро при LRU (cache pollution), но не при LFU. В Redis обе политики приближённые (сэмплинг) — и этого достаточно."
tags: [system-design, redis, eviction]
```

## Инвалидация и консистентность

```card
front: "Правильный порядок при обновлении данных: кэш или БД сначала?"
back: "Сначала БД (commit), потом инвалидация кэша. Обратный порядок (DEL → UPDATE) даёт окно, в котором читатель прочитает старое значение из БД и вернёт его в кэш — stale надолго."
tags: [system-design, caching, consistency]
```

```card
front: "Почему при записи лучше DEL, а не SET нового значения в кэш?"
back: "DEL идемпотентен: следующий читатель просто перезагрузит актуальное. Два конкурирующих SET могут лечь в произвольном порядке, и в кэше останется значение «проигравшего» писателя — рассогласование до TTL."
tags: [system-design, caching, consistency]
```

```card
front: "Что такое delayed double delete и зачем он?"
back: "UPDATE в БД → DEL ключа → через ~0.5–1 с ещё раз DEL. Второе удаление подчищает значение, которое успел записать «опоздавший» читатель, начавший чтение до апдейта. Хак, но известный и рабочий способ сузить окно рассогласования."
tags: [system-design, caching, consistency]
```

```card
front: "Приём «версия в ключе» — что решает?"
back: "Ключ вида product:42:v7; запись поднимает версию, старые ключи просто перестают читаться и умирают по TTL. Не нужно ничего удалять, нельзя «удалить не то», нет гонки DEL/SET. Цена — мусор в памяти до истечения TTL. Тот же приём в CDN — иммутабельные URL с хешем."
tags: [system-design, caching, invalidation]
```

```card
front: "Почему инвалидация кэша «сложная задача»?"
back: "Не потому что DEL трудно вызвать, а потому что копий много (браузер, CDN, gateway, N in-process кэшей, Redis) и зависимостей много (карточка входит в списки, агрегаты, счётчики). Нужно знать все ключи, зависящие от записи, и часть уровней ты не контролируешь вовсе."
tags: [system-design, caching, invalidation]
```

## Stampede и hot keys

```card
front: "Cache stampede — симптом и определение?"
back: "У горячего ключа истёк TTL, и тысячи запросов одновременно промахнулись и пошли в БД за одним и тем же значением. Симптом: периодические всплески нагрузки на БД «по расписанию» TTL, растущая латентность, исчерпанный пул. Синонимы: thundering herd, dogpile."
tags: [system-design, caching, stampede]
```

```card
front: "Четыре способа лечить stampede?"
back: "1) singleflight — дедупликация одинаковых вызовов внутри процесса. 2) Распределённый лок (SET lock NX PX) — один загрузчик на кластер. 3) Jitter в TTL — ключи не истекают синхронно. 4) Early/probabilistic refresh — обновлять до истечения, отдавая stale в это время."
tags: [system-design, caching, stampede]
```

```card
front: "Что делает singleflight.Group.Do?"
back: "Схлопывает параллельные вызовы с одинаковым ключом в один: лидер выполняет функцию, остальные ждут и получают его результат. Защищает от stampede внутри одного процесса; между подами нужен ещё распределённый лок или локальный кэш."
tags: [system-design, go, singleflight]
```

```card
front: "Negative caching — что и зачем?"
back: "Кэшировать и отрицательный результат («такого id нет») с коротким TTL 10–60 с. Иначе поток запросов к несуществующим ключам (сканер, битые ссылки) идёт в БД мимо кэша. Крайний вариант защиты — Bloom filter перед кэшем."
tags: [system-design, caching]
```

```card
front: "Hot key: почему добавление узлов Redis не помогает и что делать?"
back: "Ключ живёт на одном узле/слоте, поэтому горячий шард упирается в своё ядро. Лечится: локальный in-process кэш на 1–5 с (5000 RPS → ~1 RPS с пода), размножение ключа (config:global:0..9 и случайный выбор), реплики для чтения, инвалидация локальных копий через pub/sub."
tags: [system-design, caching, hotkey]
```

## Consistent hashing и оценки

```card
front: "Чем плох hash(key) % N для распределённого кэша?"
back: "При изменении N почти все ключи меняют владельца: кэш обнуляется, весь трафик уходит в БД (мгновенное стадо). Consistent hashing переселяет только ~1/N ключей."
tags: [system-design, caching, hashing]
```

```card
front: "Consistent hashing в двух предложениях + зачем виртуальные узлы?"
back: "Узлы и ключи хешируются в кольцо [0, 2^32); ключ обслуживает первый узел по часовой стрелке, поэтому при добавлении/удалении узла переезжает ~1/N ключей. Виртуальные узлы (100–200 точек на физический) выравнивают нагрузку, иначе распределение получается кособоким."
tags: [system-design, caching, hashing]
```

```card
front: "Что кэшировать плохо?"
back: "Данные, требующие строгой свежести (баланс, остаток при покупке); персонализированные ответы под общим ключом (утечка чужих данных); данные, уникальные для каждого запроса (hit ratio ≈ 0); то, что и так дешёвое (кэш добавит сложность без выигрыша)."
tags: [system-design, caching]
```

```card
front: "Ориентиры hit ratio и что смотреть в метриках?"
back: "< 80 % — кэш почти не работает (пересмотри ключи/TTL); 90–95 % — норма; 99 %+ — данные очень стабильны или ты кэшируешь дешёвое. Метрики: hit ratio, latency кэша, evicted_keys/s (мало памяти), expired_keys, размер горячего набора, доля stampede-загрузок."
tags: [system-design, caching, metrics]
```

```card
front: "Как оценить размер кэша для 1 млн товаров по 2 КБ?"
back: "Полный набор ≈ 2 ГБ + оверхед Redis ~30–80 байт на ключ. Но кэшируют горячее ядро: ~20 % контента даёт ~80 % трафика, значит 200 тыс. × 2 КБ ≈ 400 МБ. Сильный ответ — посчитать горячий набор, а не заказать «Redis на 64 ГБ»."
tags: [system-design, caching, estimation]
```

```card
front: "Что произойдёт и что делать, если Redis полностью недоступен?"
back: "Идём в БД напрямую (кэш не источник правды), но пик трафика её убьёт. Нужны предохранители: короткий таймаут на Redis (~50 мс), singleflight, локальный кэш как второй эшелон, circuit breaker, rate limiting/load shedding. Цель — деградировать в «медленно и частично», а не «лежим»."
tags: [system-design, caching, reliability]
```
