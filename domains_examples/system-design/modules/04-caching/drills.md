# Упражнения

`free-form` задания проговаривай **вслух**, как на интервью: 2–3 минуты на ответ, вслух
называй trade-off и failure-режим. Письменно — только если просят набросок.

## Стратегии и уровни

## Говорим вслух (free-form)

```drill
type: free-form
prompt: "Объясни вслух за 2 минуты, где именно в системе «страница товара интернет-магазина» ты поставишь кэши и почему — снизу вверх по цепочке."
answer: "Картинки и статика — CDN с иммутабельными URL (max-age=год): убирает межконтинентальные 100 мс и не требует инвалидации. HTML/JSON карточки — cache-aside в Redis, ключ product:{id}:v{ver}, TTL 5 мин + jitter, инвалидация после commit; ожидаемый hit ratio ~95 %, БД получает 5 % трафика. Общий конфиг и справочники — in-process кэш на 1–5 с, потому что это hot key и он не должен долбить Redis. Персонализированный блок «вы смотрели» не кэшируем общим ключом — либо ключ с user id и коротким TTL, либо совсем без кэша. И везде TTL как страховка, потому что явную инвалидацию когда-нибудь забудут."
check: manual
```

```drill
type: free-form
prompt: "Интервьюер: «А как вы инвалидируете кэш?» Дай сильный ответ за 90 секунд."
answer: "Три эшелона. Первый — TTL: он не даёт свежести, но ограничивает возраст лжи, и стоит всегда. Второй — явная инвалидация: после COMMIT в БД делаем DEL ключа (именно DEL, не SET, потому что DEL идемпотентен), и я перечисляю зависимые ключи: карточка, список категории, счётчик. Третий — версия в ключе, если зависимостей много: поднял версию — старые ключи никто не читает, умрут по TTL. Признаю окно рассогласования: между commit и DEL читатель может положить старое значение, лечится delayed double delete или инвалидацией из журнала БД через CDC. Если данные не терпят stale вообще — баланс, остаток на складе при оплате — их не кэшируем."
check: manual
```

```drill
type: free-form
prompt: "Напиши набросок (5–10 строк Go, псевдокод допустим) чтения с cache-aside, защитой от stampede и деградацией при недоступном кэше."
answer: "Строки по порядку: (1) key := fmt.Sprintf(\"product:%d\", id); (2) cctx, cancel := context.WithTimeout(ctx, 50*time.Millisecond) — кэш не имеет права тормозить запрос; (3) if p, ok := cache.Get(cctx, key); ok { return p, nil }; (4) v, err, _ := g.Do(key, func() (any, error) { — singleflight, один поход в БД на ключ; (5) p, err := db.Load(ctx, id); (6) if err != nil { return nil, err }; (7) cache.Set(ctx, key, p, ttl+jitter()) — jitter, чтобы ключи не истекали синхронно; (8) return p, nil }); (9) if err != nil { return nil, err }; (10) return v.(*Product), nil. Отдельно проговорить: ошибка Redis не фатальна — логируем и идём в БД, а на входе стоит rate limiter, чтобы падение кэша не превратилось в лавину."
check: manual
```

```drill
type: free-form
prompt: "Интервьюер: «Redis упал целиком. Что происходит с вашим сервисом на 30k RPS?» Ответь вслух."
answer: "Логически — ничего страшного: кэш не источник правды, читаем из БД. Физически — 30k RPS в PostgreSQL её убьют, поэтому падение кэша обязательно проектируется отдельно. Мои предохранители: таймаут на Redis 50 мс, чтобы не висеть на мёртвом сокете; singleflight и локальный кэш как второй эшелон (они снимают основную часть повторов); circuit breaker на кэш, чтобы не дёргать мёртвый узел; rate limiting и load shedding на входе — лучше отдать 429 части трафика, чем уронить БД для всех; readiness не выключаем, чтобы не выкатить каскад. Цель — деградировать в «медленно и частично», а не «лежим целиком». И заранее знать по нагрузочному тесту, какой RPS БД держит без кэша."
check: manual
```

```drill
type: free-form
prompt: "Объясни разницу между cache-aside и write-through так, чтобы понял джун, и скажи, когда write-through действительно лучше."
answer: "Cache-aside: приложение само бегает — заглянул в кэш, не нашёл, сходил в БД, положил в кэш. Write-through: пишем в кэш, а он сам синхронно пишет в БД, и только потом клиенту ok. Первое похоже на «записываю на стикер то, что уже искал», второе — «сразу пишу и в папку, и на стикер». Write-through лучше, когда чтений очень много, записи редкие и важно, чтобы после записи первый же читатель получил hit и свежее значение: тогда мы платим латентностью записи один раз и никогда не отдаём stale. Плохо, когда записей много и большая часть записанного никем не читается — греем кэш зря и удваиваем стоимость записи."
check: manual
```
