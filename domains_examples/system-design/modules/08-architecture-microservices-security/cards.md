# Карточки

## Монолит и микросервисы

```card
front: Четыре настоящие причины выносить сервис из монолита?
back: "1) независимый деплой (команды не ждут друг друга), 2) независимое масштабирование (разный профиль нагрузки), 3) изоляция отказов (OOM в отчётах не роняет заказы), 4) границы команд (закон Конвея). «Чище код» и «модно» в список не входят: чистоту даёт модульность внутри процесса."
tags: [architecture, microservices]
```

```card
front: Что микросервисы дают и чем за это платят — в одной фразе?
back: "Меняют сложность кода на сложность эксплуатации: вызов функции (~100 нс, не падает) становится сетевым вызовом (~1–10 мс, может упасть, затормозить или выполниться без ответа). Каждая стрелка на схеме — таймаут, retry, идемпотентность, метрика, алерт."
tags: [architecture, microservices]
```

```card
front: Что такое модульный монолит и зачем он нужен перед распилом?
back: "Один деплой-артефакт с жёсткими внутренними границами: модули общаются только через интерфейсы, у каждого свои таблицы. Границы проверяет компилятор, двигать их дешево. Вынос сервиса потом = подменить реализацию интерфейса сетевым клиентом + перенести таблицы."
tags: [architecture, monolith]
```

```card
front: Распределённый монолит — признаки?
back: Общая БД у нескольких сервисов; для фичи нужен согласованный релиз 3+ сервисов; длинная цепочка синхронных вызовов на одном запросе; shared library с доменными моделями. Получены сетевые отказы без независимого деплоя и изоляции — минусы обоих подходов.
tags: [architecture, antipattern]
```

```card
front: Bounded context простыми словами?
back: Участок системы, внутри которого термин значит одно и то же. «Заказ» для склада — позиции и адрес; для бухгалтерии — сумма и налог. Одна универсальная модель на всю компанию превращается в класс, который правят все.
tags: [ddd, boundaries]
```

```card
front: Aggregate и практический вывод про транзакции?
back: "Группа объектов, изменяемых как одно целое, с одной входной сущностью (заказ + позиции). Вывод: транзакция должна менять один агрегат. Нужна атомарность по двум агрегатам в двух сервисах — либо граница неверна, либо это saga."
tags: [ddd, transactions]
```

```card
front: Три теста для проверки границы сервиса?
back: Связность (много общения внутри, мало между; болтают на каждый запрос — это один сервис), владение данными (у таблицы один писатель), транзакция (бизнес-операция укладывается в один сервис, иначе saga).
tags: [boundaries]
```

```card
front: Почему «своя БД на сервис» — не бюрократия?
back: Общая БД = общая схема (нельзя менять колонку, не сломав соседа) + нет изоляции отказов (кто-то выжрал пул — легли все) + нет независимого деплоя, то есть нет и смысла в распиле. Чужие данные берут через API владельца или через его события (read model).
tags: [data-ownership]
```

```card
front: Что выносят из монолита первым и что не выносят вообще?
back: "Первым — «листья»: аналитику/отчёты (только читают), нотификации (только слушают события). Не выносят: ядро домена в каждой транзакции, то что релизится вместе, слои (валидация/логика/БД как сервисы), сервисы на 200 строк, общие сущности без определённого владельца."
tags: [architecture, migration]
```

## Общение, gateway, discovery

```card
front: Когда синхронный вызов, а когда событие?
back: Синхронно — только то, без чего нельзя ответить пользователю (проверить баланс). Всё остальное — событием. Пять синхронных хопов по 99.9% дают 99.5% доступности и складывающиеся задержки.
tags: [communication]
```

```card
front: Что делает API gateway и чего он делать не должен?
back: "Делает: TLS-терминация, authn, rate limit, маршрутизация по путям, единые таймауты/ретраи, логи и метрики, иногда агрегация. Не должен: содержать бизнес-логику — иначе это новый монолит в самом критичном месте."
tags: [gateway]
```

```card
front: Зачем BFF, если есть общий API?
back: "Backend for frontend — тонкий бэкенд под конкретного клиента: один запрос мобильного экрана вместо четырёх, свой формат ответа. Не приходится уродовать общий API под всех. Плата — ещё один деплоймент и версионирование."
tags: [gateway, bff]
```

```card
front: Три способа service discovery и их минусы?
back: DNS (просто, но TTL-кэш заставляет стучаться в мёртвые адреса); registry — Consul/etcd (регистрация + health-чек, client-side или server-side); Kubernetes Service (стабильное DNS-имя + список живых endpoints, достаётся бесплатно — потому и стандарт).
tags: [discovery]
```

```card
front: Service mesh — что даёт и когда не нужен?
back: "Sidecar-прокси у каждого сервиса берёт mTLS, retry, таймауты, circuit breaker, балансировку, метрики и трассировку без правки кода. Цена: +1–2 мс, новая система для отладки в 3 часа ночи. Нужен при десятках сервисов и единой политике; для пяти дешевле библиотека и таймауты в коде."
tags: [mesh]
```

## Kubernetes и 12-factor

```card
front: Pod, Deployment, Service, HPA — по одной строке?
back: Pod — минимальная единица запуска (контейнер + sidecar'ы), расходный материал. Deployment — «хочу N реплик образа X», умеет rolling update и rollback. Service — стабильное DNS-имя и балансировка на живые pod'ы. HPA — меняет число реплик по метрике (CPU/RPS/длина очереди).
tags: [kubernetes]
```

```card
front: liveness vs readiness — в чём разница и где ошибка?
back: "liveness = «меня надо перезапустить?», readiness = «можно давать трафик?». Ошибка: проверять БД в liveness — при недоступной БД k8s зациклит перезапуски здоровых pod'ов и превратит частичный отказ в полный. БД проверяют в readiness."
tags: [kubernetes, probes]
```

```card
front: "12-factor: назови пять факторов, которые чаще всего спрашивают."
back: Config в переменных окружения (один артефакт на все окружения); processes — stateless, состояние в БД/кэше; disposability — быстрый старт и graceful shutdown по SIGTERM; logs — поток в stdout, не файлы; build/release/run разделены, релиз неизменяем.
tags: [12factor]
```

```card
front: Как выглядят слои Go-сервиса и где стоят интерфейсы?
back: "handler (HTTP/gRPC: разбор, валидация формата, коды) → service (бизнес-логика) → repository (SQL). Интерфейсы объявляются там, где НУЖНЫ — в бизнес-слое, а не рядом с реализацией. main.go — единственное место склейки. Бизнес-логика не знает ни про HTTP, ни про SQL."
tags: [go, layers]
```

## Аутентификация

```card
front: Authn vs authz?
back: "Authn — «кто ты» (пароль, токен, сертификат). Authz — «что тебе можно» (права на конкретный объект). Проверка токена ≠ право читать заказ #42."
tags: [auth]
```

```card
front: Сессия vs JWT — таблица различий в двух фразах?
back: "Сессия: состояние на сервере, проверка = поход в Redis (~1 мс), отзыв мгновенный, cookie ~30 байт. JWT: состояние у клиента, проверка подписи локально, отзыв сложный (валиден до exp), 300–1500 байт в каждом запросе, ничего общего между сервисами не нужно."
tags: [auth, jwt]
```

```card
front: Пять подводных камней JWT?
back: "1) отзыв (нужен короткий TTL + серверный refresh или denylist по jti — и состояние возвращается), 2) размер в каждом запросе, 3) alg: none и подмена RS256→HS256 — алгоритм фиксирует сервер, 4) payload только подписан, не зашифрован — никакого PII, 5) хранение на клиенте: localStorage уязвим к XSS, cookie требует защиты от CSRF."
tags: [auth, jwt, pitfalls]
```

```card
front: Как сделать мгновенный logout при stateless access-токенах?
back: "Access-JWT короткий (5–15 мин) + refresh-токен хранится и отзывается на сервере: удалил refresh — новых access не будет. Нужен отзыв «сейчас» — denylist по jti в Redis до истечения TTL. Честно признать: denylist возвращает состояние, это плата за мгновенность."
tags: [auth, jwt]
```

```card
front: OAuth2 простыми словами и его четыре роли?
back: "Протокол делегирования доступа: приложение получает ограниченный valet key вместо твоего пароля. Роли: resource owner (пользователь), client (приложение), authorization server (выдаёт токены), resource server (API с данными). Результат — access token с scopes и коротким TTL."
tags: [oauth2]
```

```card
front: Чем OIDC отличается от OAuth2?
back: "OAuth2 — про доступ (авторизацию делегирования), OIDC — тонкий слой поверх, добавляющий аутентификацию: выдаётся id_token (JWT) с утверждениями о том, кто вошёл. Это «Войти через Google»."
tags: [oauth2, oidc]
```

```card
front: Почему authorization code flow, а не «сразу токен»? Что такое PKCE?
back: "Код одноразовый, живёт секунды и обменивается на токен бэкендом — токен не светится в URL/истории. PKCE защищает обмен для клиентов без секрета (SPA, мобильные): клиент присылает verifier к ранее отправленному challenge. Implicit и password гранты устарели."
tags: [oauth2, pkce]
```

```card
front: "API key: чем ограничен и как хранить?"
back: Долгоживущий секрет приложения, грубые права, больно отзывать. Хранить только хеш (как пароль), давать префикс для логов, держать две активные версии для ротации, ограничивать scope и IP, вешать квоту и rate limit на ключ. Альтернатива — OAuth2 client credentials.
tags: [auth, api-key]
```

```card
front: mTLS — что добавляет к обычному TLS и что проверять?
back: Обе стороны предъявляют сертификаты, поэтому сервер знает личность клиента-сервиса без пароля в конфиге. Проверять не только подпись внутреннего CA, но и КТО именно (SAN в allowlist), иначе любой pod сможет звать всё. Цена — PKI и ротация; её обычно берёт mesh.
tags: [mtls]
```

```card
front: Почему нельзя доверять заголовку X-User-Id от клиента?
back: "Это вход от недоверенной стороны: пришлёт X-User-Id: 1 — станет админом. Внутренний контекст пользователя ставит только gateway/auth-слой, а входящие одноимённые заголовки на границе вырезаются."
tags: [security, gateway]
```

## Безопасность

```card
front: Восемь пунктов «базовой безопасности» для интервью?
back: TLS везде (внутри тоже); валидация ввода на сервере (allowlist, лимиты размеров); параметризованные запросы против SQL-инъекций; секреты в хранилище с ротацией, не в git/образе/логах; least privilege (своя роль в БД, network policies); OWASP Top 10; rate limiting против абьюза (логин, коды, дорогие ручки); PII — минимизация и шифрование at rest, пароли через bcrypt/argon2.
tags: [security]
```

```card
front: Что такое IDOR и почему он самый частый?
back: "Insecure direct object reference: GET /orders/43 возвращает чужой заказ, потому что проверили только «пользователь вошёл», а не «этот объект его». Лечится проверкой владения на каждый объект в каждом запросе, а не на входе."
tags: [security, owasp]
```

## Деплой

```card
front: Rolling, blue-green, canary — по одной строке с ценой?
back: Rolling — реплики заменяются пачками, дешево по ресурсам, но версии сосуществуют. Blue-green — второй полный стек и переключение целиком, мгновенный откат кода, 2× ресурсов. Canary — 1%→5%→25%→100% под метриками, ловит проблему на малой доле, требует метрик по версиям и автоотката.
tags: [deploy]
```

```card
front: Главное условие любой стратегии zero-downtime деплоя?
back: "Старая и новая версии должны сосуществовать — по API и по схеме БД. Rolling: реплики разных версий работают одновременно. Blue-green: откат вернёт старый код к уже изменённой базе. Плюс readiness probe и graceful shutdown, иначе это «zero downtime по документации»."
tags: [deploy]
```

```card
front: Deploy vs release и при чём тут feature flags?
back: "Deploy — код на серверах; release — фича видна пользователям. Feature flag разносит их во времени: выкатываем выключенным, включаем на процент/клиента, откат = переключение за секунды. Цена — реестр флагов и обязательная уборка."
tags: [deploy, feature-flags]
```

```card
front: Схема expand/contract целиком?
back: Expand (добавить новое, не ломая старое) → deploy с двойной записью, чтение из старого → backfill пачками + сверка → deploy с чтением из нового (лучше за флагом) → прекратить запись в старое → contract (удалить старое, позже чем кажется). Каждый шаг совместим с обеими версиями кода.
tags: [deploy, migrations]
```

```card
front: Три опасных DDL-операции на большой таблице и их безопасные версии?
back: CREATE INDEX → CREATE INDEX CONCURRENTLY (иначе блокируется запись). ALTER ... SET NOT NULL / добавление колонки с volatile-значением → добавить nullable или с константным DEFAULT, заполнять пачками. Один UPDATE на все строки → батчи по 1–10 тыс. с паузами и контролем лага реплик.
tags: [migrations, postgres]
```
