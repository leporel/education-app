# Упражнения

уточняющий вопрос, потом решение, потом trade-off.

```drill
type: free-form
prompt: "Сервису рекомендаций нужны данные о товарах, которыми владеет сервис каталога. Перечисли три варианта и выбери один с обоснованием."
answer: "1) Синхронно спрашивать каталог на каждый запрос — просто, но доступность рекомендаций умножается на доступность каталога и добавляется задержка. 2) Подписаться на события каталога и держать свою денормализованную read model — рекомендации выживают при падении каталога, цена — eventual consistency и обработка дублей. 3) Понять, что часть данных (например фичи для ранжирования) вообще принадлежит рекомендациям, и перенести владение. Для рекомендаций выбираю (2): они терпят устаревание на секунды, зато не тащат каталог на горячий путь и не создают лишнюю связанность. Общую БД не рассматриваем: она убивает независимый деплой и изоляцию отказов."
check: manual
```

```drill
type: free-form
prompt: "Интервьюер: «Мы разрежем систему на api-service, logic-service и data-service. Что скажешь?» Ответь так, как ответил бы на собеседовании."
answer: "Это нарезка по слоям, а не по домену: любая фича проходит через все три, значит нужен согласованный релиз трёх сервисов и три сетевых хопа на одном запросе. Мы получили задержки и отказы, но не независимый деплой. Резать надо по bounded context (каталог, checkout, склад), где у каждого сервиса своя ответственность, свои таблицы и своя причина меняться. Слои — это структура внутри одного сервиса: handler → service → repository."
check: manual
```

```drill
type: free-form
prompt: "Опиши вслух auth между двумя нашими сервисами так, чтобы «любой pod в кластере» не мог вызывать что угодно."
answer: "mTLS с внутренним CA: у каждого сервиса свой сертификат, вызываемый проверяет и подпись CA, и конкретную личность (SAN в allowlist) — иначе валидный сертификат любого pod'а открывал бы всё. Поверх личности сервиса едет контекст пользователя: короткий внутренний токен, выданный auth-слоем и ограниченный по области («от имени user 17, только чтение заказов») — чтобы сервис не выполнял всё по первой просьбе соседа. Авторизация на объект всё равно проверяется у владельца данных. Входящие снаружи заголовки идентичности вырезаются на gateway. PKI и ротацию сертификатов обычно берёт на себя service mesh."
check: manual
```

```drill
type: free-form
prompt: "Нужно добавить NOT NULL колонку в таблицу на 100 млн строк при 2000 RPS. Опиши план без простоя."
answer: "Шаг 1: добавить колонку nullable (или с константным DEFAULT — в современном PostgreSQL это не переписывает таблицу); NOT NULL сразу не ставить, иначе тяжёлая блокировка и переписывание. Шаг 2: задеплоить код, который пишет колонку для всех новых и изменённых строк. Шаг 3: backfill пачками по 5–10 тысяч с паузами, следя за лагом реплик и WAL; сверить, что NULL-ов не осталось. Шаг 4: добавить CHECK-ограничение как NOT VALID и затем VALIDATE (или выставить NOT NULL, опираясь на уже проверенный CHECK) — валидация берёт более слабую блокировку. Индексы, если нужны, — CREATE INDEX CONCURRENTLY. Каждый шаг совместим со старым и новым кодом, потому что при rolling update версии работают одновременно."
check: manual
```

```drill
type: free-form
prompt: "Проговори вслух схему expand/contract на примере переименования колонки и объясни, почему прямого RENAME достаточно только на мёртвом сервисе."
answer: "RENAME мгновенно ломает старый код, который всё ещё работает: во время rolling update реплики двух версий обслуживают трафик одновременно, и старая версия начнёт получать ошибки «колонка не найдена». Поэтому: expand — добавить новую колонку; deploy — писать в обе, читать старую; backfill пачками + сверка; deploy — читать новую (за feature flag, чтобы откат был секундным); deploy — прекратить запись в старую; contract — удалить старую колонку позже, убедившись по коду и логам запросов, что её никто не читает. Прямой RENAME допустим только при остановленном сервисе, то есть при согласованном простое."
check: manual
```
