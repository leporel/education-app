# Карточки

## Путь запроса, DNS, TCP, TLS

```card
front: Назови семь шагов пути запроса после Enter.
back: DNS (имя → IP) → TCP handshake → TLS handshake → HTTP-запрос → балансировщик выбирает инстанс → сервис считает ответ (кэш/БД/другие сервисы) → ответ обратно. Первые три шага тратят RTT ещё до того, как код проснулся.
tags: [system-design, networking]
```

```card
front: Сколько RTT стоят TCP-handshake и TLS 1.2 / 1.3?
back: "TCP — 1 RTT (SYN, SYN-ACK, ACK). TLS 1.2 — 2 RTT, TLS 1.3 — 1 RTT, при возобновлении сессии (PSK) — 0 RTT. Отсюда терминация TLS на краю сети: пользователь платит RTT до ближайшего узла, а не до дальнего ДЦ."
tags: [system-design, tls, latency]
```

```card
front: Почему DNS — плохой механизм быстрого failover?
back: Клиенты, резолверы и рантаймы кэшируют ответы дольше TTL (некоторые — до перезапуска процесса). DNS хорош для географического распределения (GeoDNS) и грубой раздачи адресов; быстрый failover делают балансировщик и anycast.
tags: [system-design, dns]
```

```card
front: Чем UDP лучше TCP для видео и игр?
back: Потерянный кадр не нужно перепередавать — пока он дойдёт, он устареет. TCP-ретрансмит останавливает поток и даёт заморозку картинки, UDP даёт артефакт и едет дальше. Плюс нет handshake и slow start.
tags: [system-design, tcp, udp]
```

```card
front: Что такое slow start и почему из-за него новое соединение медленное?
back: Congestion control начинает с маленького окна и разгоняется постепенно, чтобы не забить сеть. Поэтому первые пакеты в новом соединении идут медленно — и переиспользование соединений (keep-alive, пул) даёт реальный выигрыш, а не «микрооптимизацию».
tags: [system-design, tcp]
```

```card
front: Три задачи, которые решает TLS.
back: Шифрование (никто по пути не прочитает), аутентификация сервера (сертификат, подписанный доверенным CA), целостность (данные не подменили). Асимметричная криптография — только для согласования ключа, дальше быстрый симметричный шифр.
tags: [system-design, tls]
```

## HTTP/1.1, 2, 3

```card
front: Что такое head-of-line blocking в HTTP/1.1?
back: В одном соединении ответы обязаны идти в порядке запросов — медленный первый ответ держит остальные. Браузеры обходили это шестью параллельными соединениями на домен.
tags: [system-design, http]
```

```card
front: HTTP/2 полностью решил head-of-line blocking?
back: "Нет. На уровне HTTP — да (мультиплексирование независимых streams в одном соединении). Но на уровне TCP осталось: потеря одного сегмента тормозит доставку данных всех streams, потому что для TCP это единый поток байт. Решает HTTP/3 на QUIC."
tags: [system-design, http2, http3]
```

```card
front: Что даёт HTTP/3 / QUIC поверх UDP?
back: Независимые потоки на транспортном уровне (потеря не блокирует остальные), объединённый handshake транспорта и TLS за 1 RTT (0 при resumption), миграция соединения между сетями (Wi-Fi → LTE) без разрыва.
tags: [system-design, http3, quic]
```

```card
front: Когда HTTP/2 не даёт выигрыша или даже хуже 1.1?
back: На одном большом файле выигрыша почти нет. При заметных потерях в сети одно TCP-соединение HTTP/2 может быть хуже шести соединений HTTP/1.1 из-за TCP HOL blocking. Выигрыш HTTP/2 — на многих мелких запросах и на сжатии заголовков.
tags: [system-design, http2]
```

## Стили API

```card
front: REST vs gRPC vs GraphQL — правило выбора одной фразой.
back: Между своими сервисами — gRPC (схема, кодогенерация, стриминг, дедлайны). Для браузера и внешних клиентов — REST (все умеют, кэшируется, отлаживается curl). Когда клиентам нужны разные наборы полей — GraphQL как слой агрегации, а не замена внутренним API.
tags: [system-design, api]
```

```card
front: Главные минусы gRPC.
back: В браузере напрямую не работает (нужен gRPC-Web + прокси); бинарный формат сложнее отлаживать; HTTP-кэширование не применимо; требует инфраструктуры кодогенерации и дисциплины версионирования proto.
tags: [system-design, grpc]
```

```card
front: Четыре вида RPC в gRPC.
back: unary (запрос → ответ), server streaming (один запрос → поток ответов), client streaming (поток запросов → один ответ), bidirectional streaming. Дедлайны gRPC маппятся на context.Context в Go — отмена доходит до сервера.
tags: [system-design, grpc]
```

```card
front: Главные минусы GraphQL.
back: Кэширование по URL не работает (всё POST на один эндпоинт); стоимость запроса трудно ограничить — нужны depth/complexity limits; N+1 на бэкенде лечится дата-лоадерами; мониторинг «медленных ручек» превращается в мониторинг медленных полей.
tags: [system-design, graphql]
```

```card
front: Что такое over-fetching и under-fetching?
back: Over-fetching — сервер отдал объект целиком, а клиенту нужны были два поля (лишний трафик). Under-fetching — одного запроса не хватило, клиент делает N дополнительных (лишние RTT). Это классические болезни REST, ради которых появился GraphQL.
tags: [system-design, api]
```

## Realtime

```card
front: Long polling, SSE, WebSocket — когда что?
back: "Long polling — легаси-клиенты и редкие события, платишь лишними запросами и задержкой цикла. SSE — односторонний поток сервер→клиент по обычному HTTP с авто-reconnect: уведомления, прогресс, тикер. WebSocket — нужен канал в обе стороны: чат, игры, совместное редактирование."
tags: [system-design, realtime]
```

```card
front: Почему WebSocket ломает stateless-архитектуру?
back: "Соединение живёт на конкретном инстансе. Нужны: реестр «пользователь → инстанс» (Redis), доставка сообщений между инстансами (pub/sub или брокер), sticky-балансировка, и план на деплой — рестарт рвёт все соединения, клиенты должны переподключаться с backoff и джиттером."
tags: [system-design, websocket]
```

```card
front: Что ограничивает число одновременных соединений на одном инстансе?
back: Файловые дескрипторы (ulimit), буферы приёма/передачи ядра на каждое соединение и память приложения; в Go — ещё минимум одна горутина на чтение. Поэтому «миллион соединений» — это разговор про лимиты и память на соединение, а не про бизнес-логику.
tags: [system-design, websocket, limits]
```

## Дизайн API

```card
front: Какие HTTP-методы идемпотентны и почему это важно?
back: "GET, HEAD, PUT, DELETE — идемпотентны (повтор не меняет результат); POST — нет. Важно, потому что клиент обязан ретраить при таймауте: повтор идемпотентной операции безопасен, повтор POST без защиты создаёт дубли."
tags: [system-design, api, idempotency]
```

```card
front: Как работает Idempotency-Key?
back: Клиент генерирует уникальный ключ на ПОПЫТКУ операции и шлёт в заголовке. Сервер атомарно вставляет ключ (уникальный индекс + ON CONFLICT DO NOTHING), выполняет операцию и сохраняет ответ; на повтор с тем же ключом возвращает тот же ответ. Если тело другое — 409.
tags: [system-design, idempotency]
```

```card
front: Почему дедупликация по хэшу тела запроса — не идемпотентность?
back: Два законных одинаковых заказа («купить ещё один такой же кофе») неотличимы от ретрая. Ключ должен генерировать клиент на конкретную попытку операции, тогда повтор отличим от нового намерения.
tags: [system-design, idempotency]
```

```card
front: Почему offset-пагинация плоха на больших списках?
back: "OFFSET 100000 заставляет БД пролистать сто тысяч строк перед выдачей — линейно медленно. Плюс окно «плывёт»: вставки между запросами дают дубли и пропуски. Курсорная (keyset) пагинация идёт по индексу и стабильна."
tags: [system-design, api, pagination]
```

```card
front: Как выглядит курсорная пагинация в SQL и чем платим?
back: "WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20 — использует составной индекс, стабильна при вставках, работает на любой глубине. Цена: нельзя прыгнуть на «страницу 57» и нельзя показать общее число страниц дёшево."
tags: [system-design, pagination]
```

```card
front: Правило совместимости версий API.
back: "Добавлять поля можно, удалять и менять смысл существующих — нельзя; клиент обязан игнорировать незнакомые поля. В protobuf это выражено явно: номера полей неизменны, удалённые помечаются reserved. Версия в пути (/v1) проста и видна в логах."
tags: [system-design, api, versioning]
```

```card
front: "Какие статусы использовать: 400, 401, 403, 409, 422, 429, 503?"
back: 400 — синтаксис запроса; 401 — не аутентифицирован; 403 — аутентифицирован, но нельзя; 409 — конфликт состояния (например, другой Idempotency-Key с тем же телом); 422 — ошибка валидации; 429 — лимит превышен (+ Retry-After); 503 — сервис недоступен (+ Retry-After).
tags: [system-design, api, errors]
```

```card
front: Как отдавать долгую операцию (отчёт, транскодирование) через HTTP?
back: "Не держать соединение: POST возвращает 202 Accepted и Location на ресурс задачи; клиент опрашивает статус (pending/running/done/failed) или получает webhook. Это делает ретраи безопасными и даёт место прогрессу и отмене."
tags: [system-design, api, async]
```

```card
front: Какие таймауты обязательны у http.Server в Go и зачем?
back: ReadHeaderTimeout (защита от Slowloris — медленной отправки заголовков), ReadTimeout, WriteTimeout (не держим клиентов, которые не читают ответ), IdleTimeout (keep-alive не вечен, освобождаем сокеты). Без них зависшие соединения съедают дескрипторы.
tags: [system-design, go, timeouts]
```

```card
front: Когда ретраить запрос, а когда нет?
back: Ретраить только идемпотентные операции, только на 5xx и таймауты, с экспоненциальным backoff и джиттером, с ограничением числа попыток. Не ретраить 4xx (клиент ошибся) и небезопасные POST без ключа идемпотентности. Синхронный шторм ретраев добивает больной сервис.
tags: [system-design, retry]
```

## HTTP-кэш, балансировщики, CDN

```card
front: Разница между no-cache и no-store.
back: no-store — не сохранять вообще. no-cache — сохранять можно, но перед использованием ВСЕГДА проверять валидность (условным запросом). Названия обманчивы и их путают постоянно.
tags: [system-design, http-cache]
```

```card
front: Как работает ETag и 304 Not Modified?
back: Сервер отдаёт ETag — отпечаток содержимого. Клиент повторно запрашивает с If-None-Match; если совпало, сервер отвечает 304 без тела — экономим полосу (RTT остаётся). ETag + If-Match даёт оптимистичную блокировку на запись.
tags: [system-design, http-cache]
```

```card
front: "Чем опасны Cache-Control: public и забытый Vary?"
back: public разрешает кэшировать в CDN — если так помечен ответ с персональными данными, один пользователь получит данные другого. То же самое даёт забытый Vary (например, по Authorization или Accept-Encoding). Это реальный класс инцидентов, не теория.
tags: [system-design, http-cache, security]
```

```card
front: L4 vs L7 балансировщик — разница и цена.
back: "L4 работает по TCP/UDP: видит адреса и порты, раскидывает соединения — быстро и дёшево, но про HTTP ничего не знает. L7 разбирает HTTP: роутинг по пути и заголовкам, терминация TLS, ретраи, X-Request-Id, rate limiting. Цена — CPU, доли миллисекунды задержки и ответственность за содержимое."
tags: [system-design, load-balancer]
```

```card
front: Round-robin, least connections, consistent hashing — когда что?
back: "Round-robin — одинаковые запросы и одинаковые серверы. Least connections — когда запросы сильно разной длительности. Consistent hashing — когда за балансировщиком состояние, привязанное к ключу (кэш-слой, шарды): добавление ноды переносит только 1/N ключей."
tags: [system-design, load-balancer]
```

```card
front: Чем отличаются liveness и readiness и какая ловушка в healthcheck?
back: "Liveness — «я жив, не перезапускай»; readiness — «я готов принимать трафик» (прогрев, потеря зависимости). Ловушка: если healthcheck ходит в общую БД, её падение выведет из ротации ВСЕ инстансы разом — вместо деградации получишь полный отказ."
tags: [system-design, health-check]
```

```card
front: Зачем нужен CDN и как в нём инвалидировать контент?
back: "Главное — сократить RTT (10–20 мс до ближайшего узла вместо 150 мс через океан) и снять полосу с origin. Инвалидация — через версионирование URL (app.9f3c1.js), а не purge: purge по всей сети медленный и ненадёжный."
tags: [system-design, cdn]
```
