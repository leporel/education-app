# Упражнения

`free-form` задачи проговаривай вслух с таймером — это буквально вопросы с интервью.

## Транспорт и HTTP

```drill
type: multiple-choice
prompt: "Сколько RTT нужно, чтобы отправить первый HTTP-запрос по новому HTTPS-соединению с TLS 1.3 (без session resumption)?"
options: ["0 — сразу", "1 (только TCP)", "2 (TCP handshake + TLS handshake)", "4"]
answer: "2 (TCP handshake + TLS handshake)"
check: exact
hint: TLS 1.3 — 1 RTT, TCP — 1 RTT.
```

```drill
type: multiple-choice
prompt: "HTTP/2 устранил head-of-line blocking полностью?"
options: ["Да, мультиплексирование решает всё", "Нет: на уровне HTTP решено, но потеря TCP-сегмента тормозит все streams; это лечит HTTP/3 на QUIC", "Нет, HTTP/2 наоборот усилил его", "HOL blocking бывает только в HTTP/1.0"]
answer: "Нет: на уровне HTTP решено, но потеря TCP-сегмента тормозит все streams; это лечит HTTP/3 на QUIC"
check: exact
hint: Два разных уровня.
```

```drill
type: fill-in

answer: QUIC | quic
check: fuzzy
```

```drill
type: free-form
prompt: "Объясни вслух за 90 секунд: что происходит после нажатия Enter на https://shop.example.com/orders/42 — с числами и с выводами."
answer: "1) DNS: браузер смотрит свой кэш, затем ОС, затем резолвер; ответ приходит по UDP, TTL решает, как долго он живёт; без кэша 20–120 мс. 2) TCP: 3-way handshake, 1 RTT, плюс slow start — новое соединение медленное. 3) TLS: ClientHello/ServerHello, проверка сертификата, вывод общего секрета; TLS 1.3 — 1 RTT, resumption — 0. 4) HTTP-запрос уходит на anycast-адрес CDN или L4-балансировщика. 5) L7-прокси терминирует TLS, роутит по пути на нужный сервис, добавляет X-Request-Id, применяет rate limit. 6) Сервис смотрит кэш, потом БД, возможно зовёт соседей. 7) Ответ идёт обратно, keep-alive оставляет соединение открытым. Вывод: при RTT 100 мс ~300 мс уходит до того, как код проснулся, — поэтому TLS терминируем на краю, держим keep-alive и отдаём кэшируемые GET из CDN."
check: manual
hint: Не забудь сказать, какой вывод для дизайна следует из каждого шага.
```

## Стили API и realtime

```drill
type: multiple-choice
prompt: "Внутренний сервис-сервис вызов с двусторонним стримингом событий. Что выбрать?"
options: ["REST + long polling", "gRPC bidirectional streaming", "GraphQL subscriptions через HTTP", "SOAP"]
answer: "gRPC bidirectional streaming"
check: exact
hint: Стриминг в gRPC встроен, а не приделан сбоку.
```

```drill
type: multiple-choice
prompt: "Нужна лента уведомлений в браузере: сервер присылает события, клиент только читает. Минимальное решение?"
options: ["WebSocket", "SSE (text/event-stream)", "Long polling каждые 500 мс", "gRPC-Web streaming"]
answer: "SSE (text/event-stream)"
check: exact
hint: Канал нужен только в одну сторону — зачем платить состоянием WebSocket.
```

```drill
type: free-form
prompt: "Выбери транспорт для чата на 2 млн одновременных пользователей и назови всё, что придётся достроить вокруг него."
answer: "WebSocket: нужен канал в обе стороны с низкой задержкой. Достроить: (1) реестр presence «пользователь → инстанс» в Redis с TTL и heartbeat; (2) маршрутизацию сообщений между инстансами — pub/sub Redis для мелких чатов или Kafka/NATS, если нужна история и гарантии; (3) sticky-балансировку или явный роутинг по реестру; (4) лимит соединений на инстанс (считаем: 2 млн / 50k на инстанс ≈ 40 инстансов) и настройку ulimit/буферов; (5) переподключение с экспоненциальным backoff и джиттером — иначе после деплоя все 2 млн придут одновременно; (6) хранение непрочитанного и доставку офлайн-сообщений через push. Альтернатива: SSE + отдельный POST на отправку — проще, но два канала и хуже задержка отправки."
check: manual
hint: Главное — состояние на сервере, а не сам протокол.
```

```drill
type: free-form
prompt: "Спроектируй вслух API «избранное у пользователя»: список, добавление, удаление. Учти пагинацию, идемпотентность, ошибки и кэширование."
answer: "GET /users/me/favorites?limit=20&cursor=<opaque> → 200 {items, next_cursor}; курсор непрозрачный (base64 от created_at+id), Cache-Control: private, max-age=0 + ETag на список. PUT /users/me/favorites/{item_id} → 204 — намеренно PUT, а не POST: операция идемпотентна по своей природе, повтор безопасен, ключ идемпотентности не нужен. DELETE /users/me/favorites/{item_id} → 204, повторное удаление тоже 204 (идемпотентно), не 404 — так клиентам проще ретраить. Ошибки: 401 без токена, 404 если item_id не существует, 409 при превышении лимита избранного, 429 с RateLimit-* и Retry-After. Версия — /v1 в пути. Ответ содержит только id и минимум полей, детали товара — отдельным запросом или через ?include=item, чтобы не тащить over-fetching."
check: manual
hint: Идемпотентность иногда достигается выбором метода, а не заголовком.
```

## Балансировщики, CDN, отказы

```drill
type: multiple-choice
prompt: "Нужно роутить /api/orders на один сервис, /api/users на другой и терминировать TLS. Какой балансировщик?"
options: ["L4 (TCP)", "L7 (HTTP)", "DNS round-robin", "Anycast"]
answer: "L7 (HTTP)"
check: exact
hint: Роутинг по пути требует разбора HTTP.
```

```drill
type: multiple-choice
prompt: "Healthcheck /healthz каждого инстанса делает SELECT 1 в общую БД. Что произойдёт при недоступности БД?"
options: ["Ничего, это правильная практика", "Все инстансы одновременно выпадут из ротации, и вместо частичной деградации будет полный отказ", "Балансировщик сам поймёт, что дело в БД", "Инстансы перезапустятся и всё починится"]
answer: "Все инстансы одновременно выпадут из ротации, и вместо частичной деградации будет полный отказ"
check: exact
hint: Liveness не должен зависеть от внешних систем.
```

```drill
type: free-form
prompt: "Пользователи в Азии жалуются на медленную загрузку, сервис только в eu-central. Проговори план: что вынести на край сети и что оставить."
answer: "Сначала измерить: RTT Азия↔EU ≈ 150–250 мс, значит 2 RTT на установку соединения — это уже 0.5 с до первого байта. План: (1) CDN/anycast-точки входа: статика (JS, CSS, картинки) с длинным max-age и версионированными URL — сразу минус большая часть запросов; (2) терминация TLS на краю — пользователь платит RTT до ближайшего узла, дальше идёт тёплое соединение до origin; (3) кэшируемые GET-API с ETag и коротким max-age на краю; (4) HTTP/3, чтобы мобильные клиенты с потерями не страдали от TCP HOL blocking; (5) для персональных данных — read-реплика в азиатском регионе, если бизнес терпит лаг репликации; (6) записи оставить в eu-central и явно дать разные SLO на чтение и запись. Что не делать: мультирегиональную запись, пока не докажем необходимость — она тянет конфликты и сложность."
check: manual
hint: Сначала убери RTT с критического пути, только потом двигай данные.
```
