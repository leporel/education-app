## Говорим вслух (free-form)

```drill
type: free-form
prompt: "Интервьюер: «Зачем вам здесь брокер? Почему не сделать всё синхронно?» Ответь за 2 минуты на примере оформления заказа."
answer: "Синхронно оставляю только то, без чего ответ клиенту был бы ложью: создать заказ и зарезервировать товар в одной транзакции. Всё остальное — письмо, бонусы, аналитика, рекомендации, задание складу — асинхронно, потому что иначе p99 ручки становится суммой p99 всех шагов, включая внешний SMTP, а падение почтового сервиса роняет оформление заказов, то есть деньги. С брокером ответ клиенту — 50 мс, а деградация выглядит как рост лага писем, что несравнимо дешевле. Плата: eventual consistency (письма ещё нет, в аналитике заказа пока не видно), дубликаты при at-least-once, необходимость идемпотентности и мониторинга лага. Если продукт требует показать бонусы сразу — либо возвращаю этот шаг в синхронную часть, либо честно показываю статус «обрабатывается»."
check: manual
```

```drill
type: free-form
prompt: "Объясни вслух, как ты обеспечишь, чтобы событие OrderPlaced никогда не потерялось, и почему consumer всё равно должен быть идемпотентным."
answer: "Никогда не публикую из кода после commit — это dual write, и падение между commit и publish теряет событие навсегда. Вместо этого transactional outbox: в одной транзакции INSERT в orders и INSERT в outbox, значит либо есть и заказ, и событие, либо ничего. Отдельный relay (свой процесс или Debezium, читающий WAL) забирает строки outbox и публикует в Kafka, потом помечает отправленными. Relay может упасть после publish, но до отметки — тогда событие уйдёт второй раз. Поэтому доставка остаётся at-least-once, и consumer обязан быть идемпотентным: ключ event_id, вставка в таблицу processed с ON CONFLICT DO NOTHING в той же транзакции, что и эффект. Outbox защищает от потери, идемпотентность — от дублей; нужно и то и другое."
check: manual
```

```drill
type: free-form
prompt: "Напиши набросок (5–10 строк, псевдокод) идемпотентного обработчика платежа с at-least-once доставкой."
answer: "Строки: (1) tx, err := db.Begin(ctx); (2) defer tx.Rollback(); (3) res, err := tx.Exec(ctx, \"INSERT INTO processed_events(event_id) VALUES ($1) ON CONFLICT DO NOTHING\", ev.ID); (4) if rowsAffected(res) == 0 { return AckDuplicate } — этот event уже применён, просто подтверждаем; (5) _, err = tx.Exec(ctx, \"UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1\", ev.Amount, ev.From); (6) проверить, что затронута одна строка, иначе бизнес-ошибка → DLQ; (7) _, err = tx.Exec(ctx, \"INSERT INTO ledger(...) VALUES (...)\"); (8) if err := tx.Commit(); err != nil { return Retry }; (9) msg.Ack(). Ключевое: вставка event_id и сам эффект в ОДНОЙ транзакции, ack только после успешного commit, постоянные ошибки уходят в DLQ, временные — на retry с backoff."
check: manual
```

```drill
type: free-form
prompt: "Интервьюер: «Consumer лежал 3 часа, вы его подняли. Что происходит дальше?» Ответь с числами."
answer: "Если это лог с retention больше трёх часов, ничего не потеряно — сообщения ждут, offset остался на месте. Считаю: при 230 msg/s за 3 часа накопилось ≈ 2.5 млн сообщений. Мои 24 воркера дают 2400 msg/s, приток 230, значит разгребём примерно за 19 минут. Дальше главный вопрос: выдержит ли БД и внешний API 2400 запросов в секунду от разогнавшихся воркеров — если нет, я сознательно ограничиваю параллелизм и разгребаю час, потому что уронить основной сервис ради скорости разгребания глупо. Отдельно проверяю, не протухли ли сообщения по бизнесу (письмо «ваш заказ принят» через 3 часа может быть уже неуместно) — иногда правильнее часть отбросить. И завожу алерт на возраст старейшего необработанного сообщения, чтобы в следующий раз узнать об этом через 5 минут, а не через 3 часа."
check: manual
```

```drill
type: free-form
prompt: "Объясни разницу между событием и командой и почему смешивать их в одном топике — плохая идея."
answer: "Событие — факт в прошлом (OrderPlaced): отправитель не знает, кто его прочитает, потребителей может быть ноль или пятнадцать, связность низкая. Команда — просьба выполнить действие (SendEmail), у неё есть конкретный адресат, ожидание выполнения и обычно право на ошибку и retry в адрес конкретного исполнителя. Смешивать плохо, потому что у них разные требования: у команд нужны приоритеты, отложенная доставка, DLQ и «ровно один исполнитель», у событий — fan-out, retention и replay. Плюс семантика имён: если producer публикует SendEmail, он уже знает про почтовый сервис, и обещанной развязки не получилось — это скрытый синхронный вызов, только через брокер."
check: manual
```
