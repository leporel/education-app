# Упражнения

`free-form` задачи проговаривай **вслух**, с таймером. Цель — не идеальный ответ, а связная
речь без пауз и с числами.

## Каркас и требования

```drill
type: multiple-choice
prompt: "Интервьюер сказал: «Спроектируйте сервис коротких ссылок». Что делать первым?"
options: ["Нарисовать схему таблиц в PostgreSQL", "Задать уточняющие вопросы: сценарии, масштаб, read/write ratio, что вне области", "Сразу посчитать QPS", "Назвать стек: Go, PostgreSQL, Redis, Kafka"]
answer: "Задать уточняющие вопросы: сценарии, масштаб, read/write ratio, что вне области"
check: exact
hint: Оценки без требований считать не из чего.
```

```drill
type: multiple-choice
prompt: "Какое из требований — нефункциональное?"
options: ["Пользователь может создать короткую ссылку", "Владелец видит список своих ссылок", "p99 редиректа не хуже 100 мс при 30k RPS", "Ссылку можно удалить"]
answer: "p99 редиректа не хуже 100 мс при 30k RPS"
check: exact
hint: Нефункциональное — «насколько хорошо», а не «что».
```

answer: требования (функциональные и нефункциональные) | требования

## Оценки

```drill
type: multiple-choice
prompt: "500 млн запросов в сутки — какой средний QPS (порядок)?"
options: ["~600", "~6 000", "~60 000", "~600 000"]
answer: "~6 000"
check: exact
hint: 5×10^8 / 10^5.
```

```drill
type: fill-in
prompt: "20 000 QPS × 1 KB ответа = ____ Mbps исходящего трафика (не забудь ×8 из байт в биты)."
answer: 160 | ~160 | 160 Mbps
check: fuzzy
hint: 20 MB/s → биты.
```

```drill
type: free-form
prompt: "Мессенджер: 50 млн DAU, каждый отправляет 40 сообщений в сутки, среднее сообщение 200 байт (плюс метаданные ~100 байт). Посчитай вслух: write QPS средний и пиковый, прирост данных в сутки, объём за 3 года с индексами."
answer: "Записей в сутки = 50e6 × 40 = 2×10^9. Write QPS = 2×10^9 / 10^5 = 20 000 средний; пик ×3 ≈ 60 000. Размер записи ≈ 300 B → в сутки 2×10^9 × 300 B = 6×10^11 B = 600 GB/день. За 3 года: 600 GB × 365 × 3 ≈ 660 TB «сырых»; ×1.4 на индексы ≈ 900 TB; ×2 на репликацию ≈ 1.8 PB железа. Вывод: одна PostgreSQL исключена, нужен шардинг или wide-column хранилище, плюс TTL/архивация старых сообщений."
check: manual
hint: Сначала записи в сутки, потом делить на 10^5.
```

```drill
type: multiple-choice
prompt: "Оценили: 300 read QPS, 40 GB данных за 3 года. Какой дизайн уместен?"
options: ["Шардированная Cassandra + Kafka + отдельный кэш-кластер", "Один PostgreSQL, 2–3 stateless инстанса сервиса за балансировщиком, кэш по необходимости", "Микросервисы на каждый агрегат + service mesh", "Собственное распределённое KV-хранилище"]
answer: "Один PostgreSQL, 2–3 stateless инстанса сервиса за балансировщиком, кэш по необходимости"
check: exact
hint: Проектировать под нагрузку, которой нет, — красный флаг.
```

## Latency и доступность

```drill
type: multiple-choice
prompt: "Что дороже по времени примерно в 1500 раз, чем обращение к RAM?"
options: ["L2 cache", "Случайное чтение 4 KB с SSD", "Mutex lock/unlock", "Сжатие 1 KB"]
answer: "Случайное чтение 4 KB с SSD"
check: exact
hint: RAM ≈ 100 нс, SSD random ≈ 150 мкс.
```

```drill
type: fill-in
prompt: "Доступность 99.99 % — это примерно ____ минут простоя в месяц."
answer: 4.38 | ~4.4 | 4.4
check: fuzzy
```

```drill
type: multiple-choice
prompt: "Запрос обязательно проходит через 3 сервиса, каждый с доступностью 99.9 %. Итоговая доступность?"
options: ["99.9 %", "≈99.7 %", "≈99.99 %", "99.0 %"]
answer: "≈99.7 %"
check: exact
hint: Девятки последовательной цепочки перемножаются.
```

```drill
type: free-form
prompt: "SLA обещает p99 = 250 мс для пользователей в Европе, а сервис развёрнут только в US-West. Объясни вслух, проходит ли дизайн и что делать."
answer: "Не проходит: один round trip Европа↔US-West ≈ 100–150 мс, а TLS-handshake и DNS добавляют ещё RTT на первом запросе. На бэкенд остаётся почти ничего. Что делать: CDN/edge для статики и кэшируемых GET; терминация TLS на краю сети (экономит RTT); региональное развёртывание сервиса в EU с локальными read-репликами; write оставить в основном регионе, если консистентность требует лидера, и честно дать разные SLO на чтение (быстро) и запись (медленнее). Плюс сократить число последовательных внутренних вызовов."
check: manual
hint: Сложи задержки по хопам, потом ищи, что убрать с критического пути.
```

## Речь и trade-off'ы

```drill
type: multiple-choice
prompt: "Какой ответ звучит как senior?"
options: ["«Поставим Kafka»", "«Тут нужен Redis, он быстрый»", "«30k чтений в пике по одинаковым ключам: варианты — read-реплики или кэш в памяти; беру Redis, он на два порядка быстрее и дешевле реплик, платим инвалидацией»", "«Зависит от ситуации»"]
answer: "«30k чтений в пике по одинаковым ключам: варианты — read-реплики или кэш в памяти; беру Redis, он на два порядка быстрее и дешевле реплик, платим инвалидацией»"
check: exact
hint: Вариант — критерий — выбор — цена.
```

```drill
type: free-form
prompt: "Проговори вслух за 2 минуты требования к сервису «лента новостей соцсети»: 5 функциональных, 6 нефункциональных, 3 пункта вне области."
answer: "Функциональные: опубликовать пост; получить ленту подписок; подписаться/отписаться; лайк; удалить пост. Нефункциональные: 20 млн DAU; read/write ≈ 100:1; p99 чтения ленты ≤ 200 мс; лента может отставать на несколько секунд (eventual consistency), но свой пост автор видит сразу (read-your-writes); доступность чтения 99.99 %, записи 99.9 %; посты хранятся вечно, размер поста ~1 KB + медиа отдельно. Вне области: регистрация/авторизация, реклама и ранжирование ML, модерация контента."
check: manual
hint: Нефункциональные всегда с числами.
```

```drill
type: free-form
prompt: "Напиши дизайн-скетч из 5–10 строк для сервиса коротких ссылок под 3k write QPS и 30k read QPS (только боксы, стрелки и по одному слову «почему»)."
answer: "1) Клиент → CDN не нужен (редирект динамический), сразу L7 LB. 2) LB → stateless Go-сервис, N реплик — горизонтальное масштабирование, легко добавлять. 3) Генерация кода: base62 от счётчика/Snowflake ID — без коллизий и без проверки существования. 4) Запись: PostgreSQL, шардирование по хэшу кода при росте — 90 TB за 5 лет в одну базу не влезет. 5) Чтение: Redis перед БД (код → URL), TTL 24 ч, hit rate ~95 % — 30k QPS в БД не пускаем. 6) Редирект отдаём 301/302: 302 если нужна аналитика по каждому переходу. 7) Аналитика — событие в Kafka, считаем асинхронно, не в критическом пути. 8) Отказ Redis: деградируем в БД, включаем rate limiting. 9) Отказ БД на запись: возвращаем 503 на создание, редиректы продолжают работать из кэша."
check: manual
hint: Каждая строка — компонент плюс причина.
```

```drill
type: free-form
prompt: "Интервьюер: «А что если данных станет 100 ТБ вместо 5?» Проговори реакцию так, как надо, и объясни, почему это не «ловушка»."
answer: "Это не ловушка, а приглашение к следующей теме. Реакция: «Тогда моё решение с одной базой ломается: 100 ТБ не обслужить одним инстансом ни по диску, ни по IOPS, ни по времени бэкапа. Варианты: (а) шардировать по user_id — равномерно и большинство запросов однопользовательские, ценой кросс-шардовых агрегаций; (б) вынести горячие свежие данные в PostgreSQL, а холодный архив — в объектное хранилище с колоночным форматом; (в) сменить хранилище на wide-column. Выбрал бы (а) плюс TTL на холодные данные». Спорить или защищать первый дизайн любой ценой — минус; показать порог, на котором дизайн меняется, — плюс."
check: manual
hint: Назови, где именно ломается прежнее решение.
```
