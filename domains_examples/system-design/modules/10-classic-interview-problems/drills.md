# Упражнения

Мини-дизайны решать **вслух и на время**: 10 минут на `free-form`, засекать. Ответ без чисел
и без trade-off'а считается несданным, даже если технически верен.

```drill
type: free-form
prompt: "Посчитай вслух хранилище для сервиса коротких ссылок: 100 млн ссылок в сутки, запись ~250 байт, срок хранения 5 лет, репликация x3."
answer: "100 млн × 250 Б = 25 ГБ в сутки. За год: 25 ГБ × 365 ≈ 9 ТБ. За 5 лет ≈ 45 ТБ полезных данных. С репликацией x3 — около 135 ТБ, плюс индексы (реально ещё 20–40%), итого порядка 150–180 ТБ. Вывод, который надо озвучить: объём такой, что одна машина не подойдёт, нужен шардированный кластер или KV-хранилище с партиционированием по коду; при этом доступ всегда точечный по ключу, диапазонных запросов нет, значит хеш-партиционирование подходит идеально."
check: manual
```

## Мини-дизайны

```drill
type: free-form
prompt: "За 10 минут спроектируй вслух счётчик просмотров видео (миллиард просмотров в сутки, точность в реальном времени не требуется)."
answer: "Требования: показывать примерное число просмотров, допустима задержка до минуты; точная цифра нужна только для отчётов и выплат авторам. Оценки: 10^9 / 86 400 ≈ 11 600 событий/с, пик x3 ≈ 35 000/с — write-heavy. Наивный UPDATE videos SET views = views + 1 недопустим: горячая строка вирусного видео станет точкой сериализации. Дизайн: событие просмотра шлём в Kafka (буфер и защита от всплесков), консьюмеры агрегируют пачками по видео за окно 10 секунд и делают один инкремент в Redis (HINCRBY) — на дисплей отдаём значение из Redis. Раз в минуту сбрасываем накопленное в постоянное хранилище одним батчем. Для аналитики и выплат считаем точные агрегаты отдельным батч-процессом из того же лога событий, с дедупликацией по event_id — это классический ламбда-подход: быстрый приблизительный путь и медленный точный. Отказы: падение Redis — теряем часть счётчиков, восстанавливаем из лога; лаг консьюмера — счётчик отстаёт, но не ломается. Trade-off: точность в реальном времени обменяна на пропускную способность."
check: manual
```

```drill
type: free-form
prompt: "За 10 минут спроектируй вслух автодополнение поиска (typeahead): 10 подсказок за 100 мс, 100 млн запросов в сутки."
answer: "Требования: до 10 подсказок по префиксу, задержка < 100 мс (иначе подсказка приходит после того, как пользователь дописал), подсказки основаны на популярности запросов, обновление раз в час допустимо. Оценки: 100 млн запросов/сутки ≈ 1200 RPS, но каждый ввод символа — отдельный запрос: при 20 символах на запрос это до 20x, то есть десятки тысяч RPS; часть гасим дебаунсом на клиенте (не чаще, чем раз в 100–200 мс) и кэшем в браузере. Дизайн: читающая часть отделена от строящей. Офлайн: собираем лог запросов, агрегируем частоты за окно, строим структуру префиксов, где в каждом узле уже лежат топ-10 готовых подсказок — тогда чтение это поиск узла и отдача готового списка, без сортировки на лету. Готовые куски раскладываем в Redis или в памяти узлов, шардируем по первым символам префикса. Чтение read-heavy и допускает устаревание — CDN и локальный кэш помогают. Отказы: недоступность хранилища подсказок деградирует функцию, но не поиск в целом. Trade-off: свежесть подсказок (час) обменяна на скорость и простоту; фильтрация нежелательных запросов делается на этапе построения."
check: manual
```

```drill
type: free-form
prompt: "Интервьюер говорит: «Сделаем ленту через fan-out on write для всех, так проще». Возрази аргументированно."
answer: "Для большинства авторов это действительно правильный выбор: 200 подписчиков — 200 вставок, зато чтение O(1). Проблема в хвосте распределения: у знаменитости 50 млн подписчиков, и один её пост даёт 50 млн вставок. Это занимает очередь на десятки секунд, задерживая ленты всех остальных, и создаёт hot spot в хранилище лент; увеличение числа воркеров нагрузку не убирает, а лишь переносит её на storage. Поэтому предлагаю гибрид: авторы выше настраиваемого порога подписчиков не разворачиваются вовсе, их свежие посты лежат в отдельном кэше и подмешиваются при чтении ленты. Плата — merge двух источников и более сложное ранжирование при чтении; выигрыш — публикация звезды стоит O(1), а обычное чтение остаётся быстрым. Дополнительно: ленивая материализация для неактивных пользователей и обрезка ленты до 500–1000 записей, чтобы не платить памятью за тех, кто не заходит."
check: manual
```

```drill
type: free-form
prompt: "Спроектируй вслух API и хранение для «резерва места с оплатой» и объясни, где именно нужна строгая консистентность."
answer: "Строгая консистентность нужна ровно в одном месте — при переходе места из free в reserved; всё остальное (список событий, карта мест на экране) допускает устаревание на секунды и обслуживается из кэша. API: POST /events/{id}/reservations {seat_ids} → создаёт резерв с reserved_until = now() + 10 минут, возвращает reservation_id; POST /reservations/{id}/payment с Idempotency-Key; DELETE /reservations/{id} для отмены. Хранение: таблица seats(event_id, seat_id, status, reserved_until, reservation_id, version) с шардированием по event_id. Захват — одна короткая транзакция: UPDATE ... SET status='reserved' WHERE seat_id=$1 AND (status='free' OR reserved_until < now()); ноль изменённых строк означает, что место занято, отдаём 409. Внутри транзакции никаких внешних вызовов: оплата идёт отдельным шагом saga после коммита, с ключом идемпотентности и компенсацией (возврат места) при отказе. События (билет выпущен, письмо) публикуются через outbox в той же транзакции, что и смена статуса. Плюс фоновый воркер, освобождающий протухшие резервы пачками, и waiting room на старте продаж."
check: manual
```

```drill
type: free-form
prompt: "Интервьюер: «Что сломается первым при росте нагрузки в 10 раз?» Объясни, как строить такой ответ на примере ленты новостей."
answer: "Ответ должен называть конкретное место, а не общие слова. Для ленты первым сломается fan-out на запись: при x10 публикаций работа воркеров растёт линейно и на знаменитостях уже сейчас на пределе — очередь начнёт отставать, ленты обновляться с задержкой в минуты. Второе место — память под предрассчитанные ленты: 800 ГБ превращаются в единицы терабайт, и решение — агрессивнее обрезать ленту и не материализовать неактивных пользователей. Третье — кэш горячих постов: вирусный контент даёт один ключ на весь кластер, лечится локальным кэшем на узлах API и singleflight. План: перевести больше авторов на pull-путь снижением порога знаменитости, шардировать хранилище лент по user_id, добавить локальный кэш и проверить лаг консьюмеров как ключевую метрику. Важно назвать и то, что НЕ сломается: чтение из Redis и гидрация постов масштабируются добавлением реплик."
check: manual
```
