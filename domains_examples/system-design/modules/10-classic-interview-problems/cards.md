# Карточки

## Решающие правила

```card
front: "Read-heavy или write-heavy: как меняется архитектура?"
back: "Read-heavy (10:1 и выше) — кэш, реплики чтения, денормализация; узкое место в попаданиях кэша и hot keys. Write-heavy — буфер/очередь, батчинг, LSM-хранилище; узкое место в скорости записи, WAL и лаге репликации. Первый вопрос после требований, потому что определяет половину дизайна."
tags: [cheatsheet]
```

```card
front: "Fan-out on write vs on read — таблица в двух фразах."
back: "On write (push): работа при публикации O(получателей), чтение O(1) — годится, когда получателей мало, а чтений много. On read (pull): публикация O(1), чтение O(источников) — годится для звёзд с миллионами подписчиков. Правильный ответ почти всегда гибрид."
tags: [cheatsheet, fan-out]
```

```card
front: "Когда шардировать (три условия) и какова цена?"
back: "Когда данные не помещаются на узел, запись упирается в один узел (реплики чтения уже не спасают), или нужна изоляция по клиенту/региону. Цена: нет межшардовых джойнов и транзакций, появляется выбор ключа и риск hot shard, решардинг становится проектом."
tags: [cheatsheet, sharding]
```

```card
front: "Когда кэш оправдан и какие четыре вопроса к нему обязательны?"
back: "Оправдан при перевесе чтений, допустимом устаревании и горячих ключах; кэш не лечит плохой запрос — сначала EXPLAIN. Вопросы: TTL, стратегия инвалидации, защита от шторма промахов (singleflight), поведение при падении Redis (медленнее, но живы)."
tags: [cheatsheet, caching]
```

```card
front: "Когда ставить очередь и чем платим?"
back: "Когда работа не нужна в ответе клиенту (письма, индексация, аналитика), всплесковая, долгая или требует ретраев с DLQ. Платим eventual consistency, дубликатами при at-least-once (нужен ключ идемпотентности), новой инфраструктурой и инцидентами «консьюмер отстал»."
tags: [cheatsheet, queues]
```

```card
front: "Три вопроса про консистентность в любой задаче?"
back: "1) Что видит автор сразу после своей записи (read-your-writes — почти всегда обязателен)? 2) Что и через сколько видят другие (секунда обычно нормально)? 3) Где нужна строгая гарантия — обычно ровно одно место: деньги, инвентарь, уникальность. Туда транзакции и блокировки, остальное eventual."
tags: [cheatsheet, consistency]
```

```card
front: "Бюджет времени на 45-минутное интервью по каркасу?"
back: "Требования 5 мин → оценки 5 мин → high-level схема из 6–8 коробок 10 мин → данные и API 5 мин → deep dive одной трудной части 15 мин → отказы и trade-off'ы 5 мин. Не начинать с решения; считать вслух с единицами; называть trade-off до того, как спросят."
tags: [framework]
```

## URL shortener

```card
front: "Фокус задачи URL shortener?"
back: "Генерация коротких уникальных ID без координации между серверами и выбор режима редиректа (301 vs 302) с его влиянием на аналитику. Схема с кэшем сама по себе — неполный ответ."
tags: [url-shortener]
```

```card
front: "Почему 7 символов base62 и как это считается?"
back: "62^6 ≈ 56 млрд, 62^7 ≈ 3.5 трлн. При 100 млн ссылок в сутки за 5 лет накопится ~180 млрд — шести символов мало, семи хватает с запасом. Числа нужно называть, а не угадывать длину."
tags: [url-shortener, estimation]
```

```card
front: "301 vs 302 для сокращателя — что выбрать и почему?"
back: "301 кэшируется браузером: минимум нагрузки, но аналитика теряется и ссылку нельзя переназначить. 302 приводит каждый переход на сервер: полная статистика и возможность отзыва ценой 100% трафика. По умолчанию 302, нагрузку закрываем кэшем с попаданием 95%+."
tags: [url-shortener]
```

```card
front: "Четыре способа генерации кода и рекомендация?"
back: "Хеш от URL (дедупликация, но коллизии), автоинкремент БД (коротко, но единая точка и предсказуемость), диапазоны ID по 10 000 на узел (без координации на каждый запрос, дырки в нумерации), случайные коды с проверкой (непредсказуемо, нужна проверка занятости). Обычно диапазоны, а при требовании неугадываемости — случайные или перемешанный счётчик."
tags: [url-shortener, id-generation]
```

## Rate limiter

```card
front: "Фокус задачи rate limiter?"
back: "Атомарность счётчика в распределённой среде: GET + проверка + SET — это гонка read-modify-write, дающая превышение лимита на десятки процентов. Нужны INCR и установка TTL одним Lua-скриптом."
tags: [rate-limiter]
```

```card
front: "Сравнение алгоритмов лимитирования по памяти и точности?"
back: "Fixed window — 1 число, грубо, всплеск на границе окна (200 запросов за 2 секунды). Sliding window log — точно, но хранит все метки времени (неприемлемо при сотнях миллионов ключей). Sliding window counter — 2 числа, хорошее приближение. Token bucket — 2 числа, разрешает полезные всплески. Leaky bucket — ровный поток без всплесков."
tags: [rate-limiter, algorithms]
```

```card
front: "Fail-open или fail-closed при недоступности Redis у лимитера?"
back: "Решение принимается по типу защиты и его надо озвучить самому. Для защиты логина от перебора — fail-closed. Для обычного API — fail-open плюс локальный лимитер как грубая страховка: лучше приблизительный лимит, чем никакого. Молчаливый выбор — слабый ответ."
tags: [rate-limiter, failure]
```

## Key-value store

```card
front: "Фокус задачи распределённого KV-хранилища?"
back: "Как остаться доступным при отказе части узлов: consistent hashing с vnodes для размещения, кворумы N/R/W как ручка консистентности, hinted handoff для записи при недоступной реплике, read repair и Merkle-деревья для схождения."
tags: [kv-store, dynamo]
```

```card
front: "Правило R + W > N — что означает?"
back: "N — число реплик, W — подтверждений для успешной записи, R — опрошенных при чтении. Если R + W > N, читающее и писавшее множества пересекаются, и чтение увидит последнюю подтверждённую запись. N=3,W=2,R=2 — типовой выбор; N=3,W=1,R=1 быстрее, но допускает устаревшее чтение."
tags: [kv-store, quorum]
```

```card
front: "Зачем виртуальные узлы в consistent hashing?"
back: "Один физический узел занимает 100–256 позиций на кольце. Это выравнивает распределение, размазывает перераспределение при добавлении/удалении узла по всем участникам (а не по двум соседям) и позволяет учесть разную мощность узлов — сильному даём больше vnodes."
tags: [kv-store, hashing]
```

```card
front: "Hinted handoff простыми словами?"
back: "Реплика C недоступна — координатор всё равно принимает запись, кладя её на другой узел с пометкой «это для C». Когда C оживает, подсказки доставляются. Именно этот механизм даёт высокую доступность на запись при частичных отказах."
tags: [kv-store, failure]
```

## Чат

```card
front: "Фокус задачи чата?"
back: "Маршрутизация к нужному соединению (A на узле 1, B на узле 37 — нужен реестр user → узел) плюс порядок и надёжность доставки: серверный seq на chat_id, ack и client_msg_id как ключ идемпотентности."
tags: [chat]
```

```card
front: "Какая цифра определяет масштаб чата и как её считать?"
back: "Число одновременных WebSocket-соединений. 20 млн онлайн при ~100 000 соединений на узел = 200 узлов только под соединения. Отсюда отдельный слой connection-узлов, отдельный от бизнес-логики, и реестр соединений в Redis с TTL."
tags: [chat, estimation]
```

```card
front: "Почему порядок сообщений задаёт сервер, а не время клиента?"
back: "Часы на устройствах расходятся, а сеть переставляет сообщения. Глобальный порядок не нужен — нужен порядок внутри чата, поэтому сервер присваивает монотонный seq на chat_id. Клиент при переподключении просит всё новее своего последнего seq и так добирает пропуски."
tags: [chat, ordering]
```

```card
front: "Presence и его ловушка масштаба?"
back: "Ключ в Redis с TTL 30 с, обновляемый heartbeat раз в 10 с; истёк — офлайн. Ловушка: рассылать «X онлайн» всем 5000 контактов — шторм fan-out. Лечится подпиской на presence по требованию (только у кого открыт чат с X) и батчингом изменений."
tags: [chat, presence]
```

## Лента

```card
front: "Фокус задачи ленты новостей?"
back: "Гибридный fan-out. Чистый push ломается на знаменитости (50 млн вставок на один пост, очередь занята десятки секунд), чистый pull ломается на обычном чтении (слить 200 источников при 35 000 RPS). Ответ: push для обычных авторов, pull-подмешивание для звёзд."
tags: [feed, fan-out]
```

```card
front: "Почему в предрассчитанной ленте лежат только id постов?"
back: "16 байт против ~1 КБ: 100 млн пользователей × 500 записей помещаются в сотни гигабайт. Плюс при редактировании поста не нужно переписывать миллионы копий. Тексты подтягиваются батчем при отдаче (гидрация) из кэша постов."
tags: [feed, storage]
```

```card
front: "Read-your-writes в ленте — как обеспечивают?"
back: "Свежий собственный пост подмешивается в начало ленты на стороне API, даже если fan-out ещё не отработал. Иначе автор решит, что пост потерялся, — а это самая заметная пользователю ошибка консистентности."
tags: [feed, consistency]
```

## Нотификации

```card
front: "Фокус задачи сервиса нотификаций?"
back: "Дедупликация и вежливость: ключ идемпотентности от отправителя, окно дедупа, ретраи с backoff и DLQ, лимиты на пользователя, тихие часы, приоритетные очереди. Плюс честное признание, что exactly-once с внешним провайдером недостижим."
tags: [notifications]
```

```card
front: "Зачем разводить уведомления по приоритетным очередям?"
back: "Маркетинговая рассылка на 10 млн даёт ~16 700/с и занимает очередь на десятки минут. В общей очереди код подтверждения придёт после рекламы, то есть слишком поздно. Раздельные очереди — это bulkhead: изоляция классов трафика."
tags: [notifications, queues]
```

```card
front: "Каким должен быть ключ идемпотентности уведомления?"
back: "Детерминированным и осмысленным: order-123:status-shipped:user-42, а не случайный UUID на каждую попытку. Случайный защищает лишь от повтора одного запроса, но не от двух сервисов, сообщающих об одном событии. Окно — часы/сутки в Redis плюс вторая линия (уникальный индекс, лимит частоты)."
tags: [notifications, idempotency]
```

## Файловое хранилище

```card
front: "Фокус задачи файлового хранилища?"
back: "Разделение метаданных (маленькие, транзакционные, SQL) и содержимого (большое, неизменяемое, объектное хранилище), чанкинг с адресацией по хешу, дедупликация и разрешение конфликтов синхронизации."
tags: [file-storage]
```

```card
front: "Что даёт чанкинг по 4 МБ — четыре выгоды?"
back: "Докачка после обрыва; дельта-синхронизация (правка 1 МБ в файле 1 ГБ заливает один чанк вместо гигабайта — экономия в сотни раз); дедупликация по хешу (одинаковый контент хранится один раз, клиент заранее спрашивает недостающие хеши); параллельная загрузка в несколько потоков."
tags: [file-storage, chunking]
```

```card
front: "Как файловое хранилище разрешает конфликт двух офлайн-правок?"
back: "Конфликтной копией: сохраняются обе версии (doc (conflicted copy from laptop)). Last-write-wins молча теряет работу пользователя и потому неприемлем. Механика — оптимистичная блокировка по версии: клиент присылает base_version, при расхождении создаётся вторая ветка."
tags: [file-storage, sync]
```

## Бронирование

```card
front: "Фокус задачи бронирования билетов?"
back: "Двойное бронирование. Плюс вторая ловушка: нельзя держать транзакцию с блокировкой строки открытой во время внешнего платёжного вызова — пул соединений исчерпается и встанет весь сервис."
tags: [booking]
```

```card
front: "Пессимистичная vs оптимистичная блокировка при захвате места?"
back: "SELECT FOR UPDATE даёт железную гарантию, но конкуренты ждут на строке — требуется очень короткая транзакция. Оптимистичная (UPDATE ... WHERE status='free' AND version=$n, ноль изменённых строк = занято) не заставляет ждать и лучше при конкуренции за разные места; хуже, когда все дерутся за одно."
tags: [booking, locking]
```

```card
front: "Почему в бронировании saga, а не 2PC, и что такое сверка?"
back: "Внешний платёжный провайдер не участник нашей транзакции, двухфазный коммит с ним невозможен. Шаги резерв → платёж → билет выполняются с компенсациями (отмена резерва, возврат), события публикуются через outbox в той же транзакции. Сверка — ночное сравнение наших платежей с выпиской провайдера; без неё не живёт ни одна платёжная система."
tags: [booking, saga]
```

```card
front: "Что такое waiting room и зачем он на старте продаж?"
back: "Пропуск пользователей в систему фиксированными волнами с показом номера очереди. При 100 000 желающих за 50 000 мест в первую минуту это единственный способ не положить БД: форма load shedding, которая сохраняет и систему, и справедливость очереди."
tags: [booking, load-shedding]
```
