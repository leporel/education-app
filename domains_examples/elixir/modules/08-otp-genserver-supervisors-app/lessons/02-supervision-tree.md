# Урок 02 — Дерево супервизии и Application

Цель: собрать дерево супервизии, увидеть рестарт упавшего процесса своими глазами, разобрать
стратегии и оформить всё как OTP-приложение. Это превращает «процессы, которые могут падать»
в «систему, которая сама себя чинит».

## Разогрев

- Что делает супервизор и почему в нём не должно быть логики? (запуск/надзор/рестарт; простота = надёжность)
- Чем `:one_for_one` отличается от `:one_for_all`? (перезапустить только упавшего / всех детей)
- Где корень дерева в OTP-приложении? (корневой супервизор, запущенный из `Application.start/2`)

## Шаг 1. KV-стор как GenServer (наш подопечный)

```elixir
defmodule KV do
  use GenServer

  def start_link(_opts), do: GenServer.start_link(__MODULE__, %{}, name: __MODULE__)
  def put(k, v), do: GenServer.cast(__MODULE__, {:put, k, v})
  def get(k), do: GenServer.call(__MODULE__, {:get, k})

  @impl true
  def init(state), do: {:ok, state}

  @impl true
  def handle_call({:get, k}, _from, state), do: {:reply, Map.get(state, k), state}

  @impl true
  def handle_cast({:put, k, v}, state), do: {:noreply, Map.put(state, k, v)}
end
```

Обычный GenServer-хранилище. Если он упадёт — состояние (мапа) потеряется. Это нам и нужно,
чтобы увидеть рестарт.

## Шаг 2. Супервизор над ним

```elixir
defmodule MyApp.Supervisor do
  use Supervisor

  def start_link(_), do: Supervisor.start_link(__MODULE__, :ok, name: __MODULE__)

  @impl true
  def init(:ok) do
    children = [
      KV,                                  # short form: вызовет KV.start_link([])
      {Registry, keys: :unique, name: MyApp.Registry}
    ]

    Supervisor.init(children, strategy: :one_for_one)
  end
end
```

`children` — список **child specs**. `KV` (просто модуль) — короткая форма для
`{KV, []}` → `KV.start_link([])`. Стратегия `:one_for_one`: упадёт один — перезапустится
только он.

## Шаг 3. Наблюдаем «let it crash» + рестарт

```elixir
MyApp.Supervisor.start_link(:ok)

KV.put(:lang, "elixir")
KV.get(:lang)                # => "elixir"

# найдём pid процесса KV и грохнем его принудительно
pid = Process.whereis(KV)
Process.exit(pid, :kill)     # имитируем падение

# супервизор почти мгновенно поднял НОВЫЙ процесс KV под тем же именем:
new_pid = Process.whereis(KV)
new_pid != pid               # => true — это другой процесс

KV.get(:lang)                # => nil  — состояние СБРОШЕНО в init (%{})
```

Что произошло:
1. Процесс `KV` умер.
2. Супервизор (он связан с детьми и ловит их выходы) **тут же** запустил новый `KV` через
   `start_link`, снова зарегистрировав имя.
3. Новый процесс стартовал с **чистого** состояния `init` (пустая мапа) — старые данные
   ушли вместе с умершим heap.

Вот он, «let it crash» как механизм: система осталась жива и работоспособна, упавший
компонент восстановлен автоматически. Важный нюанс: **рестарт обнуляет состояние**. Если
данные терять нельзя — персисти их (БД/ETS) и восстанавливай в `init` (об этом ниже).

> **Go-контраст.** В Go всё это — твой код: следящая горутина, цикл рестарта, повторная
> инициализация, бэк-офф при частых падениях. И паника в незащищённой горутине вообще
> положит процесс ОС. Здесь падение **штатно** и локально, а восстановление декларативно.

## Шаг 4. Стратегии — какую когда

```elixir
# :one_for_one — дети независимы (кэш, метрики, пул) — упал один, поднять одного
Supervisor.init(children, strategy: :one_for_one)

# :one_for_all — дети образуют единое целое и должны стартовать из согласованного состояния
# (например, процесс-писатель и процесс-индекс, которые без друг друга бессмысленны)
Supervisor.init(children, strategy: :one_for_all)

# :rest_for_one — поздние зависят от ранних (соединение → сессия → обработчик):
# упал ранний — перезапустить его и всех, кто после
Supervisor.init(children, strategy: :rest_for_one)
```

И предохранитель эскалации: если ребёнок падает чаще `max_restarts` (по умолч. 3) за
`max_seconds` (по умолч. 5), супервизор сдаётся и падает сам — проблему получает его
родитель. «Рестарт не лечит → решай уровнем выше». Так дерево не зацикливается на бесконечном
перезапуске безнадёжного компонента.

## Шаг 5. Оформляем как Application

Чтобы дерево поднималось автоматически при старте (`iex -S mix`, релиз), делаем корневой
супервизор колбэком `Application.start/2`. С `mix new myapp --sup` это уже сгенерено:

```elixir
defmodule MyApp.Application do
  use Application

  @impl true
  def start(_type, _args) do
    children = [
      KV,
      {Registry, keys: :unique, name: MyApp.Registry}
    ]

    opts = [strategy: :one_for_one, name: MyApp.Supervisor]
    Supervisor.start_link(children, opts)
  end
end
```

В `mix.exs`:

```elixir
def application do
  [
    extra_applications: [:logger],
    mod: {MyApp.Application, []}      # ← точка входа: что запускать при старте приложения
  ]
end
```

Теперь `iex -S mix` сам поднимет `MyApp.Application.start/2` → корневой супервизор → всех
детей. Зависимости (Phoenix, Ecto) — тоже OTP-приложения, и их деревья стартуют до твоего.
Вся система — «дерево деревьев» под надзором.

## Шаг 6. А если состояние терять нельзя?

Рестарт обнуляет состояние до `init`. Решение — **восстанавливать в `init`** из надёжного
источника:

```elixir
@impl true
def init(_) do
  state = MyApp.Storage.load() || %{}   # подтянуть из БД/ETS/файла
  {:ok, state}
end
```

Тогда после падения новый процесс поднимется уже с восстановленными данными. Это и есть
дисциплина OTP: процесс держит **рабочее** состояние, а **истину** — персистентный слой;
рестарт лечит «застрявшее» рабочее состояние, не теряя важного.

## Итог

Супервизор связывается с детьми, ловит их падения и перезапускает по стратегии
(`:one_for_one` / `:one_for_all` / `:rest_for_one`), а предохранитель `max_restarts`
эскалирует безнадёжное вверх. `Application.start/2` поднимает корневой супервизор — вся
система становится самовосстанавливающимся деревом процессов. Рестарт обнуляет состояние,
поэтому критичное персисти и восстанавливай в `init`. Это и есть отказоустойчивость как
архитектура — то, ради чего учат Elixir. Дальше — тулинг, тесты и сборка всего этого в
реальный проект (плюс врезка про Phoenix).
