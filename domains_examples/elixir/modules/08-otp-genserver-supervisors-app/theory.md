# OTP: GenServer, супервизоры, Application

## Зачем OTP, если есть spawn/receive

В модуле 07 ты написал работающий процесс с состоянием — руками. Но в нём не хватало кучи
скучного, но важного: корректный запрос-ответ с таймаутом и мониторингом сервера; аккуратное
завершение; единый формат состояния; интеграция с инструментами отладки; перезапуск при
падении. Писать это заново в каждом процессе — ошибки и боль.

**OTP** (Open Telecom Platform) даёт готовые **поведения** (behaviours, модуль 06):
`GenServer`, `Supervisor`, `Application`. Ты реализуешь колбэки — а проверенный временем
каркас берёт на себя весь протокол. Это не фреймворк поверх языка, а *стандартная библиотека
конкурентности*, ради которой Elixir и существует.

## GenServer: твой receive-цикл как behaviour

GenServer — обобщённый сервер. Сравни напрямую с ручным `Account` из модуля 07:

| Руками (модуль 07) | GenServer |
| --- | --- |
| `spawn(fn -> loop(state) end)` | `GenServer.start_link(__MODULE__, arg)` → колбэк `init/1` |
| `loop(state)` рекурсия | каркас сам зовёт твои колбэки в цикле |
| запрос-ответ `send` + `receive` | `GenServer.call/2` → колбэк `handle_call/3` |
| «выстрелил и забыл» `send` | `GenServer.cast/2` → колбэк `handle_cast/2` |
| произвольное сообщение в mailbox | колбэк `handle_info/2` |
| `{:state, balance}` как аргумент loop | `state` — возвращается из каждого колбэка |

```elixir
defmodule Counter do
  use GenServer

  # ── Клиентский API (прячет GenServer-протокол) ──
  def start_link(initial \\ 0), do: GenServer.start_link(__MODULE__, initial, name: __MODULE__)
  def inc(n \\ 1), do: GenServer.cast(__MODULE__, {:inc, n})    # async
  def value, do: GenServer.call(__MODULE__, :value)            # sync

  # ── Серверные колбэки (выполняются ВНУТРИ процесса) ──
  @impl true
  def init(initial), do: {:ok, initial}                        # начальное состояние

  @impl true
  def handle_call(:value, _from, state), do: {:reply, state, state}   # ответ, новое состояние

  @impl true
  def handle_cast({:inc, n}, state), do: {:noreply, state + n}        # нет ответа, новое состояние
end
```

```elixir
Counter.start_link(0)
Counter.inc(5)
Counter.inc(3)
Counter.value()     # => 8
```

Разбор:
- **`init/1`** возвращает `{:ok, state}` — начальное состояние (как `balance` в `spawn`).
- **`handle_call(request, from, state)`** — **синхронный** запрос: вызывающий **ждёт** ответ.
  Возвращает `{:reply, answer, new_state}`. Это автоматизированный запрос-ответ из модуля 07,
  с таймаутом (по умолчанию 5 с) и мониторингом — если сервер умрёт, `call` не зависнет, а
  упадёт с понятной ошибкой.
- **`handle_cast(request, state)`** — **асинхронный** «выстрелил и забыл»: возвращает
  `{:noreply, new_state}`, вызывающий не ждёт. Для команд без ответа (`inc`).
- **`handle_info(msg, state)`** — для сообщений, пришедших **не** через call/cast (таймеры
  `Process.send_after`, `{:DOWN, ...}` от мониторов, чужие `send`).
- **`name: __MODULE__`** регистрирует процесс под именем модуля — можно звать по имени, не
  таская pid.

> **Call vs cast — важный выбор.** `call` синхронен и создаёт **back-pressure**: клиент
> ждёт, значит не завалит сервер быстрее, чем тот успевает. `cast` асинхронен и быстр, но
> при перегрузке mailbox растёт без удержу (грабли из модуля 07). Правило: по умолчанию
> `call` (особенно если нужен результат или контроль темпа); `cast` — для честно «огонь и
> забыл», когда переполнение невозможно.

> **Go-параллель.** GenServer ≈ «горутина-владелец состояния + канал запросов» — паттерн,
> который в Go пишут руками (`for { select { case req := <-ch: ... } }`). Здесь это
> стандартный, оттестированный кирпич с таймаутами, мониторингом и интеграцией с супервизией
> из коробки.

### `init` должен быть быстрым: `handle_continue`

Пока `init/1` не вернулся, **супервизор заблокирован**: он ждёт запуска этого ребёнка, а
значит, стоит старт всего дерева, а с ним и приложения. Поэтому тяжёлую подготовку — прогрев
кэша, чтение из БД, соединение с внешним сервисом — из `init` выносят.

Штатный способ — `handle_continue/2`. `init` мгновенно возвращает заготовку состояния и
инструкцию «продолжи вот этим», а долгая работа выполняется уже после старта, но **до** первого
сообщения от клиентов:

```elixir
@impl true
def init(opts) do
  {:ok, %{cache: nil, opts: opts}, {:continue, :warmup}}   # старт мгновенный
end

@impl true
def handle_continue(:warmup, state) do
  {:noreply, %{state | cache: Storage.load()}}             # долгая работа здесь
end
```

Есть и `terminate/2` — колбэк «прибраться перед смертью». Но полагаться на него как на
гарантированный деструктор нельзя: он **не вызывается** при `:kill` (модуль 07) и при падении
родителя. Всё критичное персисти сразу, а не на выходе.

### `start_link` или `start`?

`start_link` **связывает** новый процесс с тем, кто его создал; `start` — нет. Под супервизором
нужен именно `start_link`: связь (`link` из модуля 07) — это и есть способ, которым супервизор
узнаёт о падении ребёнка. Отсюда конвенция: публичная функция модуля называется `start_link/1`,
а `GenServer.start` берут в редких случаях «процесс сам по себе, вне дерева» — например, в
тестовой утилите.

## Supervisor: дерево перезапуска

Супервизор — процесс, чья **единственная работа** — запускать дочерние процессы, следить за
ними (через `link` + `trap_exit`, модуль 07) и **перезапускать** упавших по заданной
стратегии. Сам супервизор логики не несёт — он надёжен именно потому, что туп и прост.

```elixir
children = [
  {Counter, 0},                 # child spec: модуль + аргумент start_link
  {MyApp.Cache, []},
  {Registry, keys: :unique, name: MyApp.Registry}
]

Supervisor.start_link(children, strategy: :one_for_one)
```

### Что такое child spec на самом деле

Список `children` состоит не из модулей, а из **спецификаций детей** (child spec) — карточек
«как запускать, как перезапускать, как останавливать». Три записи ниже означают одно и то же:

```elixir
children = [
  Counter,                # 1) короткая форма: взять Counter.child_spec([])
  {Counter, 0},           # 2) то же, но с аргументом: Counter.child_spec(0)
  %{                      # 3) полная форма — то, во что разворачиваются первые две
    id: Counter,
    start: {Counter, :start_link, [0]},
    restart: :permanent,
    shutdown: 5_000,
    type: :worker
  }
]
```

Откуда у модуля берётся `child_spec/1`? Его генерирует `use GenServer` — вот зачем в модуле 06
надо было понять, что `use` просто вставляет сгенерированный код. Отдельные поля можно
переопределить, не расписывая всю карточку:

```elixir
use GenServer, restart: :transient, shutdown: 10_000
```

Что означают поля:

- **`id`** — идентификатор ребёнка внутри супервизора (по умолчанию имя модуля; двум одинаковым
  воркерам придётся задать разные `id` вручную).
- **`start`** — тройка `{модуль, функция, аргументы}`, которую супервизор вызовет.
- **`restart`** — политика перезапуска (`:permanent` / `:temporary` / `:transient`, см. ниже).
- **`shutdown`** — сколько миллисекунд ждать вежливого завершения, прежде чем послать `:kill`.
- **`type`** — `:worker` или `:supervisor`: супервизоры тоже бывают детьми, так и растёт дерево.

**Стратегии рестарта** — что делать, когда падает один ребёнок:
- **`:one_for_one`** — перезапустить **только** упавшего. Самая частая (дети независимы).
- **`:one_for_all`** — перезапустить **всех** детей (когда они тесно связаны и должны
  стартовать вместе из согласованного состояния).
- **`:rest_for_one`** — перезапустить упавшего **и всех, кто объявлен после него** (когда
  поздние зависят от ранних).

**Restart-политика ребёнка** (`restart:`):
- `:permanent` (по умолчанию) — перезапускать всегда (долгоживущие сервисы).
- `:temporary` — не перезапускать никогда (одноразовые задачи).
- `:transient` — перезапускать, только если упал ненормально (не `:normal`/`:shutdown`).

Есть и предохранитель: если ребёнок падает слишком часто (`max_restarts` за `max_seconds`),
супервизор сдаётся и падает сам — пробрасывая проблему **выше по дереву**. Это не баг, а
фича: «если рестарт не помогает, пусть решает родитель» — так дерево локализует и эскалирует
сбои.

> **Go-контраст (ключевой).** В Go нет встроенной супервизии. «Перезапустить упавший воркер»
> ты пишешь сам: `recover` в горутине, цикл рестарта, бэк-офф, флаги здоровья. OTP даёт это
> декларативно и единообразно: опиши дерево детей и стратегию — рантайм обеспечит
> самовосстановление. Отказоустойчивость становится **структурой программы**, а не россыпью
> defensive-кода.

## Application: корень дерева

OTP-**приложение** — это единица упаковки и запуска: модуль с `use Application` и колбэком
`start/2`, который поднимает **корневой супервизор** со всем деревом. `mix new --sup` создаёт
заготовку; в `mix.exs` указывается `mod: {MyApp.Application, []}`.

```elixir
defmodule MyApp.Application do
  use Application

  @impl true
  def start(_type, _args) do
    children = [
      {Counter, 0},
      {MyApp.Cache, []}
    ]
    Supervisor.start_link(children, strategy: :one_for_one, name: MyApp.Supervisor)
  end
end
```

Запускаешь `iex -S mix` — и всё дерево поднимается автоматически. Зависимости (Phoenix,
Ecto) — тоже OTP-приложения со своими деревьями; твоё приложение стартует поверх них. Это
«дерево деревьев»: вся система — единая структура супервизии.

## Готовые абстракции поверх GenServer

Не каждый процесс надо писать как полный GenServer. OTP даёт специализированные кирпичи:

- **`Task`** — для асинхронной работы и параллелизма:
  ```elixir
  task = Task.async(fn -> expensive() end)
  result = Task.await(task)                         # ≈ go + канал результата
  Task.async_stream(urls, &fetch/1, max_concurrency: 10)  # параллельная map с лимитом!
  ```
  `Task.async_stream` — рабочая лошадка параллельной обработки коллекций с ограничением
  одновременности (то, для чего в Go городят пул горутин + семафор).

- **`Agent`** — тончайшая обёртка «процесс как изменяемая ячейка состояния», когда логика не
  нужна, только хранилище:
  ```elixir
  {:ok, pid} = Agent.start_link(fn -> %{} end)
  Agent.update(pid, &Map.put(&1, :k, 1))
  Agent.get(pid, & &1[:k])                          # => 1
  ```

- **`Registry`** — реестр «имя → pid» для динамических процессов (когда детей много и они
  создаются на лету).
- **`DynamicSupervisor`** — супервизор для детей, добавляемых в рантайме (по одному на
  пользователя/соединение).
- **`:ets`** (Erlang Term Storage) — встроенные in-memory таблицы с быстрым конкурентным
  доступом, *вне* heap процесса; для кэшей и общих read-heavy данных без узкого горлышка
  GenServer. Обзорно: знай, что это есть, когда «один GenServer стал бутылочным горлом».

### Динамические дети: `DynamicSupervisor` и `Registry`

Обычный `Supervisor` знает список детей заранее. Но часто процессы появляются **в рантайме**:
по одному на пользователя, на игровую комнату, на соединение. Для этого есть пара инструментов.

```elixir
# в дереве приложения:
children = [
  {Registry, keys: :unique, name: MyApp.Registry},
  {DynamicSupervisor, name: MyApp.RoomSupervisor, strategy: :one_for_one}
]

# создаём комнату по требованию:
DynamicSupervisor.start_child(MyApp.RoomSupervisor, {Room, id: "room-42"})

# внутри Room регистрируемся под составным именем:
def start_link(opts) do
  id = Keyword.fetch!(opts, :id)
  GenServer.start_link(__MODULE__, opts, name: {:via, Registry, {MyApp.Registry, id}})
end

# и обращаемся к комнате по идентификатору, не зная pid:
GenServer.call({:via, Registry, {MyApp.Registry, "room-42"}}, :state)
```

`Registry` — встроенная таблица «ключ → pid», которая сама вычищает записи умерших процессов;
`{:via, Registry, ...}` — способ адресовать процесс через неё. Так решается проблема из модуля
07: имён-атомов на тысячи процессов не напасёшься, а ключом `Registry` может быть любой терм —
строка, кортеж, id пользователя.

> **Go-параллель.** Это ровно то, что в Go пишут руками: `map[string]*Worker` под мьютексом,
> плюс удаление записи при завершении воркера, плюс своя логика перезапуска. Здесь обе части —
> стандартные и давно отлаженные.

## Как думать об отказоустойчивости

1. **Раздели систему на процессы** по ответственности и по «единице сбоя» (что не страшно
   перезапустить независимо).
2. **Состояние, которое не жаль потерять при рестарте**, держи в процессе; что жаль —
   персисти (БД/ETS) и восстанавливай в `init`.
3. **Построй дерево**: что перезапускать вместе (`:one_for_all`), что независимо
   (`:one_for_one`), что зависит по порядку (`:rest_for_one`).
4. **Дай падать.** Happy-path без оборонительного кода; непредвиденное → падение → рестарт в
   чистое состояние.

Это и есть «think in trees»: надёжность проектируется как форма дерева процессов.

## Глоссарий модуля

- **OTP** — набор стандартных поведений и библиотек поверх BEAM.
- **GenServer** — behaviour «обобщённый сервер»: свёрнутый `receive`-цикл с состоянием.
- **`init/1`** — колбэк старта, возвращает `{:ok, state}`; должен быть быстрым.
- **`handle_call/3` / `handle_cast/2` / `handle_info/2`** — синхронный запрос / асинхронная
  команда / прочая почта (таймеры, `{:DOWN, ...}`).
- **`handle_continue/2`** — «доделать после старта»: тяжёлая инициализация без блокировки
  супервизора.
- **`terminate/2`** — попытка прибраться перед смертью; **не** вызывается при `:kill` и при
  падении родителя.
- **Back-pressure** — естественное торможение клиента: `call` ждёт ответа, `cast` — нет.
- **`start_link` vs `start`** — со связью с родителем (нужно под супервизором) и без.
- **Child spec** — карточка ребёнка: `id`, `start` (MFA), `restart`, `shutdown`, `type`;
  генерируется `use GenServer` как `child_spec/1`.
- **Стратегии** — `:one_for_one` (только упавшего), `:one_for_all` (всех),
  `:rest_for_one` (упавшего и объявленных после него).
- **Restart-политики** — `:permanent` (всегда), `:temporary` (никогда),
  `:transient` (только при аварийном завершении).
- **`max_restarts` / `max_seconds`** — предохранитель: слишком частые падения роняют самого
  супервизора, эскалируя проблему вверх.
- **Application** — единица запуска и упаковки: `use Application` + `start/2`, поднимающий
  корневой супервизор.
- **`Task`** — асинхронная работа: `async/await`, `async_stream` с `max_concurrency`.
- **`Agent`** — процесс-ячейка состояния без своей логики.
- **`DynamicSupervisor`** — супервизор для детей, создаваемых в рантайме.
- **`Registry`** — таблица «ключ → pid» для адресации множества процессов;
  `{:via, Registry, {...}}` как имя.
- **`:ets`** — in-memory таблицы вне heap процесса; конкурентное чтение без узкого горлышка.

## Типичные ошибки и заблуждения

- **Всё на `cast`.** Асинхронный `cast` без back-pressure переполняет mailbox при перегрузке.
  По умолчанию — `call` (ждёт, тормозит клиента, держит темп); `cast` — только для честного
  «огонь и забыл».
- **Тяжёлая работа прямо в `handle_call`.** Колбэк блокирует **весь** GenServer (он
  однопоточен по сообщениям). Долгие операции выноси в `Task` или отдельный процесс, чтобы
  сервер не висел и не копил mailbox.
- **Супервизор с бизнес-логикой.** Супервизор должен только запускать/следить/перезапускать.
  Логику — в GenServer'ы под ним. Толстый супервизор ненадёжен.
- **Ловить ошибки, чтобы «не упало».** Это против OTP. Пусть падает — супервизор поднимет.
  `try/rescue` — для редкого ожидаемо-исключительного, не для «защиты от рестарта».
- **Хранить в процессе то, что нельзя терять, без персистентности.** Рестарт обнулит
  состояние до `init`. Критичные данные — в БД/ETS, восстанавливай при старте.
- **Один GenServer как глобальный шлюз ко всему.** Он сериализует доступ → становится
  бутылочным горлом. Дроби на процессы или используй ETS для read-heavy данных.
- **Путать `Task.async/await` с fire-and-forget.** `Task.async` создаёт связанный процесс и
  ждёт `await`; если результат не нужен — `Task.start`/`Task.Supervisor`. Забытый `await`
  оставит сообщение/процесс висеть.
- **Думать, что GenServer даёт параллелизм внутри.** Один GenServer обрабатывает сообщения
  строго по одному. Параллелизм — это *много* процессов, а не один «многопоточный».
- **Тяжёлая работа в `init/1`.** Пока `init` не вернулся, супервизор (а с ним и старт всего
  приложения) стоит. Долгую подготовку выноси в `handle_continue/2`.
- **Рассчитывать на `terminate/2` как на гарантированный деструктор.** Он не вызывается при
  `:kill` и при падении родителя. Критичное персисти сразу.
- **Запускать процесс под супервизором через `start` вместо `start_link`.** Без связи
  супервизор не узнает о падении ребёнка — надзор перестанет работать.
- **Городить свою «мапу pid'ов» для динамических процессов.** Для этого есть
  `DynamicSupervisor` + `Registry` (`{:via, Registry, {...}}`), причём Registry сам вычищает
  записи умерших.
