# Поток управления, `with` и ошибки

## `case`: сопоставление по значению

`case` — это multi-clause из модуля 03, но не привязанный к функции: берёт выражение и
матчит его против образцов (с опциональными guards), сверху вниз.

```elixir
case File.read("config.txt") do
  {:ok, contents}  -> "Прочитали #{byte_size(contents)} байт"
  {:error, :enoent} -> "Файла нет"
  {:error, reason}  -> "Другая ошибка: #{inspect(reason)}"
end
```

Если ни один образец не совпал — `CaseClauseError`. Часто полезно завершить ветку `_ ->`
как «всё прочее». `case` — рабочая лошадка ветвления: им разбирают тегированные результаты.

> **Go-параллель.** `case` ≈ `switch` (и по значению, и по «типу» через сопоставление
> формы). Но это **выражение** — возвращает значение, которое можно присвоить или передать
> дальше. В Go `switch` — оператор, значение из него не достать напрямую.

## `cond`: первый истинный

Когда ветвление не по форме одного значения, а по нескольким условиям — `cond` (аналог
лестницы `if/else if`):

```elixir
cond do
  age < 0   -> "невозможно"
  age < 18  -> "несовершеннолетний"
  age < 65  -> "взрослый"
  true      -> "пенсионер"        # true в конце = ветка else
end
```

Проверяет условия сверху вниз, выполняет первое истинное. Если ни одно — `CondClauseError`,
поэтому финальный `true ->` играет роль `default`/`else`.

## `if` / `unless`: для простого да/нет

`if` есть, но это **выражение** (возвращает значение), и в нём нет `else if` — для цепочек
бери `cond` или `case`. `unless` — это `if not`.

```elixir
status = if balance > 0, do: :positive, else: :non_positive
```

Что считается «ложным»: только `false` и `nil`. **Всё остальное** — истинно (включая `0`,
`""`, `[]`). Это «truthy/falsy», но крайне узкое: ложь — лишь `false`/`nil`.

> **Go-контраст.** В Go `if` — оператор, а условие должно быть строго `bool`. В Elixir `if`
> — выражение и truthy/falsy (`0` и `""` истинны!). И главное: в идиоматичном Elixir `if`
> используется **реже**, чем в Go — большую часть ветвления забирают multi-clause, `case` и
> `with`.

## Ошибки как значения: `{:ok, _}` / `{:error, _}`

Доминирующая идиома: функция, которая может не сработать, возвращает **тегированный
кортеж** — `{:ok, value}` при успехе или `{:error, reason}` при неудаче. Ты разбираешь его
сопоставлением. Это и есть «ошибки-значения», прямой родственник Go-шного `(value, err)` —
но в одном значении и с явным тегом.

```elixir
case Integer.parse("42") do
  {n, _rest} -> n           # Integer.parse возвращает {число, остаток} или :error
  :error     -> 0
end
```

Многие функции идут парами: «мягкая» `fetch/2` → `{:ok, v}`/`:error`, и «строгая» `fetch!/2`
→ либо значение, либо `raise`. Восклицательный знак в имени (`Map.fetch!`, `File.read!`) —
конвенция «бросаю исключение вместо тега ошибки». Выбирай по ситуации: ждёшь, что может не
быть — мягкую; «этого не должно случиться, иначе всё сломано» — строгую (и пусть падает).

> **Go-параллель.** `{:ok, v}`/`{:error, e}` ≈ `(v, err)`. Разница: тег `:ok`/`:error`
> делает намерение явным в самом значении, и его удобно матчить. А `!`-функции ≈ «паника
> вместо возврата ошибки» там, где ошибка означает баг, а не штатную ветку.

## `with`: цепочка happy-path без лестницы

Вот где Go-разработчик влюбляется. Представь последовательность шагов, каждый может вернуть
`{:ok, _}` или `{:error, _}`, и при первой ошибке надо остановиться:

```elixir
# Go: лестница
# a, err := step1(); if err != nil { return err }
# b, err := step2(a); if err != nil { return err }
# c, err := step3(b); if err != nil { return err }
# return c
```

`with` сворачивает это в один блок: пиши «ожидаемые» совпадения через `<-`, и пока каждый шаг
совпадает с образцом слева, идём дальше; как только не совпал — `with` **немедленно
возвращает** это несовпавшее значение (или результат `else`).

```elixir
with {:ok, user}    <- fetch_user(id),
     {:ok, account} <- fetch_account(user),
     {:ok, balance} <- check_balance(account, amount) do
  {:ok, balance}                       # выполнится, только если ВСЕ шаги дали {:ok, _}
else
  {:error, :not_found} -> {:error, "пользователь не найден"}
  {:error, reason}     -> {:error, reason}
end
```

Логика: каждая строка `образец <- выражение` — это «вычисли правую часть и сопоставь». Если
совпало — связываем переменные и идём к следующей. Если **не** совпало — всё, `with`
прекращается и отдаёт несовпавшее значение (по умолчанию) или прогоняет его через `else`.

- `else` **необязателен**: без него несовпавшее значение просто становится результатом `with`.
- `else` ловит и преобразует ошибки централизованно — в одном месте, а не в каждом `if`.
- Внутри `with` можно мешать обычные `=` (которые обязаны совпасть, иначе `MatchError`) с
  `<-` (несовпадение которых — штатный «ранний выход»).

> **Почему это лучше лестницы.** Нет повторяющегося `if err != nil { return err }` на каждом
> шаге; happy-path читается линейно сверху вниз; обработка всех ошибок собрана в `else`.
> Это самая «эликсировская» замена Go-шной обработке ошибок для последовательных операций.

### Две грабли `with`, о которых узнают поздно

**1. `else` тоже сопоставляет — и может не совпасть.** Если несовпавшее значение не подошло ни
под один образец в `else`, получишь `WithClauseError`, а не «вернём как есть»:

```elixir
with {:ok, u} <- fetch_user(id) do
  u
else
  {:error, :not_found} -> :missing      # а если придёт {:error, :timeout}?
end
# ** (WithClauseError) no with clause matching: {:error, :timeout}
```

Лечение: либо не писать `else` вовсе (тогда несовпавшее значение просто станет результатом
`with`), либо завершать его широким образцом — `error -> error`.

**2. `else` не знает, какой шаг упал.** Все ошибки сваливаются в одну кучу, и если два шага
возвращают `{:error, :not_found}`, различить их невозможно. Идиома — **пометить шаги тегами**:

```elixir
with {:user, {:ok, user}} <- {:user, fetch_user(id)},
     {:cart, {:ok, cart}} <- {:cart, fetch_cart(user)} do
  {:ok, cart}
else
  {:user, {:error, reason}} -> {:error, {:user_step, reason}}
  {:cart, {:error, reason}} -> {:error, {:cart_step, reason}}
end
```

Многословно — зато честно: `with` не отслеживает происхождение ошибки за тебя. В Go ту же
задачу решают тем же способом — обёрткой на каждом шаге: `fmt.Errorf("fetch user: %w", err)`.

## Исключения: `raise` / `rescue`

Настоящие исключения тоже есть — для по-настоящему *исключительных* ситуаций (баг, нарушенный
инвариант), а не для ожидаемых ошибок.

```elixir
raise "что-то сломалось"                       # RuntimeError
raise ArgumentError, message: "плохой аргумент" # конкретный тип

try do
  do_risky()
rescue
  e in ArgumentError -> "поймали: #{e.message}"
after
  cleanup()            # выполнится всегда (≈ defer/finally)
end
```

Но идиома Elixir — `try/rescue` встречается **редко**. Причины: (1) ожидаемые сбои выражают
тегированными кортежами, а не исключениями; (2) для непредвиденного часто правильнее не
ловить, а дать процессу упасть и довериться супервизору («let it crash», модули 07–08).
Если ловишь исключение в каждой функции — скорее всего, ты тащишь Go/Java-привычку туда, где
она не нужна.

`throw`/`catch` — нелокальный выход (вырваться из глубокой рекурсии/итерации). Нужен крайне
редко; в норме его избегают. Упомянут для полноты.

### Своё исключение: `defexception`

Если исключение всё-таки уместно (нарушенный инвариант в библиотеке), заводят свой тип — это
обычный модуль со структурой:

```elixir
defmodule MyApp.ConfigError do
  defexception [:message]          # поле :message есть у любого исключения
end

raise MyApp.ConfigError, message: "не найден ключ :db_url"

try do
  load_config()
rescue
  e in MyApp.ConfigError -> {:error, e.message}    # ловим по КОНКРЕТНОМУ типу
end
```

`defexception` — это `defstruct` плюс реализация нужных протоколов, так что исключение — тоже
обычные данные (модуль 06). Внутри `!`-функций стандартной библиотеки лежит ровно это.

### Три способа «выйти из нормы»: raise, throw, exit

Для полноты картины: в BEAM их три, и путать их не стоит.

| Механизм | Зачем нужен | Чем ловится |
| --- | --- | --- |
| `raise` | исключение: нарушенный инвариант, баг | `rescue` |
| `throw` | нелокальный выход из глубокой рекурсии/итерации (редко) | `catch` |
| `exit` | сигнал завершения процесса, в том числе `exit(:normal)` | `catch :exit` / супервизор |

`exit` — это уже про процессы: именно его шлёт `Process.exit(pid, reason)` и именно его видит
супервизор, когда ребёнок умирает (модули 07–08). В обычном коде ты его не пишешь — просто
знай, что он есть, чтобы не удивиться в стектрейсе.

## Что выбрать: ошибка-значение, исключение или падение

- **Ошибка-значение `{:error, _}`** — для *ожидаемых* ветвей: файла нет, валидация не прошла,
  пользователь не найден. Вызывающий обязан их разобрать. 90% случаев.
- **Исключение (`raise`/`!`-функция)** — для нарушенного инварианта/бага: «такого не должно
  быть». Часто проще дать ему всплыть и уронить процесс.
- **Падение процесса (let it crash)** — для непредвиденного: пусть процесс умрёт, супервизор
  поднимет в чистое состояние (модуль 08). Это не «вместо обработки», а способ изолировать
  непредвиденное.

## Глоссарий модуля

- **`case`** — сопоставление одного значения с образцами (с guards); выражение, возвращает
  значение. Не подошло ничего — `CaseClauseError`.
- **`cond`** — цепочка независимых условий, берётся первое истинное; завершают веткой
  `true ->`, иначе `CondClauseError`.
- **`if` / `unless`** — выражения; ложью считаются только `false` и `nil`.
- **Truthy / falsy** — «истинно всё, кроме `false` и `nil`» (в том числе `0`, `""`, `[]`).
- **Тегированный кортеж** — `{:ok, value}` / `{:error, reason}`: ошибки как значения.
- **`with`** — цепочка шагов `образец <- выражение` с ранним выходом на первом несовпадении.
- **`<-` vs `=` внутри `with`** — мягкий шаг с ранним выходом vs жёсткий матч, дающий
  `MatchError`.
- **`WithClauseError`** — несовпавшее значение не подошло ни под один образец в `else`.
- **`!`-функции** (`File.read!`, `Map.fetch!`) — бросают исключение вместо тега ошибки.
- **`raise` / `rescue`** — бросить и поймать исключение; **`after`** — блок «выполнить всегда»
  (аналог `defer`/`finally`).
- **`defexception`** — объявление своего типа исключения (структура + протоколы).
- **`throw` / `catch`** — нелокальный выход; в идиоматичном коде почти не встречается.
- **`exit`** — сигнал завершения процесса; его ловит супервизор (модули 07–08).
- **«Let it crash»** — стратегия: непредвиденное не ловим, а даём процессу упасть под
  присмотром супервизора.

## Типичные ошибки и заблуждения

- **Тащить `try/rescue` как в Go/Java.** В Elixir ожидаемые сбои — это `{:error, _}`, а не
  исключения. `try/rescue` — редкий инструмент для действительно исключительного.
- **Лестница `case` вместо `with`.** Вложенные `case File.read do {:ok, x} -> case ... end`
  быстро превращаются в «стрелку судного дня». Последовательность шагов с ранним выходом —
  это `with`.
- **Забыть `else`/`true` ветку.** `cond` без `true ->` бросит `CondClauseError`; `case` без
  подходящего образца — `CaseClauseError`. Завершай общим вариантом, если нужно.
- **Считать `0`/`""`/`[]` ложными.** В Elixir ложь — только `false` и `nil`. `if 0 do ...`
  выполнит ветку «истина». Это не Go и не C.
- **Путать `=` и `<-` в `with`.** `<-` — «не совпало → ранний выход с этим значением». `=`
  внутри `with` — «обязано совпасть, иначе MatchError (не ловится `else`)». Используй `<-`
  для шагов, которые *штатно* могут вернуть ошибку.
- **`!`-функция там, где сбой ожидаем.** `File.read!` упадёт исключением, если файла нет.
  Если отсутствие файла — нормальная ветка, бери мягкую `File.read` и матчь `{:error, _}`.
- **Узкий `else` у `with`.** Если несовпавшее значение не подойдёт ни под один образец `else`,
  будет `WithClauseError`. Либо не пиши `else`, либо закрывай его широким `error -> error`.
- **Ждать, что `else` подскажет, какой шаг упал.** Не подскажет: ошибки приходят вперемешку.
  Нужна различимость — помечай шаги тегами (`{:user, fetch_user(id)}`).
- **Считать, что «выход из нормы» бывает только один.** Их три: `raise`/`rescue` (исключение),
  `throw`/`catch` (нелокальный выход, редко), `exit` (сигнал завершения процесса, его ловит
  супервизор).
