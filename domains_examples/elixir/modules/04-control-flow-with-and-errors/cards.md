# Карточки

## case / cond / if

```card
front: Когда брать case, а когда cond?
back: case — сопоставление ОДНОГО значения против образцов (с guards), отлично для тегированных кортежей {:ok,_}/{:error,_}. cond — ветвление по НЕСКОЛЬКИМ независимым условиям (аналог if/else-if лестницы), берёт первое истинное. Оба — выражения, возвращают значение.
tags: [elixir, case, cond]
```

```card
front: Что считается «ложным» в Elixir?
back: "Только false и nil. Всё остальное истинно, включая 0, \"\" и []. Это узкая truthy/falsy: `if 0 do ... end` выполнит ветку «истина». Не путать с Go/C/Python."
tags: [elixir, truthy]
```

```card
front: Чем if в Elixir отличается от if в Go?
back: if в Elixir — выражение (возвращает значение, можно присвоить), truthy/falsy (0 и "" истинны), без else-if (для цепочек — cond/case). В Go if — оператор, условие строго bool. И в идиоматичном Elixir if используется реже — ветвление забирают multi-clause/case/with.
tags: [elixir, if, go]
```

```card
front: Что будет, если ни одна ветка cond не истинна?
back: CondClauseError. Поэтому финальную ветку делают `true ->` — она играет роль else/default. Аналогично case без подходящего образца бросает CaseClauseError.
tags: [elixir, cond, error]
```

## Ошибки-значения

```card
front: Как в Elixir принято возвращать «может не сработать»?
back: Тегированным кортежем {:ok, value} / {:error, reason}, который вызывающий разбирает сопоставлением. Это «ошибки-значения», родственник Go-шного (value, err), но в одном значении с явным тегом.
tags: [elixir, error-tuple]
```

```card
front: Что означает `!` в имени функции (File.read! vs File.read)?
back: "Конвенция: `!`-версия бросает исключение при сбое и возвращает голое значение; обычная версия возвращает {:ok, _}/{:error, _}. Бери мягкую, если сбой ожидаем (матчишь :error); строгую `!`, если сбой = баг и пусть падает."
tags: [elixir, bang, error]
```

```card
front: Ошибка-значение, исключение или падение процесса — когда что?
back: "{:error, _} — для ОЖИДАЕМЫХ ветвей (файла нет, валидация), ~90% случаев. raise/!-функция — для нарушенного инварианта/бага. Падение процесса (let it crash) — для непредвиденного: супервизор поднимет в чистое состояние. Не «вместо» обработки, а изоляция непредвиденного."
tags: [elixir, errors, philosophy]
```

## with

```card
front: Что делает конструкция with и зачем она?
back: "Цепочка шагов `образец <- выражение`: пока каждый шаг совпадает с образцом слева — идём дальше, связывая переменные. На первом несовпадении with немедленно возвращает несовпавшее значение (или прогоняет через else). Заменяет лестницу `if err != nil { return err }` линейным happy-path."
tags: [elixir, with]
```

```card
front: В чём разница `<-` и `=` внутри with?
back: "`<-` — штатный матч с ранним выходом: не совпало → with останавливается и отдаёт это значение (ловится else). `=` внутри with — обычный матч, который ОБЯЗАН совпасть, иначе MatchError (не ловится else). Шаги, которые могут вернуть ошибку, пиши через `<-`."
tags: [elixir, with]
```

```card
front: Зачем нужен else в with и обязателен ли он?
back: "else необязателен: без него несовпавшее значение становится результатом with. С else можно централизованно преобразовать ошибки (в одном месте, а не в каждом if). Например {:error, :not_found} -> {:error, \"не найдено\"}."
tags: [elixir, with, else]
```

## Исключения

```card
front: Почему try/rescue в Elixir встречается редко?
back: Ожидаемые сбои выражают тегированными кортежами {:error, _}, а не исключениями; а непредвиденное часто правильнее не ловить, а дать процессу упасть (let it crash) — супервизор перезапустит. Ловить исключение в каждой функции — Go/Java-привычка, тут лишняя.
tags: [elixir, exceptions, let-it-crash]
```

```card
front: Что такое after в try и аналог в Go?
back: "Блок after выполняется всегда — и при успехе, и при исключении (очистка ресурсов). Аналог defer/finally. try/rescue/after: rescue ловит исключения, after гарантирует очистку."
tags: [elixir, try, after]
```

## Грабли with

```card
front: "Когда with бросает WithClauseError?"
back: "Когда шаг не совпал, а несовпавшее значение не подошло ни под один образец в else. Лечение: либо вообще не писать else (несовпавшее станет результатом with), либо закрыть его широким образцом error -> error."
tags: [elixir, with, error]
```

```card
front: "Почему else в with не знает, на каком шаге произошла ошибка?"
back: "В else приходит только само несовпавшее значение, без информации о шаге: два разных шага могут вернуть одинаковый {:error, :not_found}. Идиома различимости — тегировать шаги: with {:user, {:ok, u}} <- {:user, fetch_user(id)}, ... и матчить {:user, {:error, r}} в else."
tags: [elixir, with, errors]
```

## Исключения

```card
front: "Как объявить своё исключение?"
back: "defmodule MyApp.ConfigError do defexception [:message] end, затем raise MyApp.ConfigError, message: \"...\" и ловля по типу: rescue e in MyApp.ConfigError -> ... . defexception — это defstruct плюс нужные протоколы, то есть исключение это обычные данные."
tags: [elixir, defexception]
```

```card
front: "raise, throw и exit — три механизма: чем отличаются?"
back: "raise — исключение (нарушенный инвариант, баг), ловится rescue. throw — нелокальный выход из глубокой рекурсии, ловится catch, в идиоматичном коде почти не встречается. exit — сигнал завершения ПРОЦЕССА (его шлёт Process.exit и видит супервизор). В обычном коде пишут только raise."
tags: [elixir, raise, throw, exit]
```
