# Структуры, протоколы и behaviours

## Структуры: типизированные мапы

`defstruct` определяет структуру — мапу с фиксированным набором полей и тегом типа. Под
капотом это **мапа** со специальным ключом `__struct__`, равным имени модуля.

```elixir
defmodule User do
  defstruct name: "", age: 0, admin: false   # поля + значения по умолчанию

  def adult?(%User{age: age}), do: age >= 18
end

u = %User{name: "Сэм", age: 30}     # создание
u.name                               # => "Сэм" (строгий доступ, поля известны)
u2 = %{u | age: 31}                  # обновление (как у мапы; ключ обязан существовать)
User.adult?(u)                       # => true
%User{name: n} = u                   # матч по структуре, n = "Сэм"
```

Чем структура лучше голой мапы:
- **Известный набор полей.** Опечатка в поле при создании/обновлении — ошибка компиляции,
  а не тихий `nil`. Это узкая, но реальная страховка.
- **Тег типа для матча.** `%User{}` в образце совпадёт только с `User`, не с любой мапой.
  Так multi-clause различает типы данных.
- **Дефолты.** Поля получают значения по умолчанию из `defstruct`.

`@enforce_keys [:name]` сделает указанные поля обязательными при создании.

> **Go-параллель.** Структура ≈ `struct` в Go, но: неизменяемая (обновление = новая копия),
> без методов *внутри* (функции живут в модуле и принимают структуру первым аргументом —
> «data-first»), и это всё ещё мапа (можно гонять через `Map.*` и `Enum`). Нет тегов полей,
> нет встраивания (embedding) — композиция через обычные поля.

### Три вещи о структурах, которые всплывают на практике

**1. `@enforce_keys` — обязательные поля.**

```elixir
defmodule User do
  @enforce_keys [:name]
  defstruct [:name, :age]
end

%User{age: 30}
# ** (ArgumentError) the following keys must also be given when building struct User: [:name]
```

Это проверка **на создание**, а не типов: она не даёт собрать структуру без ключевых полей.

**2. Структура — мапа, но не во всём.** `is_map(%User{})` даёт `true`, `Map.get/3` и
`Map.put/3` работают. А вот **доступ по скобкам не работает**: `user[:name]` упадёт, потому что
структуры по умолчанию не реализуют протокол `Access`. Остаются `user.name` (строгий доступ) и
`Map.get(user, :name)`. Это частая ловушка при переезде с обычных мап.

**3. `Map.from_struct/1` и `struct!/2`** — мост между структурой и голой мапой:

```elixir
Map.from_struct(%User{name: "Сэм", age: 30})   # => %{name: "Сэм", age: 30} (без __struct__)
struct!(User, %{name: "Сэм"})                   # собрать структуру из мапы, с проверкой ключей
```

Первое удобно перед сериализацией, второе — при разборе входных данных.

## Протоколы: полиморфизм по типу данных

Протокол — это набор функций, чья **реализация выбирается по типу первого аргумента в
рантайме**. Ты видел их в действии: `Enumerable` (его реализуют список, мапа, `Range`,
`Stream` — поэтому `Enum` работает со всеми), `String.Chars` (за ним стоит `to_string/1`),
`Inspect` (как значение печатается в `iex`/`IO.inspect`).

```elixir
defprotocol Describable do
  @doc "Человекочитаемое описание значения."
  def describe(value)
end

defmodule User do
  defstruct [:name, :age]
end

defimpl Describable, for: User do
  def describe(%User{name: n, age: a}), do: "#{n}, #{a} лет"
end

defimpl Describable, for: Integer do
  def describe(n), do: "число #{n}"
end

defimpl Describable, for: List do
  def describe(list), do: "список из #{length(list)} элементов"
end

Describable.describe(%User{name: "Сэм", age: 30})  # => "Сэм, 30 лет"
Describable.describe(42)                            # => "число 42"
Describable.describe([1, 2, 3])                     # => "список из 3 элементов"
```

Ключевые свойства:
- **Открытость.** Реализацию можно добавить для **чужого** типа (даже встроенного, как
  `Integer`), не трогая его исходники. Ты сам реализуешь протокол «снаружи».
- **Диспетч в рантайме** по типу данных. Если для типа реализации нет — `Protocol.UndefinedError`
  (можно задать `@fallback_to_any true` + реализацию `for: Any`).
- **`@derive`.** Часто протокол можно «вывести» для структуры автоматически:
  `@derive {Inspect, only: [:name]}` перед `defstruct` сгенерит реализацию `Inspect`.

> **Go-контраст (важный).** Go-интерфейс реализуется *неявно* типом, у которого есть нужные
> методы, и проверяется компилятором. Протокол Elixir — наоборот: реализация пишется
> *отдельно* (`defimpl ... for: Type`), диспетчеризуется *в рантайме* и может быть добавлена
> для типов, которые ты не контролируешь. Это «open polymorphism»: расширяешь поведение
> существующих типов снаружи — чего Go-интерфейсы не умеют.

## Behaviours: контракт модуля

Behaviour — это объявленный набор функций-колбэков, которые **модуль обязан реализовать**,
чтобы соответствовать контракту. Это про полиморфизм на уровне *модулей*, а не данных.

```elixir
defmodule Parser do
  @callback parse(String.t()) :: {:ok, term()} | {:error, String.t()}
  @callback extensions() :: [String.t()]
end

defmodule JSONParser do
  @behaviour Parser

  @impl Parser
  def parse(str), do: {:ok, "json: #{str}"}

  @impl Parser
  def extensions(), do: ["json"]
end
```

- `@callback name(args) :: return` объявляет требуемую функцию (с типами).
- `@behaviour Parser` в реализующем модуле включает проверку: забыл колбэк — **warning при
  компиляции**.
- `@impl Parser` помечает функцию как реализацию колбэка (компилятор проверит, что такой
  колбэк есть и подпись согласуется). Хорошая практика — ставить всегда.

Behaviours — фундамент OTP: `GenServer`, `Supervisor`, `Application` — это behaviours со
своими колбэками (`init/1`, `handle_call/3`, ...). Когда в модуле 08 ты напишешь
`use GenServer` и `@impl true`, ты реализуешь behaviour.

> **Go-параллель.** Behaviour ближе всего к Go-интерфейсу *по смыслу* («набор методов,
> которые надо реализовать»), но реализуется модулем (не типом данных), проверяется на
> компиляции лишь предупреждением, и используется для «подключаемых модулей» (стратегий,
> адаптеров, OTP-серверов).

## Что на самом деле делает `use`

Четвёртая директива (после `alias` / `import` / `require` из модуля 03) и главный источник
ощущения «в OTP какая-то магия». Когда ты пишешь:

```elixir
defmodule Counter do
  use GenServer
end
```

происходит буквально следующее: компилятор делает `require GenServer` и вызывает макрос
`GenServer.__using__/1`, а **всё, что этот макрос вернёт, вставляется прямо в твой модуль**.
Никакого наследования — просто генерация кода на этапе компиляции.

Что обычно приносит `use GenServer`:

- `@behaviour GenServer` — тот самый контракт с колбэками;
- реализации некоторых колбэков **по умолчанию**, чтобы не писать все руками;
- функцию `child_spec/1`, благодаря которой модуль можно просто положить в список детей
  супервизора (модуль 08).

Свой `use` пишется так:

```elixir
defmodule MyApp.Helpers do
  defmacro __using__(_opts) do
    quote do
      import Enum, only: [map: 2]     # всё отсюда окажется в модуле-пользователе
      def helper_name, do: "helpers"
    end
  end
end

defmodule MyApp.Users do
  use MyApp.Helpers                   # теперь тут есть helper_name/0 и импортирован map/2
end
```

`quote` — это «вот кусок кода как данные», а `__using__` — точка входа для `use`. Глубоко в
макросы мы не идём (это за рамками курса), но важно запомнить: **`use` — не наследование и не
фреймворк-магия, а вставка сгенерированного кода**. Если непонятно, что именно приносит чужой
`use`, открой исходник его `__using__` — там обычный Elixir.

> **Go-параллель.** По ощущению ближе всего встраивание структуры (`type Server struct {
> BaseServer }`), которое даёт «унаследованные» методы. Разница принципиальная: в Go это
> композиция типов в рантайме, а `use` — генерация кода на компиляции, и он может добавить что
> угодно, включая `@behaviour`, атрибуты модуля и целые функции.

## Протокол vs behaviour: как не путать

> **Простыми словами.** Протокол — это **глагол, который умеют разные данные**: «покажи себя»,
> «посчитай свой размер», «дай по себе пройтись». Глагол объявляется один раз, а потом
> отдельно рассказывается, как его выполняет каждый тип. Behaviour — это **вакансия для
> модуля**: список обязанностей («уметь `parse/1` и `extensions/0`»), на которую можно нанять
> любой модуль, который их выполняет. В Go обе роли играет интерфейс; здесь они разведены, и
> подсказка простая: полиморфизм по **значению** — протокол, по **модулю** — behaviour.

| | Протокол | Behaviour |
| --- | --- | --- |
| Полиморфизм по | **типу данных** (значению) | **модулю** |
| Диспетч | в рантайме, по `__struct__`/типу | ты сам выбираешь/передаёшь модуль |
| Объявление | `defprotocol` + `defimpl for: Type` | `@callback` + `@behaviour` + `@impl` |
| Аналогия | «как напечатать/перечислить ЭТО значение» | «этот модуль умеет parse/handle» |
| Примеры | `Enumerable`, `Inspect`, `String.Chars` | `GenServer`, `Supervisor`, свой `Parser` |

Грубо: **протокол** — «разные данные, одно действие» (полиморфизм значений). **Behaviour** —
«разные модули, один контракт» (полиморфизм стратегий/плагинов). Go-интерфейс совмещает обе
роли в одном механизме; Elixir их разделил.

## `@spec` и типы

Типы в Elixir не пишут в сигнатурах, но можно объявить **спецификацию** для документации,
инструментов (Dialyzer) и набирающей силу set-theoretic системы типов:

```elixir
@spec add(integer(), integer()) :: integer()
def add(a, b), do: a + b
```

- `@spec` — необязательная аннотация типов функции; `@type` — свои псевдонимы типов.
- **Set-theoretic типизация** (с 1.17, расширяется): компилятор **выводит** типы и ловит
  часть ошибок (несовместимые сопоставления, неверные вызовы) **без** аннотаций. С 1.19 —
  и для анонимных функций, и для протоколов.
- **Dialyzer** — отдельный статический анализатор (success typing), использует `@spec`/выводы,
  находит «невозможные» вызовы. Запускается отдельно, не на каждой компиляции.

Важно: это не статика Go. Аннотации необязательны, вывод неполон, многие ошибки по-прежнему
в рантайме (`MatchError`, `FunctionClauseError`). Но направление ясно, и `@spec` + Dialyzer +
встроенные проверки реально ловят баги — пиши `@spec` на публичные функции, это окупается.

## Глоссарий модуля

- **Структура (`defstruct`)** — мапа с фиксированным набором полей и ключом `__struct__`,
  равным имени модуля.
- **`@enforce_keys`** — список полей, без которых структуру нельзя создать.
- **`Access`** — протокол доступа по скобкам (`data[:key]`); структуры его по умолчанию **не**
  реализуют.
- **Протокол (`defprotocol` / `defimpl`)** — полиморфизм по типу данных: реализация выбирается
  в рантайме по первому аргументу.
- **`@derive`** — попросить автоматически вывести реализацию протокола для структуры.
- **`@fallback_to_any` + `defimpl ... for: Any`** — реализация по умолчанию для типов без своей.
- **`Protocol.UndefinedError`** — для этого типа реализации протокола нет.
- **Behaviour** — контракт модуля: набор `@callback`, которые модуль обязан реализовать.
- **`@callback` / `@behaviour` / `@impl`** — объявить пункт контракта / подписаться на контракт
  / пометить реализацию (и включить проверку имени и арности).
- **`use` / `__using__`** — директива «вставь в мой модуль сгенерированный код» и макрос,
  который этот код возвращает. Не наследование.
- **`quote`** — представление кода как данных (основа макросов).
- **`@spec` / `@type`** — необязательные аннотации типов для документации, Dialyzer и
  встроенной проверки.
- **Set-theoretic типы** — выводимая система типов Elixir: работает без аннотаций, ловит часть
  ошибок на компиляции, но это не статика Go.
- **Dialyzer** — отдельный статический анализатор (success typing), запускается командой.

## Типичные ошибки и заблуждения

- **«Структура — это новый тип, не мапа».** Это мапа с `__struct__`. Можно гонять `Map.*`/
  `Enum`, но **не** все функции мап уместны (у структуры фиксированные поля). `is_map(%User{})`
  → `true`.
- **Обновлять структуру несуществующим полем.** `%User{nick: "x"}` или `%{u | nick: 1}` —
  ошибка компиляции/`KeyError`: поля структуры фиксированы (это и есть страховка).
- **Путать протокол и behaviour.** Протокол — диспетч по *данным* (`defimpl for: Type`),
  behaviour — контракт *модуля* (`@callback`/`@behaviour`). «Печать значения» — протокол;
  «подключаемый парсер» — behaviour.
- **Ждать неявной реализации протокола, как у Go-интерфейса.** Протокол нужно реализовать
  явно (`defimpl`). Нет реализации для типа — `Protocol.UndefinedError` в рантайме.
- **Забыть `@impl`.** Без него компилятор не проверит, что функция действительно реализует
  колбэк (опечатка в имени/арности пройдёт молча). Ставь `@impl` на все колбэки.
- **Думать, что `@spec` обязателен или что это статическая типизация.** Он необязателен и
  декларативен. Реальную проверку дают set-theoretic вывод (частично, автоматически) и
  Dialyzer (отдельно). Не путай с компилятором Go.
- **Тащить ООП-наследование.** Нет классов, наследования и методов-на-объекте. Композиция —
  через данные и функции; «полиморфизм» — через протоколы/behaviours. `defstruct` ≠ class.
- **`user[:name]` на структуре.** Не работает: структуры не реализуют протокол `Access`.
  Используй `user.name` или `Map.get(user, :name)`.
- **Считать `use` наследованием или магией фреймворка.** `use Mod` просто вызывает
  `Mod.__using__/1` и вставляет возвращённый код в твой модуль. Непонятно, что он делает —
  открой исходник `__using__`.
- **Забывать про `@enforce_keys`.** Без него структуру можно создать без обязательных полей, и
  вместо ошибки при создании ты получишь `nil` где-то дальше по коду.
