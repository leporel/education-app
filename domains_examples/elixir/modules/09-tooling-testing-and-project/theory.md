# Тулинг, тесты и проект

## ExUnit: тесты из коробки

ExUnit — встроенный тест-фреймворк (как `testing` в Go, только богаче). Тестовый файл —
`test/*_test.exs`, запуск — `mix test`.

```elixir
defmodule MathTest do
  use ExUnit.Case, async: true        # async: тесты этого модуля идут параллельно с другими

  test "сложение" do
    assert 2 + 2 == 4
    refute 2 + 2 == 5
  end

  test "список" do
    assert [1, 2, 3] |> Enum.sum() == 6
  end
end
```

- **`assert` / `refute`** — макросы; при падении показывают разобранное выражение (что слева,
  что справа от `==`), а не просто «false». Это приятнее ручного `if got != want { t.Errorf }`.
- **`assert_raise`** — проверка исключений; **`assert_receive`/`assert_received`** —
  проверка, что процессу пришло сообщение (тестирование конкурентного кода).
- **`describe`** группирует связанные тесты; **`test/2` с контекстом** получает данные из `setup`.

> **Go-параллель.** `mix test` ≈ `go test`, `ExUnit.Case` ≈ пакет `testing`. Но `assert` —
> макрос с интроспекцией выражения (Go так не умеет без сторонних либ), а тесты по умолчанию
> внутри одного модуля идут последовательно, разные модули с `async: true` — параллельно.

## setup и фикстуры

`setup` выполняется перед каждым тестом и кладёт данные в контекст:

```elixir
defmodule AccountTest do
  use ExUnit.Case, async: true

  setup do
    {:ok, pid} = Account.start_link(100)
    %{account: pid}                  # станет частью контекста теста
  end

  test "депозит увеличивает баланс", %{account: pid} do
    Account.deposit(pid, 50)
    assert Account.balance(pid) == 150
  end
end
```

`setup_all` — один раз на модуль (дорогая подготовка). Возвращаемая мапа сливается в контекст,
который тест получает вторым аргументом через сопоставление (`%{account: pid}` — снова pattern
matching!).

## async: true — когда безопасно

`async: true` гоняет тестовые **модули** параллельно (внутри модуля — последовательно). Это
ускоряет прогон, но безопасно **только если тесты не делят изменяемое глобальное состояние**:
не пишут в один и тот же именованный процесс, файл, БД-таблицу без изоляции. Благодаря
изоляции процессов BEAM большинство юнит-тестов async-безопасны из коробки. Тесты, дёргающие
общий именованный GenServer или внешний ресурс, оставляй синхронными (без `async`).

> **Go-параллель.** Похоже на `t.Parallel()`, но по умолчанию решается на уровне модуля
> флагом. Та же оговорка про общее состояние.

## Изоляция тестов: `start_supervised!`

Как только в тестах появляются процессы, встаёт вопрос: откуда брать «свежий» GenServer на
каждый тест и кто его погасит? Ответ — хелпер ExUnit `start_supervised!/1`: он запускает
процесс под **тестовым супервизором** и гарантированно останавливает его после теста.

```elixir
defmodule CounterTest do
  use ExUnit.Case, async: true            # async снова безопасен: процесс у каждого теста свой

  setup do
    pid = start_supervised!({Counter, 0})  # свежий Counter на каждый тест
    %{counter: pid}
  end

  test "инкремент", %{counter: pid} do
    Counter.inc(pid, 5)
    assert Counter.value(pid) == 5
  end
end
```

Правило простое: **процесс, зарегистрированный под глобальным именем и общий для всех тестов,
делает тесты зависимыми** — тогда `async: true` включать нельзя. Как только процесс поднимается
через `start_supervised!` в `setup` и адресуется по pid, тесты становятся независимыми и
параллельный прогон снова безопасен. Именно так лечится оговорка из капстоуна (урок 01).

Полезные мелочи вокруг `mix test`:

```bash
mix test test/my_test.exs:42     # запустить ровно один тест по файлу и строке
mix test --stale                 # только то, что затронуто изменениями
mix test --failed                # только упавшие в прошлый прогон
mix test --only integration      # только тесты с @tag :integration
mix test --seed 0                # отключить случайный порядок (для отладки флаков)
```

Теги ставятся прямо над тестом (`@tag :integration`), а исключить их по умолчанию можно в
`test/test_helper.exs`: `ExUnit.configure(exclude: [:integration])`.

## Doctests: документация, которая тестируется

Примеры в `@doc` с префиксом `iex>` можно проверять как тесты — документация не «протухает».

```elixir
defmodule Calc do
  @doc """
  Удваивает число.

      iex> Calc.double(21)
      42

      iex> Calc.double(0)
      0
  """
  def double(n), do: n * 2
end
```

В тест-файле подключаешь:

```elixir
defmodule CalcTest do
  use ExUnit.Case, async: true
  doctest Calc        # превратит примеры из @doc в тесты
end
```

`mix test` выполнит `Calc.double(21)` и сверит с `42`. Если изменишь поведение и забудешь
обновить пример — тест упадёт. В Go есть `Example`-функции, но doctests легче и живут прямо в
документации.

## Логи: `Logger`

`IO.inspect` и `dbg` (модуль 03) — инструменты разработки. В проде пишут через **`Logger`**,
он идёт в стандартной поставке.

```elixir
defmodule MyApp.Worker do
  require Logger      # Logger.info и компания — МАКРОСЫ, отсюда require (модуль 03)

  def handle(job) do
    Logger.metadata(job_id: job.id)              # метаданные прилипнут ко всем логам процесса
    Logger.info("начал обработку")

    case run(job) do
      :ok -> Logger.debug("готово")
      {:error, reason} -> Logger.error("сбой: #{inspect(reason)}")
    end
  end
end
```

Что стоит знать сразу:

- **Уровни**: `:debug` → `:info` → `:notice` → `:warning` → `:error` (и ещё выше —
  `:critical`, `:alert`, `:emergency`). Всё ниже настроенного уровня отсекается в рантайме, а
  при желании **вырезается прямо на компиляции** (`compile_time_purge_matching`) — ради этого
  `Logger` и сделан макросом, поэтому `Logger.debug` в горячем коде почти бесплатен.
- **Настройка** — в конфиге: `config :logger, level: :info`.
- **Метаданные** (`Logger.metadata/1`) привязаны к процессу и попадают в каждую последующую
  запись. Это ровно то, ради чего в Go таскают `logger := logger.With("job_id", id)` через все
  вызовы; здесь контекст живёт в процессе.
- **`inspect/1`** обязателен для не-строк: `"#{reason}"` для кортежа просто не соберётся, а
  `inspect(reason)` покажет структуру.
- Падение процесса логируется супервизором **автоматически** — ловить и логировать сбой «на
  всякий случай» не нужно, это как раз анти-OTP (модуль 08).

> **Go-параллель.** `Logger` ≈ `log/slog`: уровни, структурированные метаданные, настройка
> через конфиг. Отличия: это макросы (дешёвая отсечка ещё до рантайма) и метаданные живут в
> процессе, а не передаются аргументом.

## Структура проекта, deps и Hex

`mix new myapp` (или `--sup` для OTP-приложения с супервизором) создаёт:

```
myapp/
├── mix.exs            # манифест: проект, deps, OTP-приложение (mod:)
├── lib/               # исходники (.ex компилируются)
│   └── myapp/...
├── test/              # тесты (.exs, не компилируются в артефакт)
├── config/            # конфигурация (config.exs, runtime.exs)
└── mix.lock           # зафиксированные версии deps (≈ go.sum)
```

Зависимости объявляют в `mix.exs` и тянут через **Hex** (`hex.pm`):

```elixir
defp deps do
  [
    {:jason, "~> 1.4"},                  # JSON; ~> 1.4 = >= 1.4.0 и < 2.0.0
    {:req, "~> 0.5"},                    # HTTP-клиент
    {:credo, "~> 1.7", only: [:dev], runtime: false},
    {:dialyxir, "~> 1.4", only: [:dev], runtime: false}
  ]
end
```

`mix deps.get` скачивает (как `go mod download`), `mix.lock` фиксирует точные версии. `~>` —
«совместимая версия» (semver-диапазон); `only:` ограничивает окружение, `runtime: false` —
инструмент только для разработки.

> **Go-параллель.** `mix.exs` deps ≈ `require` в `go.mod`, `mix.lock` ≈ `go.sum`, Hex ≈ модуль-
> прокси/реестр. Отличие: версии задают диапазоном (`~>`), а сам `mix.exs` — это исполняемый
> Elixir-код, а не декларативный файл.

## Качество кода: format, Credo, Dialyzer

- **`mix format`** — встроенный форматтер (как `gofmt`, но конфигурируемый через
  `.formatter.exs`). Спор о стиле закрыт инструментом.
- **Credo** — линтер стиля и читаемости (советы по идиомам); запускается `mix credo`.
- **Dialyzer** (через `dialyxir`) — статический анализ success typing на основе `@spec` и
  выводов; ловит «невозможные»/несогласованные вызовы. `mix dialyzer`. Первый прогон строит
  PLT (кеш типов) и потому долгий.
- Встроенная **set-theoretic типизация** (модуль 06) работает на каждой компиляции без
  настройки — просто читай предупреждения компилятора.

## Релизы (обзорно)

`mix release` собирает самодостаточный релиз — твой код + зависимости + (опц.) среда Erlang —
в артефакт, который запускается без установленного Elixir на сервере. Поддерживает конфиг в
рантайме (`runtime.exs`), команды управления, и (фишка BEAM) горячую замену кода. Для этого
курса достаточно знать, что релизы есть и это стандартный способ деплоя; глубоко — отдельная
тема.

## Врезка: Phoenix и LiveView — витрина BEAM в проде

Phoenix — основной веб-фреймворк Elixir, и он не «ещё один MVC», а демонстрация того, ради
чего нужен BEAM:

- **Процесс на соединение.** Каждый HTTP-запрос/WebSocket обслуживается своим изолированным
  процессом под супервизией. Сто тысяч одновременных соединений — сто тысяч дешёвых
  процессов; падение одного не задевает других. То, что в других стеках требует тюнинга,
  здесь — модель по умолчанию.
- **LiveView** — real-time UI **без** написания JS: состояние страницы живёт в серверном
  процессе (GenServer!), DOM-диффы летят по WebSocket. «Живые» дашборды, формы, чаты — на
  серверном Elixir. Это прямое следствие дешёвых процессов и pub/sub поверх BEAM.
- **PubSub/Presence** — рассылка событий и отслеживание присутствия между процессами/нодами
  из коробки (поверх той же модели сообщений).
- Тулинг: `mix phx.new` (или Igniter-инсталляторы) генерит проект; на лето 2026 актуальны
  Phoenix с **LiveView 1.1** (1.2 на подходе с colocated CSS).

Идея врезки: всё, что ты выучил — процессы, GenServer, супервизоры, `{:ok, _}`/`with` — это и
есть «как написан Phoenix внутри». Веб тут не магия фреймворка, а тонкий слой над OTP. Полное
освоение Phoenix/Ecto — отдельный домен; здесь — понять, *почему* Elixir силён в проде.

## Глоссарий модуля

- **ExUnit** — встроенный тест-фреймворк; тесты живут в `test/*_test.exs`, запуск — `mix test`.
- **`assert` / `refute`** — макросы проверок с разбором выражения при падении.
- **`assert_raise`, `assert_receive`, `assert_received`** — проверки исключений и сообщений в
  mailbox (тестирование конкурентного кода).
- **`setup` / `setup_all`** — подготовка перед каждым тестом / один раз на модуль; возвращает
  мапу, которая сливается в контекст теста.
- **Контекст теста** — данные из `setup`, получаемые вторым аргументом через сопоставление.
- **`async: true`** — параллельный прогон тестовых модулей; безопасен только при изоляции.
- **`start_supervised!/1`** — поднять процесс под тестовым супервизором; он сам погасит его
  после теста. Ключ к независимым тестам.
- **`@tag`** — метка теста (`@tag :integration`) для `--only` / `exclude`.
- **Doctest** — пример в `@doc` с `iex>`, проверяемый как тест (`doctest MyMod`).
- **`mix.exs` / `mix.lock`** — манифест проекта (исполняемый код) / фиксация версий deps.
- **Hex** — реестр пакетов; **`~> 1.4`** — «совместимая версия»: `>= 1.4.0` и `< 2.0.0`.
- **`mix format` / Credo / Dialyzer** — форматтер / линтер стиля / статический анализ по
  success typing.
- **`Logger`** — стандартное логирование: уровни, метаданные процесса, отсечка на компиляции;
  требует `require`.
- **`mix release`** — самодостаточный артефакт для деплоя без установленного Elixir.
- **Phoenix / LiveView** — веб-фреймворк и серверный real-time UI поверх тех же процессов и
  супервизоров.

## Типичные ошибки и заблуждения

- **`async: true` на тестах с общим состоянием.** Параллельные тесты, пишущие в один
  именованный процесс/таблицу/файл, дадут флаки. Async безопасен при изоляции; общий ресурс →
  синхронный тест или изолированная фикстура (свой процесс на тест).
- **Сравнивать вручную вместо `assert`.** `assert a == b` даёт разбор при падении; голый `if`
  лишает тебя диагностики. Используй макросы ExUnit.
- **Доктесты для всего.** Doctests хороши для маленьких чистых функций-примеров; сложные
  сценарии (процессы, побочные эффекты) тестируй обычными `test`, а не громоздкими `iex>`.
- **Править `mix.lock` руками / не коммитить его.** Лок фиксирует версии — коммить его (как
  `go.sum`); обновляй через `mix deps.update`, а не редактором.
- **Считать Phoenix «обязательным Elixir».** Phoenix — это библиотека поверх OTP; язык и OTP
  самоценны (CLI, демоны, обработка данных). Веб — одно из применений, а не суть.
- **Тяжёлую конкурентную работу в капстоуне без лимита.** `spawn` 100500 процессов на задачу
  без `max_concurrency`/пула перегрузит внешние ресурсы. Используй `Task.async_stream` или
  `DynamicSupervisor` с ограничением.
- **Забыть, что `mix.exs` — код.** Это исполняемый Elixir, а не статический манифест; ошибки
  в нём — ошибки компиляции конфигурации, а не «неверный формат файла».
- **Логировать через `IO.inspect`/`IO.puts`.** Это отладочная печать без уровней, метаданных и
  возможности отключить её в проде. Для логов есть `Logger` (не забудь `require Logger` — это
  макросы).
- **Общий именованный процесс в тестах.** Он делает тесты зависимыми и вынуждает отключать
  `async`. Поднимай процесс на тест через `start_supervised!/1` в `setup` и обращайся по pid.
- **Ловить и логировать сбои «на всякий случай».** Падение процесса супервизор логирует сам;
  лишний `try/rescue` только прячет причину.
