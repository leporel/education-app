# Упражнения

## Модель процессов

```drill
type: multiple-choice
prompt: "Чем процесс BEAM принципиально отличается от goroutine?"
options: ["Тяжелее и медленнее стартует", "Изолирован (свой heap/GC), общается только копией сообщений — нет общей памяти", "Делит память, как goroutine, но с мьютексом по умолчанию", "Это поток ОС"]
answer: "Изолирован (свой heap/GC), общается только копией сообщений — нет общей памяти"
check: exact
hint: Share-nothing — ключ.
```

```drill
type: free-form
prompt: "Go-разработчик защищает счётчик мьютексом. Как ту же задачу решают на BEAM и почему мьютекс не нужен?"
answer: "Заводят процесс-счётчик: его состояние — аргумент рекурсивного receive-цикла. Клиенты шлют сообщения {:inc} / {:get, self()}; процесс обрабатывает их по одному, последовательно (FIFO mailbox), и на каждом сообщении вызывает loop(new_state). Доступ сериализован самой моделью — гонок за состояние нет, мьютекс не нужен. Параллелизм между процессами, а не внутри."
check: manual
```


## Состояние

```drill
type: free-form
prompt: "Напиши процесс-стек: понимает {:push, x}, {:pop, from} (отвечает {:value, top или nil}). Состояние — список. Покажи loop."
answer: "defp loop(stack) do\n  receive do\n    {:push, x} -> loop([x | stack])\n    {:pop, from} ->\n      case stack do\n        [top | rest] -> send(from, {:value, top}); loop(rest)\n        [] -> send(from, {:value, nil}); loop([])\n      end\n  end\nend\nСостояние (stack) — аргумент loop; каждое сообщение даёт новый виток с обновлённым стеком."
check: manual
```

## link / monitor / let it crash

```drill
type: multiple-choice
prompt: "Хочу УЗНАТЬ о падении процесса, но НЕ падать вместе с ним. Что взять?"
options: ["spawn_link", "Process.link", "Process.monitor", "Process.flag(:trap_exit, true) на самом падающем"]
answer: "Process.monitor"
check: exact
hint: monitor односторонний и неинвазивный; даёт сообщение {:DOWN, ...}.
```

```drill
type: multiple-choice
prompt: "Зачем супервизору Process.flag(:trap_exit, true)?"
options: ["Чтобы быстрее падать", "Чтобы сигналы выхода связанных детей приходили как сообщения {:EXIT, ...} и супервизор ловил падения, а не падал сам", "Чтобы запретить детям падать", "Чтобы отключить link"]
answer: "Чтобы сигналы выхода связанных детей приходили как сообщения {:EXIT, ...} и супервизор ловил падения, а не падал сам"
check: exact
hint: Иначе по link супервизор упал бы вместе с ребёнком.
```

```drill
type: free-form
prompt: "Объясни «let it crash» через три выгоды и одно ограничение (что НЕ нужно так обрабатывать)."
answer: "Выгоды: 1) сбой локализован — умирает только затронутый процесс и его состояние; 2) после рестарта состояние чистое — лечит «застрявшее» битое состояние; 3) happy-path код чище — меньше оборонительного try/rescue. Ограничение: ОЖИДАЕМЫЕ ошибки (файла нет, валидация) — это по-прежнему значения {:error, reason}, их обрабатывают явно; падение — только для НЕПРЕДВИДЕННОГО, и оно осознанно изолировано супервизором."
check: manual
```


## Имена процессов

```drill
type: free-form
prompt: "Сервис-счётчик зарегистрирован под именем :counter и упал; супервизор поднял новый процесс. Что произойдёт с клиентами, которые шлют send(:counter, ...)?"
answer: "Они продолжат работать: имя освободилось при смерти старого процесса и было занято новым при старте, поэтому send по имени попадёт уже в новый процесс. Изменится только pid (Process.whereis(:counter) вернёт другой), а состояние нового процесса будет чистым — тем, что задал init."
check: manual
hint: "Имя переживает рестарт, pid — нет."
```

```drill
type: multiple-choice
prompt: "Нужно адресовать тысячи динамических процессов (по одному на пользователя). Что использовать?"
options: ["Process.register с атомом-именем на каждого", "Registry (модуль 08)", "Глобальную мапу в GenServer-синглтоне", "Каждому свой узел"]
answer: "Registry (модуль 08)"
check: exact
hint: "Имена — атомы, а атомы не собираются GC."
```

```drill
type: free-form
prompt: "Процесс выставил Process.flag(:trap_exit, true). Может ли он пережить Process.exit(pid, :kill)? А Process.exit(pid, :shutdown)?"
answer: ":kill пережить нельзя — это неперехватываемый сигнал, процесс умирает при любом флаге. А :shutdown при trap_exit придёт обычным сообщением {:EXIT, from, :shutdown}, и процесс сможет прибраться и решить, завершаться ли."
check: manual
```
