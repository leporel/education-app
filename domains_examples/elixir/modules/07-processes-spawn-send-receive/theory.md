# Процессы: spawn, send, receive

## Что такое процесс BEAM

Процесс BEAM — это **не** процесс ОС и **не** поток ОС. Это легчайшая сущность рантайма:

- **Дёшев.** Создание — микросекунды, стартовый размер ~2.6 КБ. Миллион процессов на одной
  машине — норма, не подвиг.
- **Изолирован.** У каждого процесса **свой heap и свой сборщик мусора**. Память не
  разделяется ни с кем. GC одного процесса не останавливает другие (нет «stop the world»).
- **Вытесняем (preemptive).** Планировщик BEAM сам прерывает процессы по бюджету редукций —
  один жадный процесс не заморозит остальные. (В Go планировщик кооперативно-вытесняющий на
  уровне горутин; здесь — на уровне процессов рантайма, гранулярнее и честнее.)
- **Общается только сообщениями.** Никакой общей памяти. Сообщение **копируется** в mailbox
  получателя (для больших бинарей есть оптимизации, но модель — копирование).

> **Главный контраст с goroutine.** Goroutine дешева, но живёт в общей памяти процесса ОС:
> две горутины могут читать/писать одну переменную, и ты защищаешь это каналами, мьютексами
> и ловишь гонки `-race`. Процесс BEAM — это *изолированный* актор: делить нечего, гонок за
> память нет как класса. Цена — всё общение через копирование сообщений (и нельзя «просто
> взять указатель»). Это фундаментальный размен: безопасность и изоляция против прямого
> доступа к общей памяти.

> **Простыми словами: почтовый ящик.** Представь, что каждый процесс — это сотрудник со своим
> почтовым ящиком. Любой, кто знает адрес (pid), может бросить туда письмо и сразу уйти по
> делам — это `send`. Сам сотрудник время от времени подходит к ящику и разбирает почту — это
> `receive`. Важная деталь: он ищет **первое письмо, подходящее под то, чего он сейчас ждёт**,
> а остальные оставляет в ящике на потом (это называется *селективный* receive). Отсюда два
> практических следствия: (1) непонятные письма не теряются, но и не исчезают — они копятся;
> (2) если ящик забит тысячами неподходящих писем, каждый разбор дорожает, потому что
> просматривать приходится всё заново. Поэтому в боевом коде мусор в mailbox не копят и, где
> уместно, добавляют ветку «всё остальное».

## spawn: рождение процесса

`spawn/1` запускает функцию в новом процессе и возвращает его **pid** (идентификатор):

```elixir
pid = spawn(fn ->
  IO.puts("привет из процесса #{inspect(self())}")
end)
# pid — это #PID<0.123.0>; self() внутри — собственный pid процесса
```

Процесс живёт, пока выполняется его функция; закончилась — процесс штатно завершился
(`:normal`). `spawn` не ждёт результата и не возвращает его — связь только через сообщения.

> **Go-параллель.** `spawn(fn -> ... end)` ≈ `go func(){ ... }()`. Но `go` ничего не
> возвращает, а `spawn` отдаёт `pid` — адрес для отправки сообщений. И «вернуть результат»
> в Go ты делаешь через канал; здесь — отправив сообщение обратно отправителю.

## send и receive: почта

Процессы общаются сообщениями. `send(pid, message)` кладёт сообщение (любой терм) в mailbox
получателя и **сразу возвращается** (асинхронно, не блокирует). `receive` достаёт из
собственного mailbox сообщение, **совпавшее с образцом**:

```elixir
send(pid, {:hello, "мир"})

receive do
  {:hello, who} -> IO.puts("Привет, #{who}")
  {:bye, who}   -> IO.puts("Пока, #{who}")
after
  5_000 -> IO.puts("ничего не пришло за 5 секунд")
end
```

Ключевое:
- `receive` **блокирует** процесс, пока в mailbox не появится подходящее сообщение (или не
  истечёт `after`-таймаут). Блокируется только *этот* процесс, остальные работают.
- Образцы в `receive` — это тот же pattern matching (модуль 02). Сообщение, не совпавшее ни
  с одним образцом, **остаётся в mailbox** (не теряется, ждёт следующего `receive`).
- Mailbox упорядочен (FIFO), но `receive` выбирает первое *совпавшее* по образцам — то есть
  можно «выловить» нужное сообщение раньше прочих.

> **Go-контраст.** Канал в Go — это общая труба между горутинами с типом и (опц.) буфером;
> `<-ch` блокирует. Mailbox процесса — это **личная** очередь получателя, куда любой, у кого
> есть pid, может асинхронно положить сообщение любого вида; `receive` разбирает их
> сопоставлением. Нет «типа канала» — есть образцы. Нет отправителя в сообщении по умолчанию
> — если нужен ответ, кладёшь `self()` в сообщение явно.

## Запрос-ответ: как «вернуть значение»

Раз `spawn` не возвращает результат, паттерн «запрос-ответ» строят руками: отправитель
вкладывает свой pid, сервер отвечает ему сообщением.

```elixir
# клиент:
send(server, {:get, self()})       # «дай значение, вот мой адрес»
receive do
  {:value, v} -> v
end

# сервер (внутри своего цикла):
receive do
  {:get, from} -> send(from, {:value, 42})
end
```

Это «руками» — а `GenServer.call` (модуль 08) автоматизирует ровно этот танец (с тегами,
таймаутами и мониторингом). Понять ручной вариант важно, чтобы GenServer не казался магией.

## Состояние живёт в процессе (через рекурсию)

В Go состояние — это переменная/структура, которую правят несколько горутин под мьютексом. В
Elixir **нет** общей изменяемой памяти. Состояние держит **сам процесс** — как аргумент
своего рекурсивного цикла. Каждое сообщение порождает новый виток цикла с обновлённым
состоянием:

```elixir
defmodule Counter do
  def start(initial), do: spawn(fn -> loop(initial) end)

  defp loop(state) do
    receive do
      {:inc, n}      -> loop(state + n)               # новое состояние = state + n
      {:get, from}   -> send(from, {:count, state}); loop(state)
      :stop          -> :ok                            # выходим из цикла → процесс завершается
    end
  end
end

c = Counter.start(0)
send(c, {:inc, 5})
send(c, {:inc, 3})
send(c, {:get, self()})
receive do {:count, n} -> n end     # => 8
```

Это **сердце** модели: процесс — это бесконечный `receive`-цикл, а «изменяемое состояние» —
неизменяемый аргумент, передаваемый в следующий виток (хвостовой вызов, стек не растёт). Один
процесс обрабатывает свои сообщения **по одному, последовательно** — поэтому внутри гонок
нет, мьютекс не нужен: сериализация доступа встроена в модель. `GenServer` — это ровно этот
цикл, завёрнутый в behaviour.

> **Размышление для Go-головы.** «Счётчик под мьютексом» превращается в «процесс-счётчик»:
> вместо блокировки общей памяти ты *сериализуешь* доступ через mailbox. Параллелизм — между
> процессами; внутри процесса всё строго последовательно. Это убирает целый класс багов
> синхронизации, но требует думать «кому послать сообщение», а не «какой замок взять».

## Имена процессов: как обойтись без pid

Таскать pid по всему коду неудобно, а после рестарта (модуль 08) он ещё и меняется. Поэтому
процессу можно дать **имя** — атом, по которому его найдёт кто угодно:

```elixir
pid = spawn(fn -> loop() end)
Process.register(pid, :counter)   # зарегистрировали под именем

send(:counter, {:inc, 1})         # шлём по имени, pid не нужен
Process.whereis(:counter)         # => pid или nil, если имя не занято
Process.alive?(pid)               # жив ли конкретный процесс
```

Имена уникальны в пределах узла: двух процессов под одним именем не бывает. Когда процесс
умирает, имя автоматически освобождается — поэтому супервизор может поднять новый процесс и
снова занять то же имя. В модуле 08 мы увидим это буквально: `Process.whereis(KV)` до и после
падения вернёт **разные** pid под одним именем.

В OTP имя обычно задают при старте (`name: __MODULE__` у GenServer), а `Process.register`
руками пишут редко. И помни: атомы не собираются GC (модуль 02), поэтому для тысяч
динамических процессов имён-атомов не напасёшься — там берут `Registry` (модуль 08).

> **Go-параллель.** Ближайший аналог — глобальная переменная с указателем на сервис, которую
> читают все. Разница в том, что регистрация встроена в рантайм и имя переживает рестарт:
> клиенты продолжают слать сообщения по имени, не зная, что внутри уже другой процесс.

## link и monitor: узнавать о смерти

Процессы изолированы, но их связывают, чтобы реагировать на падения.

- **`spawn_link`/`Process.link`** — двусторонняя связь: если один процесс падает (не
  `:normal`), второй **тоже** получает сигнал выхода и падает (по умолчанию). Это основа
  супервизии: «всё связанное поддерево падает вместе, потом супервизор поднимает».
- **`Process.flag(:trap_exit, true)`** — превращает сигналы выхода связанных процессов в
  обычные сообщения `{:EXIT, pid, reason}`, которые можно `receive`. Так супервизор *ловит*
  падения, а не падает сам.
- **`Process.monitor(pid)`** — **односторонний**, неинвазивный надзор: ты получишь сообщение
  `{:DOWN, ref, :process, pid, reason}`, когда тот процесс умрёт, но сам не пострадаешь.
  Удобно, когда нужно «узнать о смерти», но не «умереть вместе».

```elixir
ref = Process.monitor(pid)
receive do
  {:DOWN, ^ref, :process, ^pid, reason} -> IO.puts("процесс умер: #{inspect(reason)}")
end
```

> **Go-параллель.** В Go нет встроенного «уведомления о смерти горутины»: ты сам гоняешь
> `done`-каналы, `context`, `sync.WaitGroup` и ловишь паники через `recover`. `link`/
> `monitor` — встроенный механизм рантажа знать о завершении/падении и реагировать. На нём
> стоит вся отказоустойчивость OTP.

### Причины завершения и особый сигнал `:kill`

У любой смерти процесса есть **причина** (reason) — именно она приезжает в `{:EXIT, ...}` и
`{:DOWN, ...}`:

- **`:normal`** — функция процесса штатно закончилась. Такой сигнал связанные процессы
  **игнорируют**, никто не падает.
- **`{%RuntimeError{...}, stacktrace}`** и подобное — процесс упал на исключении. Связанные
  падают, мониторящие получают `{:DOWN, ...}` с этой причиной.
- **`:shutdown`** / `{:shutdown, term}` — плановое завершение; так супервизор просит детей
  остановиться.
- любой свой терм: `exit(:no_more_work)`.

Убить процесс снаружи можно двумя способами, и разница принципиальная:

```elixir
Process.exit(pid, :shutdown)   # вежливо: процесс с trap_exit получит это сообщением
Process.exit(pid, :kill)       # брутально: :kill нельзя перехватить, процесс умирает всегда
```

`:kill` — особый сигнал: его не остановит даже `trap_exit`. Поэтому в демонстрациях рестарта
(модуль 08) процесс убивают именно так — чтобы наверняка.

## «Let it crash» — почему падать нормально

Изоляция (свой heap) + связи (link/monitor) + супервизия (модуль 08) дают стратегию: **не
оборачивай каждый шаг в защиту — дай процессу честно упасть на непредвиденном, и пусть
супервизор перезапустит его в чистое известное состояние.** Преимущества:

- Сбой **локализован**: умирает только затронутый процесс (и его состояние), не вся система.
- Состояние после рестарта **чистое**: многие баги — это «застрявшее» битое состояние;
  рестарт его обнуляет (знаменитое «вы пробовали выключить и включить?» как архитектура).
- Код happy-path **чище**: меньше оборонительных `try/rescue`, больше ясной логики.

Это не «пиши небрежно». Ожидаемые ошибки по-прежнему — значения `{:error, _}` (модуль 04).
Падение — для *непредвиденного*, и оно осознанно изолировано. В модуле 08 супервизоры
превратят это в работающую архитектуру.

## Глоссарий модуля

- **Процесс BEAM** — лёгкая изолированная сущность рантайма со своим heap и GC; не поток ОС.
- **Актор (actor)** — модель: сущность со своим состоянием, общающаяся только сообщениями.
- **pid** — адрес процесса (`#PID<0.123.0>`); `self()` — свой собственный.
- **Mailbox** — личная FIFO-очередь сообщений процесса.
- **Селективный `receive`** — выбирается первое сообщение, совпавшее с образцом; несовпавшие
  остаются в ящике.
- **`after`** — ветка `receive` с таймаутом ожидания.
- **`spawn` / `spawn_link`** — создать процесс / создать и связать с собой.
- **`link`** — двусторонняя связь: падение одного (не `:normal`) роняет второго.
- **`monitor`** — односторонний надзор: приходит `{:DOWN, ref, :process, pid, reason}`,
  наблюдатель не страдает.
- **`trap_exit`** — флаг, превращающий сигналы выхода связанных в сообщения `{:EXIT, ...}`.
- **Причина завершения (reason)** — `:normal` (игнорируется связанными), исключение,
  `:shutdown`, свой терм.
- **`:kill`** — неперехватываемый сигнал: убивает процесс даже при `trap_exit`.
- **Регистрация имени** — `Process.register/2`, `Process.whereis/1`, `name:` при старте;
  имя переживает рестарт процесса.
- **Состояние через рекурсию** — «изменяемое» состояние как аргумент бесконечного
  `receive`-цикла.
- **«Let it crash»** — непредвиденное не ловим, а даём процессу упасть под присмотром
  супервизора (модуль 08).

## Типичные ошибки и заблуждения

- **Думать «процесс = goroutine».** Goroutine делит память; процесс BEAM изолирован (свой
  heap/GC) и общается копией сообщений. Это разные модели, не синонимы.
- **Искать общую изменяемую переменную для состояния.** Её нет. Состояние держит процесс в
  аргументе рекурсивного цикла; «изменить» = послать сообщение и получить новый виток.
- **Забыть рекурсивный вызов в цикле.** Если `loop` не вызвал себя снова после `receive`,
  процесс обработает одно сообщение и завершится. Цикл = `receive ... -> loop(new_state)`.
- **Неограниченный mailbox.** Если присылают быстрее, чем процесс разгребает, mailbox растёт
  и съедает память (а `receive` с селективным образцом ещё и замедляется). Следи за темпом;
  в OTP есть back-pressure-инструменты.
- **Блокирующий `receive` без `after`.** Ждёшь сообщение, которое не придёт → процесс висит
  вечно. Где уместно — ставь `after` с таймаутом.
- **`send` ничего не гарантирует о доставке/порядке между разными отправителями.** `send`
  асинхронен и «лучшее усилие»: успешная отправка не значит, что получатель жив или ответит.
  Для надёжного запрос-ответа нужен мониторинг/таймаут (это даёт `GenServer.call`).
- **Класть в сообщение гигантские структуры.** Сообщение копируется в чужой heap; огромные
  термы — это копирование и память. Шли необходимое (или ссылки на ETS/хранилище).
- **Ловить всё `trap_exit`, имитируя try/catch.** `trap_exit` — для супервизорной логики, а
  не «глушилка падений». Не превращай процесс в ловца всех ошибок — это анти-OTP.
- **Думать, что `trap_exit` защищает от всего.** Сигнал `:kill` неперехватываем: процесс
  умрёт при любом флаге. Это осознанный «выключатель последней инстанции».
- **Ждать, что штатное завершение уронит связанных.** Причина `:normal` связанными
  игнорируется — падают только на аварийных причинах.
- **Плодить имена-атомы для динамических процессов.** Атомы не собираются GC; на тысячи
  процессов их не напасёшься. Регистрируй по имени единичные сервисы, а для множества —
  `Registry` (модуль 08).
