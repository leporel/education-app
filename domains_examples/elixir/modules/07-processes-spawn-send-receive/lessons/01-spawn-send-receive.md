# Урок 01 — Первый процесс и обмен сообщениями

Цель: создать процесс, обменяться с ним сообщениями, построить запрос-ответ и `receive`-цикл.
Якорь — Go: где `spawn` это `go`, а mailbox это «личный канал», и чем модель отличается.

## Разогрев

- Что возвращает `spawn`? (pid — адрес для сообщений)
- Блокирует ли `send`? А `receive`? (`send` нет; `receive` блокирует текущий процесс)
- Как получить ответ от процесса, если `spawn` не возвращает результат? (вложить `self()` и ждать сообщение)

## Шаг 1. Самый простой процесс

```elixir
pid = spawn(fn -> IO.puts("я процесс #{inspect(self())}") end)
# печатает что-то вроде: я процесс #PID<0.142.0>
Process.alive?(pid)   # скорее всего false — он уже отработал и завершился
```

Процесс выполнил функцию и штатно умер. `self()` внутри — его собственный pid. Пока это
просто «горутина, которая ничего не возвращает».

## Шаг 2. Отправляем и принимаем

Заведём процесс, который ждёт одно сообщение:

```elixir
pid = spawn(fn ->
  receive do
    {:greet, name} -> IO.puts("Привет, #{name}!")
    other          -> IO.puts("не понял: #{inspect(other)}")
  end
end)

send(pid, {:greet, "Go-разработчик"})   # => печатает "Привет, Go-разработчик!"
```

`receive` заблокировал процесс, пока в его mailbox не пришло `{:greet, _}`. Образцы — обычный
pattern matching. После единственного `receive` функция закончилась → процесс умер. Чтобы он
жил и принимал много сообщений, нужен цикл (шаг 4).

## Шаг 3. Запрос-ответ: вернуть значение

`spawn` не возвращает результат, поэтому ответ организуем сообщением обратно. Клиент кладёт
свой `self()`:

```elixir
server = spawn(fn ->
  receive do
    {:square, n, from} -> send(from, {:result, n * n})
  end
end)

send(server, {:square, 9, self()})

result =
  receive do
    {:result, r} -> r
  after
    1_000 -> :timeout
  end

result   # => 81
```

Разбор танца:
1. Клиент шлёт `{:square, 9, self()}` — данные **и свой адрес**.
2. Сервер считает и шлёт `{:result, 81}` на адрес `from`.
3. Клиент `receive`-ит ответ. `after 1_000` страхует от зависания, если сервер умер/не ответил.

> **Go-контраст.** В Go ты бы сделал `ch := make(chan int); go func(){ ch <- n*n }(); <-ch`.
> Здесь нет общего канала: клиент даёт серверу свой pid, сервер отвечает в личный mailbox
> клиента. Адрес ответа путешествует **внутри** сообщения. Именно это автоматизирует
> `GenServer.call` (модуль 08) — добавляя теги и мониторинг, чтобы не зависнуть на мёртвом сервере.

## Шаг 4. Долгоживущий процесс: receive-цикл

Чтобы процесс принимал сообщения бесконечно, после обработки он **снова вызывает себя**:

```elixir
defmodule Echo do
  def start, do: spawn(&loop/0)

  defp loop do
    receive do
      {:say, text, from} ->
        send(from, {:echo, text})
        loop()                       # ← снова ждём; без этого процесс умрёт
      :stop ->
        IO.puts("echo остановлен")
        # нет вызова loop → процесс завершается
    end
  end
end

e = Echo.start()
send(e, {:say, "hello", self()})
receive do {:echo, t} -> t end       # => "hello"
send(e, {:say, "again", self()})
receive do {:echo, t} -> t end       # => "again"
send(e, :stop)                       # => печатает "echo остановлен", процесс умирает
```

`loop/0` — бесконечный (хвостовая рекурсия, стек не растёт). Каждое сообщение → обработка →
снова `receive`. Это скелет любого «сервера» на BEAM. Пока без состояния — добавим его в
уроке 02.

## Шаг 5. Параллелизм: много процессов разом

Процессы дёшевы — заведём тысячу и соберём ответы:

```elixir
me = self()

# запустить 1..1000 процессов, каждый шлёт назад свой квадрат
for n <- 1..1000 do
  spawn(fn -> send(me, {:done, n, n * n}) end)
end

# собрать 1000 ответов
results =
  for _ <- 1..1000, into: %{} do
    receive do
      {:done, n, sq} -> {n, sq}
    end
  end

map_size(results)   # => 1000
results[500]        # => 250000
```

Тысяча процессов стартовали практически мгновенно, отработали параллельно (планировщик BEAM
раскидал их по ядрам) и сложили результаты в наш mailbox. Никаких мьютексов, `WaitGroup` или
race-детектора — каждый процесс изолирован, общий ресурс (карта результатов) собирается в
одном процессе из его личного mailbox.

## Итог

`spawn` рождает изолированный процесс и даёт его pid; `send` асинхронно кладёт сообщение в
mailbox, `receive` блокирующе разбирает его сопоставлением. Результат возвращают сообщением
обратно (вложив `self()`), долгоживущий сервер — это `receive`-цикл с хвостовой рекурсией, а
тысяча процессов стартует без церемоний. Дальше — состояние внутри процесса и то, что
происходит, когда процесс падает: link, monitor и «let it crash» в деле.
