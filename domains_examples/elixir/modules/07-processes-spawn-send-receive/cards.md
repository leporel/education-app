# Карточки

## Модель процессов

```card
front: Три ключевых свойства процесса BEAM?
back: 1) Дёшев (старт ~микросекунды, ~2.6 КБ, миллионы на машине). 2) Изолирован — свой heap и свой GC, память не разделяется. 3) Вытесняем (preemptive scheduling) — жадный процесс не заморозит остальные. Общение только сообщениями (копией).
tags: [elixir, process]
```

```card
front: Главное отличие процесса BEAM от goroutine?
back: "Goroutine дешева, но в ОБЩЕЙ памяти — гонки защищают каналами/мьютексами/-race. Процесс BEAM ИЗОЛИРОВАН (свой heap/GC), делить нечего, гонок за память нет как класса; всё общение через копирование сообщений. Размен: безопасность/изоляция против прямого доступа к общей памяти."
tags: [elixir, process, goroutine]
```

```card
front: Что возвращает spawn и чем отличается от `go` в Go?
back: spawn(fn -> ... end) запускает функцию в новом процессе и возвращает его pid (адрес для сообщений). `go` в Go не возвращает ничего. Результат через spawn не получить — только отправив сообщение обратно отправителю.
tags: [elixir, spawn, pid]
```

## send / receive

```card
front: Как ведут себя send и receive?
back: send(pid, msg) кладёт сообщение в mailbox получателя и сразу возвращается (асинхронно, не блокирует). receive блокирует ТЕКУЩИЙ процесс, пока в его mailbox не появится сообщение, совпавшее с образцом (или истечёт after-таймаут). Остальные процессы при этом работают.
tags: [elixir, send, receive]
```

```card
front: Что происходит с сообщением в receive, не совпавшим ни с одним образцом?
back: Оно остаётся в mailbox (не теряется) и будет рассмотрено при следующем receive. receive выбирает первое СОВПАВШЕЕ сообщение по образцам — можно «выловить» нужное раньше прочих (селективный receive).
tags: [elixir, receive, mailbox]
```

```card
front: Чем mailbox процесса отличается от канала Go?
back: Канал — общая типизированная труба между горутинами с (опц.) буфером. Mailbox — ЛИЧНАЯ очередь получателя, куда любой с его pid кладёт сообщение любого вида асинхронно; receive разбирает их сопоставлением (нет типа канала — есть образцы). Для ответа кладёшь self() в сообщение явно.
tags: [elixir, mailbox, channel, go]
```

```card
front: Как реализовать запрос-ответ между процессами вручную?
back: "Клиент шлёт {:get, self()} (вкладывает свой pid), затем receive {:value, v}. Сервер в своём цикле: receive {:get, from} -> send(from, {:value, ...}). GenServer.call автоматизирует этот танец с тегами/таймаутами/мониторингом."
tags: [elixir, request-reply]
```

## Состояние

```card
front: Где живёт «изменяемое состояние» процесса, если общей памяти нет?
back: "В самом процессе — как аргумент его рекурсивного receive-цикла. Каждое сообщение порождает новый виток loop с обновлённым (неизменяемым) состоянием: receive ... -> loop(new_state). Это предтеча GenServer."
tags: [elixir, state, recursion]
```

```card
front: Почему внутри одного процесса не нужен мьютекс?
back: Процесс обрабатывает свои сообщения по одному, последовательно (FIFO из mailbox). Доступ сериализован самой моделью — параллелизм между процессами, а не внутри. Гонок за состояние внутри процесса нет, мьютекс не нужен.
tags: [elixir, state, mutex]
```

```card
front: Что будет, если в receive-цикле забыть рекурсивный вызов loop?
back: Процесс обработает ОДНО сообщение и завершится (функция дойдёт до конца). Чтобы процесс жил и держал состояние, каждая ветка должна вызвать loop(new_state) снова (хвостовой вызов — стек не растёт).
tags: [elixir, loop, recursion]
```

## link / monitor / let it crash

```card
front: Чем link отличается от monitor?
back: "link (spawn_link) — двусторонняя связь: падение одного (не :normal) роняет связанного (по умолчанию). monitor (Process.monitor) — односторонний неинвазивный надзор: получаешь {:DOWN, ref, :process, pid, reason}, но сам не падаешь. link — для супервизорных поддеревьев, monitor — «узнать о смерти, не умирая»."
tags: [elixir, link, monitor]
```

```card
front: Что делает Process.flag(:trap_exit, true)?
back: Превращает сигналы выхода СВЯЗАННЫХ процессов в обычные сообщения {:EXIT, pid, reason}, которые можно receive, вместо того чтобы падать вместе. Так супервизор ловит падения детей, а не умирает сам. Не использовать как глушилку всех ошибок.
tags: [elixir, trap-exit]
```

```card
front: Почему «let it crash» — это надёжность, а не небрежность?
back: "Изоляция (свой heap) + link/monitor + супервизия дают: сбой локализован (умирает только затронутый процесс), состояние после рестарта чистое (рестарт лечит «застрявшее» битое состояние), happy-path код чище (меньше оборонительного try/rescue). Ожидаемые ошибки — всё равно {:error,_}; падение — для непредвиденного, осознанно изолированного."
tags: [elixir, let-it-crash]
```

```card
front: Что НЕ гарантирует send?
back: "send асинхронен и «лучшее усилие»: успешная отправка не значит, что получатель жив, обработает или ответит, и нет гарантий порядка между РАЗНЫМИ отправителями. Для надёжного запрос-ответа нужны мониторинг и таймаут — их даёт GenServer.call."
tags: [elixir, send, guarantees]
```

## Mailbox простыми словами

```card
front: "Объясни mailbox и селективный receive на бытовой аналогии."
back: "Процесс — сотрудник со своим почтовым ящиком. send бросает письмо и сразу уходит; receive — сотрудник подходит и ищет ПЕРВОЕ письмо, подходящее под то, чего он ждёт, остальные оставляет в ящике. Следствия: непонятные сообщения не теряются, но копятся; забитый ящик делает каждый разбор дороже."
tags: [elixir, mailbox, receive]
```

## Имена процессов

```card
front: "Зачем регистрировать процесс под именем и что при этом переживает рестарт?"
back: "Чтобы слать сообщения по имени, не таская pid: Process.register(pid, :counter), send(:counter, msg), Process.whereis(:counter). Имя уникально в пределах узла и освобождается при смерти процесса, поэтому супервизор поднимает новый процесс под тем же именем — клиенты продолжают работать, хотя pid уже другой."
tags: [elixir, process, register]
```

```card
front: "Почему нельзя регистрировать тысячи динамических процессов по имени?"
back: "Имена процессов — атомы, а атомы не собираются GC (модуль 02): много уникальных имён приведут к росту таблицы атомов и в пределе уронят узел. Единичные сервисы регистрируют по имени, множество динамических процессов — через Registry (модуль 08)."
tags: [elixir, process, registry, atom]
```

## Причины завершения

```card
front: "Какие бывают причины завершения процесса?"
back: ":normal — функция штатно закончилась (связанные процессы такой сигнал ИГНОРИРУЮТ); исключение вида {%RuntimeError{}, stacktrace} — аварийное падение (связанные падают, мониторящие получают {:DOWN, ...}); :shutdown — плановая остановка от супервизора; любой свой терм через exit(term)."
tags: [elixir, exit, reason]
```

```card
front: "Чем Process.exit(pid, :kill) отличается от Process.exit(pid, :shutdown)?"
back: ":shutdown — вежливое завершение: процесс с trap_exit получит его сообщением {:EXIT, ...} и сможет прибраться. :kill неперехватываем: процесс умирает всегда, даже с trap_exit. Поэтому демонстрации рестарта делают через :kill — чтобы наверняка."
tags: [elixir, exit, kill]
```
