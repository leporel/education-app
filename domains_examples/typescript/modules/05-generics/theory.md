# Дженерики

## Суть: параметризуем код типом

Представь функцию «вернуть первый элемент массива». Без дженериков у тебя два плохих
варианта: либо писать отдельную версию под каждый тип (`firstNumber`, `firstString` —
копипаста), либо взять `any` и потерять типобезопасность (`first(arr: any[]): any`).
Дженерик решает обе беды разом:

```ts
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}

const a = first([1, 2, 3]);          // a: number | undefined
const b = first(["x", "y"]);         // b: string | undefined
const c = first([true, false]);      // c: boolean | undefined
```

`<T>` — **параметр типа**: переменная, но не для значений, а для типов. Вызывая
функцию, ты (или TS за тебя) подставляешь конкретный тип вместо `T`, и связь
сохраняется: «что внутри массива, то и вернётся». Никакой копипасты, полная
типобезопасность.

> **Простыми словами.** Дженерик — это не «любой тип» (это `any`), а **«тот же самый тип
> в нескольких местах»**. Смысл в проводке: чем связаны вход и выход. Если связывать
> нечего, дженерик не нужен.

По традиции параметры типа называют короткими буквами: `T` (type), `K` (key), `V`
(value), `E` (element или error), `U`/`R` для второго типа и результата. Для сложных
API осмысленное имя (`TItem`, `TResult`) читается лучше — правило то же, что с именами
переменных: коротко там, где очевидно, длиннее там, где нет.

Для Go-разработчика это знакомо — там это `func First[T any](s []T) T`. Синтаксис
другой (`<T>` против `[T any]`), идея одна. Но дальше начинаются различия, и они
важные.

## Вывод типов: T обычно подставляется сам

В примере выше мы **нигде не написали** `first<number>(...)`. TS вывел `T = number` из
аргумента. Это сильная сторона: явно указывать тип-параметр приходится редко, в
основном когда вывести его неоткуда:

```ts
const x = first<number>([]);   // явно: пустой массив, выводить T неоткуда → x: number | undefined
```

В Go вывод типов-параметров тоже есть, но в TS он, как правило, «умнее» и охватывает
больше случаев, потому что он встроен в очень развитую систему вывода всего языка.

## Ограничения (constraints): `<T extends ...>`

Чистый `<T>` означает «вообще любой тип» — и значит, внутри функции ты почти ничего не
можешь с `T` делать (ведь это может оказаться `number`, у которого нет `.length`, или
`boolean`, у которого нет вообще ничего). Часто нужно сказать «`T` — любой, но
обязательно с такими-то свойствами». Это **ограничение** через `extends`:

```ts
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

longest("ab", "abc");          // OK: строки имеют length → вернёт "abc"
longest([1], [1, 2, 3]);       // OK: массивы имеют length → вернёт [1,2,3]
longest(10, 20);               // ❌ у number нет свойства length
```

`T extends { length: number }` читается как «`T` — любой тип, лишь бы у него было
свойство `length: number`». Это структурное ограничение, и здесь видна разница с Go:

- В **Go** ограничение дженерика — это **интерфейс** (набор методов) или специальный
  type set (`~int | ~string`). Ты ограничиваешь по поведению/набору типов.
- В **TS** ограничение — это **любой тип-выражение**: форма объекта, union, другой
  параметр типа. Гибче, но и легче выстрелить себе в ногу.

### Ограничение одним параметром через другой

Параметр типа может ограничиваться **другим** параметром типа — классический пример —
типобезопасный доступ к свойству объекта:

```ts
function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { id: 1, name: "Ann" };
getProp(user, "name");    // тип результата: string
getProp(user, "id");      // тип результата: number
getProp(user, "email");   // ❌ "email" не является ключом user
```

Здесь `K extends keyof T` означает «`K` — любой из ключей объекта `T`», а `T[K]` — тип
значения под этим ключом. Компилятор не только запрещает несуществующий ключ, но и
**точно знает тип возвращаемого значения** для каждого ключа. В Go такого по объектам
сделать нельзя в принципе — `keyof`/indexed access это уже территория «типы как
вычисления», которой Go-дженерики не предусматривают. (`keyof` подробно — в модуле 06,
но базовую идею стоит увидеть здесь.)

## Default-параметры типа

Как у функций бывают значения по умолчанию, у дженериков бывают **типы по умолчанию**:

```ts
type ApiResponse<T = unknown> = {
  ok: boolean;
  data: T;
};

const r1: ApiResponse = { ok: true, data: 42 };          // T = unknown (по умолчанию)
const r2: ApiResponse<string> = { ok: true, data: "hi" }; // T = string
```

Удобно, когда в большинстве случаев подходит разумный дефолт, но иногда хочется
уточнить.

## Дженерики в типах и классах

Параметризовать можно не только функции, но и типы/интерфейсы/классы:

```ts
interface Box<T> {
  value: T;
  map<U>(fn: (v: T) => U): Box<U>;   // метод тоже может вводить свой параметр U
}

class Stack<T> {
  private items: T[] = [];
  push(item: T): void { this.items.push(item); }
  pop(): T | undefined { return this.items.pop(); }
  get size(): number { return this.items.length; }
}

const s = new Stack<number>();
s.push(1);
s.push(2);
s.pop();      // number | undefined
s.push("x");  // ❌ "x" не number
```

`Stack<number>` — стек, типобезопасный для чисел; `Stack<string>` — для строк, и так
далее. Один класс, бесконечно много типобезопасных применений.

## Дженерики тоже стираются: почему нельзя `new T()`

Помни главное правило курса: типы исчезают при компиляции. Для дженериков это значит, что
**внутри функции нельзя ничего спросить у `T`**:

```ts
function make<T>(): T {
  // return new T();          // ❌ 'T' only refers to a type, but is being used as a value
  // if (x instanceof T) {}   // ❌ то же самое
  return null as T;           // единственный способ — соврать компилятору (плохая идея)
}
```

Ни создать значение типа `T`, ни проверить его в рантайме нельзя — `T` в скомпилированном
JS просто нет. Как это делают на практике: передают **фабрику** или **само значение**
аргументом.

```ts
// вместо new T() — передаём функцию-создатель
function makeList<T>(factory: () => T, n: number): T[] {
  return Array.from({ length: n }, factory);
}
makeList(() => ({ id: 0 }), 3);   // T выведен из фабрики

// вместо instanceof T — передаём конструктор (он реален в рантайме)
function isInstance<T>(x: unknown, ctor: new (...args: never[]) => T): x is T {
  return x instanceof ctor;
}
isInstance(err, Error);           // работает: Error — значение, а не только тип
```

Go-разработчику это знакомо: там тоже нельзя написать `new(T)` без ограничений и
приходится передавать конструктор или использовать `reflect`. Разница в том, что в Go
`reflect` реально существует, а в TS отступать некуда — только передавать значения.

## Дженерик vs `any`: чем именно они различаются

Частая путаница, которую стоит проговорить: и `<T>`, и `any` позволяют «принимать что
угодно». Разница в том, **что происходит с информацией о типе**:

```ts
function firstAny(arr: any[]): any { return arr[0]; }
function firstT<T>(arr: T[]): T | undefined { return arr[0]; }

const a = firstAny(["hi"]);   // a: any    — тип потерян, дальше ошибки не ловятся
a.toFixed(2);                  // компилятор молчит, рантайм упадёт

const b = firstT(["hi"]);     // b: string | undefined — тип сохранён
b.toFixed(2);                  // ❌ ошибка сразу: у string нет toFixed
```

`any` **выключает** проверку, дженерик её **переносит** от места вызова к результату.
Поэтому «взять `any`, чтобы работало с любым типом» — почти всегда неправильный ответ, а
правильный — дженерик или `unknown` с сужением.

## Вариантность: почему `Dog[]` и `Animal[]` — отдельная история

Тонкая, но важная тема, на которой стоит получить хотя бы интуицию (полное понимание
приходит с опытом). Вопрос: если `Dog` — подтип `Animal`, является ли `Dog[]` подтипом
`Animal[]`? Является ли функция `(x: Animal) => void` подтипом `(x: Dog) => void`?

Короткие ответы для TS:

- **Контейнеры (массивы, объекты) ведут себя ковариантно по чтению:** `Dog[]` можно
  использовать там, где ждут `Animal[]` (читать собак как животных безопасно). Но это
  **не всегда безопасно при записи** — TS здесь местами «оптимистичен» и пропускает то,
  что строгая теория запретила бы (исторический компромисс ради удобства).
- **Аргументы функций ведут себя контравариантно** (с оговорками, см. флаг
  `strictFunctionTypes`): функцию, принимающую более общий тип, можно подставить туда,
  где ждут функцию для более узкого. Звучит наизнанку — но если функция умеет работать
  с любым `Animal`, она тем более справится с `Dog`.

```ts
type Animal = { name: string };
type Dog = { name: string; breed: string };

const dogs: Dog[] = [{ name: "Rex", breed: "lab" }];
const animals: Animal[] = dogs;   // OK: читать как Animal[] безопасно

function petAnimal(a: Animal) { console.log(a.name); }
const handler: (d: Dog) => void = petAnimal;   // OK: функция для Animal примет и Dog
```

Практический вывод на старте: **не пугайся, если присваивание массивов/функций иногда
проходит, а иногда нет — это вариантность.** Глубоко закапываться сейчас не нужно;
достаточно знать, что такое явление есть и как оно называется, чтобы потом понять
сообщение об ошибке.

## Когда дженерик не нужен (частая ошибка новичков)

Соблазн, в который попадают все: «добавлю-ка везде `<T>`, будет гибче». Не надо.
Дженерик оправдан, **только если есть реальная связь между типами** — вход и выход,
два аргумента, контейнер и его содержимое. Если параметр типа используется ровно один
раз и ни с чем не связан — он бесполезен:

```ts
function logLength<T extends { length: number }>(x: T): void {  // T лишний!
  console.log(x.length);
}
// проще и честнее:
function logLength2(x: { length: number }): void {
  console.log(x.length);
}
```

Правило-эвристика: **если параметр типа встречается в сигнатуре только один раз — он,
скорее всего, не нужен.** Дженерик существует, чтобы *связать* несколько мест одним
типом.

## Типичные ошибки и заблуждения

- **«`<T>` надо указывать при каждом вызове».** Нет, чаще TS выводит его сам из
  аргументов. Явно — только когда выводить неоткуда.
- **«Чистый `<T>` позволяет делать с `T` что угодно».** Наоборот — почти ничего, ведь
  `T` может быть любым. Нужны операции → добавь ограничение `extends`.
- **«Ограничения в TS — это интерфейсы, как в Go».** Нет, ограничение — любой
  тип-выражение (форма, union, `keyof T`). Гибче.
- **«Чем больше дженериков, тем лучше».** Нет. Параметр типа, встречающийся один раз и
  ни с чем не связанный, — лишний шум. Используй обычный тип.
- **«Массив подтипа всегда взаимозаменяем с массивом супертипа».** Тут вступает
  вариантность; TS местами оптимистичен. Не строй на этом жёстких допущений.
- **«`<T>` — это красивый `any`».** Нет: `any` выключает проверку, дженерик переносит
  тип от вызова к результату. Информация о типе сохраняется.
- **«Внутри дженерика можно сделать `new T()`».** Нельзя: `T` стирается. Передавай
  фабрику или конструктор аргументом.

## Глоссарий модуля

- **Параметр типа** (`<T>`) — «переменная» для типа; подставляется при использовании.
- **Аргумент типа** — конкретный тип, подставленный вместо параметра (`Stack<number>`).
- **Ограничение (constraint)** — `T extends ...`, требование к параметру типа.
- **Вывод аргументов типа** — TS сам определяет `T` по переданным значениям.
- **Default-параметр типа** — `<T = unknown>`, значение по умолчанию.
- **`keyof T`** — union ключей типа `T` (подробно в модуле 06).
- **Indexed access `T[K]`** — тип значения по ключу.
- **Вариантность** — правила совместимости составных типов (`Dog[]` и `Animal[]`).
- **Ковариантность / контравариантность** — «в ту же сторону» / «в обратную сторону»
  по отношению к подтипам.
- **Стирание дженериков** — `T` не существует в рантайме: нет ни `new T()`, ни
  `instanceof T`.
