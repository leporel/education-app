# Зачем нужен TypeScript и как его запускать

## Суть: TS — это документация, которую проверяет компилятор

JavaScript — динамически типизированный язык. Тип значения известен только в момент
выполнения, и язык радостно разрешает абсурд:

```js
function area(w, h) {
  return w * h;
}

area(3, 4);          // 12
area("3", "4");      // 12 — оператор * молча привёл строки к числам. Сработало «случайно»
area("3", "abc");    // NaN — а тут приведение не удалось
area(3);             // NaN (h === undefined, 3 * undefined = NaN)
area({}, []);        // NaN
```

Обрати внимание на второй вызов: он **не упал и даже дал правильный ответ** — оператор
`*` сам привёл строки к числам. Это хуже, чем ошибка: код «работает», пока однажды не
придёт `"abc"` или `"3,5"`. А остальные вызовы вернут `NaN` — и тоже не упадут в момент
вызова: ты поедешь дальше, пока через десять функций `NaN` не всплывёт как
`"Цена: NaN ₽"` на экране у клиента. Динамическая типизация откладывает обнаружение ошибки до рантайма, причём
часто далеко от места, где она возникла.

TypeScript добавляет **слой статической проверки типов поверх JavaScript**. Ты
описываешь намерения:

```ts
function area(w: number, h: number): number {
  return w * h;
}

area(3, 4);          // OK
area("3", "4");      // ❌ Ошибка ещё в редакторе: Argument of type 'string'...
area(3);             // ❌ Expected 2 arguments, but got 1
```

Ошибки всплывают **до запуска**, прямо при наборе текста, с подсветкой в редакторе.
Это и есть главная ценность: сдвиг обнаружения ошибок «влево» — с прода в момент
написания. Для Go-разработчика это родная идея: ты привык, что компилятор не пустит
кривой код. TS возвращает это ощущение в мир JavaScript.

Но есть нюанс, переворачивающий всё, — следующий раздел.

## Стирание типов: TS живёт только до запуска

Повторим ключевую мысль из модуля 01, потому что она определяет вообще всё. **Типы
TypeScript не существуют в рантайме.** Компилятор проверяет их и выбрасывает.

```ts
type User = { id: number; name: string };

function save(u: User) {
  // ❌ так нельзя: типа User в рантайме нет, проверять нечего
  // if (u instanceof User) ...

  // ✅ проверять можно только реальные JS-значения
  if (typeof u.id === "number" && typeof u.name === "string") {
    // ...
  }
}
```

Контраст с Go острый. В Go тип — рантайм-сущность: `switch v := x.(type)`,
`reflect.TypeOf`, проверка интерфейса в рантайме — всё работает, потому что типы
реальны во время выполнения. В TS ничего этого нет: после компиляции `type User`
исчезает бесследно. Из этого вытекает железное практическое правило:

> **Данные с границы программы (сеть, файл, ввод пользователя) TypeScript не
> проверяет в рантайме.** Если сервер прислал JSON, ты можешь объявить, что это
> `User`, но TS поверит на слово — и если сервер соврал, ты получишь рантайм-сюрприз.
> Для реальной проверки таких данных используют рантайм-валидаторы (например, `zod`).
> TS защищает твой код от тебя самого, но не от внешнего мира.

Это не недостаток, а следствие дизайна: TS обещал не менять рантайм JavaScript и
сдержал обещание. Понимая это, ты не будешь искать `instanceof MyType` там, где его
быть не может.

> **Простыми словами.** TypeScript — это очень строгий редактор, который читает твой
> код и ругается на несоответствия. Когда он закончил читать, он уходит. Дальше твой код
> живёт один, без него, в обычном JavaScript.

## Структурная типизация: «если крякает как утка»

Вот тема, где у тебя как у Go-разработчика готова половина интуиции, но есть тонкая
ловушка. Вопрос: когда тип `A` совместим с типом `B`?

- **Номинальная типизация** (Go для именованных типов, Java, C#): по **имени**. Тип
  `Celsius` и тип `Fahrenheit`, даже если оба — это `float64`, **несовместимы**,
  потому что названы по-разному. Имя — часть идентичности типа.
- **Структурная типизация** (TypeScript целиком): по **форме**. Два типа совместимы,
  если у них совпадает структура (набор свойств подходящего вида), как бы они ни
  назывались.

```ts
type Point = { x: number; y: number };

function len(p: Point): number {
  return Math.hypot(p.x, p.y);
}

const vector = { x: 3, y: 4, label: "v" };  // тип НЕ назван Point
len(vector);   // ✅ OK! У vector есть x:number и y:number — форма подходит
```

`vector` нигде не объявлен как `Point`, но TS его принимает: важна форма, а не ярлык.
Это и называют «утиной типизацией» — «если оно ходит как утка и крякает как утка, то
это утка». Лишнее поле `label` не мешает: главное, что нужные свойства на месте.

**Где ловушка для Go-разработчика.** В Go структурная совместимость есть, но только
для **интерфейсов**: тип удовлетворяет интерфейсу, если реализует его методы, без
явного объявления — это похоже на TS. Но **именованные структуры в Go номинальны**:

```go
// Go
type Celsius float64
type Fahrenheit float64
var c Celsius = 100
var f Fahrenheit = c   // ❌ ошибка компиляции: разные именованные типы
```

В TS аналогичный трюк по умолчанию **не защитит** тебя:

```ts
type Celsius = number;
type Fahrenheit = number;
let c: Celsius = 100;
let f: Fahrenheit = c;   // ✅ TS не против: оба — это просто number
```

Для TS `Celsius` и `Fahrenheit` — синонимы `number`, форма одна, значит совместимы.
Если тебе нужна Go-подобная номинальная защита (чтобы не сложить градусы с
долларами), её приходится эмулировать «брендированными типами» — это продвинутая
техника из модуля 06. Пока просто запомни: **TS по умолчанию смотрит на форму, не на
имя.** Это удобно (меньше церемоний), но иногда пропускает то, что Go бы поймал.

## Градуальная типизация и `any`

TS — **градуально типизированный** язык: можно типизировать строго, можно — частично,
можно вообще оставлять куски нетипизированными. Это сделано нарочно, чтобы можно было
постепенно переносить старый JS-проект на TS, файл за файлом. Инструмент этой
постепенности — тип `any`.

`any` означает «отключи проверку типов для этого значения». С `any` можно делать
что угодно, и компилятор молчит:

```ts
let x: any = 5;
x.foo.bar();      // компилятор не возражает
x = "теперь строка";
x();              // и тут не возражает — а в рантайме всё рухнет
```

`any` — это аварийный люк из системы типов. Иногда он необходим (быстрый прототип,
интеграция с совсем нетипизированной библиотекой), но у него есть мерзкое свойство:
**он заразен**. Стоит `any` просочиться, и проверка отключается по цепочке, тихо
сводя на нет всю пользу TS. Поэтому относись к `any` как к слову из трёх букв на
заборе: иногда вырывается, но в приличном коде его стараются не писать. В `tsconfig`
есть флаги, которые запрещают неявный `any` (см. ниже про `strict`).

### `unknown` — безопасный брат `any`

Когда тип честно неизвестен (например, результат `JSON.parse`), вместо `any`
правильнее взять `unknown`. `unknown` тоже «что угодно», но с обязательной проверкой: с ним
**ничего нельзя делать, пока не сузишь тип**.

```ts
const data: unknown = JSON.parse(input);

data.name;                    // ❌ нельзя: тип ещё неизвестен
if (typeof data === "object" && data !== null && "name" in data) {
  // здесь TS уже знает достаточно, чтобы пустить дальше
}
```

Правило: **внешние данные принимай как `unknown`, а не `any`** — и компилятор
заставит тебя проверить их перед использованием. Это прямой инструмент против той
самой проблемы «сервер соврал».

### `never` — тип, которого не бывает

`never` — значение, которого не может существовать. Им TS обозначает «сюда поток
выполнения не дойдёт»: функция, которая всегда бросает исключение или вечно крутится,
возвращает `never`. На старте просто узнавай его; по-настоящему он раскроется в
модуле 04 (проверка исчерпанности `switch`).

## `as` и `!`: два способа сказать «поверь мне»

Раз компилятор не всегда знает то, что знаешь ты, должен быть способ ему это сообщить.
Таких способов два, и оба — с оговоркой «под твою ответственность».

**Утверждение типа (type assertion)** `x as T` — «считай это значение типом `T`»:

```ts
const data: unknown = JSON.parse(raw);
const user = data as { id: number };   // обещаем компилятору, что там объект с id
user.id;                                // TS доволен... а рантайм — как повезёт
```

**Утверждение «не пустота»** `x!` (non-null assertion) — «здесь точно не `null`/`undefined`»:

```ts
const el = document.getElementById("root");   // тип: HTMLElement | null
el!.textContent = "hi";                        // «я знаю, элемент есть»
```

Ключевое, что надо усвоить: **`as` и `!` не выполняют никакой проверки** и полностью
исчезают при компиляции. Это не приведение типа, как `int(x)` в Go, и не проверка, как
`v, ok := x.(T)`. Это записка «не ругайся» — если ты соврал, TS промолчит, а упадёт
рантайм.

```ts
const n = "42" as unknown as number;   // двойной as — обход любой проверки
n.toFixed(2);                          // ❌ TypeError в рантайме: у строки нет toFixed
```

Практическое правило: **сначала пытайся сузить тип проверкой** (`if (typeof x === ...)`,
`if (el)`) — это модуль 04, «сужение типов». `as`/`!` оставляй для случаев, когда
проверить нельзя, а ты действительно знаешь больше компилятора (например, точно
контролируешь HTML-разметку). Каждый `as` в коде — маленький долг доверия.

> **Простыми словами.** `as` — это не «преврати», а «притворись». Значение не меняется,
> меняется только мнение компилятора о нём.

## Как читать ошибки TypeScript (навык, который экономит часы)

Сообщения TS выглядят страшно, но собраны по шаблону. Разберём типовое:

```
Argument of type 'string' is not assignable to parameter of type 'number'.
```

Читается справа налево от слова `assignable`: **«тип, который ты дал» → не подходит →
«туда, куда ты его даёшь»**. `string` (что у тебя есть) не подходит для параметра
`number` (что нужно). Три слова, которые надо узнавать:

- **`assignable to`** — «присваиваемо в». Слева — источник (твоё значение), справа —
  цель (ожидаемый тип). 90% ошибок TS — про это.
- **`Property 'x' does not exist on type 'Y'`** — обращаешься к полю, которого нет в
  типе. Либо опечатка, либо тип надо сузить, либо тип описан неполно.
- **`Object is possibly 'null'` / `'undefined'`** — `strictNullChecks` требует
  обработать пустоту перед использованием.

Для составных типов TS дописывает уточнения после двоеточия — читай их сверху вниз, как
стек: первая строка говорит «что не сошлось в целом», последние — «в каком именно
свойстве». И держи в голове, что ошибка часто указывает не туда, где баг, а туда, где он
стал заметен, — как и в Go с неявными интерфейсами.

## Базовые типы: краткая карта

```ts
let n: number = 42;
let s: string = "hi";
let b: boolean = true;
let big: bigint = 10n;
let sym: symbol = Symbol("id");
let nothing: null = null;
let notset: undefined = undefined;

let arr: number[] = [1, 2, 3];            // массив чисел
let arr2: Array<number> = [1, 2, 3];      // то же самое, generic-форма
let tuple: [string, number] = ["age", 30];// кортеж: фикс. длина и типы по позициям

let pair: { x: number; y: number } = { x: 1, y: 2 };  // объектный тип «по месту»

// функция как тип
let fn: (a: number, b: number) => number = (a, b) => a + b;
```

И главное: **чаще всего типы писать не надо** — TS их выводит сам (type inference):

```ts
let n = 42;            // TS вывел: number
const s = "hi";        // TS вывел: "hi" (литеральный тип, т.к. const — см. модуль 04)
const nums = [1, 2, 3];// TS вывел: number[]
```

Хороший стиль — **аннотировать границы (параметры функций, возвращаемые значения,
публичные API) и доверять выводу внутри**. Не засыпай каждую локальную переменную
аннотацией — это шум, который TS и так знает. В Go ты привык к `:=` с выводом типа —
тут та же философия, только мощнее.

## Установка и запуск: три современных пути

Тебе понадобится **Node.js** (среда выполнения JS вне браузера; ставится с nodejs.org;
бери LTS-версию, 24+). Дальше есть варианты, как гонять `.ts`-файлы.

> **Простыми словами** про разделение обязанностей, которое поначалу удивляет: в Go
> `go run` и проверяет, и запускает. В TS эти задачи разделены между инструментами:
> **`tsc` проверяет типы** (и, если надо, генерирует `.js`), а **запускает Node** — он
> типы только выбрасывает. Поэтому «запустилось» ≠ «типы в порядке», и наоборот.

### Путь 1. Node 24 нативно (самый свежий, минимум зависимостей)

Начиная с Node 24, рантайм умеет запускать TypeScript **напрямую**, просто «срезая»
типы (type stripping) без отдельной сборки:

```bash
node app.ts          # работает из коробки в Node 24+
```

Важная тонкость: Node **только стирает типы, но не проверяет их**. То есть запустить
запустит, но об ошибке типа не предупредит. Поэтому проверку типов запускают отдельно
компилятором (см. ниже `tsc --noEmit`). Разделение «запуск» и «проверка» — нормальная
практика.

### Путь 2. `tsx` (удобно для разработки)

`tsx` — обёртка на базе esbuild, мгновенно запускает и перезапускает `.ts`:

```bash
npm install -D tsx       # ставим в проект как dev-зависимость
npx tsx app.ts           # запустить
npx tsx watch app.ts     # перезапускать при изменениях
```

(Историческое: раньше для этого использовали `ts-node`. Сейчас `tsx` быстрее и
проще; `ts-node` встречается в старых проектах.)

### Путь 3. `tsc` — официальный компилятор (сборка и проверка)

`tsc` (TypeScript Compiler) компилирует `.ts` → `.js` и/или проверяет типы:

```bash
npm install -D typescript
npx tsc                   # собрать по tsconfig.json (получить .js файлы)
npx tsc --noEmit          # ТОЛЬКО проверить типы, ничего не генерируя
```

`npx tsc --noEmit` — твоя «линия обороны»: гоняешь её перед коммитом (или в CI), чтобы
убедиться, что типы сходятся. Запускаешь код через Node 24/`tsx`, а корректность типов
проверяешь через `tsc`.

> Про версии: текущий стабильный — TypeScript 6.x. Параллельно вышел **TS 7.0** — это
> тот самый компилятor, переписанный на **Go** ради скорости. На уровне языка для тебя
> ничего не меняется: тот же синтаксис, те же типы, просто `tsc` работает в разы
> быстрее. Так что учим язык, а инструмент под капотом пусть ускоряется сам.

### `tsconfig.json` и почему `strict: true` — это не обсуждается

`tsconfig.json` — конфиг проекта: какие файлы компилировать, в какую версию JS, по
каким правилам проверять. Минимально разумный старт:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "esModuleInterop": true,
    "skipLibCheck": true
  }
}
```

Самый важный флаг — **`strict: true`**. Он включает набор строгих проверок, и главная
из них — `strictNullChecks`: TS перестаёт молча разрешать `null`/`undefined` везде и
заставляет обрабатывать пустоты явно. Без `strict` TypeScript превращается в
«JavaScript с подсказками» и теряет половину смысла.

`noUncheckedIndexedAccess` — приятный бонус: доступ по индексу (`arr[i]`,
`map[key]`) начинает учитывать, что там может не оказаться значения. Ближе к
дисциплине, к которой ты привык в Go (где забрать из map можно с проверкой `, ok`).

**Правило:** новый проект — всегда со `strict: true`. Спорить с компилятором в строгом
режиме поначалу непривычно, но именно эти споры и есть та польза, ради которой берут TS.

## Типичные ошибки и заблуждения

- **«TS проверяет типы в рантайме».** Нет, стирает их. Внешние данные не проверяются —
  для этого нужен рантайм-валидатор.
- **«Раз есть TS, входной JSON уже типобезопасен».** Нет. `as User` — это обещание
  компилятору, а не проверка. Сервер может прислать что угодно.
- **«TS — номинальный, как Go».** Нет, структурный. `Celsius = number` и
  `Fahrenheit = number` для него одно и то же.
- **«`any` — это нормально».** Это аварийный люк, причём заразный. Для неизвестных
  данных бери `unknown`.
- **«Можно без `strict`».** Технически да, но тогда теряется половина пользы. Новый
  проект — всегда `strict: true`.
- **«Надо аннотировать каждую переменную».** Нет, доверяй выводу типов; аннотируй
  границы (параметры, возвраты, API).
- **«`as` приводит тип, как `int(x)` в Go».** Нет. `as` ничего не делает в рантайме —
  это обещание компилятору. Соврал — упадёт рантайм.
- **«`!` проверяет на null».** Нет, он лишь запрещает компилятору спрашивать. Проверка —
  это `if (x)` или `if (x !== null)`.
- **«Если `node app.ts` запустился, значит типы сошлись».** Нет: Node типы не проверяет.
  Проверка — только `tsc --noEmit`.

## Глоссарий модуля

- **Статическая типизация** — проверка типов до запуска, по тексту программы.
  **Динамическая** — только во время выполнения.
- **Градуальная типизация** — возможность типизировать код частично (в TS это `any`).
- **Вывод типов (type inference)** — компилятор сам определяет тип по значению.
- **Аннотация** — явное указание типа (`x: number`).
- **Утверждение типа (assertion)** — `x as T`, обещание компилятору без проверки.
- **`strict`** — набор строгих проверок в `tsconfig.json`; главная из них
  `strictNullChecks`.
- **`tsc`** — официальный компилятор TypeScript. `--noEmit` = «только проверить».
- **`tsx`** — утилита для мгновенного запуска `.ts` при разработке.
- **`tsconfig.json`** — файл настроек проекта для компилятора.
- **`.d.ts`** — файл объявлений: типы без реализации (подробнее в модуле 09).
- **Рантайм-валидация** — проверка данных во время выполнения (например, `zod`), то
  единственное, что реально защищает от «сервер соврал».
- **TS Playground** — редактор TypeScript в браузере (typescriptlang.org/play), где
  сразу видны и ошибки, и сгенерированный JS.
