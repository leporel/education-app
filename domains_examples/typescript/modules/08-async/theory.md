# Асинхронность

## Суть: один поток, который никогда не ждёт

Вернёмся к модели из модуля 01 и углубим её, потому что это ключ ко всему фронтенду.
JavaScript исполняет твой код в **одном потоке**. Значит, пока выполняется одна
операция, никакая другая не идёт. Казалось бы, катастрофа: запрос к серверу длится
секунды — неужели всё это время страница «висит»?

Нет. Фокус в том, что **сам JS долгих операций не выполняет**. Запрос к сети, таймер,
чтение файла — это делает окружение (браузер или Node, у них для этого есть свои потоки
под капотом). JS лишь говорит: «начни запрос и позови мой колбэк, когда будет готово»,
и немедленно идёт выполнять следующий код. Этот механизм «отдал и забыл, потом позовут»
и есть **event loop**.

Сравни с Go напрямую — это прояснит всё:

| | Go | JavaScript |
|---|---|---|
| Единица конкурентности | горутина (тысячи) | колбэк/промис в очереди |
| Параллелизм твоего кода | да (много потоков ОС) | нет (один поток) |
| Стиль ожидания | блокирующий (`resp := http.Get()`) | неблокирующий (`await fetch()`) |
| Кто ждёт ввод-вывод | рантайм, освобождая поток | окружение (браузер/Node) |

В Go ты пишешь «блокирующий» код, а рантайм незаметно переключает горутины, когда одна
ждёт ввод-вывод. В JS блокироваться нельзя (поток один!), поэтому ожидание сделано
явным: ты помечаешь точки ожидания словом `await`, и в этих точках поток уходит делать
другие дела.

## Event loop в деталях: микро- и макрозадачи

Чуть точнее, чем в модуле 01 — это объясняет порядок выполнения, который иначе кажется
магией. У event loop есть две очереди:

- **Макрозадачи** (macrotasks): `setTimeout`, события ввода-вывода, клики.
- **Микрозадачи** (microtasks): колбэки промисов (`.then`, продолжение после `await`).

Правило исполнения: после каждой синхронной «порции» кода движок **сначала опустошает
всю очередь микрозадач**, и только потом берёт одну макрозадачу. Микрозадачи —
«срочные», у них приоритет.

```ts
console.log("1: синхронно");

setTimeout(() => console.log("4: макрозадача (setTimeout)"), 0);

Promise.resolve().then(() => console.log("3: микрозадача (promise)"));

console.log("2: синхронно");

// Порядок вывода: 1, 2, 3, 4
```

Разбор: сначала весь синхронный код (`1`, `2`). Затем микрозадачи — промис (`3`).
И только потом макрозадача — `setTimeout` (`4`), хотя задержка у него `0`. Знание этого
порядка не нужно каждый день, но спасает, когда отладка показывает «невозможный»
порядок логов.

> **Простыми словами.** Представь одного кассира (поток). Пока он обслуживает клиента, к
> нему никто не подходит. Микрозадачи — это «дела на две секунды», которые он добивает
> сразу после текущего клиента; макрозадачи — следующий клиент из очереди. Отсюда правило:
> **`setTimeout(fn, 0)` значит «не сейчас», а не «немедленно»**, а долгий синхронный цикл
> — это кассир, ушедший на обед с клиентом у стойки.

## Promise: обещание будущего значения

**Promise** — объект, представляющий значение, которого ещё нет, но оно появится
(или появится ошибка). У промиса три состояния:

- **pending** — в процессе (ещё неизвестно);
- **fulfilled** — успешно завершён, есть значение;
- **rejected** — завершён с ошибкой.

Из pending промис переходит в одно из финальных состояний **ровно один раз** и больше
не меняется. Это как Go-канал, по которому придёт строго один результат — или значение,
или ошибка.

Создают промис редко вручную (обычно их возвращают библиотеки), но один раз увидеть
полезно:

```ts
const delay = (ms: number): Promise<void> =>
  new Promise((resolve) => setTimeout(resolve, ms));

const fetchUser = (id: number): Promise<{ id: number; name: string }> =>
  new Promise((resolve, reject) => {
    if (id <= 0) reject(new Error("bad id"));
    else resolve({ id, name: "Ann" });
  });
```

`resolve` переводит промис в fulfilled, `reject` — в rejected. Тип `Promise<T>` говорит
«в случае успеха будет значение типа `T`».

### Старый способ: `.then` / `.catch`

```ts
fetchUser(1)
  .then((user) => console.log("Имя:", user.name))   // на успех
  .catch((err) => console.error("Ошибка:", err))    // на ошибку
  .finally(() => console.log("в любом случае"));     // всегда
```

Это работает, но цепочки `.then` плохо читаются, когда шагов много (так называемый
«callback hell» в новой обёртке). Поэтому появился синтаксис получше.

## async / await: асинхронный код, который читается как синхронный

`async/await` — синтаксический сахар над промисами, делающий асинхронный код **похожим
на обычный последовательный**. Это то, что ты будешь писать в 99% случаев.

```ts
async function showUser(id: number): Promise<void> {
  const user = await fetchUser(id);     // ждём промис, получаем значение
  console.log("Имя:", user.name);
}
```

Два правила:

- **`async`** перед функцией означает: она всегда возвращает `Promise`. Даже
  `async function f(): Promise<number> { return 5; }` вернёт `Promise<number>`, а не
  число.
- **`await`** можно писать только внутри `async`-функции. Он «разворачивает» промис:
  приостанавливает функцию до завершения промиса и возвращает значение (или бросает
  ошибку, если промис отклонён).

Ключевая интуиция: `await` **не блокирует поток**. В точке `await` функция как бы
ставится на паузу, поток уходит обслуживать другие задачи (event loop работает), а
когда промис готов — функция продолжается с того же места. Это «кооперативная» пауза,
не блокировка. В Go `resp := http.Get()` блокирует горутину (но рантайм освобождает
поток); в JS `await fetch()` ставит на паузу одну функцию, не трогая единственный поток.
Результат для читателя кода — похожий: пишешь «сверху вниз», без лапши колбэков.

### Обработка ошибок: обычный try/catch

Главная прелесть `await`: ошибки ловятся **привычным** `try/catch`, а не отдельным
`.catch`:

```ts
async function showUser(id: number): Promise<void> {
  try {
    const user = await fetchUser(id);
    console.log("Имя:", user.name);
  } catch (err) {
    console.error("Не удалось загрузить:", err);
  }
}
```

Тонкость TS: в `catch (err)` переменная `err` имеет тип **`unknown`** (со `strict`),
а не `Error`. Почему? Потому что в JS бросить (`throw`) можно что угодно — хоть строку,
хоть число, не обязательно `Error`. TS честно это отражает и заставляет проверить:

```ts
catch (err) {
  if (err instanceof Error) {
    console.error(err.message);     // здесь err сужен до Error
  } else {
    console.error("Неизвестная ошибка:", err);
  }
}
```

Это та же дисциплина обработки ошибок, к которой тебя приучил Go (`if err != nil`),
только через исключения. В Go ошибки — значения; в JS — исключения; но проверять надо
и там, и там.

## Комбинаторы: работа с несколькими промисами

Поскольку «много ожиданий одновременно» — обычное дело, есть готовые комбинаторы.

### `Promise.all` — ждать все (и упасть, если хоть один упал)

```ts
const [user, posts, comments] = await Promise.all([
  fetchUser(1),
  fetchPosts(1),
  fetchComments(1),
]);
```

Все три запроса **стартуют одновременно** и идут «параллельно» (точнее — конкурентно:
ждёт-то их окружение). `Promise.all` ждёт, пока завершатся все, и возвращает массив
результатов в том же порядке. Если **любой** промис отклонится — `all` немедленно
отклоняется с этой ошибкой (остальные результаты теряются). Это самый частый способ
ускорить код: вместо «жди A, потом жди B» — «запусти оба, дождись обоих».

### `Promise.allSettled` — ждать все, не падая

Когда нужно дождаться всех и узнать судьбу каждого (успех или ошибка), не обрывая на
первой ошибке:

```ts
const results = await Promise.allSettled([fetchUser(1), fetchUser(-1)]);
// каждый элемент: { status: "fulfilled", value } | { status: "rejected", reason }
```

Заметь — результат это **дискриминированный union** из модуля 04! Проверяешь
`r.status === "fulfilled"` и получаешь доступ к `value`. Всё связано.

### `Promise.race` и `Promise.any`

- **`race`** — завершается, как только завершится **первый** (успехом ИЛИ ошибкой).
  Классика — таймаут: «дай результат или ошибку через 5 секунд».
- **`any`** — завершается на первом **успешном**, игнорируя ошибки (падает, только если
  все упали).

## Промис уже бежит: eager, а не lazy

Тонкость, которая отличает промисы от горутин и от «ленивых» абстракций других языков:
**промис начинает работать в момент создания, а не в момент `await`**.

```ts
const p = fetchUser(1);      // запрос УЖЕ отправлен
await delay(1000);           // ждём секунду, занимаясь другим
const user = await p;        // просто забираем готовый результат
```

Отсюда следуют неочевидные вещи:

- `Promise.all([f(), g()])` работает конкурентно именно потому, что `f()` и `g()` уже
  запустились до попадания в массив. Не путай с `Promise.all([f, g])` — так передавать
  функции нельзя.
- «Создать промис, но пока не запускать» невозможно. Если нужна отложенность, передавай
  **функцию**, возвращающую промис (`() => fetchUser(1)`), — именно так устроены очереди и
  пулы задач.
- Ошибка в промисе, который никто не `await`-ит, всплывёт как unhandled rejection, даже
  если ты собирался его «потом не использовать».

> **Простыми словами.** Промис — это не «рецепт работы», а «квитанция об уже начатой
> работе». В Go ты решаешь, когда стартовать (`go f()`); в JS работа стартует сама, а ты
> решаешь только, когда забрать результат.

## `fetch`: сетевой запрос за две минуты

`fetch` — стандартный способ сходить по HTTP (он есть и в браузере, и в Node 18+). Он
появлялся в примерах выше, поэтому разберём минимум:

```ts
type User = { id: number; name: string };

async function loadUser(id: number): Promise<User> {
  const res = await fetch(`https://api.example.com/users/${id}`);

  if (!res.ok) {                       // ⚠️ ВАЖНО: 404 и 500 — это НЕ ошибка для fetch
    throw new Error(`HTTP ${res.status}`);
  }

  const data: unknown = await res.json();   // тело читается вторым await
  // здесь по-хорошему нужна валидация (модуль 02): res.json() ничего не проверяет
  return data as User;
}
```

Три вещи, на которых спотыкаются все:

1. **`fetch` отклоняется только при сетевой ошибке.** HTTP-статус 404 или 500 — это
   успешный ответ с точки зрения промиса. Проверяй `res.ok` сам.
2. **Тело читается отдельно и тоже асинхронно** — `await res.json()`. И прочитать его
   можно только один раз.
3. **`res.json()` возвращает `any`** (по типам — «что угодно»). Принимай как `unknown` и
   валидируй: это ровно та граница программы, о которой шла речь в модуле 02.

## Отмена: `AbortController`

В Go отменяют через `context.Context`: передал `ctx`, вызвал `cancel()`, операция
свернулась. В JS у промиса **нет** встроенной отмены — промис нельзя «отозвать». Вместо
этого есть отдельный механизм — `AbortController`:

```ts
const controller = new AbortController();

const promise = fetch("/api/big-report", { signal: controller.signal });

// где-то ещё: пользователь ушёл со страницы / нажал «отмена»
controller.abort();

try {
  await promise;
} catch (err) {
  if (err instanceof Error && err.name === "AbortError") {
    console.log("запрос отменён — это нормально, не ошибка приложения");
  } else {
    throw err;
  }
}
```

Соответствие с Go почти дословное: `AbortController` ≈ `context.WithCancel`,
`controller.signal` ≈ сам `ctx`, `abort()` ≈ `cancel()`. `signal` понимают `fetch` и многие
API Node; свои асинхронные функции тоже можно научить его слушать
(`signal.addEventListener("abort", ...)` или проверкой `signal.aborted`).

Зачем это знать до фронтенда: самый частый сценарий — компонент запросил данные и был
закрыт до ответа. Без отмены ты получишь «ответ в пустоту» и лишнюю работу, а иногда и
race condition, когда старый ответ перезаписывает новый. Есть и готовая обёртка на
таймаут: `AbortSignal.timeout(5000)`.

## Грабли асинхронности

### Floating promise — забытый await

Самая частая и коварная ошибка: вызвать async-функцию и **забыть `await`**:

```ts
async function save(): Promise<void> { /* ... */ }

function handler() {
  save();           // ❌ floating promise: запустили и не дождались/не обработали ошибку
}
```

Промис «висит»: функция продолжится, не дождавшись сохранения, а если внутри случится
ошибка — она потеряется (unhandled rejection). Это JS-аналог «проигнорировал
возвращённую ошибку» в Go. Линтер с правилом `no-floating-promises` ловит это —
**обязательно включи его** (см. модуль 09).

### Последовательно там, где можно параллельно

```ts
// МЕДЛЕННО: запросы идут по очереди (await блокирует следующий старт)
const a = await fetchUser(1);
const b = await fetchUser(2);   // стартует только после завершения a

// БЫСТРО: оба стартуют сразу
const [a2, b2] = await Promise.all([fetchUser(1), fetchUser(2)]);
```

Если запросы независимы — запускай их вместе через `Promise.all`. Цепочка `await` за
`await` для независимых операций — распространённая потеря производительности.

### await в цикле

```ts
// Часто медленно: каждый шаг ждёт предыдущий
for (const id of ids) {
  await processOne(id);
}

// Если порядок неважен и можно параллельно:
await Promise.all(ids.map((id) => processOne(id)));
```

Иногда последовательность нужна (шаги зависят друг от друга) — тогда `await` в цикле
оправдан. Но если нет — `Promise.all` по массиву кратно быстрее.

## Типичные ошибки и заблуждения

- **«async делает код многопоточным, как горутины».** Нет. Один поток + event loop.
  Конкурентность ожиданий есть, параллелизма твоего кода — нет.
- **«await блокирует поток».** Нет, ставит на паузу одну функцию; поток уходит работать.
- **«setTimeout(fn, 0) выполнится сразу».** Нет, это макрозадача — после синхронного
  кода и всех микрозадач (промисов).
- **«err в catch — это Error».** Со `strict` это `unknown`: бросить можно что угодно.
  Сужай через `instanceof Error`.
- **«Можно не писать await».** Floating promise теряет ошибки и ломает порядок. Всегда
  обрабатывай промис (`await`, `.catch`, или явно `void`).
- **«await в цикле — нормально всегда».** Для независимых операций это медленно; бери
  `Promise.all`.
- **«Промис запускается на `await`».** Нет, он уже бежит с момента создания. Отложенность
  даёт только функция, возвращающая промис.
- **«`fetch` бросит ошибку на 404».** Нет: 404 и 500 для него нормальный ответ. Проверяй
  `res.ok` руками.
- **«`await res.json()` возвращает типизированные данные».** Нет, по сути это `any`.
  Принимай как `unknown` и валидируй.
- **«Промис можно отменить».** Сам промис — нет. Отмена делается через `AbortController`
  (JS-аналог `context.WithCancel`).

## Глоссарий модуля

- **Синхронный / асинхронный код** — выполняется сразу подряд / с ожиданием, которое
  прерывает функцию, но не поток.
- **Блокировка** — поток стоит и ничего не делает (в JS почти всегда ошибка).
- **Event loop** — механизм разбора очередей задач.
- **Макрозадача (task)** — `setTimeout`, события, ввод-вывод.
- **Микрозадача (microtask)** — колбэк промиса, продолжение после `await`; выполняется
  раньше макрозадач.
- **Promise** — объект-«квитанция» на будущее значение; состояния pending / fulfilled /
  rejected.
- **`async` / `await`** — сахар над промисами: функция возвращает промис, `await` ждёт его
  без блокировки потока.
- **Комбинатор** — `Promise.all` / `allSettled` / `race` / `any`.
- **Floating promise** — промис, результат и ошибки которого никто не обрабатывает.
- **Unhandled rejection** — необработанная ошибка промиса.
- **Eager (жадный)** — промис стартует при создании, а не при `await`.
- **`AbortController` / `signal`** — механизм отмены; аналог `context.Context` в Go.
- **Web Worker** — отдельный поток для тяжёлых вычислений (единственный способ получить
  в браузере настоящий параллелизм).
