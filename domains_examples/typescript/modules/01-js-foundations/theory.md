# JavaScript под капотом TypeScript

## Суть: TS — это грим, а актёр — JavaScript

Главное, что нужно усвоить с самого начала: **TypeScript не существует во время
выполнения программы**. Совсем. Браузер про него не знает, Node.js (в классическом
режиме) — тоже. Перед запуском весь твой `.ts`-код проходит через компилятор, который
делает ровно две вещи:

1. **Проверяет типы** — ругается, если ты передал строку туда, где ждали число.
2. **Стирает типы** — выкидывает все аннотации и превращает код в обычный JavaScript.

```ts
// то, что ты пишешь (TypeScript)
function greet(name: string): string {
  return `Привет, ${name}`;
}
```

```js
// то, что реально выполняется (JavaScript) — типы испарились
function greet(name) {
  return `Привет, ${name}`;
}
```

Сравни с Go. В Go тип `int` — это реальная сущность в рантайме: у тебя есть
`reflect.TypeOf`, есть type switch, рантайм знает фактический тип значения. **В TS
этого нет.** Аннотация `: string` — записка компилятору, которую он прочитает и
выбросит. Из этого следует огромное практическое правило, к которому мы вернёмся не
раз: *нельзя в рантайме спросить «а какой у этой переменной TS-тип?»* — спрашивать
уже не у кого.

Поэтому модуль и называется «JavaScript под капотом». Чтобы понимать TypeScript,
нужно понимать тот язык, который реально работает.

## Немного контекста: откуда вообще взялся этот зверь

JavaScript придумали в 1995 году за **десять дней** — чтобы «оживлять» странички в
браузере Netscape. Его не проектировали для приложений на сотни тысяч строк. Отсюда
все странности: язык рос как город без генплана, и обратную совместимость никто не
ломал (сломать JS в браузере = сломать половину интернета). Поэтому в нём до сих пор
живут решения 90-х рядом с современными фичами 2020-х.

TypeScript (Microsoft, 2012) — попытка надеть на этот разросшийся город систему
адресов и правил дорожного движения, **не снося ни одного дома**. Это объясняет и
силу TS (он описывает реальный JS, включая дикие углы), и его сложность (приходится
типизировать язык, который сам про типы думать не хотел).

> Кстати, ирония для Go-разработчика: компилятор TypeScript исторически был написан на
> самом TypeScript. А в 2025–2026 Microsoft **переписали его на Go** (проект «tsgo»,
> вышел как TypeScript 7.0) — ради ~10-кратного ускорения. Так что язык, который ты
> уже знаешь, теперь компилирует язык, который ты учишь. Мир тесен.

## Значения и типы: их всего восемь

В JavaScript любое значение принадлежит одному из восьми типов. Семь из них —
**примитивы**, восьмой — объекты.

Примитивы:

- `number` — **все** числа, и целые, и дробные. Никаких `int`/`int64`/`float32`.
  Внутри это всегда 64-битный `float` (IEEE 754). Да, целые числа в JS — это floats.
- `string` — строки (всегда Unicode, в UTF-16 внутри).
- `boolean` — `true` / `false`.
- `undefined` — «значения нет, потому что его не задавали».
- `null` — «значения нет, и это сделано намеренно».
- `bigint` — целые произвольной длины (`123n`), для случаев, когда `number` не хватает.
- `symbol` — уникальные идентификаторы (нужны редко, на старте можно отложить).

И объекты:

- `object` — всё остальное: объекты `{}`, массивы `[]`, функции, даты, регулярки…
  В JS **функция — это тоже объект** (об этом ниже).

### `number`: один тип на всё — благословение и проклятие

В Go ты выбираешь тип под задачу: `int32`, `uint64`, `float64`. В JS выбора нет —
есть только `number`, и это 64-битный float. Последствия:

```js
0.1 + 0.2;            // 0.30000000000000004  (привет, IEEE 754)
0.1 + 0.2 === 0.3;    // false
```

Это не баг JS — точно так же ведёт себя `float64` в Go. Просто в Go у тебя был выбор
взять целочисленный тип и не наступать на грабли, а в JS для целых чисел всё равно
используется float. Безопасные целые — до 2^53. Дальше нужен `bigint`.

> Практический вывод: **не храни деньги в `number`** как доли (рубли с копейками
> дробью). Храни в копейках как целое, либо бери библиотеку для десятичных дробей.
> Та же дисциплина, что и в Go с `float64`, только без альтернативы в виде `int`.

### Две пустоты: `null` и `undefined`

В Go пустота одна — zero value. Нет значения у `string`? Это `""`. У указателя?
`nil`. Одна концепция «ничего».

В JS пустот **две**, и это постоянный источник путаницы:

- `undefined` — «здесь ничего не клали». Так выглядит необъявленное свойство объекта,
  параметр функции, который не передали, переменная, которой не присвоили значение.
  Это «пустота по умолчанию» от самого языка.
- `null` — «здесь намеренно пусто». Это твоё осознанное «значения нет». Язык сам
  почти никогда не возвращает `null` — его кладёшь ты.

```js
let x;             // undefined — объявили, но не присвоили
const obj = {};
obj.missing;       // undefined — такого свойства нет
const y = null;    // null — я сам сказал «пусто»
```

Грубая аналогия: `undefined` — это «коробку даже не приносили», `null` — «коробку
принесли, но она пустая». В хорошем TS-коде со `strict`-режимом компилятор заставит
тебя обрабатывать обе пустоты, и это спасёт от львиной доли «cannot read property of
undefined» — JS-эквивалента nil-паники.

## Объявление переменных: `const`, `let` и музейный экспонат `var`

```js
const pi = 3.14;   // нельзя переприсвоить (но см. ниже)
let count = 0;     // можно менять
var old = 1;       // так писали до 2015 года; не используй
```

Правило простое: **по умолчанию `const`, и только если реально нужно переприсваивать —
`let`. `var` не используем никогда** (он живёт с дурными правилами видимости из 90-х,
TS его терпит ради совместимости, но это ловушка).

Важный нюанс про `const`. Он запрещает **переприсвоить саму переменную**, но не
«замораживает» содержимое объекта:

```js
const user = { name: "Ann" };
user.name = "Bob";   // ОК! Меняем поле, а не саму переменную
user = {};           // Ошибка: нельзя переприсвоить const
```

Для Go-разработчика: `const` в JS — это не Go-шный `const` (тот только для констант
времени компиляции). Ближе к «указатель, который нельзя перенаправить, но объект по
указателю менять можно».

### Hoisting и «мёртвая зона» (что это за слово такое)

Слово **hoisting** («подъём») встречается в любом тексте про JS, поэтому разберёмся
сразу. Движок перед выполнением кода «сканирует» область видимости и заранее регистрирует
все объявления. Из-за этого объявление функции работает даже выше по коду:

```js
sayHi();                        // работает! объявление функции «поднято»
function sayHi() { console.log("hi"); }
```

С `let`/`const` иначе: имя тоже регистрируется заранее, но обращаться к нему до строки
объявления **нельзя** — этот промежуток называют **TDZ** (temporal dead zone, «временная
мёртвая зона»):

```js
console.log(x);   // ❌ ReferenceError: Cannot access 'x' before initialization
let x = 1;
```

А `var` в такой ситуации молча даёт `undefined` — ещё одна причина им не пользоваться.

> **Простыми словами.** Hoisting — «объявления функций видны во всём файле сразу,
> переменные — только начиная со своей строки». В Go компилятор просто не пустил бы
> обращение к переменной до объявления; в JS часть таких ошибок стала рантайм-ошибками.

## Объекты и массивы: две рабочие лошадки

Прежде чем говорить о поведении, нужно уметь описывать данные. В Go для этого есть
структуры, map, слайсы и массивы. В JS весь этот зоопарк сведён к двум конструкциям:
**объект** (`{}`) и **массив** (`[]`). Всё остальное — производное от них.

### Объект: и структура, и словарь в одном лице

```js
const user = {
  name: "Ann",           // ключ: значение
  age: 30,
  "full name": "Ann A.", // ключ с пробелом — можно, но в кавычках
  address: {             // вложенный объект
    city: "Praha",
  },
  greet() {              // метод — просто функция в поле (сокращённая запись)
    return `Привет, ${this.name}`;
  },
};

user.name;               // "Ann"    — доступ через точку
user["full name"];       // "Ann A." — через скобки (когда ключ не идентификатор)
user.address.city;       // "Praha"
user.email;              // undefined — свойства нет, но это НЕ ошибка!
user.email = "a@b.c";    // добавили свойство на ходу
delete user.age;         // удалили свойство
```

Три отличия от Go-структуры, о которые спотыкаются все:

1. **Форма объекта не фиксирована.** Свойства можно добавлять и удалять в любой момент.
   Тип — это то, что *обещает* TypeScript, а не то, что физически запрещает рантайм.
2. **Обращение к несуществующему свойству даёт `undefined`, а не ошибку.** Опечатался в
   `user.nmae` — получил `undefined` и поехал дальше. Это ровно та боль, ради которой
   существует TS.
3. **Ключи — строки** (или `symbol`). `obj[1]` под капотом станет `obj["1"]`. Настоящий
   словарь с произвольными ключами — это `Map` (см. ниже), а не объект.

### Массив: динамический список чего угодно

```js
const nums = [1, 2, 3];
nums[0];            // 1
nums.length;        // 3
nums.push(4);       // добавить в конец → длина 4
nums[10] = 99;      // ⚠️ массив «растянулся» до 11 элементов, дырки = undefined
const mixed = [1, "two", { three: 3 }];   // разные типы — JS не против (TS будет)
```

Массив в JS ближе к Go-шному слайсу, чем к массиву: длина меняется, `push` работает как
`append`. Но в отличие от Go, доступ за границу **не паникует**, а тихо возвращает
`undefined`. Именно поэтому в TS есть флаг `noUncheckedIndexedAccess` (модуль 02),
который заставляет это учитывать.

### Ссылочная семантика: главная ловушка для Go-разработчика

В Go структура — значение: присвоил — скопировал. В JS **объекты и массивы всегда живут
по ссылке**, и присваивание копирует только ссылку:

```js
const a = { n: 1 };
const b = a;            // b и a — ОДИН И ТОТ ЖЕ объект
b.n = 42;
a.n;                    // 42 (!) — изменили «через b», видно «через a»

a === b;                // true  — сравнение объектов сравнивает ссылки, не содержимое
({ n: 1 }) === ({ n: 1 });  // false — два разных объекта с одинаковым содержимым
```

Отсюда два ежедневных правила:

- **Хочешь копию — делай её явно** (`{ ...a }` для поверхностной, `structuredClone(a)`
  для глубокой; про `...` — следующий раздел).
- **Сравнивать объекты через `===` бессмысленно** — это проверка «тот же самый объект?».
  Для сравнения по содержимому пишут свою функцию или берут библиотеку.

Примитивы (`number`, `string`, …), наоборот, копируются по значению — как в Go.

> **Простыми словами.** Объект — это не коробка со значением, а *адрес* коробки. Передал
> объект в функцию — передал адрес: функция может изменить твои данные. В Go ты бы увидел
> это по `*User` в сигнатуре; в JS звёздочки нет, но она подразумевается всегда.

### Итерация: `for...of`, `for...in` и `Object.entries`

```js
const arr = ["a", "b"];
for (const item of arr) console.log(item);   // a, b      — по ЗНАЧЕНИЯМ
for (const i in arr) console.log(i);         // "0", "1"  — по КЛЮЧАМ (строкам!)

const obj = { x: 1, y: 2 };
Object.keys(obj);      // ["x", "y"]
Object.values(obj);    // [1, 2]
Object.entries(obj);   // [["x", 1], ["y", 2]] — пары ключ/значение

for (const [key, value] of Object.entries(obj)) {
  console.log(key, value);      // x 1 / y 2
}
```

Мнемоника: **`for...of` — по значениям (массивы, `Map`, `Set`), `for...in` — по ключам
(и для массивов его лучше не использовать вообще)**. В Go один `for range` делал и то, и
другое; здесь конструкции разные, и путать их — классическая ошибка новичка.

### Методы массивов: тулкит, который ты будешь использовать всегда

В Go ты пишешь циклы руками. В JS/TS **циклы почти не пишут** — есть набор методов,
принимающих функцию (вот зачем нужны были замыкания и стрелки):

```js
const nums = [1, 2, 3, 4, 5];

nums.map((n) => n * 2);               // [2,4,6,8,10] — преобразовать каждый
nums.filter((n) => n % 2 === 0);      // [2,4]        — оставить подходящие
nums.find((n) => n > 3);              // 4            — первый подходящий (или undefined)
nums.findIndex((n) => n > 3);         // 3            — его индекс (или -1)
nums.some((n) => n > 4);              // true         — есть хоть один?
nums.every((n) => n > 0);             // true         — все подходят?
nums.includes(3);                     // true         — есть такое значение?
nums.reduce((acc, n) => acc + n, 0);  // 15           — свернуть в одно значение
nums.slice(1, 3);                     // [2,3]        — копия части (не мутирует)
[...nums].sort((a, b) => a - b);       // сортировка по возрастанию
nums.join(", ");                      // "1, 2, 3, 4, 5"
```

Две вещи запомнить накрепко:

- **`map`/`filter`/`slice` возвращают новый массив** и не портят исходный. А `sort`,
  `reverse`, `push`, `splice` **мутируют** тот массив, на котором вызваны — поэтому перед
  `sort` часто делают копию `[...arr]`.
- **`sort` без аргумента сортирует как строки!** `[10, 9, 1].sort()` даёт `[1, 10, 9]`.
  Для чисел всегда передавай компаратор: `.sort((a, b) => a - b)`.

`reduce` — это свёртка: аккумулятор плюс элемент на каждом шаге. Читается сложнее цикла,
поэтому не стесняйся обычного `for...of`, если так понятнее: идиоматичность не стоит
потерянной ясности.

### `Map` и `Set`: когда объекта недостаточно

Объект как словарь работает, но ключи в нём только строки, а перебор и подсчёт размера
неудобны. Для настоящего словаря и множества есть отдельные типы:

```js
const scores = new Map();           // словарь с ЛЮБЫМИ ключами (включая объекты)
scores.set("ann", 10);
scores.get("ann");                  // 10
scores.has("bob");                  // false
scores.size;                        // 1
for (const [k, v] of scores) console.log(k, v);

const seen = new Set([1, 2, 2, 3]); // множество уникальных значений
seen.has(2);                        // true
seen.size;                          // 3
```

Ориентир: **фиксированный набор известных полей → объект; произвольные меняющиеся ключи →
`Map`; уникальные значения → `Set`.** Это ближайшая родня Go-шных `map[K]V` и
`map[K]struct{}`.

## Деструктуризация, spread и rest: три точки, которые встречаются везде

Дальше — синтаксис, без которого невозможно читать современный код (и код Vue-компонентов
в следующем домене). Он выглядит загадочно ровно до того момента, как поймёшь идею.

### Деструктуризация: «разобрать» объект или массив на переменные

```js
const user = { name: "Ann", age: 30, city: "Praha" };

const { name, age } = user;              // достали два поля в переменные
console.log(name, age);                  // Ann 30

const { city: town } = user;             // переименование: city → town
const { email = "нет" } = user;          // значение по умолчанию, если поля нет

const nums = [10, 20, 30];
const [first, second] = nums;            // по позициям: first=10, second=20
const [, , third] = nums;                // пропустить первые два: third=30
```

Особенно часто это применяют к **параметрам функции** — так делают «именованные
аргументы», которых в JS нет как отдельной фичи:

```js
function createUser({ name, age = 18, isAdmin = false }) {
  return `${name}, ${age}, admin: ${isAdmin}`;
}

createUser({ name: "Ann", isAdmin: true });   // порядок аргументов не важен!
```

Для Go-разработчика это тот же приём, что «структура с опциями» вместо длинного списка
параметров, только встроенный в язык.

### Spread `...`: «рассыпать» содержимое

```js
const a = [1, 2];
const b = [0, ...a, 3];               // [0, 1, 2, 3] — вставили элементы a
const copy = [...a];                  // поверхностная копия массива

const base = { host: "localhost", port: 80 };
const cfg = { ...base, port: 8080 };  // копия + переопределение: { host, port: 8080 }
```

Правило для объектов: **при совпадении ключей побеждает тот, что правее.** Это
идиоматичный способ «обновить поле, не мутируя объект» — то, чем постоянно пользуются
Vue/React и любая логика состояния.

### Rest `...`: «собрать остаток»

Те же три точки, но в позиции *получателя* работают наоборот — собирают остаток:

```js
const { password, ...safeUser } = fullUser;   // вынули password, остальное — в safeUser
const [head, ...tail] = [1, 2, 3];            // head=1, tail=[2,3]

function sum(...nums) {                        // все аргументы в массив
  return nums.reduce((a, n) => a + n, 0);
}
sum(1, 2, 3);                                  // 6
```

> **Простыми словами.** Одни и те же `...` делают две противоположные вещи в зависимости
> от того, где стоят: **внутри литерала/вызова — рассыпают**, **в позиции объявления или
> параметра — собирают**. Rest-параметр — это Go-шный `nums ...int`, spread при вызове —
> Go-шный `f(nums...)`.

### Осторожно: копия поверхностная

```js
const orig = { user: { name: "Ann" } };
const shallow = { ...orig };
shallow.user.name = "Bob";
orig.user.name;            // "Bob" — вложенный объект остался общим!
```

`...` копирует только верхний уровень. Для настоящей глубокой копии есть встроенный
`structuredClone(orig)`. Ссылочная семантика никуда не делась.

## Опциональная цепочка `?.`: аккуратная работа с пустотой

Классическая рантайм-ошибка JS звучит так: `TypeError: Cannot read properties of
undefined (reading 'city')`. Это JS-версия nil-паники: в цепочке `user.address.city`
промежуточное звено оказалось `undefined`.

**Опциональная цепочка** `?.` прерывает обращение, если слева `null`/`undefined`, и
возвращает `undefined` вместо падения:

```js
const user = { name: "Ann" };            // address нет

user.address.city;        // ❌ TypeError — падение
user.address?.city;       // ✅ undefined — вычисление аккуратно прервалось

user.getName?.();         // вызов метода, только если он существует
list?.[0];                // индексация, только если list не пустота

const city = user.address?.city ?? "неизвестно";   // + значение по умолчанию (см. ниже)
```

Связка `?.` и `??` — самый частый способ безопасно достать вложенное значение. Но не
превращай `?.` в оберег: если по логике `address` обязан быть, лучше упасть громко, чем
тихо получить `undefined` и искать причину через три экрана. Ставь `?.` там, где
отсутствие значения — **нормальный** сценарий.

## Функции — это значения (и это меняет всё)

В JS функция — полноправное значение: её можно положить в переменную, передать
аргументом, вернуть из другой функции, хранить в массиве. В Go так тоже можно
(функции — значения), так что эта идея тебе знакома. Но в JS она пронизывает язык
насквозь — на ней держатся замыкания, колбэки, весь асинхронный код.

Три способа записать функцию:

```js
// 1. Function declaration — «поднимается» наверх (hoisting), можно вызвать выше по коду
function add(a, b) { return a + b; }

// 2. Function expression — функция как значение в переменной
const sub = function (a, b) { return a - b; };

// 3. Arrow function — короткая запись, и (важно!) со своим поведением `this`
const mul = (a, b) => a * b;
```

Стрелочные функции (`=>`) — самая частая запись в современном коде. Если тело — одно
выражение, его значение возвращается автоматически (без `return`):

```js
const square = (x) => x * x;        // вернёт x * x
const greet  = (name) => `Hi ${name}`;
```

### Замыкания: функция, которая помнит, где родилась

Вот первая по-настоящему важная идея, которой в Go нет в таком виде (хотя Go-замыкания
существуют — здесь они центральнее). **Замыкание** — это функция вместе с «рюкзачком»
переменных из той области, где она была создана. Функция уносит этот рюкзачок с собой,
даже когда внешняя функция уже завершилась.

```js
function makeCounter() {
  let count = 0;            // живёт в "рюкзачке"
  return () => {
    count += 1;             // внутренняя функция видит и меняет count
    return count;
  };
}

const next = makeCounter();
next(); // 1
next(); // 2
next(); // 3  — count сохраняется между вызовами
```

`makeCounter` давно отработала и «ушла», но переменная `count` жива, потому что на неё
ссылается возвращённая функция. Это и есть замыкание: приватное состояние без всяких
классов и полей. В Go ты бы написал то же самое через функцию, возвращающую функцию, —
механика идентична, просто в JS этим приёмом пользуются на каждом шагу (особенно в
колбэках и в коде на React/Vue).

> Замыкания — фундамент. Если что-то одно из этого модуля унести в долгую память —
> пусть это будут замыкания. Половина «магии» фронтенда — это они.

## `this`: переменная, которая зависит от того, *как* её позвали

А вот теперь — главная странность JS, у которой в Go нет аналога вообще. В Go метод
получает приёмник (`func (u *User) Name()`), и `u` — это всегда именно тот объект,
у которого метод вызвали. Однозначно и предсказуемо.

В JS есть `this`, и его значение определяется **не тем, где функция написана, а тем,
как её вызвали**. Один и тот же код может видеть разный `this`.

```js
const user = {
  name: "Ann",
  greet() {
    return `Я ${this.name}`;
  },
};

user.greet();              // "Я Ann"   — вызвали как метод объекта → this = user

const fn = user.greet;     // оторвали метод от объекта
fn();                      // this.name → ошибка/undefined: this уже не user!
```

Функцию «оторвали» от объекта, и `this` потерялся. Для новичка это источник боли
номер один. Поэтому есть спасательный круг — **стрелочные функции не имеют своего
`this`**: они берут его из окружающего кода, где были написаны (лексически,
предсказуемо). Поэтому в колбэках почти всегда пишут стрелки:

```js
const obj = {
  items: [1, 2, 3],
  total: 0,
  sum() {
    this.items.forEach((n) => {
      this.total += n;   // стрелка взяла this из метода sum → всё работает
    });
    return this.total;
  },
};
```

Если бы внутри `forEach` была обычная `function`, её `this` оказался бы не `obj`, и
`this.total` сломался бы. Запомни эвристику на старте: **в колбэках — стрелки**, и
90% проблем с `this` тебя не коснутся. Глубже разберём `this` в модуле про классы.

## Прототипы: наследование без классов

В Go нет наследования вообще — есть встраивание структур и интерфейсы. В JS
исторически нет классов «как в Java» — есть **прототипы**. (Ключевое слово `class`
появилось в 2015-м, но это синтаксический сахар поверх прототипов, не отдельный
механизм.)

Идея такая: у почти каждого объекта есть скрытая ссылка на другой объект — его
**прототип**. Когда ты обращаешься к свойству, которого у объекта нет, движок идёт по
этой ссылке к прототипу и ищет там. Не нашёл — идёт к прототипу прототипа. Так
выстраивается **цепочка прототипов**, заканчивающаяся на `null`.

```js
const animal = {
  breathe() { return "вдох-выдох"; },
};

const dog = Object.create(animal);   // прототип dog = animal
dog.bark = () => "гав";

dog.bark();      // "гав"          — нашли у самого dog
dog.breathe();   // "вдох-выдох"   — у dog нет, нашли в прототипе animal
```

`dog` не «копировал» метод `breathe` — он его **делегирует** прототипу по живой
ссылке. Это не наследование-копирование (как мыслят в классических ООП-языках), а
наследование-делегирование.

На практике ты редко будешь возиться с прототипами руками — для этого есть `class`
(модуль 07). Но знать, что под классами лежат прототипы, важно: это объясняет,
почему массивы, строки и объекты «откуда-то» имеют методы (`[].map`, `"abc".length`)
— они приходят из прототипа.

## Равенство: `===` хороший, `==` злой

В JS два оператора сравнения, и это, пожалуй, самый известный мем языка.

- `===` (строгое равенство) — сравнивает **без приведения типов**. Разные типы → сразу
  `false`. Ведёт себя предсказуемо, как `==` в Go.
- `==` (нестрогое равенство) — пытается **привести типы** друг к другу перед
  сравнением, и правила этого приведения — лабиринт безумия:

```js
0 == "";          // true  (оба привелись к 0... ну почти)
0 == "0";         // true
"" == "0";        // false (а вот тут уже строки, без приведения)
null == undefined;// true
1 == true;        // true
[] == ![];        // true   ← вот это уже за гранью добра и зла
```

Правило одно и железобетонное: **всегда используй `===` и `!==`**. Линтер будет на
этом настаивать, и правильно сделает. Единственное живущее исключение, которое иногда
полезно: `x == null` — лаконичная проверка «`x` это `null` ИЛИ `undefined`» (обе
пустоты разом). Но и её можно не использовать, если непривычно.

### Truthiness: что считается «истинным»

В `if`, `&&`, `||` любое значение приводится к логическому. Запомни список
**falsy**-значений (всё, что считается «ложью») — он короткий:

```
false, 0, "" (пустая строка), null, undefined, NaN, 0n
```

**Всё остальное — truthy**, включая `"0"`, `"false"`, `[]` (пустой массив!) и `{}`
(пустой объект!). Это регулярно ловит новичков:

```js
if ([]) console.log("выполнится");  // пустой массив — truthy!
```

Отсюда удобные идиомы:

```js
const name = inputName || "Гость";        // если inputName пустой/undefined → "Гость"
const port = config.port ?? 3000;          // ?? срабатывает ТОЛЬКО на null/undefined
```

`??` (nullish coalescing) — важное уточнение к `||`. `||` подставит запасной вариант
на **любое** falsy (включая `0` и `""`, что часто не то, что хотелось). `??` —
только на `null`/`undefined`. Для «значение по умолчанию, но 0 и пустая строка
валидны» нужен именно `??`.

## Ошибки: `throw`, `try/catch` и почему это совсем не Go

Вот место, где твои Go-привычки придётся отложить. В Go ошибка — это **значение**, которое
функция возвращает вторым результатом, и ты обязан на него посмотреть. В JS ошибка — это
**исключение**: оно «выстреливает» из функции и летит вверх по стеку вызовов, пока кто-то
его не поймает. Не поймал никто — программа падает (в Node) или ошибка попадает в консоль
браузера.

```js
function parseAge(raw) {
  const n = Number(raw);
  if (Number.isNaN(n)) {
    throw new Error(`не число: ${raw}`);   // выбрасываем ошибку
  }
  return n;
}

try {
  const age = parseAge("abc");
  console.log(age);                        // сюда не дойдём
} catch (err) {
  console.error("Поймали:", err.message);  // "не число: abc"
} finally {
  console.log("выполнится в любом случае");  // как defer, только привязан к блоку
}
```

Что важно знать сразу:

- **Бросать можно что угодно**, не обязательно `Error`: `throw "строка"` — валидный JS.
  Так делать не надо, но чужой код может, поэтому в TS переменная в `catch` имеет тип
  `unknown` (подробно — в [модуле 08](../08-async/theory.md)).
- **`new Error(msg)` несёт стектрейс** (`err.stack`) — в отличие от Go-шной ошибки-строки.
  Есть готовые подтипы: `TypeError`, `RangeError`, `SyntaxError`; свои классы ошибок
  делают через `class MyError extends Error` (модуль 07).
- **`finally` похож на `defer`**, но привязан к блоку `try`, а не к функции.
- **Сигнатура функции не говорит, бросает ли она.** В Go по `(T, error)` видно всё; в
  JS/TS этого в типах нет вообще — ни `throws`, ни аналога. Отсюда практическая
  дисциплина: либо документируй, либо возвращай результат-объект (паттерн `Result` из
  модуля 05), либо оборачивай вызовы в `try/catch` на границе.

> **Простыми словами.** В Go ошибку тебе **отдают**, в JS ошибку в тебя **швыряют**.
> Компилятор не напомнит поймать — напоминать придётся себе самому.

## Модули: как файлы видят друг друга

В Go единица организации — пакет, импорт по пути, экспортируется всё с большой буквы.
В JS единица — **файл-модуль**, и нужно явно говорить, что экспортировать и что
импортировать. Современный стандарт — **ES Modules (ESM)**:

```ts
// math.ts — экспортируем
export function add(a: number, b: number) { return a + b; }
export const PI = 3.14159;
export default function multiply(a: number, b: number) { return a * b; } // дефолтный
```

```ts
// app.ts — импортируем
import multiply, { add, PI } from "./math.ts";  // multiply — дефолтный, остальное — именованные
import { add as plus } from "./math.ts";        // переименование при импорте
```

Два вида экспорта: **именованные** (`export function`, импортируются в `{ }` по
точному имени) и **один дефолтный** на файл (`export default`, при импорте имя
выбираешь сам). На старте предпочитай именованные — с ними понятнее, что откуда.

> Историческая засада: до ESM в Node была своя система модулей — **CommonJS**
> (`require()` / `module.exports`). Ты ещё встретишь её в старом коде и туториалах.
> Это два разных, местами несовместимых мира. Современный ориентир — ESM
> (`import`/`export`); CommonJS просто узнавай в лицо. Подробнее — в модуле 09.

## Event loop: почему JS однопоточный, но не виснет

И последний фундаментальный сюжет — модель исполнения. Здесь контраст с Go максимальный.

В Go конкурентность встроена в язык: запускаешь горутины (`go f()`), их тысячи, рантайм
раскидывает их по потокам ОС, общаешься через каналы. Настоящая многопоточность.

В JavaScript **один поток**. Ровно один. Нет горутин, нет потоков (в базовой модели),
нет параллельного выполнения твоего кода. Казалось бы — как же тогда грузить данные по
сети, не заморозив всю страницу? Ответ — **event loop** (цикл событий).

Идея: долгие операции (запрос к серверу, таймер, чтение файла) JS **не выполняет сам и
не ждёт**. Он отдаёт их окружению (браузеру или Node) со словами «позови меня, когда
будет готово», и идёт дальше выполнять остальной код. Когда операция завершилась,
её колбэк ставится в очередь, и event loop выполнит его, как только основной поток
освободится.

```js
console.log("1");
setTimeout(() => console.log("3"), 0);   // «потом», даже с задержкой 0
console.log("2");
// порядок вывода: 1, 2, 3
```

`setTimeout` с нулевой задержкой всё равно выполнится **после** синхронного кода:
он отправлен в очередь, а очередь обрабатывается, только когда текущий код доработал
до конца. Это называется кооперативной моделью: задачи не прерывают друг друга
насильно, а вежливо ждут своей очереди.

Отсюда два важнейших следствия:

1. **Долгий синхронный цикл «вешает» всё** — пока он крутится, event loop не может
   обработать ни клик, ни сетевой ответ. В Go долгий цикл занял бы одну горутину,
   остальные жили бы. В JS он занимает единственный поток. Поэтому тяжёлые вычисления
   на фронте — проблема.
2. **Асинхронность — это не параллелизм.** Тысячи «одновременных» сетевых запросов в
   JS прекрасно живут (ждут-то их браузер/ОС, а не твой код), но твой собственный код
   при этом всё равно выполняется по одной операции за раз.

На этой модели построены промисы и `async/await` — но это большая тема, ей посвящён
весь модуль 08. Пока достаточно интуиции: **один поток + очередь отложенных задач**.

## Типичные ошибки и заблуждения

- **«Раз есть TypeScript, JS можно не учить».** Нет. TS описывает JS и стирается перед
  запуском. Все рантайм-странности (`this`, пустоты, event loop) остаются твоими.
- **«`null` и `undefined` — одно и то же».** Технически разные значения с разным
  смыслом. `strict`-режим TS заставит различать — и это к лучшему.
- **«`const` делает объект неизменяемым».** Нет, только запрещает переприсвоить
  переменную. Поля объекта меняются свободно.
- **«Можно сравнивать через `==`».** Можно, но не нужно — приведение типов
  непредсказуемо. Всегда `===`.
- **«Пустой массив/объект — falsy».** Нет! `[]` и `{}` — **truthy**. Falsy только
  `false, 0, "", null, undefined, NaN, 0n`.
- **«`async` = многопоточность как горутины».** Нет. Один поток + event loop.
  Конкурентность есть, параллелизма твоего кода — нет.
- **«Присвоил объект — получил копию».** Нет, получил вторую ссылку на тот же объект.
  Копию делают явно (`{ ...obj }`, `structuredClone`).
- **«`arr.sort()` отсортирует числа».** Нет, отсортирует их как строки. Нужен компаратор
  `(a, b) => a - b`. И помни: `sort` мутирует исходный массив.
- **«`for...in` — это как `for range` по массиву».** Нет: `for...in` даёт ключи-строки и
  для массивов не предназначен. Значения — `for...of`.
- **«`?.` можно ставить везде на всякий случай».** Нет: он маскирует настоящие баги.
  `?.` — только там, где отсутствие значения ожидаемо.
- **«Ошибку в JS обязательно надо поймать, компилятор проверит».** Не проверит: в типах
  нет информации о бросаемых ошибках. Дисциплина только на тебе.

## Глоссарий модуля

Термины, которые дальше будут использоваться без расшифровки.

- **Движок (engine)** — программа, исполняющая JS: V8 (Chrome, Node), JavaScriptCore
  (Safari), SpiderMonkey (Firefox).
- **Рантайм (runtime)** — движок плюс окружение с его API: браузер (DOM, `fetch`) или
  Node (файлы, сеть, процессы). Один и тот же JS в разных рантаймах умеет разное.
- **Node.js** — рантайм JS вне браузера, на нём пишут серверы, CLI и инструменты сборки.
- **DOM** — объектное представление HTML-страницы, доступное из JS в браузере. В Node
  его нет.
- **Транспиляция** — перевод кода из одного диалекта в другой (TS → JS, новый JS →
  старый JS). Не то же, что компиляция в машинный код.
- **Стирание типов (type erasure)** — удаление всех TS-аннотаций перед запуском.
- **Замыкание (closure)** — функция вместе с переменными области, где она создана.
- **Прототип** — объект, к которому делегируется поиск отсутствующего свойства.
- **Hoisting / TDZ** — «подъём» объявлений и запрет обращаться к `let`/`const` до строки
  объявления.
- **Truthy / falsy** — значения, которые в условии ведут себя как истина/ложь.
- **Мутация** — изменение объекта на месте (в противоположность созданию нового).
- **Деструктуризация** — разбор объекта/массива на отдельные переменные.
- **Колбэк (callback)** — функция, переданная в другую функцию, чтобы её вызвали позже.
- **Event loop** — механизм очередей, позволяющий однопоточному JS не блокироваться.
- **ESM / CommonJS** — современная (`import`/`export`) и старая (`require`) системы
  модулей.
