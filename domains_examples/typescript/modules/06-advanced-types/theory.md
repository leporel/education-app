# Продвинутые типы

## Суть: типы, которые вычисляются

До сих пор типы были «статичными ярлыками». Теперь главный сдвиг сознания: **в TS типы
можно вычислять из других типов**. Есть операторы (`keyof`), условные выражения
(`extends ? :`), преобразования (mapped types). По сути это маленький, чисто
функциональный язык, который исполняется в голове компилятора во время проверки.

В Go ничего подобного нет — система типов там намеренно простая. Поэтому здесь у тебя
не будет готовой интуиции из Go; зато это самая «магическая» часть TS, и понимание её
открывает, как устроены библиотечные типы вроде `Partial<T>` или типы во Vue/React.

Важная оговорка наперёд: **знать эти инструменты надо, злоупотреблять — нет.** В конце
поговорим, где грань между «элегантно» и «никто, включая автора, это уже не прочитает».

## Операторы над типами

### `keyof` — union ключей типа

```ts
type User = { id: number; name: string; age: number };

type UserKey = keyof User;   // "id" | "name" | "age"
```

`keyof T` берёт тип-объект и возвращает union его ключей как литеральных строк. Это
мостик из мира значений в мир типов: список свойств становится типом. Мы уже видели его
в дженериках (`K extends keyof T`).

### `typeof` (в контексте типов) — тип из значения

В модуле 01 был `typeof` времени выполнения (возвращает строку). А в позиции типа
`typeof` делает другое — **извлекает тип уже существующего значения**:

```ts
const config = { host: "localhost", port: 3000 };

type Config = typeof config;   // { host: string; port: number }
```

Это бесценно, когда значение — источник истины (например, объект настроек), и
дублировать его форму руками не хочется. Описал значение — получил тип бесплатно.

### Indexed access — `T[K]`, тип значения по ключу

```ts
type User = { id: number; name: string };

type IdType = User["id"];          // number
type ValueType = User[keyof User]; // number | string (union всех значений)
```

Синтаксис как у доступа к свойству, но работает с типами. `User["id"]` — «тип того, что
лежит под ключом id».

## Mapped types — преобразуем все свойства разом

Самая мощная идея модуля. **Mapped type** проходит по всем ключам типа и строит новый
тип, преобразуя каждое свойство. Синтаксис напоминает `for ... in`, но для типов:

```ts
type User = { id: number; name: string };

// сделать все свойства опциональными
type PartialUser = {
  [K in keyof User]?: User[K];
};
// = { id?: number; name?: string }

// сделать все свойства readonly
type ReadonlyUser = {
  readonly [K in keyof User]: User[K];
};
```

Читается так: `[K in keyof User]` — «для каждого ключа K из User», `User[K]` — «возьми
тип значения под этим ключом», модификаторы `?` / `readonly` применяются ко всем сразу.
Это и есть «цикл по свойствам типа». Именно так под капотом устроена половина
библиотечных утилит.

> **Простыми словами.** Mapped type — это `for` по полям типа, только выполняется он в
> голове компилятора, а результат — не значение, а новый тип. Ближайшая аналогия в Go —
> кодогенерация: тоже «пройтись по полям структуры и сделать новую», только там это
> отдельный шаг сборки, а здесь одна строка в системе типов.

Обобщённая форма (работает для любого `T`) — это уже готовый рецепт `Partial`:

```ts
type MyPartial<T> = {
  [K in keyof T]?: T[K];
};
```

Можно и **снимать** модификаторы префиксом `-`:

```ts
type Mutable<T> = {
  -readonly [K in keyof T]: T[K];   // убрать readonly у всех свойств
};
type Concrete<T> = {
  [K in keyof T]-?: T[K];           // убрать опциональность (сделать обязательными)
};
```

## Conditional types — `extends ? :` для типов

Тип может **выбираться по условию** — это тернарный оператор, но на уровне типов:

```ts
type IsString<T> = T extends string ? "да" : "нет";

type A = IsString<"hello">;   // "да"
type B = IsString<42>;        // "нет"
```

`T extends string ? X : Y` означает «если `T` совместим со `string`, то результат `X`,
иначе `Y`». В сочетании с ключевым словом `infer` условные типы умеют **извлекать**
части типа:

```ts
// извлечь тип элемента массива
type ElementOf<T> = T extends (infer E)[] ? E : never;

type X = ElementOf<number[]>;   // number
type Y = ElementOf<string[]>;   // string
type Z = ElementOf<boolean>;    // never (не массив)
```

`infer E` говорит: «сопоставь `T` с шаблоном `(что-то)[]` и назови это что-то `E`». Так
устроены `ReturnType`, `Awaited` и многие другие. На старте достаточно понимать, что
такое бывает, и уметь читать; писать свои `infer`-типы — навык для позже.

## Template literal types — типы из строк

Литеральные строковые типы можно склеивать, как строки в шаблоне:

```ts
type Color = "red" | "blue";
type Shade = "light" | "dark";

type ColorShade = `${Shade}-${Color}`;
// "light-red" | "light-blue" | "dark-red" | "dark-blue"  (все комбинации!)
```

Это даёт типобезопасные строковые идентификаторы (имена событий, CSS-классы, ключи) с
проверкой на этапе компиляции. Снова — то, чего в Go нет вовсе.

## Utility types — готовая стандартная библиотека типов

Большинство преобразований выше **уже написаны** за тебя и встроены в TS. Их надо знать
в лицо — это повседневный инструмент:

```ts
type User = { id: number; name: string; email: string };

Partial<User>          // все свойства опциональны: { id?, name?, email? }
Required<User>         // все обязательны (снимает ?)
Readonly<User>         // все readonly
Pick<User, "id" | "name">   // только выбранные: { id: number; name: string }
Omit<User, "email">         // все, КРОМЕ указанных: { id, name }
Record<string, number>      // объект-словарь: { [k: string]: number }
```

И утилиты, извлекающие типы (на базе `infer`):

```ts
function makeUser() { return { id: 1, name: "Ann" }; }
type U = ReturnType<typeof makeUser>;   // { id: number; name: string }

type P = Parameters<(a: number, b: string) => void>;   // [number, string]
type A = Awaited<Promise<string>>;      // string (разворачивает Promise — пригодится в модуле 08)
type N = NonNullable<string | null>;    // string (убирает null/undefined)
```

И две утилиты для работы с union — их постоянно путают, поэтому запомни по действию:

```ts
type Method = "GET" | "POST" | "DELETE";

type Safe = Exclude<Method, "DELETE">;          // "GET" | "POST"  — ВЫКИНУТЬ указанное
type Mutating = Extract<Method, "POST" | "PUT">; // "POST"         — ОСТАВИТЬ пересечение
```

`Exclude`/`Extract` работают с union-ами (как `Omit`/`Pick` — с объектами). Устроены они
на условных типах: `Exclude<T, U> = T extends U ? never : T`. Работает это благодаря
**дистрибутивности**: условный тип с «голым» параметром применяется к каждому члену union
по отдельности, а `never` в union просто исчезает. Знать наизусть не нужно, но увидеть
механику один раз полезно — она объясняет, почему условные типы над union ведут себя
«поэлементно».

Связка с дженериками делает их особенно полезными. Например, «обновление пользователя,
где можно прислать любое подмножество полей, кроме id»:

```ts
function updateUser(id: number, patch: Partial<Omit<User, "id">>) { /* ... */ }

updateUser(1, { name: "Bob" });               // OK, частичное обновление
updateUser(1, { email: "x@y.z", name: "C" }); // OK
updateUser(1, { id: 99 });                    // ❌ id исключён Omit'ом
```

`Partial<Omit<User, "id">>` читается изнутри наружу: «взять `User`, убрать `id`
(`Omit`), сделать остальное необязательным (`Partial`)». Один тип точно выражает
сложное бизнес-правило. Это и есть сила композиции типов.

## `as const` — фиксируем литералы

Мы видели (модуль 04): `const x = "north"` даёт литеральный тип, а объекты по умолчанию
«расширяются» до общих типов. `as const` фиксирует всю структуру как максимально узкую и
`readonly`:

```ts
const routes = {
  home: "/",
  user: "/user/:id",
} as const;
// тип: { readonly home: "/"; readonly user: "/user/:id" }
// без as const было бы: { home: string; user: string }

type RoutePath = (typeof routes)[keyof typeof routes];   // "/" | "/user/:id"
```

`as const` + `typeof` + `keyof` — частая связка, чтобы превратить обычный объект-данные
в источник точных литеральных типов. Удобно для конфигов, наборов констант, «энумов на
объектах».

## `satisfies`: проверить, не расширяя

Классическая дилемма, в которую упирается каждый: как **проверить** объект на
соответствие типу, но **сохранить** точные литеральные типы его полей? Аннотация и
`as const` тянут в разные стороны:

```ts
type Route = { path: string; auth: boolean };

// Вариант 1: аннотация — проверяет, но «расширяет» типы значений
const routes1: Record<string, Route> = {
  home: { path: "/", auth: false },
};
routes1.hom;              // ⚠️ никакой ошибки: Record<string, ...> разрешает любой ключ
routes1.home.path;        // тип string (а не "/")

// Вариант 2: as const — точные типы, но никакой проверки
const routes2 = {
  home: { path: "/", auth: "no" },   // ⚠️ опечатка в типе auth осталась незамеченной
} as const;
```

Оператор **`satisfies`** решает обе проблемы: он проверяет значение на соответствие типу,
но выводит тип по самому значению, а не по аннотации:

```ts
const routes = {
  home:  { path: "/",          auth: false },
  admin: { path: "/admin",     auth: true  },
} satisfies Record<string, Route>;

routes.home.path;     // тип "/" — литерал сохранён!
routes.hom;           // ❌ ошибка: такого ключа нет (ключи известны точно)
// { path: 1 } внутри дало бы ошибку проверки Route
```

Формула, которую стоит запомнить: **`: T` — «сделай тип таким», `as T` — «притворись, что
тип такой», `satisfies T` — «проверь, что подходит под T, но тип оставь точный»**. Для
конфигов, таблиц маршрутов, наборов констант `satisfies` (часто вместе с `as const`) —
современный ответ по умолчанию.

> **Простыми словами.** `satisfies` — это экзамен без переодевания: значение проверяют по
> требованиям типа, но в паспорте остаётся его собственное, более точное описание.

## Где остановиться: дисциплина важнее трюков

А теперь — раздел, который в большинстве туториалов забывают, и зря. Система типов TS
тьюринг-полна: на ней можно вычислять что угодно, вплоть до парсеров в типах. **Это не
значит, что нужно.**

Признаки, что ты зашёл слишком далеко:

- Чтобы понять тип, приходится разворачивать его на бумажке. Если автор через месяц не
  прочитает свой тип — это плохой тип.
- Сообщения об ошибках превращаются в простыню на 40 строк, где не видно сути.
- Компиляция начинает заметно тормозить (сложные условные типы не бесплатны).

Здравое правило (в духе *Effective TypeScript*): **тип должен прояснять намерение, а не
демонстрировать виртуозность.** В 95% реального кода хватает дженериков и горстки
utility-типов из этого модуля. Глубокая type-level магия — инструмент авторов библиотек,
а не повседневного прикладного кода. Как Go-разработчик ты ценишь простоту и читаемость —
держись этого и здесь: умный тип, который никто не понимает, хуже честного `// TODO`.

## Типичные ошибки и заблуждения

- **«`typeof` в типах — то же, что в рантайме».** Нет. В рантайме `typeof` → строка;
  в позиции типа `typeof value` → тип значения.
- **«mapped type — это значение».** Нет, это преобразование типа; в рантайме его нет
  (стирание).
- **«Надо писать свои Partial/Pick».** Не надо, они встроены. Узнавай и используй
  готовые utility-типы.
- **«Чем умнее тип, тем лучше код».** Чаще наоборот. Читаемость > виртуозность.
  Глубокая type-магия — для библиотек, не для прикладного кода.
- **«`as const` — то же, что `const`».** Нет: `const` фиксирует переменную, `as const`
  фиксирует структуру значения как узкие `readonly`-литералы.
- **«`satisfies` — то же, что аннотация типа».** Нет: аннотация расширяет тип значения до
  указанного, `satisfies` только проверяет, сохраняя точный вывод.
- **«`Omit`/`Pick` работают с union-ами».** Нет, они про объекты. Для union — `Exclude`
  (выкинуть) и `Extract` (оставить).

## Глоссарий модуля

- **Type-level программирование** — вычисления над типами, выполняемые компилятором.
- **`keyof T`** — union ключей типа.
- **Indexed access `T[K]`** — тип значения по ключу; `T[keyof T]` — union всех значений.
- **`typeof value`** (в позиции типа) — тип существующего значения.
- **Mapped type** — `{ [K in keyof T]: ... }`, преобразование всех свойств.
- **Conditional type** — `T extends U ? X : Y`, ветвление на уровне типов.
- **`infer`** — извлечение части типа по шаблону внутри условного типа.
- **Дистрибутивность** — условный тип применяется к каждому члену union по отдельности.
- **Template literal type** — тип-строка, собранная из других типов (`` `${A}-${B}` ``).
- **Utility type** — встроенный готовый преобразователь типов (`Partial`, `Omit`, …).
- **`as const`** — зафиксировать значение как узкие `readonly`-литералы.
- **`satisfies`** — проверить значение по типу, не расширяя выведенный тип.
- **Брендированный тип** — приём эмуляции номинальной типизации через «тег»-поле.
