# Union-типы, сужение и дискриминированные union

## Суть: тип «одно ИЗ»

Главная новая идея модуля проста на словах: тип-объединение (**union**) `A | B`
означает «значение это либо `A`, либо `B`». TypeScript позволяет описывать «одно из
нескольких» прямо в системе типов — и это та область, где он заметно выразительнее Go.

В Go, чтобы сказать «либо число, либо строка», ты бы взял `interface{}` (`any`) и
потерял всю типобезопасность, либо городил структуру с флагом и проверками вручную.
TS даёт это честно и с проверкой компилятора.

```ts
type Id = number | string;

function printId(id: Id) {
  // здесь id — это number | string, и пока неизвестно что именно
  console.log(id);
}
printId(42);       // OK
printId("u-42");   // OK
printId(true);     // ❌ boolean не входит в number | string
```

Но есть оборотная сторона: пока `id` имеет тип `number | string`, тебе доступны
**только операции, общие для обоих**. Нельзя вызвать `id.toUpperCase()` — у `number`
такого метода нет. Чтобы получить доступ к специфичным операциям, тип нужно **сузить**
(narrowing) — об этом ниже, это сердце модуля.

### Intersection: тип «и то И другое»

Двойственная операция — пересечение (**intersection**) `A & B`: значение должно
удовлетворять **обоим** типам сразу. Полезно для комбинирования форм:

```ts
type WithId = { id: number };
type WithName = { name: string };

type Entity = WithId & WithName;   // должен иметь и id, и name

const e: Entity = { id: 1, name: "Ann" };   // оба поля обязательны
```

Интуиция, которая многих путает: `|` для объектов даёт **меньше** гарантированных
свойств (только общие), а `&` — **больше** (объединение всех). Это кажется
вывернутым наизнанку, но логично: «значение одного из двух типов» гарантирует лишь то,
что есть в обоих; «значение обоих типов» обязано иметь всё из каждого.

> **Простыми словами.** Думай не о свойствах, а о **множестве значений**. `A | B` —
> объединение двух множеств значений (значений больше → гарантий меньше). `A & B` —
> пересечение (значений меньше → гарантий больше). Через эту оптику вся система типов TS
> становится намного понятнее: тип — это множество допустимых значений, `never` — пустое
> множество, `unknown` — множество всего.

## Литеральные типы: когда `string` слишком широк

Тип может быть не «любая строка», а **конкретное значение**:

```ts
type Direction = "north" | "south" | "east" | "west";

function move(dir: Direction) { /* ... */ }
move("north");   // OK
move("up");      // ❌ "up" не входит в набор
```

Это **литеральные типы**: `"north"` — это тип, которому принадлежит ровно одно
значение. Объединяя литералы в union, ты получаешь типобезопасный «перечислимый» набор
вариантов — аналог того, для чего в Go берут `const` + `iota` (псевдо-enum). Только
здесь это проверяется на уровне типов и не даёт передать «левое» значение.

> Кстати, в TS есть и настоящий `enum`, но в современном коде его часто избегают: union
> литералов проще, лучше выводится и не оставляет следа в рантайме (а `enum`, в отличие
> от остального TS, генерирует реальный объект — редкое исключение из правила «типы
> стираются»). На старте предпочитай union литералов.

### Откуда берутся литеральные типы: `const` vs `let`

Тонкость вывода типов, которую полезно понимать:

```ts
let a = "north";      // тип выведен как string (let можно переприсвоить → широкий тип)
const b = "north";    // тип выведен как "north" (const неизменна → точный литерал)

move(b);              // OK
move(a);              // ❌ a имеет тип string, а не "north"
```

`const` «фиксирует» литеральный тип, `let` — расширяет до общего (`string`). Если тебе
нужно зафиксировать литералы в объекте, используют `as const` (подробнее в модуле 06).

## Сужение типов (narrowing) — сердце модуля

Если union — это вопрос «что это может быть», то **сужение** — это инструмент «давай
выясним, что это конкретно сейчас». Гениальность TS в том, что он понимает обычные
JS-проверки и **сам уточняет тип внутри ветки**. Это называется анализом потока
управления (control flow analysis).

### 1. `typeof` — для примитивов

```ts
function printId(id: number | string) {
  if (typeof id === "string") {
    // в этой ветке TS ЗНАЕТ, что id — string
    console.log(id.toUpperCase());   // OK, метод строки доступен
  } else {
    // а здесь автоматически остаётся number
    console.log(id.toFixed(2));      // OK, метод числа доступен
  }
}
```

Ты не делаешь ничего особенного — пишешь обычный `typeof`, как написал бы в JS. Но TS
читает эту проверку и сужает тип в каждой ветке. В Go ближайший аналог — type switch
по `interface{}`, только тут это работает с обычными рантайм-проверками и без приведений.

### 2. Проверка на `null`/`undefined`

Со `strictNullChecks` это твой повседневный инструмент:

```ts
function greet(name: string | null) {
  if (name === null) {
    return "Аноним";
  }
  // ниже TS знает: name — это string (null отсечён)
  return name.toUpperCase();
}
```

Тот же эффект дают «ранний выход» и truthy-проверки (`if (!name) return ...`). После
проверки TS сужает тип, и доступ к строковым методам становится безопасным.

### 3. `instanceof` — для классов

```ts
function logError(e: Error | string) {
  if (e instanceof Error) {
    console.log(e.message);   // e сужен до Error
  } else {
    console.log(e);           // string
  }
}
```

`instanceof` работает только с тем, что реально существует в рантайме (классы,
конструкторы) — помним про стирание типов: `e instanceof SomeType` для `type` не
сработает.

### 4. Оператор `in` — по наличию свойства

```ts
type Dog = { bark: () => void };
type Cat = { meow: () => void };

function speak(pet: Dog | Cat) {
  if ("bark" in pet) {
    pet.bark();   // сужено до Dog
  } else {
    pet.meow();   // сужено до Cat
  }
}
```

### 4a. `Array.isArray` и другие штатные проверки

`typeof` для массива бесполезен (`typeof [] === "object"`), поэтому массивы сужают
отдельной функцией — и TS её понимает:

```ts
function flatten(x: string | string[]): string {
  return Array.isArray(x) ? x.join(", ") : x;
}
```

Так же работают проверки на конкретное значение (`x === "GET"`), проверка длины кортежа
и `switch` по литералам — обо всём этом TS «знает». Общее правило: **если проверка
выглядит как обычный JS-код, у TS есть шанс её понять**; если ты вынес её в отдельную
функцию — шанса нет, пока не оформишь предикат типа (следующий раздел).

### 5. Пользовательский type guard (предикат типа)

Когда проверка сложная, её выносят в функцию с особым возвращаемым типом
`x is T` — это **предикат типа**. Он говорит компилятору: «если я вернул `true`,
считай, что аргумент имеет тип `T`».

```ts
type User = { id: number; name: string };

function isUser(x: unknown): x is User {
  return (
    typeof x === "object" && x !== null &&
    "id" in x && typeof (x as any).id === "number" &&
    "name" in x && typeof (x as any).name === "string"
  );
}

const data: unknown = JSON.parse(input);
if (isUser(data)) {
  console.log(data.name);   // здесь data сужен до User
}
```

Это та самая граница, о которой говорили в модуле 02: внешние данные принимаем как
`unknown`, проверяем рантайм-кодом, и type guard «легализует» их в систему типов.
Внутри `isUser` приходится использовать `as any`/`in`, потому что мы и есть тот код,
который вручную доказывает компилятору тип — но снаружи всё чисто и типобезопасно.

### 6. Функции-утверждения (`asserts`) — коротко

Родственник предиката: функция, которая не возвращает `boolean`, а **бросает** ошибку,
если условие не выполнено. После её вызова TS считает тип уточнённым:

```ts
function assertIsString(v: unknown): asserts v is string {
  if (typeof v !== "string") throw new Error("ожидалась строка");
}

function shout(v: unknown) {
  assertIsString(v);
  return v.toUpperCase();   // здесь v уже string
}
```

Это удобно для инвариантов на границе («дальше идти нельзя, если данные не такие»).
Аналог Go-шного «проверил и вернул ошибку» — только через панику вместо возврата.
Пользуйся умеренно: `if` + предикат обычно читаемее.

## Где сужение теряется (важный практический раздел)

Сужение — это анализ потока управления, и у него есть границы. Знание этих границ снимает
90% недоумений «я же проверил, почему ошибка?!».

**1. Сужение не переживает вызов функции.** Компилятор не знает, что делает чужой код,
поэтому осторожничает со свойствами объектов:

```ts
type Box = { value: string | null };

function print(box: Box) {
  if (box.value === null) return;
  doSomething();              // мог ли doSomething() поменять box.value? TS не знает
  box.value.toUpperCase();    // здесь сужение всё ещё держится для этого случая...
}
```

Здесь всё в порядке, но стоит появиться замыканию или `await` — и картина меняется.
Надёжный приём: **скопируй значение в локальную `const`** и работай с ней.

```ts
function print2(box: Box) {
  const value = box.value;    // локальная const — сужение к ней «прилипает» надёжно
  if (value === null) return;
  doSomething();
  value.toUpperCase();        // ✅ гарантированно string
}
```

**2. Сужение теряется внутри колбэка.**

```ts
function handle(name: string | null) {
  if (name === null) return;

  setTimeout(() => {
    // ❌ TS снова видит string | null: колбэк вызовется когда-то потом,
    //    и к тому моменту name (если бы это был let/свойство) мог измениться
    console.log(name.toUpperCase());
  }, 100);
}
```

Для параметра-`const` современный TS обычно справляется, а для `let` и свойств объекта —
нет. Опять же лечится локальной `const` **до** колбэка.

**3. Сужение сбрасывается переприсваиванием.** Присвоил в `let` новое значение — анализ
начинается заново, что логично.

**4. Опциональные свойства не «связываются» между собой.** Проверка `if (a.b)` ничего не
говорит TS про `a.c`, даже если по логике они всегда приходят вместе. Именно поэтому
такие ситуации лучше моделировать дискриминированным union (следующий раздел), а не
набором опциональных полей.

> **Простыми словами.** Сужение — это память компилятора о том, что он «только что
> проверил». Память короткая: любое место, где значение теоретически могло измениться,
> её обнуляет. Хочешь надёжности — фиксируй значение в `const`.

## Дискриминированные union — главный приём модуля

А теперь — техника, которую стоит выучить намертво, потому что она встречается в
реальном TS-коде постоянно (и особенно во Vue/React для моделирования состояния).

Проблема: у нас есть несколько «вариантов» данных разной формы — например, результат
операции: успех с данными или ошибка с сообщением. Как описать это типобезопасно?

Решение: **общее поле-дискриминант** (тег) с литеральным типом, по которому TS
различает варианты:

```ts
type Success = { status: "ok"; data: string };
type Failure = { status: "error"; message: string };

type Result = Success | Failure;   // дискриминант — поле status

function handle(r: Result) {
  if (r.status === "ok") {
    // TS знает: это Success → доступно r.data
    console.log("Данные:", r.data);
  } else {
    // здесь это Failure → доступно r.message
    console.log("Ошибка:", r.message);
  }
}
```

Магия в поле `status`: его литеральный тип (`"ok"` / `"error"`) уникален для каждого
варианта, и проверка `r.status === "ok"` автоматически сужает весь объект до нужной
формы. Ты не можешь случайно обратиться к `r.data` в ветке ошибки — компилятор не
пустит.

Сравни с Go. В Go классический способ вернуть «результат или ошибку» — это
`(value, error)`, и дисциплина «проверь err != nil» держится на договорённости и линтере.
Дискриминированный union в TS делает невозможные состояния **непредставимыми**: нет
способа получить и `data`, и `message` одновременно, и нельзя прочитать `data`, не
доказав, что это успех. Это и называют «making illegal states unrepresentable» —
моделируй так, чтобы неправильное состояние нельзя было даже выразить.

## `never` и проверка исчерпанности

Последний штрих, который превращает дискриминированные union в супероружие. Что, если
в `Result` добавят третий вариант, а ты забудешь обработать его в `switch`? Хочется,
чтобы компилятор напомнил. Инструмент — тип `never`:

```ts
type Shape =
  | { kind: "circle"; r: number }
  | { kind: "square"; side: number }
  | { kind: "rect"; w: number; h: number };

function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return Math.PI * s.r ** 2;
    case "square": return s.side ** 2;
    case "rect":   return s.w * s.h;
    default:
      // Если обработаны ВСЕ варианты, сюда s приходит с типом never.
      // Присваивание never в never — ОК. Но стоит добавить новый вариант в Shape
      // и забыть case — TS здесь выдаст ошибку: «X не присваивается never».
      const _exhaustive: never = s;
      return _exhaustive;
  }
}
```

Логика красивая: после обработки всех веток в `default` не остаётся ни одного
возможного типа — это `never`. Если же ты добавишь `{ kind: "triangle"; ... }` в
`Shape`, но забудешь `case "triangle"`, то в `default` будет «протекать» этот
необработанный тип, и строка `const _exhaustive: never = s` перестанет компилироваться.
Компилятор буквально заставит тебя дописать обработку нового варианта. В Go такой
гарантии нет: добавил константу в «enum» — компилятор не напомнит про забытый `case`.

## Типичные ошибки и заблуждения

- **«С `number | string` можно сразу вызывать методы».** Нет, только общие операции.
  Сначала сузь тип (`typeof`), потом вызывай специфичное.
- **«`|` для объектов даёт все свойства».** Наоборот — только общие. Все свойства даёт
  `&` (intersection).
- **«`instanceof` сработает с любым TS-типом».** Только с тем, что есть в рантайме
  (классы). Для `type` — не сработает (стирание).
- **«`enum` — лучший способ для набора вариантов».** Чаще лучше union литералов: проще,
  без рантайм-следа. `enum` — особый случай, генерирующий реальный объект.
- **«Дискриминированный union — это просто union».** Ключ в общем поле-теге с
  литеральным типом; без него сужение по `switch` работать не будет.
- **«Проверка исчерпанности не нужна».** Нужна: трюк с `never` ловит забытые ветки при
  добавлении новых вариантов — то, чего Go не гарантирует.
- **«Один раз проверил — сужение действует до конца функции».** Не всегда: колбэки,
  переприсваивания и обращения к свойствам объекта его сбрасывают. Фиксируй в `const`.
- **«`typeof x === 'array'` сужает массив».** Такого `typeof` нет; для массивов —
  `Array.isArray(x)`.
- **«Набор опциональных полей — нормальная модель для вариантов».** Нет: проверка одного
  поля ничего не говорит TS про другие. Нужен дискриминированный union.

## Глоссарий модуля

- **Union (`A | B`)** — «одно из»; объединение множеств значений.
- **Intersection (`A & B`)** — «и то, и другое»; пересечение множеств значений.
- **Литеральный тип** — тип из одного значения (`"north"`, `42`, `true`).
- **Расширение типа (widening)** — превращение литерала в общий тип при `let`
  (`"north"` → `string`).
- **Narrowing (сужение)** — уточнение типа внутри ветки на основе проверки.
- **Control flow analysis** — механизм компилятора, который это делает.
- **Type guard / предикат типа** — функция с типом возврата `x is T`.
- **Функция-утверждение** — функция с типом возврата `asserts x is T`, бросающая ошибку.
- **Дискриминант (тег)** — общее поле литерального типа, по которому различают варианты
  union.
- **Exhaustiveness check** — проверка, что обработаны все варианты (через `never`).
- **`never`** — пустое множество значений; «сюда поток не дойдёт».
