# Классы и ООП

## Суть: классы есть, но это всё ещё прототипы

В JS появилось ключевое слово `class` (2015), и TS добавил к нему типы и модификаторы
доступа. Но помни из модуля 01: **`class` — синтаксический сахар над прототипами.** Под
капотом всё те же объекты с цепочкой прототипов; `class` просто делает запись привычной
для тех, кто пришёл из Java/C#.

> **Простыми словами.** `class` — это фабрика похожих объектов плюс общий «склад методов»
> (прототип), к которому все созданные объекты обращаются за поведением. Методы не
> копируются в каждый экземпляр — они лежат в одном месте, и потому классы экономнее, чем
> объекты-с-функциями-в-полях.

Для тебя как Go-разработчика это территория с двойственным чувством: с одной стороны,
классы дают то, чего в Go нарочно нет (наследование, абстрактные классы). С другой —
именно потому, что Go это выкинул, у тебя уже есть здоровый скепсис к ООП-пирамидам, и
он тут очень кстати.

## Базовый класс

```ts
class Counter {
  private count: number;          // поле с модификатором доступа

  constructor(start: number = 0) {
    this.count = start;
  }

  increment(): void {
    this.count += 1;
  }

  get value(): number {           // геттер — обращаются как к свойству: c.value
    return this.count;
  }
}

const c = new Counter(10);
c.increment();
console.log(c.value);   // 11
c.count;                // ❌ private — снаружи недоступно
```

Сравни с замыканием-счётчиком из модуля 01: тот давал приватность через замыкание, этот
— через `private`. Оба валидны; класс удобнее, когда сущностей много и нужна общая
«форма с методами».

### Сокращённая инициализация полей (parameter properties)

Очень частый и удобный приём TS: объявить поле прямо в параметрах конструктора, добавив
модификатор. TS сам создаст поле и присвоит:

```ts
class Point {
  constructor(
    public readonly x: number,
    public readonly y: number,
  ) {}
  // эквивалент: объявить x, y и написать this.x = x; this.y = y;
}

const p = new Point(3, 4);
p.x;   // 3 (readonly — менять нельзя)
```

Это убирает скучную копипасту «объяви поле — присвой в конструкторе». В Go аналога нет
(там поля структуры объявляются отдельно), но идея «меньше ритуала» тебе близка.

### `static`: то, что принадлежит классу, а не объекту

Статические поля и методы живут на самом классе, а не на экземплярах. Самое частое
применение — **фабричные методы** и константы:

```ts
class Temperature {
  static readonly ABSOLUTE_ZERO = -273.15;      // константа класса

  private constructor(public readonly celsius: number) {}   // прямой new запрещён

  static fromCelsius(c: number): Temperature {
    if (c < Temperature.ABSOLUTE_ZERO) throw new RangeError("ниже абсолютного нуля");
    return new Temperature(c);
  }

  static fromFahrenheit(f: number): Temperature {
    return Temperature.fromCelsius((f - 32) / 1.8);
  }
}

Temperature.ABSOLUTE_ZERO;              // обращение через КЛАСС
const t = Temperature.fromCelsius(20);  // "конструктор с именем"
// new Temperature(20);                 // ❌ конструктор приватный
```

Это ровно тот приём, к которому ты привык в Go: `NewFromCelsius(...)` в пакете вместо
голого создания структуры — потому что имя объясняет смысл и позволяет провалидировать
аргументы. `private constructor` — способ сказать «создавать только через фабрику».

Внутри статического метода `this` указывает на сам класс, а не на экземпляр — ещё одна
причина не полагаться на `this` без нужды.

## Модификаторы доступа: два разных механизма

Тут есть тонкость, которую важно не пропустить — приватность в TS бывает **двух видов**:

1. **`private` / `protected` / `public`** — проверки **только во время компиляции**.
   Помним про стирание: в рантайме `private`-поле обычное, к нему можно добраться, если
   очень хотеть (`(obj as any).count`). Это договорённость, которую стережёт TS, как и
   `readonly`.
2. **`#`-приватные поля** (часть стандарта JS, не TS) — **настоящая рантайм-приватность**.
   К `#count` физически нельзя обратиться извне класса, никаким `as any`.

```ts
class A {
  private softPrivate = 1;   // приватно «по мнению TS»
  #hardPrivate = 2;          // приватно по-настоящему, в рантайме тоже
}
```

На старте достаточно `private` (читаемее, привычнее). `#` бери, когда приватность важна
по-настоящему (например, в публичной библиотеке). Для Go-разработчика: `private` ближе
к «неэкспортируемому имени» по строгости намерения, но без рантайм-гарантии; `#` — это
уже настоящая инкапсуляция.

`readonly` (видели в модуле 03) на полях класса работает так же: присвоить можно только
в конструкторе.

## Наследование, абстракции, интерфейсы

### `extends` — наследование реализации

```ts
class Animal {
  constructor(public name: string) {}
  move(): string { return `${this.name} двигается`; }
}

class Dog extends Animal {
  bark(): string { return "Гав!"; }
  move(): string { return `${this.name} бежит`; }  // переопределение метода
}

const d = new Dog("Рекс");
d.move();   // "Рекс бежит"
d.bark();   // "Гав!"
```

`Dog` наследует поле `name` и метод `move`, добавляет `bark`, переопределяет `move`.
Это классическое наследование — то, чего в Go **нет вообще** (там только встраивание
структур, которое выглядит похоже, но это композиция, а не наследование с
полиморфизмом).

### `abstract` — класс-шаблон, который нельзя инстанцировать

```ts
abstract class Shape {
  abstract area(): number;            // нет реализации — обязаны определить наследники

  describe(): string {                // общая реализация для всех
    return `Площадь: ${this.area()}`;
  }
}

class Circle extends Shape {
  constructor(private r: number) { super(); }
  area(): number { return Math.PI * this.r ** 2; }
}

new Shape();           // ❌ нельзя создать абстрактный класс
new Circle(5).describe();   // "Площадь: 78.53..."
```

`abstract` задаёт «контракт + частичную реализацию»: наследники обязаны доопределить
абстрактные методы, но получают готовые конкретные.

### `implements` — обязать класс соответствовать интерфейсу

```ts
interface Comparable<T> {
  compareTo(other: T): number;
}

class Version implements Comparable<Version> {
  constructor(public major: number, public minor: number) {}
  compareTo(other: Version): number {
    return this.major - other.major || this.minor - other.minor;
  }
}
```

`implements` — проверка «класс реализует интерфейс». Важное отличие от Go: в Go тип
удовлетворяет интерфейсу **неявно** (структурно — если есть нужные методы, то
удовлетворяет, ничего писать не надо). В TS можно так же (структурно), но `implements`
даёт **явную** проверку и понятную ошибку, если метод забыли. Это вопрос стиля: `implements`
документирует намерение, но не обязателен — структурная типизация всё равно сработает
без него.

## Свои классы ошибок: единственное наследование, которое нужно всем

Есть один случай, где наследование бесспорно уместно даже в самом «композиционном» коде,
— **свои типы ошибок**. Помнишь из [модуля 01](../01-js-foundations/theory.md), что в JS
ошибки бросают, а не возвращают? Чтобы на другом конце понять, *что именно* сломалось, у
ошибки должен быть тип:

```ts
class AppError extends Error {
  constructor(message: string, readonly code: string) {
    super(message);                 // обязателен: передаём сообщение базовому Error
    this.name = "AppError";         // чтобы в логах было видно, что это за ошибка
  }
}

class NotFoundError extends AppError {
  constructor(what: string) {
    super(`${what} не найден`, "NOT_FOUND");
    this.name = "NotFoundError";
  }
}

class ValidationError extends AppError {
  constructor(message: string, readonly field: string) {
    super(message, "VALIDATION");
    this.name = "ValidationError";
  }
}
```

Зачем это нужно: **классы существуют в рантайме**, поэтому по ним работает `instanceof` —
и это единственный надёжный способ разобрать ошибку по типу (`type`-алиас, как мы знаем,
стёрся бы):

```ts
try {
  doWork();
} catch (err) {
  if (err instanceof ValidationError) {
    console.error(`Поле ${err.field}: ${err.message}`);   // тип сужен, поле доступно
  } else if (err instanceof AppError) {
    console.error(`Ошибка приложения [${err.code}]`);
  } else if (err instanceof Error) {
    console.error("Неожиданная ошибка:", err.message);
  } else {
    console.error("Брошено вообще не Error:", err);        // и так бывает
  }
}
```

Три правила гигиены:

- **Всегда вызывай `super(message)`** — иначе потеряешь сообщение и стектрейс.
- **Ставь `this.name`** — иначе в логах будет просто `Error`.
- **Причину-обёртку передавай через `cause`**: `new AppError("не смог сохранить", "IO",
  { cause: err })` — стандартное поле `Error.cause`, аналог `fmt.Errorf("...: %w", err)` в
  Go. Оно сохраняет исходную ошибку, а не только её текст.

Сравнение с Go полезно проговорить: там для этого делают свои типы ошибок и разбирают их
`errors.Is`/`errors.As`. Механизм близкий (тип ошибки существует в рантайме, проверяется
явно), разница только в способе доставки — возврат против броска.

## Наследование vs композиция: почему Go выбрал второе

Вот идейный центр модуля. Раз в TS есть наследование, тянет строить иерархии:
`Animal → Dog → Puppy`. Десятилетия опыта (и дизайн Go) говорят: **осторожнее**.

Проблемы глубокого наследования:

- **Хрупкий базовый класс.** Изменение в `Animal` неожиданно ломает всех потомков.
- **Жёсткая связь.** Потомок намертво привязан к реализации родителя.
- **Проблема «is-a».** Иерархии плохо описывают реальность: пингвин — птица, но не
  летает. Прямоугольник и квадрат — классический пример, где наследование подводит.

**Композиция** — собирать поведение из независимых частей, а не наследовать единым
блоком:

```ts
// Вместо иерархии классов — маленькие интерфейсы и делегирование
interface Logger { log(msg: string): void; }

class ConsoleLogger implements Logger {
  log(msg: string): void { console.log(msg); }
}

class OrderService {
  // зависимость передаётся снаружи (dependency injection) — не наследуется
  constructor(private logger: Logger) {}

  placeOrder(id: number): void {
    this.logger.log(`Заказ ${id} оформлен`);
  }
}

const service = new OrderService(new ConsoleLogger());
```

`OrderService` не наследует логирование — он **использует** `Logger`, переданный извне.
Захотел писать логи в файл — подменил реализацию `Logger`, не трогая `OrderService`.
Это ровно философия Go: маленькие интерфейсы + композиция структур, никакого
наследования. «Favor composition over inheritance» — старое правило ООП, которое Go
возвёл в закон языка. В TS закона нет, но правило остаётся: **наследование — для редких
честных «is-a», композиция — для всего остального** (а «остального» подавляющее
большинство).

> Практический ориентир: если рисуешь иерархию глубже двух уровней — почти наверняка
> стоит остановиться и спросить, не лучше ли композиция. Твой Go-инстинкт здесь —
> хороший компас.

## `this` в классах: знакомая ловушка

Помнишь `this` из модуля 01? В классах он снова кусается. Метод, «оторванный» от
экземпляра (например, переданный как колбэк), теряет `this`:

```ts
class Timer {
  seconds = 0;
  tick() { this.seconds += 1; }
  start() {
    // setInterval(this.tick, 1000);       // ❌ this потеряется
    setInterval(() => this.tick(), 1000);  // ✅ стрелка сохраняет this
  }
}
```

Решение то же, что и раньше: **оборачивай в стрелку** (`() => this.tick()`) или объявляй
метод как стрелочное поле (`tick = () => { ... }`). Это самая частая ошибка с классами в
JS/TS, и она прямое следствие того, что `this` динамический.

## Декораторы (обзорно)

`@`-декораторы — способ навесить поведение на класс/метод/поле декларативно. Ты увидишь
их в фреймворках (Angular, NestJS, ORM вроде TypeORM):

```ts
class UserService {
  @log                      // декоратор оборачивает метод
  findUser(id: number) { /* ... */ }
}
```

Декораторы стали частью стандарта сравнительно недавно и используются в основном
фреймворками. **Писать свои на старте не нужно** — достаточно узнавать `@`-синтаксис и
понимать, что это «обёртка, навешанная декларативно». Vue 3, к слову, в современном
стиле (Composition API) декораторы почти не использует — так что для твоего следующего
домена это не критично.

## Типичные ошибки и заблуждения

- **«`class` в JS — это не прототипы».** Это сахар над прототипами; механизм тот же.
- **«`private` гарантирует приватность в рантайме».** Нет, это compile-time контракт.
  Настоящая приватность — `#`-поля.
- **«Надо всё моделировать наследованием».** Нет. Композиция предпочтительнее; глубокие
  иерархии хрупки. Go не зря выкинул наследование.
- **«`implements` обязателен, чтобы класс подходил под интерфейс».** Нет, структурная
  типизация сработает и без него. `implements` — явная проверка/документация намерения.
- **«Метод можно свободно передать как колбэк».** Потеряешь `this`. Оборачивай в стрелку.
- **«Свой класс ошибки не нужен, хватит строки в `throw`».** Нужен: по классу работает
  `instanceof` (единственный надёжный разбор ошибки по типу), есть стектрейс и `cause`.
- **«В классе-наследнике `Error` можно не звать `super(message)`».** Нельзя: без него
  потеряются сообщение и стектрейс, а обращение к `this` до `super()` вообще запрещено.
- **«`static` — это просто поле».** Это поле/метод самого класса: обращение через
  `ClassName.x`, у экземпляров его нет. Основное применение — константы и фабрики.

## Глоссарий модуля

- **Экземпляр (instance)** — объект, созданный из класса через `new`.
- **Конструктор** — метод, вызываемый при `new`; `super(...)` — вызов конструктора
  родителя.
- **Parameter property** — объявление поля прямо в параметрах конструктора.
- **Геттер / сеттер** — методы `get`/`set`, к которым обращаются как к свойству.
- **`static`** — член, принадлежащий классу, а не экземпляру.
- **`private` / `protected` / `public`** — модификаторы доступа уровня компилятора.
- **`#field`** — приватное поле стандарта JS (настоящая рантайм-приватность).
- **`abstract`** — класс/метод без реализации, обязательный к доопределению.
- **`implements`** — явное заявление, что класс соответствует интерфейсу.
- **Полиморфизм** — вызов переопределённого метода по фактическому типу объекта.
- **Композиция / DI** — передача зависимостей извне вместо наследования.
- **`Error.cause`** — стандартное поле для «ошибки-причины» (аналог оборачивания `%w`).
