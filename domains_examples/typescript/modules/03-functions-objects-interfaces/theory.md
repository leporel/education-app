# Функции, объекты и интерфейсы

## Суть

В этом модуле мы учимся описывать две главные «единицы» программы — **функции**
(как они принимают и возвращают значения) и **объекты** (какой они формы). Объект в
JS/TS — это рабочая лошадка: им моделируют почти всё, что в Go ты бы сделал структурой
или map. Поэтому уметь точно описывать форму объекта — половина мастерства в TS.

## Функции: больше способов, чем в Go

### Параметры: обязательные, опциональные, со значением по умолчанию, rest

```ts
function f(a: number, b?: number): number {       // b — опциональный (может отсутствовать)
  return a + (b ?? 0);
}
f(1);        // OK, b === undefined
f(1, 2);     // OK

function g(a: number, b: number = 10): number {   // b со значением по умолчанию
  return a + b;
}
g(5);        // 15

function sum(...nums: number[]): number {          // rest — «остальные» в массив
  return nums.reduce((acc, n) => acc + n, 0);
}
sum(1, 2, 3, 4);   // 10
```

Сразу важные правила:

- **Опциональный параметр** (`b?`) автоматически получает в тип `| undefined`. Внутри
  функции TS заставит учесть, что `b` может быть `undefined`.
- **Опциональные и default-параметры идут в конце.** Нельзя сделать необязательным
  первый параметр, оставив обязательным второй — позиционный вызов сломался бы.
- **Rest-параметр** (`...nums`) собирает «хвост» аргументов в массив. Это типизированный
  аналог вариативных функций Go (`func sum(nums ...int)`).

В Go опциональных параметров нет вообще — там для этого городят структуры-опции или
варианты функций. TS даёт это из коробки, что приятно, но требует дисциплины с
`undefined`.

### Тип функции как значение

Раз функция — значение (модуль 01), у неё есть тип. Записывается стрелкой:

```ts
type BinOp = (a: number, b: number) => number;   // тип: функция (number, number) → number

const add: BinOp = (a, b) => a + b;
const mul: BinOp = (a, b) => a * b;

function apply(op: BinOp, x: number, y: number): number {
  return op(x, y);
}
apply(add, 2, 3);   // 5
```

Обрати внимание: у `add` параметры **не аннотированы** — TS вывел их типы из `BinOp`.
Это «контекстная типизация»: когда место назначения известно, TS подставляет типы сам.
Очень удобно в колбэках:

```ts
[1, 2, 3].map((n) => n * 2);   // n: number выведен из типа массива, аннотация не нужна
```

### `void` и одна изящная тонкость

Функция, которая ничего осмысленного не возвращает, имеет тип возврата `void`:

```ts
function log(msg: string): void {
  console.log(msg);
}
```

Тонкость, которая экономит нервы: если параметр объявлен как функция, возвращающая
`void`, в неё **можно передать функцию, которая на самом деле что-то возвращает** — её
результат просто проигнорируется. Это нарочно: позволяет, например, передать
`array.push` (возвращающий число) туда, где ждут колбэк-без-результата `forEach`.
Запоминать не обязательно, но если столкнёшься — не удивляйся.

### Объект-параметр вместо длинного списка аргументов

Приём из [урока про деструктуризацию](../01-js-foundations/lessons/02-objects-arrays-destructuring.md)
в типизированном виде — то, что в JS-мире называют «options object». Именно так
оформляют функции с тремя и более настройками:

```ts
type SearchOptions = {
  query: string;
  limit?: number;
  sort?: "relevance" | "date";
};

function search({ query, limit = 10, sort = "relevance" }: SearchOptions): string {
  return `q=${query}&limit=${limit}&sort=${sort}`;
}

search({ query: "молоко" });                 // OK
search({ query: "хлеб", limit: 3 });         // OK
search({ limit: 3 });                        // ❌ отсутствует обязательное query
```

Тип ставится **после** всей деструктуризации, а не на отдельные поля — частая ошибка
новичка (внутри `{ }` двоеточие уже занято переименованием). Значения по умолчанию
задаются в деструктуризации, и тогда внутри функции `limit` имеет тип `number`, а не
`number | undefined`.

Если все поля опциональны, полезно дать дефолт всему параметру, иначе вызов без
аргументов не скомпилируется (и упадёт в рантайме):

```ts
function connect({ host = "localhost", port = 80 }: { host?: string; port?: number } = {}) {
  return `${host}:${port}`;
}
connect();   // OK благодаря = {} в конце
```

Для Go-разработчика: это ближайший родственник «структуры с опциями». Функциональных
опций (`WithTimeout(...)`) в TS обычно не делают — объект читаемее.

### Перегрузки функций (и почему их стоит избегать)

Иногда функция ведёт себя по-разному в зависимости от аргументов, и это надо описать
точнее, чем одним союзом типов. Для этого есть **перегрузки**: несколько сигнатур и одна
реализация.

```ts
function parseInput(x: string): string[];          // сигнатура 1
function parseInput(x: number): number[];          // сигнатура 2
function parseInput(x: string | number): unknown[] {   // реализация (не видна снаружи!)
  return typeof x === "string" ? x.split(",") : [x];
}

const a = parseInput("1,2");   // a: string[]
const b = parseInput(5);       // b: number[]
```

Важно: сигнатура реализации **не участвует** в вызовах — снаружи видны только объявленные
перегрузки. И перегрузки нельзя вызвать «смешанно»: `parseInput(x)` для `x: string | number`
не скомпилируется, потому что ни одна отдельная перегрузка не подходит. Это классическая
боль.

Современный совет (в духе *Effective TypeScript*): **сначала попробуй обойтись union-типом
или дженериком** — читаемее и дружелюбнее к выводу типов. Перегрузки оставь для случаев,
где связь «конкретный вход → конкретный выход» иначе не выразить.

## Объекты: описываем форму

Объектный тип — это перечисление свойств с их типами:

```ts
type User = {
  id: number;
  name: string;
  email?: string;          // опциональное свойство (может отсутствовать)
  readonly createdAt: Date;// readonly — присвоить только при создании, потом нельзя
};

const u: User = {
  id: 1,
  name: "Ann",
  createdAt: new Date(),
};

u.name = "Bob";        // OK
u.createdAt = new Date(); // ❌ Cannot assign to 'createdAt' because it is read-only
u.email;               // string | undefined (опциональное → может быть undefined)
```

- `email?` — опциональное свойство; его тип становится `string | undefined`, и TS
  заставит проверить наличие перед использованием.
- `readonly createdAt` — «только для чтения» на уровне типов. Это, как и всё в TS,
  проверка времени компиляции: в рантайме поле обычное, никто физически не запрещает
  его менять. Это договорённость, которую стережёт компилятор. (В Go ближайшая аналогия
  — неэкспортируемое поле + отсутствие сеттера; механизм другой, цель та же.)

### Опциональные свойства в работе: `?.` и `??`

Опциональное поле — это `T | undefined`, поэтому обращаться к его методам напрямую TS не
даст. Рабочая связка — опциональная цепочка и значение по умолчанию:

```ts
u.email.toUpperCase();               // ❌ 'u.email' is possibly 'undefined'
u.email?.toUpperCase();              // ✅ тип результата: string | undefined
const mail = u.email ?? "нет почты"; // ✅ тип результата: string

if (u.email) {
  u.email.toUpperCase();             // ✅ внутри if тип сужен до string (модуль 04)
}
```

Компилятор здесь работает ровно тем же способом, что описан в модуле 04: он читает
проверку и уточняет тип. `?.` не «отключает ошибку», а честно добавляет `undefined` в
результат — и это правильно.

### `readonly` для массивов

Массивы тоже бывают «только для чтения», и это самый практичный способ сказать «я не
буду портить твои данные»:

```ts
function total(prices: readonly number[]): number {
  // prices.push(1);                 // ❌ у readonly-массива нет мутирующих методов
  return prices.reduce((s, p) => s + p, 0);
}

const nums: number[] = [1, 2];
total(nums);                          // ✅ обычный массив подходит под readonly-параметр
```

Работает в одну сторону: `number[]` можно передать туда, где ждут `readonly number[]`, но
не наоборот. Хорошая привычка — принимать входные коллекции как `readonly`, если функция
их не меняет. Записывается и как `ReadonlyArray<number>` — это одно и то же.

### Индексная сигнатура: объект как словарь

Если ключи заранее неизвестны (объект используется как map), описывают **индексную
сигнатуру**:

```ts
type Scores = {
  [player: string]: number;     // любой строковый ключ → число
};

const s: Scores = { ann: 10, bob: 7 };
s.charlie = 12;                 // OK, добавляем новый ключ
const x = s.dave;               // тип number... но в рантайме undefined!
```

Вот здесь и спасает флаг `noUncheckedIndexedAccess` из прошлого модуля: с ним `s.dave`
получает тип `number | undefined`, и TS напомнит, что ключа может не быть — ровно как в
Go тебе пришлось бы написать `v, ok := m[k]`. Без этого флага TS наивно считает, что по
любому ключу что-то есть, и это классический источник рантайм-`undefined`.

> Совет: для словарей с произвольными ключами часто берут готовый тип `Record<K, V>`
> (`Record<string, number>` ≡ индексная сигнатура выше). Про него — в модуле 06.

## `interface` против `type`: главный вопрос новичка

Описать форму объекта можно двумя способами, и они выглядят почти одинаково:

```ts
interface User {
  id: number;
  name: string;
}

type User2 = {
  id: number;
  name: string;
};
```

Оба задают одну и ту же форму, оба используют структурную совместимость. Девяносто
процентов времени они взаимозаменяемы. Но различия есть.

**`interface` умеет:**

- Описывать **только объекты/функции** (форму с полями и методами).
- **«Сливаться» при повторном объявлении** (declaration merging): два `interface User`
  в одной области сложатся в один. Звучит странно, но это нужно для расширения чужих
  типов (например, добавить поле в типы библиотеки).
- Расширяться через `extends` (привычный ООП-синтаксис наследования формы).

**`type` (alias) умеет всё, что interface, и сверх того:**

- Давать имя **любому** типу, не только объекту: union (`type Id = number | string`),
  кортежу, примитиву, функции, шаблонному литералу.
- Участвовать в продвинутых типах (mapped, conditional — модуль 06).
- **Не сливается** при повторном объявлении — повторный `type User` будет ошибкой
  (часто это и к лучшему: меньше неожиданностей).

**Практическое правило (по гайдлайнам TS):**

- Описываешь **форму объекта или публичный контракт, который, возможно, кто-то будет
  расширять** → бери `interface`.
- Нужен **union, кортеж, функция, alias примитива или продвинутый тип** → бери `type`.
- Сомневаешься и это просто объект → бери `interface` (так советует официальный
  Handbook) и не страдай: переключиться потом легко.

Не делай из этого выбора религию. Команды часто просто фиксируют один стиль в линтере
и живут счастливо.

## Структурная совместимость на практике и ловушка лишних свойств

Мы знаем (модуль 02): TS сравнивает типы по форме. На практике это значит, что
«больше — подходит под меньше»:

```ts
type Named = { name: string };

const person = { name: "Ann", age: 30 };
const n: Named = person;     // ✅ OK: у person есть name:string, остальное неважно
```

Но есть особое исключение — **excess property check** (проверка лишних свойств). Оно
срабатывает **только когда ты присваиваешь объектный литерал напрямую**:

```ts
type Config = { url: string };

const c: Config = { url: "x", timeout: 5000 };   // ❌ Ошибка! 'timeout' не из Config
```

Почему так строго именно тут? Потому что если ты прямо в этом месте написал литерал с
полем `timeout`, скорее всего ты **опечатался** или думал, что такое поле есть — это
почти всегда баг, а не намерение. А вот когда то же самое значение приходит через
переменную (как `person` выше), TS считает, что ты знаешь, что делаешь, и пропускает
лишнее. Тонко, но логично:

```ts
const opts = { url: "x", timeout: 5000 };
const c2: Config = opts;     // ✅ OK: пришло через переменную, лишнее прощается
```

Эта асимметрия путает почти всех новичков: «то же значение в одном случае ошибка, в
другом нет». Запомни триггер: **ошибка про лишнее свойство = ты передал объектный
литерал прямо в типизированное место.** Лечится либо убрать лишнее поле, либо вынести
литерал в переменную, либо (если поле правда нужно) поправить тип.

> **Простыми словами.** Структурная типизация говорит: «мне нужны эти поля, остальное не
> моё дело». Excess property check добавляет: «но если ты прямо здесь дописал поле,
> которого я не знаю, — ты, наверное, ошибся, дай я спрошу».

## Типичные ошибки и заблуждения

- **«Опциональное свойство — это то же, что свойство со значением `undefined`».** Почти,
  но `email?: string` разрешает вообще не писать `email`, тогда как `email: string |
  undefined` **требует** написать его явно (хотя бы как `undefined`). Разница в
  обязательности присутствия ключа.
- **«`readonly` нельзя обойти».** На уровне типов нельзя, но это compile-time контракт;
  в рантайме поле обычное. Это не `const` и не заморозка.
- **«`interface` и `type` — это две разные сущности с разной мощью».** В 90% случаев
  взаимозаменяемы. `type` чуть универсальнее (union и пр.), `interface` умеет
  слияние/extends. Выбирай по задаче, не агонизируй.
- **«Лишнее свойство всегда ошибка».** Только при прямом литерале. Через переменную
  структурная совместимость пропускает лишнее.
- **«Доступ по ключу всегда даёт значение».** Нет; включи `noUncheckedIndexedAccess`,
  и TS честно покажет `| undefined`.
- **«Тип для деструктурированного параметра пишется внутри `{ }`».** Нет: `{ a, b }: T`
  — тип идёт после всей деструктуризации. Двоеточие внутри `{ }` означает переименование.
- **«Перегрузки — правильный способ описать разное поведение».** Часто нет: union или
  дженерик читаемее и лучше выводятся. Перегрузки — крайняя мера.
- **«`readonly number[]` и `number[]` взаимозаменяемы».** Только в одну сторону: обычный
  массив подойдёт под `readonly`-параметр, но не наоборот.

## Глоссарий модуля

- **Сигнатура** — «форма» функции: типы параметров и возвращаемого значения.
- **Опциональный параметр / свойство** (`b?`) — можно не передавать; тип получает
  `| undefined`.
- **Default-параметр** (`b = 10`) — подставляется значение, тип остаётся узким.
- **Rest-параметр** (`...nums`) — собирает остальные аргументы в массив (Go: `nums ...int`).
- **Контекстная типизация** — TS выводит типы параметров колбэка из места, куда его
  передают.
- **Индексная сигнатура** (`[k: string]: number`) — описание объекта-словаря.
- **Excess property check** — дополнительная строгость к объектным литералам,
  присваиваемым напрямую.
- **Declaration merging** — слияние нескольких объявлений одного `interface`.
- **`readonly`** — запрет присваивания на уровне компилятора (не заморозка объекта).
- **Перегрузка (overload)** — несколько сигнатур для одной реализации.
- **Options object** — приём «одна структура настроек вместо многих параметров».
