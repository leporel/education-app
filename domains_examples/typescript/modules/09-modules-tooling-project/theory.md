# Модули, тулинг и первый проект

## Суть: язык — это половина, экосистема — вторая

В Go тебя избаловали: один инструмент `go` собирает, тестирует, форматирует, управляет
зависимостями. Стандартная библиотека огромна, сторонних зависимостей часто почти нет.
В JS-мире всё иначе: маленькое ядро языка, гигантская экосистема `npm` (самый большой
реестр пакетов в мире) и зоопарк инструментов. Это и сила (на любую задачу есть пакет),
и слабость (легко утонуть, легко притащить 300 зависимостей ради левого пэддинга).
Задача модуля — дать карту, чтобы ты не терялся.

## Система модулей: ESM и CommonJS

Мы коснулись модулей в модуле 01. Теперь предметно, потому что это частый источник
путаницы у новичков.

### ESM (ES Modules) — современный стандарт

```ts
// helpers.ts
export function greet(name: string): string { return `Hi ${name}`; }
export const VERSION = "1.0";
export default class App {}            // дефолтный экспорт (один на файл)

// main.ts
import App, { greet, VERSION } from "./helpers.ts";   // дефолт + именованные
import * as helpers from "./helpers.ts";                // всё пространство имён
```

ESM — это стандарт языка (`import`/`export`), он работает и в браузере, и в современном
Node. Импорты **статичны**: их расположение известно до запуска, что позволяет
инструментам анализировать зависимости и выкидывать неиспользуемое («tree shaking»).

### CommonJS — наследие Node

```js
// старый стиль Node
const helpers = require("./helpers");
module.exports = { greet };
```

CommonJS (`require`/`module.exports`) — это система, которую Node использовал до
стандартизации ESM. Ты встретишь её в старых пакетах, туториалах, конфигах. Ключевые
отличия: `require` динамичен (можно вызвать в середине кода), нет дефолтного экспорта в
том же смысле. Сегодняшний ориентир — **писать на ESM**, а CommonJS просто узнавать.
Иногда два мира конфликтуют (известная боль «Cannot use import statement outside a
module» или наоборот) — почти всегда лечится правильным `"type": "module"` в
`package.json` и настройками `tsconfig`.

> Аналогия с Go: представь, что у Go было бы две несовместимые системы импортов, старая
> и новая, и часть пакетов на одной, часть на другой. Неуютно — вот это оно. К счастью,
> экосистема почти доехала до ESM, и в новых проектах проблема всё реже.

### Разрешение путей

- `import x from "./utils"` — **относительный** путь к твоему файлу.
- `import x from "lodash"` — **пакет** из `node_modules` (без `./`).

Это как разница между импортом своего пакета и зависимости в Go, только тут граница —
наличие `./`.

## npm и package.json: паспорт проекта

`package.json` — сердце любого JS/TS-проекта (аналог `go.mod`, только богаче):

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "dev": "tsx watch src/main.ts",
    "build": "tsc",
    "typecheck": "tsc --noEmit",
    "lint": "eslint ."
  },
  "dependencies": {
    "zod": "3.23.8"
  },
  "devDependencies": {
    "typescript": "6.0.3",
    "tsx": "4.19.2"
  }
}
```

Разберём важное:

- **`"type": "module"`** — говорит Node, что `.js`-файлы проекта это ESM (а не CommonJS).
  Для современного проекта — ставь.
- **`scripts`** — именованные команды, запускаются `npm run dev`, `npm run build` и т.д.
  Это твой аналог Makefile/таска. `npm run typecheck` перед коммитом — добрая привычка.
- **`dependencies`** — нужны в рантайме (попадут в продакшен).
- **`devDependencies`** — нужны только при разработке (компилятор, линтер, тестовый
  фреймворк). В прод не идут.

### Установка зависимостей

```bash
npm install zod              # добавить в dependencies
npm install -D typescript    # добавить в devDependencies (-D = --save-dev)
npm install                  # установить всё из package.json (в node_modules)
```

Пара слов о том, что происходит физически, — иначе `node_modules` выглядит как чёрная
магия:

- **`node_modules/`** — папка, куда npm складывает *все* установленные пакеты вместе с их
  зависимостями. Она бывает огромной, её **не коммитят** (в `.gitignore`) и восстанавливают
  командой `npm install`. Ближайший аналог — кэш модулей Go (`$GOPATH/pkg/mod`), только
  локальный для проекта.
- **`npx <команда>`** — запустить исполняемый файл из установленного пакета (или скачать
  его на один раз). `npx tsc` — это «запусти `tsc` из `node_modules` этого проекта», а не
  какой-то глобально установленный. Отсюда правило: инструменты ставим локально в проект,
  а не глобально, чтобы у всех была одна версия.
- **`npm ci`** — установка строго по lock-файлу, без «умных» обновлений. Именно её
  используют в CI.

> **Простыми словами.** `package.json` — это «чего я хочу» (диапазоны версий),
> `package-lock.json` — «что у меня реально стоит» (точные версии всего дерева),
> `node_modules` — сами файлы. Первые два коммитим, третье — никогда.

### Semver: что значат версии

Версии в npm следуют **семантическому версионированию** `MAJOR.MINOR.PATCH`:

- **PATCH** (`1.0.0 → 1.0.1`) — багфиксы, обратно совместимо.
- **MINOR** (`1.0.0 → 1.1.0`) — новые возможности, обратно совместимо.
- **MAJOR** (`1.0.0 → 2.0.0`) — ломающие изменения.

Диапазоны в `package.json`:

- `"zod": "3.23.8"` — **точная** версия (предсказуемо; так часто делают намеренно).
- `"zod": "^3.23.8"` — `^` разрешает minor/patch обновления (`3.x.x`, но не `4.0.0`).
- `"zod": "~3.23.8"` — `~` разрешает только patch (`3.23.x`).

> Совет: для воспроизводимости многие фиксируют **точные** версии (без `^`/`~`) и
> полагаются на lock-файл (ниже). Это ближе к строгости, к которой ты привык.

### Lock-файл

`package-lock.json` фиксирует **точные** версии всего дерева зависимостей (включая
зависимости зависимостей). Это гарантия «у всех и в проде — ровно те же версии». Аналог
`go.sum`. **Коммить его в репозиторий.** Не редактируй руками.

## Бандлеры: зачем и когда

Тут новичков часто пугают словами «webpack», «rollup», «vite». Давай по-простому: зачем
вообще нужен бандлер?

Браузеру неудобно грузить сотни мелких файлов-модулей по сети. **Бандлер** собирает их
в несколько оптимизированных файлов, попутно: транспилирует современный синтаксис под
старые браузеры, выкидывает мёртвый код (tree shaking), минифицирует, обрабатывает CSS
и картинки. Для **фронтенда** бандлер практически обязателен.

> **Простыми словами.** Бандлер — это линковщик и упаковщик для веба. В Go `go build`
> собирает один бинарник из пакетов; здесь бандлер собирает несколько `.js`/`.css`-файлов
> из тысячи модулей и заодно приводит их к виду, который поймёт браузер. Слова, которые
> при этом всплывают: **транспиляция** (перевод современного синтаксиса в более старый),
> **tree shaking** (выбросить то, что никто не импортирует), **минификация** (сжать имена
> и пробелы), **dev-сервер** (локальный сервер, который пересобирает страницу на каждое
> сохранение файла).

- **Vite** — текущий стандарт де-факто для фронтенд-проектов (и именно его использует
  Vue). Быстрый, на базе esbuild/Rollup, отличный dev-сервер с мгновенной перезагрузкой.
- **esbuild** — сверхбыстрый сборщик/транспилятор (написан на Go, кстати — снова Go!),
  часто работает «под капотом» других инструментов.
- **webpack** — старый мощный гигант, ты встретишь его в legacy-проектах.

Когда бандлер **не нужен**: если ты пишешь backend/CLI на Node, никакой сборки в бандл
часто не требуется — Node сам выполняет твои модули (а `.ts` в Node 24 — напрямую). Не
тащи фронтенд-инструменты в серверный код «на всякий случай».

## ESLint: зачем линтер, если есть компилятор

Резонный вопрос Go-разработчика (у тебя был `go vet`/`golangci-lint`). Компилятор TS
проверяет **типы**. Линтер проверяет **стиль и подозрительные паттерны**, которые
типобезопасны, но всё равно плохи:

- забытый `await` (floating promise — помнишь модуль 08?);
- неиспользуемые переменные;
- `==` вместо `===`;
- `console.log`, оставленный в коде;
- использование `any`.

```bash
npm install -D eslint
npx eslint --init       # интерактивно создаст конфиг
npx eslint .            # проверить весь проект
```

Связка «TS (типы) + ESLint (паттерны) + Prettier (форматирование)» — стандартный набор
гигиены в современном проекте. Особенно важно правило `@typescript-eslint/no-floating-promises`
— оно ловит ту самую асинхронную ловушку, которую компилятор пропускает.

## Типы для сторонних библиотек: @types и DefinitelyTyped

Не все npm-пакеты написаны на TS. Если пакет на чистом JS, у него нет типов — и TS не
знает его API. Решения:

1. Многие современные пакеты **поставляют типы внутри** (видно по `.d.ts`-файлам в
   пакете) — ничего делать не надо.
2. Для популярных JS-пакетов без типов есть **отдельные пакеты типов** в проекте
   **DefinitelyTyped**, ставятся как `@types/имя`:

```bash
npm install lodash             # сам пакет (на JS)
npm install -D @types/lodash   # типы к нему отдельно
```

`.d.ts` — это «файл объявлений»: описание типов **без реализации**. Он говорит TS, как
выглядит API библиотеки. Грубая аналогия — заголовочный файл. Если типов нет нигде,
в крайнем случае объявляют модуль вручную или временно берут `any` (но это, как мы
помним, аварийный люк).

## Тесты: `node:test` и Vitest (обзорно)

В Go тесты — часть языка: файл `_test.go`, `go test`, и всё. В JS исторически тестовый
раннер был внешним, поэтому вариантов несколько. Два, которые актуальны сейчас:

**1. Встроенный в Node — `node:test`.** Ничего не надо ставить:

```ts
// sum.test.ts
import { test } from "node:test";
import assert from "node:assert/strict";
import { add } from "./sum.ts";

test("add складывает числа", () => {
  assert.equal(add(2, 3), 5);
});
```

```bash
node --test          # найдёт *.test.ts и прогонит
```

**2. Vitest** — самый популярный раннер во фронтенде (и не только): быстрый, понимает TS
и ESM «из коробки», умеет запускаться в режиме watch и считать покрытие. Именно его берут
в проектах на Vite/Vue, поэтому он тебе пригодится в следующем домене:

```ts
import { describe, it, expect } from "vitest";
import { add } from "./sum.ts";

describe("add", () => {
  it("складывает числа", () => {
    expect(add(2, 3)).toBe(5);
  });
});
```

```bash
npm install -D vitest
npx vitest            # watch-режим
npx vitest run        # однократный прогон (для CI)
```

Ориентир по выбору: **чистый Node-код без фронтенда → `node:test` достаточно; проект с
Vite/Vue → Vitest.** Стиль ассертов разный (`assert.equal` против `expect().toBe()`), идея
одна.

Что стоит унести из Go-привычек: тесты как таблица случаев (в JS это обычный массив
объектов и цикл с `it`), тесты рядом с кодом (`sum.ts` + `sum.test.ts`), быстрые
юнит-тесты по умолчанию. Чего в JS-мире принято больше, чем в Go, — **моки**: подмена
модулей и таймеров, но это уже отдельная тема.

## Карта инструментов (чтобы не пугаться)

| Задача | Инструмент(ы) | Аналог в Go |
|---|---|---|
| Запуск .ts | Node 24, tsx | `go run` |
| Проверка типов | `tsc --noEmit` | компилятор |
| Сборка/компиляция | `tsc`, бандлер (Vite) | `go build` |
| Зависимости | npm + package.json | go modules |
| Линтинг | ESLint | go vet / golangci-lint |
| Форматирование | Prettier | gofmt |
| Тесты | Vitest, node:test | go test |

Главное — не пытаться выучить весь зоопарк сразу. Бери минимум (`tsx` + `tsc` + ESLint),
а остальное подключай по мере надобности.

## Типичные ошибки и заблуждения

- **«ESM и CommonJS — одно и то же».** Разные системы модулей. Пиши ESM, CommonJS
  узнавай. Конфликты лечатся `"type": "module"` и настройками tsconfig.
- **«dependencies и devDependencies — без разницы».** В прод идут только
  `dependencies`. Компилятор/линтер/тесты — в `devDependencies`.
- **«lock-файл можно не коммитить».** Коммить обязательно — это воспроизводимость
  (аналог `go.sum`).
- **«Линтер дублирует компилятор».** Нет: компилятор про типы, линтер про паттерны и
  стиль (floating promises, `any`, мёртвый код).
- **«Любому проекту нужен бандлер».** Нет. Фронтенду — да (Vite); backend/CLI на Node
  часто обходится без сборки.
- **«Если у пакета нет типов — он не пригоден для TS».** Часто есть `@types/имя` из
  DefinitelyTyped; в крайнем случае — ручное объявление.
- **«`node_modules` нужно коммитить, иначе потеряется».** Нет: коммитят `package.json` и
  lock-файл, а папку восстанавливают через `npm install` / `npm ci`.
- **«Инструменты лучше ставить глобально».** Нет: локально в проект + `npx`, иначе у
  разных людей будут разные версии.
- **«Для тестов обязательно нужен фреймворк».** В Node уже есть встроенный `node:test`;
  Vitest берут, когда проект и так на Vite (фронтенд).

## Глоссарий модуля

- **ESM / CommonJS** — современная (`import`/`export`) и старая (`require`/`module.exports`)
  системы модулей.
- **`node_modules`** — локальная папка со всеми установленными пакетами; не коммитится.
- **`npx`** — запуск исполняемого файла из пакета проекта.
- **`npm ci`** — установка строго по lock-файлу (для CI).
- **Semver** — соглашение о версиях `MAJOR.MINOR.PATCH`; `^` и `~` — разрешённые
  диапазоны обновлений.
- **Lock-файл** — снимок точных версий всего дерева зависимостей (аналог `go.sum`).
- **Транспиляция** — перевод кода в другой (обычно более старый) диалект JS.
- **Бандлер** — сборщик модулей в оптимизированные файлы для браузера (Vite, webpack).
- **Tree shaking** — удаление неиспользуемого кода при сборке.
- **Минификация** — сжатие кода (короткие имена, без пробелов).
- **Dev-сервер / HMR** — локальный сервер сборки и «горячая» замена модулей без
  перезагрузки страницы.
- **Линтер** — анализатор подозрительных паттернов (ESLint); **форматтер** — Prettier.
- **`.d.ts`** — файл объявлений типов без реализации.
- **DefinitelyTyped / `@types/*`** — сообщество и пакеты с типами для JS-библиотек.
- **Раннер тестов** — инструмент, который находит и запускает тесты (`node --test`, Vitest).
