# Composables и паттерны переиспользования

## Что такое composable

**Composable** — это просто функция, которая использует Composition API (`ref`,
`computed`, `watch`, lifecycle-хуки) и **возвращает реактивное состояние и/или методы**
для работы с ним. По соглашению её имя начинается с `use` (`useMouse`, `useFetch`,
`useLocalStorage`). Никакой особой «магии фреймворка» тут нет — это обычная JS-функция, в
которой можно вызывать реактивные API.

Зачем: вынести **логику фичи** так, чтобы её можно было переиспользовать в разных
компонентах, не дублируя. Помнишь главный довод из модуля 03 — «Options API размазывает
логику по секциям»? Composable — это решение: вся логика одной фичи (состояние +
вычисления + эффекты + уборка) живёт в одной функции.

```ts
// useCounter.ts
import { ref, computed } from "vue";

export function useCounter(start = 0, step = 1) {
  const count = ref(start);
  const doubled = computed(() => count.value * 2);

  function inc() { count.value += step; }
  function dec() { count.value -= step; }
  function reset() { count.value = start; }

  return { count, doubled, inc, dec, reset };   // отдаём наружу реактивное + методы
}
```

```vue
<!-- любой компонент -->
<script setup lang="ts">
import { useCounter } from "./useCounter";

const { count, doubled, inc, reset } = useCounter(10, 5);
</script>

<template>
  <p>{{ count }} (×2 = {{ doubled }})</p>
  <button @click="inc">+5</button>
  <button @click="reset">сброс</button>
</template>
```

> **Go-параллель.** Composable — это как конструктор, возвращающий «объект с поведением»:
> `func NewCounter(start, step int) *Counter`. Только вместо методов на структуре ты
> получаешь набор реактивных значений и замыканий. И, в отличие от Go, возвращаемое
> состояние «живое» — компонент, который его прочитал, переподпишется на изменения.

## Деструктуризация composable — почему здесь она безопасна

В модуле 01 мы пугали: деструктуризация `reactive` теряет реактивность. А тут мы спокойно
пишем `const { count, inc } = useCounter()`. В чём разница?

Composable возвращает **объект, поля которого — это `ref`-ы (и функции)**, а не голый
`reactive`-объект. Деструктуризация копирует **сам `ref`** (ссылку на живую ячейку), а не
его значение. `count` после деструктуризации — это всё ещё `Ref<number>`, связь сохранена.
Поэтому соглашение: **composable отдаёт `ref`-ы (или `computed`/функции), а не reactive**,
именно чтобы результат можно было свободно деструктурировать. Если очень нужен
reactive-объект — отдай его обёрнутым в `toRefs`.

## Одно правило всё-таки есть: вызывай синхронно

Ниже мы сравним composables с React-хуками и порадуемся, что «правил хуков» тут нет. Одно
ограничение всё же существует, и нарушают его регулярно.

**Composable, который регистрирует lifecycle-хуки или использует `inject`, нужно вызывать
синхронно, в теле `setup` / `<script setup>`.** Причина простая и без магии: `onMounted`,
`onUnmounted`, `inject` привязываются к «текущему активному экземпляру компонента», а Vue
знает его только во время синхронного выполнения `setup`.

```ts
// ❌ после await активного экземпляра уже нет — хук не привяжется
const data = await loadSomething();
const { x } = useMouse();            // onMounted внутри тихо не сработает

// ❌ внутри обработчика — та же беда
function onClick() {
  const { x } = useMouse();
}

// ✅ синхронно, на верхнем уровне
const { x } = useMouse();
```

Условие или цикл сами по себе не запрещены (в отличие от React), но composable с
lifecycle-хуками в условии — плохая идея по той же причине: хук должен зарегистрироваться
предсказуемо. Практическое правило: **все `useX()` — вверху `<script setup>`, до любого
`await`.**

## Что composable должен возвращать

Мелочь, определяющая удобство API:

- **`ref` и `computed`, а не `reactive`** — чтобы результат можно было деструктурировать
  (см. раздел выше).
- **`computed` для производных** — не заставляй вызывающего считать самому.
- **`readonly(state)` для состояния, у которого есть свои методы изменения** — так снаружи
  нельзя случайно записать мимо `action`-подобной функции:

```ts
export function useCounter() {
  const count = ref(0);
  function inc() { count.value++; }
  return { count: readonly(count), inc };   // менять — только через inc()
}
```

- **Функции — обычные**, не оборачивай их ни во что.
- **`shallowRef` для тяжёлых значений** (см. модуль 01), если содержимое не нужно
  отслеживать поэлементно.

> **Готовые composables.** Прежде чем писать свой `useMouse`/`useDebounce`/`useFetch`,
> загляни в **VueUse** (vueuse.org) — большая библиотека готовых composables от участников
> ядра Vue. В учебных целях мы пишем свои руками (чтобы понимать механику), в рабочем
> проекте разумно не изобретать `useLocalStorage` заново.

## Экземпляр на вызов vs синглтон на модуле

Критичный для понимания момент. Где объявлено состояние — определяет, **общее** оно или
**своё** у каждого пользователя.

**Состояние внутри функции — свой экземпляр на каждый вызов:**

```ts
export function useCounter() {
  const count = ref(0);   // создаётся ЗАНОВО при каждом вызове useCounter()
  return { count };
}
// Компонент A: const { count } = useCounter()  → свой count
// Компонент B: const { count } = useCounter()  → ДРУГОЙ, независимый count
```

**Состояние на уровне модуля — один на всех (синглтон):**

```ts
const count = ref(0);     // создаётся ОДИН раз при импорте модуля

export function useSharedCounter() {
  return { count };       // все вызовы делят ОДИН и тот же count
}
// Компонент A и B получают общий count — изменил один, увидели оба.
```

Это не баг и не фича — это инструмент. Нужен локальный, независимый стейт (позиция мыши в
конкретном компоненте) — объявляй внутри функции. Нужно общее состояние без полноценного
стора (например, единый тоггл сайдбара) — объяви на уровне модуля. Но осторожно: **синглтон
на модуле — это глобальное состояние со всеми его минусами** (неявные связи, сложнее
тестировать). Для серьёзного общего состояния — Pinia (модуль 06), которая делает то же
самое, но явно и с devtools.

> Частая граблина новичка: положил `ref` на уровень модуля «чтобы было удобно», и вдруг
> два независимых виджета на странице влияют друг на друга. Или наоборот: хотел общий
> стейт, а объявил внутри функции — и каждый компонент живёт своей жизнью.

## Template refs: дотянуться до реального DOM

Обычно ты не трогаешь DOM руками — в этом весь смысл декларативности. Но иногда надо:
сфокусировать `<input>`, измерить размер, дёрнуть `<canvas>` или метод сторонней
библиотеки. Для этого — **template ref**:

```vue
<script setup lang="ts">
import { ref, onMounted, useTemplateRef } from "vue";

// Vue 3.5+: useTemplateRef по строковому ключу из шаблона
const inputRef = useTemplateRef<HTMLInputElement>("field");

onMounted(() => {
  inputRef.value?.focus();    // DOM уже есть — можно фокусировать
});
</script>

<template>
  <input ref="field" />
</template>
```

Связь: атрибут `ref="field"` в шаблоне + `useTemplateRef("field")` в скрипте. До `onMounted`
значение `null` (элемента ещё нет в DOM), поэтому доступ — через `?.`. Это «аварийный люк»
в императивный мир: пользуйся, когда реально нужно (фокус, измерения, интеграция), но не
ради того, что можно сделать декларативно.

> До Vue 3.5 template ref связывали по совпадению имени переменной `ref` и атрибута
> `ref="..."`. В новых проектах используем `useTemplateRef` — он явнее и типобезопаснее.

## Watchers глубже

Базовый `watch` мы видели. Полезные опции:

```ts
import { ref, watch } from "vue";

const query = ref("");

// immediate: выполнить коллбэк сразу при создании, не только на будущие изменения
watch(query, (q) => load(q), { immediate: true });

// deep: следить за изменениями ВНУТРИ объекта/массива (по умолчанию watch на reactive
// глубокий, а на getter, возвращающий объект, — нет)
const filters = ref({ tag: "", sort: "asc" });
watch(filters, () => refetch(), { deep: true });
```

**Очистка эффекта (`onCleanup`)** — для отмены устаревших асинхронных операций. Если
источник меняется быстрее, чем успевает отработать запрос, надо отменить предыдущий:

```ts
watch(query, (q, _old, onCleanup) => {
  const controller = new AbortController();
  onCleanup(() => controller.abort());      // отменить предыдущий запрос при новой смене
  fetch(`/search?q=${q}`, { signal: controller.signal });
});
```

Это лечит классическую гонку: набрал «vue» по букве — улетели три запроса, а пришли в
случайном порядке. `onCleanup` гарантирует, что устаревший отменён. (По духу — как
`context.WithCancel` в Go: новый запрос отменяет предыдущий.)

**Остановка watcher** — `watch` возвращает функцию остановки; нужна, если следишь вручную
вне обычного жизненного цикла:

```ts
const stop = watch(source, cb);
// ...
stop();   // больше не следим
```

Watchers, созданные синхронно в `setup`/`<script setup>`, останавливаются автоматически при
размонтировании компонента — вручную `stop()` нужен редко.

## Паттерны: что выбрать

| Нужно… | Инструмент |
|---|---|
| Переиспользовать **логику** (состояние+методы) между компонентами | **composable** (`useX`) |
| Раздать **контекст** вниз по поддереву (тема, локаль) | **provide/inject** |
| **Общее состояние приложения** с действиями, devtools, типобезопасностью | **стор (Pinia)** |
| Дотянуться до **реального DOM-элемента** | **template ref** |

### Сравнение с React-хуками

Composable ≈ кастомный React-хук по идее (переиспользуемая логика как функция), но механика
другая и приятнее: **тело composable выполняется один раз** при создании, а не на каждый
рендер. Поэтому нет «правил хуков» (нельзя в условии/цикле), нет массивов зависимостей
`useEffect([deps])`, нет проблем со «старыми замыканиями». Реактивность Vue сама отслеживает
зависимости, тебе не нужно их перечислять.

### Сравнение с миксинами (Vue 2)

Раньше логику шарили **миксинами** — объектами, поля которых подмешивались в компонент. Их
беды: конфликты имён (два миксина с полем `loading` — кто победит?), неясно, откуда взялось
свойство, неявные зависимости между миксинами. Composables это чинят: ты **явно** вызываешь
функцию и **явно** именуешь то, что она вернула (`const { loading } = useFetch()` —
переименовал и развёл конфликт сам). Если встретишь `mixins: [...]` — это легаси, и
composable почти всегда лучше.

## Типичные ошибки и заблуждения

- **«Composable — это особая сущность фреймворка».** Нет, обычная функция с приставкой
  `use`, вызывающая реактивные API. Магии нет.
- **«Деструктуризация composable теряет реактивность».** Не теряет, если composable
  отдаёт `ref`-ы (копируется ссылка на ячейку, а не значение). Поэтому отдавай `ref`/
  `computed`, а не голый `reactive`.
- **«`ref` на уровне модуля удобнее».** Это синглтон/глобальное состояние — два компонента
  начнут влиять друг на друга. Осознанно выбирай: внутри функции (свой) vs на модуле (общий).
- **«Template ref — нормальный способ менять UI».** Это аварийный люк для фокуса/измерений/
  интеграции. Всё, что можно сделать состоянием — делай состоянием.
- **«`watch` на объект сам следит за вложенными полями».** На `ref(object)`/`reactive` —
  глубокий; на getter, возвращающий объект, нужен `{ deep: true }`. А `{ immediate: true }`
  — чтобы выполнить сразу, не дожидаясь первого изменения.
- **«Гонки запросов — это нормально».** Используй `onCleanup`/`AbortController`, иначе
  устаревший ответ перезапишет свежий.
- **«Composable можно вызвать где угодно, правил хуков же нет».** Почти: если внутри есть
  lifecycle-хуки или `inject`, вызов должен быть синхронным в `setup` — после `await` или
  внутри обработчика они молча не привяжутся.
- **«Composable должен возвращать `reactive` — так удобнее».** Наоборот: `reactive`-объект
  нельзя деструктурировать без потери реактивности. Возвращай `ref`/`computed`.
- **«Свой `useLocalStorage` писать обязательно».** Для учёбы — да, для проекта посмотри
  VueUse: там это уже написано и протестировано.

## Глоссарий модуля

- **Composable** — функция (`useX`), инкапсулирующая реактивное состояние, логику и уборку.
- **Экземпляр на вызов** — состояние объявлено внутри функции: у каждого вызывающего своё.
- **Синглтон на модуле** — состояние объявлено вне функции: общее для всех вызовов.
- **`toRefs` / `toRef`** — превращение свойств реактивного объекта в `ref`-ы.
- **`readonly`** — версия состояния только для чтения.
- **Template ref** — ссылка на реальный DOM-элемент (`useTemplateRef`).
- **`immediate` / `deep`** — опции `watch`: выполнить сразу / следить за вложенным.
- **`onCleanup`** — колбэк отмены предыдущего запуска эффекта (гонки запросов).
- **Функция остановки watcher** — возвращается из `watch`, останавливает наблюдение.
- **Миксин** — устаревший способ переиспользования логики через подмешивание объекта.
- **VueUse** — библиотека готовых composables.
