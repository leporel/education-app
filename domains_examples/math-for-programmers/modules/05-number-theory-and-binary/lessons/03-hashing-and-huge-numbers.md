# Урок 03 — Хеширование по модулю и оценка «насколько велико 2¹²⁸»

## Разогрев

- Хеш-функция отображает произвольные данные в фиксированный диапазон; выбор бакета —
  это `hash mod n`.
- `2¹⁰ ≈ 10³` — приём, которым любую степень двойки переводят в десятичный порядок.
- Простые числа и степени двойки — две конкурирующие стратегии выбора размера таблицы.

## Часть 1. Полиномиальный хеш строки — это модульная арифметика

Классический строковый хеш (тот самый, что в Java у `String.hashCode`, и тот, что лежит в
основе алгоритма Рабина—Карпа):

```text
h(s) = (s₀·bⁿ⁻¹ + s₁·bⁿ⁻² + … + sₙ₋₁·b⁰) mod m
```

Читается так: строку трактуем как число, записанное в системе счисления по основанию b,
где цифры — коды символов, и берём остаток по модулю m. Никакой отдельной «магии хеша»
здесь нет — это позиционная запись из [теории](../theory-2-binary-and-bits.md) плюс `mod`.

Считать это можно схемой Горнера, беря остаток на каждом шаге, чтобы ничего не переполнилось:

```go
func polyHash(s string, b, m uint64) uint64 {
	var h uint64
	for i := 0; i < len(s); i++ {
		h = (h*b + uint64(s[i])) % m // остаток берём на каждой итерации
	}
	return h
}
```

Почему на каждой итерации, а не в конце: без этого `h*b` уже на десятом символе вылезет за
uint64. Правило «остаток можно брать в любой момент» здесь не оптимизация, а условие
работоспособности.

## Часть 2. Почему размер таблицы — простое или степень двойки

Возьмём плохой, но реалистичный случай: ключи — адреса, кратные 16 (указатели на
выровненные структуры).

```text
ключи:   16, 32, 48, 64, 80, 96, …
n = 16 (степень двойки):  k & 15 = 0 для всех     → один бакет, катастрофа
n = 17 (простое):         16%17=16, 32%17=15, 48%17=14, 64%17=13 …
                          → все разные, распределение отличное
```

Простой модуль спасает, потому что остаток по простому p «перемешивает» вклад всех
разрядов: ни один делитель, кроме 1, не может «съесть» структуру ключей. Степень двойки
такого не умеет — она просто отрезает старшие биты.

Значит ли это, что степени двойки плохи? Нет: `& (n−1)` дешевле деления в разы, поэтому
Java, Go-рантайм и почти все высокопроизводительные хеш-таблицы берут степень двойки, но
предварительно **размешивают** хеш, подмешивая старшие биты в младшие:

```go
func mix(h uint32) uint32 { return h ^ (h >> 16) } // упрощённая идея Java HashMap
```

## Часть 3. Насколько велико 2¹²⁸

Оценивать порядки — навык не менее полезный, чем считать точно. Единственный нужный
инструмент: `2¹⁰ = 1024 ≈ 10³`, то есть каждые 10 двоичных разрядов дают примерно 3
десятичных.

```text
2¹²⁸ = 2⁸ · (2¹⁰)¹²        — разложили показатель: 128 = 8 + 120
     ≈ 256 · (10³)¹²        — заменили 2¹⁰ на 10³
     = 2.56 · 10²·10³⁶
     ≈ 3.4 · 10³⁸           — точное значение 3.40282·10³⁸
```

Для UUIDv4 случайных бит не 128, а 122 (шесть уходят на версию и вариант):

```text
2¹²² = 2² · (2¹⁰)¹² ≈ 4·10³⁶      — примерно 5.3·10³⁶ точно
```

Сопоставим с известными величинами:

| Величина | Порядок |
|---|---|
| людей на Земле | 10¹⁰ |
| секунд с Большого взрыва | 10¹⁷ |
| песчинок на всех пляжах Земли | 10¹⁹ |
| звёзд в наблюдаемой Вселенной | 10²² |
| атомов в теле человека | 10²⁷ |
| вариантов UUIDv4 | 10³⁶ |
| вариантов 256-битного хеша | 10⁷⁷ |

Теперь главный практический вопрос: когда ждать коллизию? Полное перечисление не нужно —
достаточно √N генераций (это парадокс дней рождения, разбирается в модуле
[`07-probability`](../../07-probability/index.md)).

```text
√(2¹²²) = 2⁶¹ ≈ 2.3·10¹⁸           — при таком числе UUID шанс коллизии ~50%
при 10⁶ генераций в секунду:
2.3·10¹⁸ / 10⁶ = 2.3·10¹² секунд
2.3·10¹² / (3.15·10⁷ секунд в году) ≈ 73 000 лет
```

Вывод, который стоит унести: «случайных 122 бита достаточно» — не вера, а арифметика.
А вот 64 бита уже не достаточно: √(2⁶⁴) = 2³² ≈ 4.3·10⁹, и миллиард записей приведёт к
коллизиям с заметной вероятностью — именно поэтому короткие «случайные id» в базах болеют.

## Итог

Хеширование — это модульная арифметика, надетая на позиционную запись: строка читается как
число по основанию b, остаток берётся на каждом шаге, чтобы не переполниться. Выбор размера
таблицы — компромисс: простое число само перемешивает биты, степень двойки быстрее, но
требует ручного размешивания. И, наконец, привычка переводить 2ⁿ в десятичные порядки через
`2¹⁰ ≈ 10³` превращает вопросы вроде «хватит ли 128 бит» из мистики в арифметику: хватит,
потому что коллизия ожидается около 2⁶¹ генераций, а это десятки тысяч лет непрерывной работы.
