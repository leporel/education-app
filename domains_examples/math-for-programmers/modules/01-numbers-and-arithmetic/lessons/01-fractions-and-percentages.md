# Урок 01 — Дроби и проценты в реальных задачах

Разминка на том, что встречается каждую неделю: скидки, рост нагрузки, доля ошибок.
Теория — в [`theory.md`](../theory.md), разделы «Вспоминаем школу» и «Точнее».
Здесь мы её применяем, обязательно записывая шаги.

Правило урока: сначала считаем на бумаге, потом сверяемся. Считать в уме «примерно» —
хороший навык, но он тренируется после того, как руки помнят точный способ.

## Задача 1. Скидка на скидку

В магазине акция: «−20% по промокоду, и ещё −10% для подписчиков». Товар стоил 5000 ₽.
Менеджер написал в баннере «−30%». Прав ли он?

```text
после первой скидки:  5000 · (1 − 0.20) = 5000 · 0.8 = 4000
после второй скидки:  4000 · (1 − 0.10) = 4000 · 0.9 = 3600
итоговый множитель:   0.8 · 0.9 = 0.72
итоговая скидка:      1 − 0.72 = 0.28  →  28%, а не 30%
```

Разница в два процентных пункта появилась потому, что вторая скидка считается от уже
уменьшенной цены. Общее правило: **последовательные проценты перемножаются множителями,
а не складываются процентами**.

Проверим кодом:

```go
package main

import "fmt"

func main() {
	price := 5000.0
	final := price * 0.8 * 0.9
	fmt.Println(final)                    // 3600
	fmt.Println((1 - final/price) * 100)  // 28.000000000000004
}
```

Хвост `...004` в выводе — привет от float64; про него будет [третий урок](./03-numbers-in-the-machine.md).

```drill
type: fill-in

check: fuzzy
hint: перемножь 0.9 три раза
```

## Задача 2. Обратный процент

В отчёте написано: «выручка за квартал выросла на 12% и составила 8 736 000 ₽».
Сколько было в прошлом квартале?

Соблазн — вычесть 12% из 8 736 000. Так делать нельзя: 12% считались от **старой**
величины, а не от новой. Правильно решать уравнение.

```text
стало = было · (1 + 0.12)
8736000 = было · 1.12           — подставили
было = 8736000 / 1.12           — разделили обе части на 1.12
было = 7800000                  — посчитали
```

Проверка: 7 800 000 · 1.12 = 8 736 000. Сходится.

А если бы вычли 12%? Получили бы 8 736 000 · 0.88 = 7 687 680 — ошибка больше ста
тысяч на ровном месте. Это самая дорогая ошибка в этом уроке, поэтому запомним
формулу отдельно: **было = стало / (1 + p/100)**.

```drill
type: fill-in
prompt: "Счёт с НДС 20% составил 42000. Какова сумма без НДС?"
answer: "35000"
check: exact
hint: 42000 / 1.2
```

## Задача 3. Доля ошибок и дроби с разными знаменателями

Два сервиса за сутки:

- сервис A: 3 ошибки на 400 запросов;
- сервис B: 5 ошибок на 1200 запросов.

Вопрос: какова общая доля ошибок и у кого хуже?

Сначала общая доля. Складывать 3/400 и 5/1200 напрямую нельзя — это доли от разных
знаменателей, и «сумма долей» тут вообще не то, что нужно. Правильно сложить события
и попытки по отдельности:

```text
всего ошибок  = 3 + 5 = 8
всего запросов = 400 + 1200 = 1600
общая доля = 8/1600 = 1/200 = 0.005 = 0.5%
```

Теперь сравнение сервисов — вот здесь уже нужен общий знаменатель:

```text
A: 3/400  = 9/1200        — умножили числитель и знаменатель на 3
B: 5/1200 = 5/1200        — уже в нужном виде
9/1200 > 5/1200           — сравнили числители
```

У сервиса A доля ошибок выше: 0.75% против 0.417%. Обратите внимание, что B дал
*больше* ошибок в абсолютных числах, но работает лучше — типичная ловушка дашбордов,
где показывают счётчик вместо доли.

```drill
type: fill-in
prompt: "Сервис C: 7 ошибок на 2800 запросов. Какова доля ошибок в процентах?"
answer: "0.25 | 0,25 | 0.25%"
check: fuzzy
```

## Задача 4. Средняя доля — не среднее долей

Продолжим предыдущую задачу. Можно ли получить общую долю ошибок как среднее
арифметическое двух долей?

```text
среднее долей = (0.75% + 0.4167%) / 2 = 0.5833%
настоящая доля = 8/1600 = 0.5%
```

Не совпало. Причина: у сервисов разное количество запросов, и «просто среднее» даёт
им одинаковый вес. Правильное среднее здесь — **взвешенное**, где вес каждой доли —
её знаменатель:

```text
(0.0075·400 + 0.0041667·1200) / (400 + 1200)
= (3 + 5) / 1600            — числители вернулись к исходным ошибкам
= 0.005                     — 0.5%, совпало
```

Это первое появление сюжета, который в курсе будет ещё не раз: усреднять готовые
проценты без учёта весов — почти всегда неверно.

```drill
type: free-form
prompt: "Объясни своими словами, в каком случае среднее арифметическое двух процентов всё-таки даёт правильный общий процент. Приведи пример."
answer: "Только когда знаменатели одинаковы, то есть у обеих долей одинаковый вес. Например, если оба сервиса обработали ровно по 1000 запросов, среднее их долей ошибок совпадёт с общей долей. В остальных случаях нужно взвешенное среднее по числу запросов."
check: manual
```

## Итог

- Последовательные проценты перемножаются множителями: −20% и −10% дают −28%, а не −30%.
- Обратный процент считается делением: было = стало / (1 + p/100). Вычитание здесь даёт неверный ответ.
- Доля ошибок нескольких источников считается как «сумма ошибок / сумма запросов»,
  а не как сумма или среднее долей.
- Абсолютное число ошибок без знаменателя ничего не говорит о качестве.
- Для сравнения дробей приводим к общему знаменателю и смотрим на числители.
