# Урок 01 — Таблицы истинности и чистка условий

## Разогрев

Три вещи из [`theory.md`](../theory.md), которые понадобятся прямо сейчас:

- `¬` — отрицание (`!`), `∧` — «и» (`&&`), `∨` — «или» (`||`); `∨` неисключающее.
- Таблица истинности для `n` переменных имеет ровно `2ⁿ` строк.
- Закон де Моргана: `¬(p ∧ q) = ¬p ∨ ¬q`, `¬(p ∨ q) = ¬p ∧ ¬q`. Отрицание входит
  внутрь скобок и **переворачивает связку**.

## Новая тема

### Как строить таблицу руками

Таблица истинности — это не ритуал, а способ не спорить. Если два выражения совпали во
всех строках, они равносильны; спорить больше не о чем.

Правила, которые экономят время:

1. **Перечисляйте наборы как двоичные числа.** Для `b, v, t` идите от `FFF` к `TTT`,
   как от `000` к `111`. Так вы гарантированно не потеряете строку и не повторите её.
2. **Заводите промежуточные колонки.** Не пытайтесь вычислить всё выражение в уме —
   выпишите отдельные колонки для каждой подскобки. Ошибки почти всегда происходят
   в голове, а не на бумаге.
3. **Идите изнутри наружу**, как при вычислении арифметического выражения.

Три переменные — восемь строк, это всё ещё комфортно руками. Четыре — шестнадцать,
уже утомительно; пишите цикл.

Маленькая хитрость для скорости: колонки для `∧` и `∨` можно не заполнять построчно,
а закрашивать целиком. У `p ∧ q` истинна ровно одна строка из четырёх — та, где оба
`true`; у `p ∨ q` ложна ровно одна — та, где оба `false`; у `p ⇒ q` ложна тоже ровно
одна — `true, false`. Если помнить, где стоит единственное исключение, колонка
заполняется за секунду, а не за четыре.

### Уродливое условие из настоящего кода

Вот такой `if` встречается регулярно — он рос эволюционно, по одной правке за раз:

```go
if !(user.Banned || !user.EmailVerified) && !(user.Banned && user.Trial) {
	allowLogin(user)
}
```

Прочитать его с первого раза невозможно: два отрицания снаружи скобок, одно внутри,
и смешаны `||` и `&&`. Обозначим коротко: `b` = `Banned`, `v` = `EmailVerified`,
`t` = `Trial`. Условие превращается в

```text
¬(b ∨ ¬v) ∧ ¬(b ∧ t)
```

Теперь чистим по шагам. Первое правило чистки: **сначала загнать все отрицания внутрь**,
чтобы не осталось `¬` перед скобкой.

```text
¬(b ∨ ¬v) ∧ ¬(b ∧ t)
= (¬b ∧ ¬(¬v)) ∧ ¬(b ∧ t)     — де Морган в первой скобке: ∨ стало ∧
= (¬b ∧ v) ∧ ¬(b ∧ t)         — двойное отрицание: ¬(¬v) = v
= (¬b ∧ v) ∧ (¬b ∨ ¬t)        — де Морган во второй скобке: ∧ стало ∨
```

Отрицаний перед скобками не осталось. Второе правило: **искать повторяющиеся куски**.
Здесь `¬b` встречается дважды — в первой скобке как множитель, во второй внутри `∨`.
Это ровно узор закона поглощения `p ∧ (p ∨ q) = p`. Перегруппируем, чтобы его увидеть:

```text
(¬b ∧ v) ∧ (¬b ∨ ¬t)
= v ∧ (¬b ∧ (¬b ∨ ¬t))        — коммутативность и ассоциативность ∧
= v ∧ ¬b                      — поглощение: ¬b ∧ (¬b ∨ ¬t) = ¬b
= ¬b ∧ v                      — переставили для читаемости
```

Итог:

```go
if !user.Banned && user.EmailVerified {
	allowLogin(user)
}
```

Переменная `Trial` исчезла полностью — она никогда ни на что не влияла. Такое бывает
чаще, чем хочется: условие с полем, которое давно перестало иметь значение, но
продолжает пугать читателя.

Полезно проговорить, откуда такие условия берутся. Обычно из истории правок: сначала
было `!user.Banned`, потом добавили проверку почты, потом кто-то испугался, что
триальные аккаунты пролезут, и дописал ещё одну скобку — не заметив, что забаненные
уже отсечены первой частью. Каждая правка по отдельности выглядела разумной, а сумма
превратилась в шум. Именно поэтому чистку условий стоит делать не «на глаз», а по
законам: глаз видит намерения автора, а закон — то, что написано.

### Проверяем, а не верим

Восемь строк, три промежуточные колонки:

| b | v | t | b ∨ ¬v | ¬(b ∨ ¬v) | b ∧ t | ¬(b ∧ t) | исходное | ¬b ∧ v |
|---|---|---|---|---|---|---|---|---|
| false | false | false | true | false | false | true | false | false |
| false | false | true | true | false | false | true | false | false |
| false | true | false | false | true | false | true | **true** | **true** |
| false | true | true | false | true | false | true | **true** | **true** |
| true | false | false | true | false | false | true | false | false |
| true | false | true | true | false | true | false | false | false |
| true | true | false | true | false | false | true | false | false |
| true | true | true | true | false | true | false | false | false |

Последние две колонки совпали во всех восьми строках — упрощение корректно.

То же самое кодом, если считать руками не хочется:

```go
vals := []bool{false, true}
for _, b := range vals {
	for _, v := range vals {
		for _, t := range vals {
			before := !(b || !v) && !(b && t)
			after := !b && v
			if before != after {
				fmt.Println("mismatch:", b, v, t)
			}
		}
	}
}
```

Молчание на выходе — это и есть подтверждение. Такой перебор стоит писать всякий раз,
когда вы трогаете нетривиальное условие в чужом коде: пять минут работы против часа
разбирательств с продакшеном.

Одна оговорка, о которой легко забыть. Логическая равносильность обещает одинаковый
**результат**, но не одинаковый порядок вычислений. Если бы `b`, `v`, `t` были не
полями, а вызовами методов, короткое замыкание `&&` и `||` изменило бы, какие из них
вообще выполнятся. Логика в порядке, а количество запросов в базу — нет.


## Итог

Таблица истинности — это инструмент разрешения споров: `2ⁿ` строк, промежуточные
колонки, никакой памяти на приоритеты. Чистка условия делается в два приёма: сначала
загнать все отрицания внутрь скобок законами де Моргана (не забывая переворачивать
связку и снимать двойные отрицания), потом искать повторяющиеся куски и убирать их
поглощением и дистрибутивностью. Результат обязательно проверяется — таблицей или
перебором в коде. И помните про короткое замыкание: равносильные условия могут вызывать
разный набор функций.
