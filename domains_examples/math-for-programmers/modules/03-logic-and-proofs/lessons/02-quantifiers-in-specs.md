# Урок 02 — Кванторы в требованиях и тестах

## Разогрев

Из [`theory.md`](../theory.md) понадобится:

- `∀x P(x)` — «для любого x верно P(x)»; `∃x P(x)` — «существует x, для которого P(x)».
- `¬∀x P(x) = ∃x ¬P(x)`, `¬∃x P(x) = ∀x ¬P(x)` — отрицание проходит внутрь и
  переворачивает квантор.
- `∀` по пустому множеству истинно, `∃` по пустому — ложно.

## Новая тема

### Требование → формула

Формулировки в тикетах пишут по-русски, и по-русски они почти всегда чуть-чуть
двусмысленны. Перевод в кванторы — способ убрать двусмысленность до того, как её
обнаружит продакшен.

Возьмём требование: **«каждый пользователь имеет хотя бы один активный токен»**.

Разбираем по частям:

```text
«каждый пользователь»        → ∀u ∈ Users
«имеет хотя бы один»         → ∃t ∈ Tokens(u)
«активный токен»             → Active(t)
```

Собираем:

```text
∀u ∈ Users  ∃t ∈ Tokens(u)  Active(t)
```

Читается вслух: «для любого пользователя u существует его токен t, который активен».
Порядок кванторов здесь `∀ ∃` — токен свой у каждого пользователя, и это правильно.

### Отрицание требования = условие падения теста

Тест ищет нарушение. Нарушение — это отрицание требования. Отрицаем механически,
по правилам, а не по интуиции:

```text
¬(∀u ∈ Users ∃t ∈ Tokens(u) Active(t))
= ∃u ∈ Users ¬(∃t ∈ Tokens(u) Active(t))    — ¬∀ превратилось в ∃
= ∃u ∈ Users ∀t ∈ Tokens(u) ¬Active(t)      — ¬∃ превратилось в ∀
```

Читается: «существует пользователь, у которого **все** токены неактивны». И вот здесь
включается тот самый краевой случай: `∀` по пустому множеству истинно, значит,
пользователь **вообще без токенов** тоже попадает под это условие. То есть тест обязан
ловить и «все токены протухли», и «токенов нет ни одного» — это один и тот же случай
нарушения, а не два разных.

Обратите внимание, что интуитивное «нашёлся пользователь, у которого есть неактивный
токен» — совсем другое условие и почти всегда ложная тревога: неактивные токены могут
спокойно лежать рядом с активными.

В SQL то же отрицание выглядит так:

```sql
SELECT u.id
FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM tokens t WHERE t.user_id = u.id AND t.active
);
```

`NOT EXISTS` — это буквально `¬∃`, и пользователи без строк в `tokens` найдутся сами
собой, без отдельной ветки в коде.

### Оттенки «хотя бы один»

В требованиях встречаются три близких формулировки, и путать их дорого:

```text
«хотя бы один активный»   → ∃t Active(t)
«ровно один активный»     → ∃t (Active(t) ∧ ∀s (Active(s) ⇒ s = t))
«не более одного»         → ∀t ∀s ((Active(t) ∧ Active(s)) ⇒ t = s)
```

Второе часто сокращают до `∃!t Active(t)` — «существует единственный». Обратите
внимание, что «ровно один» = «хотя бы один» И «не более одного», и проверять в коде
их приходится по-отдельности: подсчитать количество и сравнить с единицей — это
как раз склейка двух условий в одно.

Ещё одна ловушка перевода: слово «если» внутри требования. «Каждый **активный** заказ
имеет оплату» — это не `∀o (Active(o) ∧ Paid(o))`, а
`∀o (Active(o) ⇒ Paid(o))`. Первое требует, чтобы **все** заказы были активны, второе —
только чтобы активные были оплачены. Прилагательное перед существительным почти всегда
означает импликацию внутри квантора, а не конъюнкцию.

### Порядок кванторов меняет смысл требования

Два предложения, отличающиеся порядком слов:

- «для каждого запроса существует обработчик» → `∀r ∃h Handles(h, r)`;
- «существует обработчик для каждого запроса» → `∃h ∀r Handles(h, r)`.

Первое — обычное требование маршрутизации: ни один запрос не остаётся без ответа,
обработчики могут быть разные. Второе — гораздо более сильное: должен быть один
универсальный обработчик, который тянет вообще всё.

Проверить, что это разные утверждения, можно контрпримером из двух элементов:
запросы `r₁`, `r₂`, обработчики `h₁` (умеет только `r₁`) и `h₂` (умеет только `r₂`).
Первая формула истинна, вторая ложна. Одна и та же система, разные ответы — значит,
формулы не равносильны.

Правило на каждый день: **одинаковые кванторы подряд переставлять можно, разные —
нельзя**. И если в требовании стоит `∃ ∀`, стоит переспросить автора: скорее всего,
он имел в виду `∀ ∃`.

### `∀` и `∃` в коде

Кванторы — это два цикла, которые вы писали сотни раз:

```go
func allOf[T any](xs []T, p func(T) bool) bool {
	for _, x := range xs {
		if !p(x) { // контрпример найден — ∀ ложно
			return false
		}
	}
	return true // пустой слайс тоже сюда
}

func anyOf[T any](xs []T, p func(T) bool) bool {
	for _, x := range xs {
		if p(x) { // свидетель найден — ∃ истинно
			return true
		}
	}
	return false // пустой слайс тоже сюда
}
```

Требование целиком превращается в одну строку, читаемую как формула:

```go
ok := allOf(users, func(u User) bool {
	return anyOf(u.Tokens, func(t Token) bool { return t.Active })
})
```

Порядок вложенности функций — тот же, что порядок кванторов: `allOf` снаружи,
`anyOf` внутри. Поменяете местами — получите другое требование, ровно как с
обработчиками выше.

И ещё раз про пустоту, потому что на этом ломаются тесты: `allOf(nil, p)` вернёт `true`.
Если бизнес-логика ожидает «список непустой И все элементы валидны», это **два**
условия, и второе не следует из первого. Пишите `len(xs) > 0 && allOf(xs, p)`, если
пустой список считается ошибкой.

## Итог

Требование переводится в формулу по кускам: «каждый» — `∀`, «хотя бы один» — `∃`,
«если … то» — `⇒`. Условие падения теста получается механическим отрицанием: `¬∀`
становится `∃`, `¬∃` становится `∀`, а `¬(p ⇒ q)` — это `p ∧ ¬q`. Порядок разных
кванторов менять нельзя: `∀ ∃` слабее, чем `∃ ∀`, и путаница между ними — это спор
о том, нужен ли универсальный обработчик или достаточно любого. В коде `∀` и `∃` —
это `allOf` и `anyOf`, и на пустой коллекции они дают `true` и `false` соответственно;
если пустота для вас ошибка, проверяйте `len` отдельно.
