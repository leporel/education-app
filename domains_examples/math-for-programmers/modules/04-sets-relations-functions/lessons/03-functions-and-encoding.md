# Урок 03 — Функции: id, хеши и кодирование

## Разогрев

Из [`theory-2-relations-functions.md`](../theory-2-relations-functions.md):

- `f: A → B` — каждому `a` ровно один `b`. `A` — область определения,
  `B` — область прибытия, образ `f(A) ⊆ B` — то, что реально получается.
- **Инъекция**: `f(x) = f(y) ⇒ x = y`. Разные входы — разные выходы.
- **Сюръекция**: образ покрывает всё `B`.
- **Биекция**: и то, и другое. Только у биекции есть обратная `f⁻¹`.

Сегодня эти три слова получат три очень конкретных рабочих воплощения.

## Часть 1. Генератор id обязан быть инъективным

Генератор идентификаторов — это функция `id: Objects → IDs`. Требование к нему
формулируется одной строкой:

```text
Требование: два разных объекта не должны получить один id.
На языке функций: x ≠ y ⇒ id(x) ≠ id(y)
Это в точности контрапозиция определения инъекции: id(x) = id(y) ⇒ x = y
```

Почему инъекция, а не биекция? Сюръективность не нужна: никто не требует, чтобы
**каждое** 64-битное число когда-нибудь было выдано. Нужно ровно отсутствие склеек.
Отсюда практическая проверка любого генератора: «какие два разных входа могут дать
один выход?»

```text
autoincrement в БД      — инъективен, пока счётчик один и не переиспользуется
UUIDv4 (случайный)      — инъективен «с высокой вероятностью», но не гарантированно
timestamp в секундах    — НЕ инъективен: два объекта в одну секунду склеятся
timestamp + node + seq  — инъективен, если seq не переполняется внутри тика
```

Именно поэтому в snowflake-подобных схемах к времени приписывают номер узла и
счётчик внутри миллисекунды: без них функция «объект → id» перестаёт быть инъективной
ровно там, где нагрузка выше одного объекта в тик.

Есть и жёсткое ограничение сверху: если `|A| > |B|`, инъекции не существует вообще.
Это принцип Дирихле — подробнее в [модуле 06](../../06-combinatorics/index.md).

## Часть 2. Хеш — намеренно неинъективная функция

Хеш-функция `h: Strings → [0, 2⁶⁴)` устроена ровно наоборот: она **не может** быть
инъективной, и это не дефект.

```text
|Strings| — бесконечно (строки любой длины)
|[0, 2⁶⁴)| = 2⁶⁴ — конечно
Инъекция из бесконечного множества в конечное невозможна.
⇒ существуют x ≠ y с h(x) = h(y) — коллизии неизбежны
```

Отсюда сразу два следствия, которые часто путают:

1. **«Расхешировать» нельзя** не потому, что алгоритм хитрый, а потому, что обратной
   функции не существует: у значения много прообразов, и вернуть «тот самый» неоткуда.
2. **Совпадение хешей не означает равенство данных.** Поэтому в хеш-таблице после
   попадания в бакет всё равно сравнивают ключи целиком.

Что от хеша действительно требуется — чтобы прообразы были примерно одинакового
размера (равномерность) и чтобы найти коллизию было трудно. Насколько «редко» бывают
случайные коллизии — вопрос вероятностный, и он разбирается в
[модуле 07](../../07-probability/index.md) вместе с парадоксом дней рождения.

А вот бакеты хеш-таблицы — это уже знакомая эквивалентность: `a ~ b`, если
`h(a) % nbuckets == h(b) % nbuckets`. Классы этого отношения и есть корзины.

```go
// Демонстрация неинъективности на маленьком «хеше»: 8 бакетов.
bucket := func(s string) uint32 {
    var h uint32 = 2166136261
    for i := 0; i < len(s); i++ {
        h = (h ^ uint32(s[i])) * 16777619 // FNV-1a
    }
    return h % 8
}
fmt.Println(bucket("alice"), bucket("bob"), bucket("carol"))
// три ключа на восемь корзин — совпадения появляются очень быстро
```

answer: "Хеш отображает бесконечное множество входов в конечное множество значений, поэтому он не инъективен и у одного значения много прообразов. В map хеш используется только для выбора бакета, а внутри бакета ключи сравниваются целиком — иначе коллизия приводила бы к возврату чужого значения."

## Часть 3. Биекция — это и есть кодирование

Кодировщик и декодировщик — пара взаимно обратных функций, а значит кодирование
обязано быть биекцией.

**base64.** `encode: Bytes → Base64Strings` инъективна (разные байты дают разные
строки) и сюръективна на множество корректных base64-строк. Поэтому
`decode(encode(x)) = x` для любого `x` — это и есть `f⁻¹ ∘ f = id`. Заметьте
формулировку области прибытия: сюръективность выполняется относительно множества
**корректных** base64-строк, а не всех строк вообще. `decode` на произвольной строке
законно возвращает ошибку — эта строка просто не входит в образ.

**Плоский двумерный массив.** Матрица `H × W`, разложенная в один слайс. Пара функций:

```text
toIdx(row, col) = row · W + col
fromIdx(idx)    = (idx / W, idx % W)          — целочисленное деление и остаток

Проверим на W = 5, (row, col) = (3, 2):
  toIdx(3, 2) = 3 · 5 + 2 = 17          — подставили и посчитали
  fromIdx(17) = (17 / 5, 17 % 5)
              = (3, 2)                  — вернулись ровно туда, откуда пришли
```

Почему это биекция, а не «просто формула»:

```text
инъекция:   разные (row, col) дают разные idx, потому что col < W,
            то есть col — это остаток, а row — частное: пара восстанавливается однозначно
сюръекция:  любое idx из [0, H·W) получается из (idx / W, idx % W)
⇒ биекция между {0..H−1} × {0..W−1} и {0, ..., H·W−1}
```

Заодно это доказывает `|A × B| = |A| · |B|` конструктивно: мы предъявили биекцию между
множеством пар и отрезком натуральных чисел длины `H · W`. Модульная арифметика,
на которой всё держится, разбирается в [модуле 05](../../05-number-theory-and-binary/index.md).

Проверка обеих сторон кодом — композиция должна давать тождество:

```go
const H, W = 4, 5

toIdx := func(row, col int) int { return row*W + col }
fromIdx := func(idx int) (int, int) { return idx / W, idx % W }

ok := true
for row := 0; row < H; row++ {
    for col := 0; col < W; col++ {
        r, c := fromIdx(toIdx(row, col)) // (f⁻¹ ∘ f)(row, col)
        ok = ok && r == row && c == col
    }
}
fmt.Println(ok, H*W) // true 20
```

Ту же биекцию стоит увидеть и с другой стороны: она объясняет, почему плоский слайс
почти всегда быстрее `[][]T`. Двумерный слайс — это отдельные аллокации на каждую
строку, разбросанные по памяти; плоский — один непрерывный кусок, по которому
процессор идёт последовательно. Биекция `(row, col) ↔ idx` — это ровно то, что
позволяет сменить представление, ничего не потеряв: раз соответствие взаимно
однозначно, никакая информация при перекладывании не пропадает и не дублируется.
Именно это и есть содержательный смысл слова «биекция» в инженерии — «представление
можно поменять и вернуть обратно».

Обратите внимание, что `W` — ширина — участвует в обеих формулах. Перепутать `W` и `H`
здесь означает получить другую биекцию (транспонированную), которая тоже «работает»,
но раскладывает данные не так, как ожидает остальной код. Обратная функция обязана
знать тот же самый параметр, что и прямая, — иначе это уже не пара.

## Итог

Три свойства функций — это три разных инженерных требования. **Инъективность** —
«без склеек»: её обязан обеспечивать генератор id, и проверяется она вопросом «какие
два разных входа дадут один выход?». Хеш инъективным быть не может в принципе, потому
что отображает бесконечное множество в конечное, — отсюда неизбежные коллизии, отсюда
же невозможность «расхешировать» и необходимость сравнивать ключи внутри бакета.
**Биекция** — это кодирование: у неё, и только у неё, есть корректная обратная
функция, а `decode(encode(x)) = x` — это композиция `f⁻¹ ∘ f = id`. Пара
`idx = row · W + col` и `(idx / W, idx % W)` — самая полезная биекция в повседневном
коде: она же конструктивно доказывает `|A × B| = |A| · |B|`.
