# Урок 02 — Отношения: дедупликация и порядок

## Разогрев

Из [`theory-2-relations-functions.md`](../theory-2-relations-functions.md):

- Отношение — просто множество пар, `R ⊆ A × A`.
- Эквивалентность = рефлексивность + симметричность + транзитивность. Она режет
  множество на непересекающиеся классы.
- Частичный порядок = рефлексивность + антисимметричность + транзитивность.
  Линейный порядок — тот же плюс «любые два элемента сравнимы».

Сегодня обе конструкции решают по одной рабочей задаче: эквивалентность — дедупликацию,
порядок — сортировку и порядок сборки.

## Часть 1. Дедупликация — это классы эквивалентности

Постановка: в базе накопились дубли пользователей. `Ivan@Mail.RU`, `ivan@mail.ru`,
`ivan+github@mail.ru` — это один человек или три? Ответ зависит не от базы, а от того,
какое отношение «считаем одинаковыми» вы выберете.

Пусть `norm(e)` — функция нормализации, и `a ~ b ⟺ norm(a) == norm(b)`. Проверим,
что это эквивалентность:

```text
рефлексивность:  norm(a) == norm(a)                       — верно, равенство рефлексивно
симметричность:  norm(a) == norm(b) ⇒ norm(b) == norm(a)  — верно, равенство симметрично
транзитивность:  norm(a)==norm(b) и norm(b)==norm(c)
                 ⇒ norm(a)==norm(c)                       — верно, равенство транзитивно
Вывод: любое «равенство после нормализации» — отношение эквивалентности.
```

Это очень удобный факт: чтобы получить корректную группировку, достаточно придумать
одну чистую функцию `norm`. Её значение и есть **представитель класса** (каноническая
форма), а сами классы — группы дублей.

```text
norm(e) = strings.ToLower(e)

[ivan@mail.ru] = { Ivan@Mail.RU, ivan@mail.ru, IVAN@mail.RU }
[petr@mail.ru] = { Petr@mail.ru }
Разбиение: каждый адрес попал ровно в один класс, классы не пересекаются.
```

Важная оговорка: `ivan+github@mail.ru` попадёт в отдельный класс, пока `norm` не
научится срезать суффикс после `+`. Расширили `norm` — изменили отношение — изменилось
разбиение. Отношение здесь — ваше продуктовое решение, а не свойство данных.

Код — одна группировка по каноническому ключу:

```go
func classes(items []string, norm func(string) string) map[string][]string {
    out := make(map[string][]string, len(items))
    for _, it := range items {
        out[norm(it)] = append(out[norm(it)], it) // ключ = представитель класса
    }
    return out
}
// classes([]string{"Ivan@Mail.RU", "ivan@mail.ru", "petr@mail.ru"}, strings.ToLower)
// → 2 класса: "ivan@mail.ru" (2 элемента) и "petr@mail.ru" (1 элемент)
```

Опасность ровно одна: если `norm` вычисляется в двух местах по-разному (в записи и в
поиске, в Go и в SQL), транзитивность ломается — `a ~ b`, `b ~ c`, но `a ≁ c`.
Классы начинают «расползаться», и появляются дубли, которые никак не склеиваются.
Каноническую форму нужно считать в одном месте.

Стоит заметить, почему именно транзитивность здесь самая хрупкая. Рефлексивность и
симметричность у «равенства после нормализации» выполняются бесплатно — они достаются
от равенства строк. А вот транзитивность держится на том, что `norm` — **чистая
детерминированная функция одного аргумента**. Как только правило «одинаковости»
становится попарным («похожи, если расстояние Левенштейна ≤ 2»), транзитивность
теряется: `abc` похоже на `abd`, `abd` похоже на `abe`, а `abc` и `abe` — уже нет.
Отношение остаётся рефлексивным и симметричным, но эквивалентностью быть перестаёт,
и «классов» в строгом смысле больше нет — есть только связные компоненты, которые
зависят от порядка обработки. Практический вывод: нечёткое сравнение не заменяет
нормализацию, его результат надо честно называть «кандидатами на объединение».

```drill
type: free-form
prompt: "Предложите norm для телефонных номеров и докажите, что «равенство после norm» — отношение эквивалентности. Затем приведите пример изменения norm, которое склеивает два ранее разных класса."
answer: "Например, norm оставляет только цифры и приводит к формату с кодом страны. Рефлексивность, симметричность и транзитивность наследуются от равенства строк, поэтому свойство выполняется автоматически. Если добавить в norm отбрасывание ведущей восьмёрки в пользу +7, номера «8...» и «+7...» окажутся в одном классе."
check: manual
```

## Часть 2. Порядок: semver — линейный, зависимости — частичный

**Сравнение версий semver** — линейный порядок. Сравниваем покомпонентно:

```text
1.9.0  ≼ 1.10.0 ?
  major: 1 == 1        — идём дальше
  minor: 9 < 10        — решено, 1.9.0 раньше
Строковое сравнение дало бы обратное: "1.9.0" > "1.10.0", потому что '9' > '1'.
Отсюда классический баг «версия 1.10 считается старее 1.9».
```

Любые две различные версии сравнимы — значит, порядок линейный, и `sort` с ним
работает корректно. Проверим свойства явно, чтобы не верить на слово: сравнение
покомпонентно рефлексивно (`v ≼ v`), антисимметрично (если `v ≼ w` и `w ≼ v`, то все
три компонента совпали, то есть это одна и та же версия) и транзитивно (первое
различие в тройке чисел определяет исход одинаково для всех пар). Плюс сравнимость —
любые две тройки чисел можно расставить по порядку. Полный набор — линейный порядок.

Оговорка для честности: у semver есть пререлизные суффиксы (`1.0.0-rc.1`), и правила
их сравнения задаются отдельно в спецификации. Пока эти правила фиксированы, порядок
остаётся линейным; сломать его можно, если сравнивать суффиксы «как получится».

**Граф зависимостей** — частичный порядок. Пусть `a ≼ b` означает «a должен быть
собран не позже b».

```text
Диаграмма (снизу вверх — «раньше → позже»):

              cmd/server
              /        \
        http-api      metrics
            |
        storage
            |
         logger

logger ≼ storage ≼ http-api ≼ cmd/server   — сравнимы
metrics и storage                          — НЕсравнимы: ни одно не зависит от другого
```

Несравнимость здесь не проблема, а информация: независимые пакеты можно собирать в
любом порядке или параллельно. **Топологическая сортировка** выбирает один из
допустимых линейных порядков — например `logger, storage, http-api, metrics, cmd/server`
или `logger, metrics, storage, http-api, cmd/server`. Оба корректны; выбор одного из
многих линейных продолжений — это и есть достройка частичного порядка до линейного.

```drill
type: multiple-choice
prompt: "Отношение «пакет A должен быть собран раньше пакета B» на графе зависимостей — это..."
options: ["отношение эквивалентности", "частичный порядок", "линейный порядок", "ни то, ни другое"]
answer: "частичный порядок"

hint: "два независимых пакета невозможно сравнить"
```

## Часть 3. Что ломается, когда компаратор не задаёт линейный порядок

Функции сортировки (`sort.Slice`, `slices.SortFunc`, `ORDER BY`) предполагают
линейный порядок. Если компаратор его не задаёт, ничего не падает — результат просто
становится непредсказуемым.

```text
Задачи: T1(p=5), T2(p=5), T3(p=1)
Компаратор: less(x, y) = x.Priority < y.Priority

T1 ≼ T2? нет (5 < 5 ложно)
T2 ≼ T1? нет
⇒ T1 и T2 несравнимы — порядок частичный, а не линейный
⇒ их взаимное расположение определяется внутренними решениями алгоритма
⇒ тот же вход может дать разный вывод на разных размерах данных или версиях
```

Два способа починки:

```go
// 1. Добавить вторичный ключ и сделать порядок линейным.
slices.SortFunc(tasks, func(x, y Task) int {
    if c := cmp.Compare(x.Priority, y.Priority); c != 0 {
        return c
    }
    return cmp.Compare(x.ID, y.ID) // теперь любые две разные задачи сравнимы
})

// 2. Взять стабильную сортировку — она сохранит исходный порядок «равных».
slices.SortStableFunc(tasks, func(x, y Task) int {
    return cmp.Compare(x.Priority, y.Priority)
})
```

Стабильность — это ровно способ детерминированно доопределить частичный порядок:
«при равенстве по ключу считаем раньше того, кто раньше стоял». Отдельно стоит помнить
про компараторы вида `return a.X - b.X`: на больших числах разность переполняется, и
«сравнение» перестаёт быть транзитивным. Используйте `cmp.Compare`.

```drill
type: free-form
prompt: "Возьмите слайс из десяти элементов с повторяющимися ключами, отсортируйте его нестабильной и стабильной сортировкой по одному ключу и объясните, какое свойство порядка отвечает за разницу в результатах."
answer: "Элементы с равным ключом несравнимы, поэтому порядок между ними частичный. Нестабильная сортировка вправе расположить их как угодно, стабильная обязана сохранить исходный взаимный порядок — это и есть детерминированное доопределение частичного порядка до линейного."
check: manual
```

## Итог

Отношение — множество пар, и два его вида покрывают огромную часть повседневных задач.
**Эквивалентность** (рефлексивность + симметричность + транзитивность) разбивает данные
на классы: дедупликация — это выбор функции нормализации, а не хитрый алгоритм;
каноническую форму считайте в одном месте, иначе транзитивность ломается.
**Порядок** бывает частичным и линейным: semver сравним всегда, граф зависимостей —
нет, и топологическая сортировка просто выбирает одно из допустимых линейных
продолжений. Сортировка требует линейного порядка; компаратор без вторичного ключа
даёт частичный, а значит невоспроизводимый результат — чините вторичным ключом или
стабильной сортировкой.
