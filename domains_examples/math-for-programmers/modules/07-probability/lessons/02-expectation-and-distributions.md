# Урок 02 — Матожидание, дисперсия и распределения на бэкенд-кейсах

## Разогрев

- `E[X]` — среднее по бесконечному числу повторений; линейность работает всегда.
- `Var(X) = E[X²] − (E[X])²`, `σ = √Var(X)`; дисперсии складываются только у независимых.
- Выбор распределения — по вопросу «что именно мы считаем» (дерево во
  [второй части теории](../theory-2-random-variables-and-distributions.md)).

## Кейс 1. Retry и бюджет времени

Внешний API отвечает успешно с вероятностью p = 0.8. Мы ретраим до успеха, между попытками
пауза 100 мс, сам запрос занимает 200 мс.

```text
X — номер первой успешной попытки → геометрическое(0.8)
E[X] = 1/p = 1.25 попытки
E[время] = E[X]·200 мс + (E[X] − 1)·100 мс
         = 250 + 25 = 275 мс                — линейность матожидания
```

Но среднее — не вся история. Посмотрим на хвост:

```text
P(X > 3) = 0.2³ = 0.008        — 0.8% запросов потребуют больше трёх попыток
P(X > 5) = 0.2⁵ = 0.00032      — 0.032%
время при 5 попытках = 5·200 + 4·100 = 1400 мс
```

Вывод для таймаутов: если SLA обещает p99 в 600 мс, ретраи «до победного» его нарушат.
Ограничение в 3 попытки закрывает 99.2% случаев — это и есть инженерное решение, выведенное
из распределения.

```drill

answer: "2 и 0.0625 | 2, 1/16"
check: fuzzy

```

## Кейс 2. Сколько машин выдержит нагрузку

Поток запросов пуассоновский, в среднем λ = 900 запросов в секунду. Одна машина держит 100
RPS, и мы хотим, чтобы перегрузка случалась реже, чем раз в час.

```text
E[X] = 900, Var(X) = 900, σ = √900 = 30
раз в час = 1 из 3600 секунд ≈ 0.00028 вероятность
это примерно 3.5σ вправо (для 3σ вероятность ≈ 0.0013, для 3.5σ ≈ 0.00023)
запас: 900 + 3.5·30 = 1005 запросов в пиковую секунду
машин: 1005 / 100 = 10.05 → 11 машин
```

Наивный расчёт «900/100 = 9 машин» промахивается на два узла. Причём заметьте: относительный
разброс `σ/λ = 1/√λ` **падает** с ростом нагрузки. При λ = 9 (девять запросов в секунду)
σ = 3, то есть 33% разброса — маленькие сервисы «дёрганее» больших. Это неочевидное, но
очень практичное следствие свойства Пуассона `Var = λ`.

```drill
type: fill-in
prompt: "Поток пуассоновский со средним 2500 запросов в секунду. Чему равно σ и какой это процент от среднего?"
answer: "50 и 2% | 50, 2%"
check: fuzzy
hint: "σ = √λ, доля = 1/√λ"
```

## Кейс 3. Суммарная задержка и почему появляется колокол

Запрос проходит 10 независимых стадий, каждая занимает случайное время со средним 20 мс и
σ = 6 мс.

```text
E[сумма] = 10 · 20 = 200 мс                    — линейность, всегда
Var(сумма) = 10 · 36 = 360                     — только из-за независимости
σ(сумма) = √360 ≈ 19 мс                        — НЕ 10·6 = 60!
```

Ключевой момент: складываются **дисперсии**, а не сигмы. Поэтому относительный разброс суммы
меньше, чем у слагаемых: 19/200 ≈ 9.5% против 6/20 = 30%. По ЦПТ сумма ещё и приближённо
нормальна, значит здесь правило трёх сигм работает: p99.7 ≈ 200 + 3·19 = 257 мс.

Важная оговорка: всё это верно, пока стадии **независимы**. Если все они делят один
перегруженный пул соединений, дисперсии сложатся с плюсом на ковариацию, и хвост окажется
куда толще предсказанного.

## Кейс 4. Линейность там, где комбинаторика бессильна

Задача: n ключей равномерно раскладываются по n бакетам. Сколько бакетов останется пустыми?

Считать «в лоб» — кошмар: события «бакет пуст» зависимы. Но матожидание линейно **всегда**:

```text
Iⱼ = 1, если бакет j пуст, иначе 0
P(Iⱼ = 1) = (1 − 1/n)ⁿ ≈ e^(−1) ≈ 0.368
E[пустых] = Σ E[Iⱼ] = n · 0.368
при n = 1000: ≈ 368 пустых бакетов
```

Треть таблицы простаивает, и это не дефект хеш-функции, а свойство случайного равномерного
распределения. Тот же приём (индикаторы + линейность) решает половину задач про ожидания.

```drill

  - "потому что линейность матожидания не требует независимости"
  - "потому что бакетов много"
  - "нельзя, это приближение"

```

## Кейс 5. Проверяем всё симуляцией

Любое утверждение выше проверяется десятком строк на Go.

```go
import "math/rand/v2"

// Среднее время серии retry при вероятности успеха p.
func retryLatency(p float64, reqMs, pauseMs float64, trials int) float64 {
	total := 0.0
	for range trials {
		attempts := 0
		for {
			attempts++
			if rand.Float64() < p {
				break
			}
		}
		total += float64(attempts)*reqMs + float64(attempts-1)*pauseMs
	}
	return total / float64(trials)
}
// retryLatency(0.8, 200, 100, 1_000_000) ≈ 275
```

И проверка «пустых бакетов»:

```go
func emptyBuckets(n, trials int) float64 {
	total := 0
	for range trials {
		used := make([]bool, n)
		for i := 0; i < n; i++ {
			used[rand.IntN(n)] = true
		}
		for _, u := range used {
			if !u {
				total++
			}
		}
	}
	return float64(total) / float64(trials)
}
// emptyBuckets(1000, 100) ≈ 368
```

```drill
answer: "Складываются дисперсии, а не стандартные отклонения: Var(сумма) = 10·σ², значит σ(сумма) = √10·σ. Отклонения стадий частично компенсируют друг друга, поэтому относительный разброс суммы меньше, чем у слагаемого. Если стадии зависимы (общий пул соединений, общая база, общий GC-паузы), к сумме дисперсий добавляются положительные ковариации, σ растёт быстрее √10 и в пределе полной зависимости достигает 10·σ — хвост оказывается заметно толще предсказанного."
check: manual
```

## Итог

Матожидание отвечает на «сколько в среднем», дисперсия — на «насколько разбросано», и
инженерные решения принимаются по второму, а не по первому. Линейность матожидания работает
всегда и превращает страшные задачи в сумму индикаторов; дисперсии складываются только у
независимых величин, и именно поэтому σ суммы растёт как √n. Выбор распределения делается по
вопросу «что именно я считаю»: попытки до успеха — геометрическое, события за интервал —
Пуассон, время до события — экспоненциальное, сумма многих — нормальное. И всё это
проверяется симуляцией за десять строк. Дальше —
[урок 03](./03-birthday-collisions-availability.md), где мы посчитаем коллизии и доступность
кластера.
