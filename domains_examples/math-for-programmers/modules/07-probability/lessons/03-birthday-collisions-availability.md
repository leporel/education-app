# Урок 03 — Дни рождения, коллизии и доступность N реплик

## Разогрев

- «Хотя бы один» считается через дополнение: `1 − P(ни одного)`.
- Независимые события перемножаются: `P(все живы) = pⁿ`.
- Коллизии в пространстве размера N ждут около `√N` генераций, а не около N.

## Часть 1. Парадокс дней рождения шаг за шагом

Вопрос: сколько человек нужно в комнате, чтобы вероятность совпадения дней рождения
превысила 50%? Интуиция говорит «около 180». Посчитаем.

```text
считаем через дополнение — вероятность, что все дни рождения различны
1-й человек: любой день                  365/365
2-й: любой, кроме занятого               364/365
3-й: любой из оставшихся                 363/365
…
k-й:                                     (365 − k + 1)/365

P(все различны) = (365/365)·(364/365)·…·((365−k+1)/365)
```

Для k = 23:

```text
P(все различны) ≈ 0.4927
P(есть совпадение) = 1 − 0.4927 = 0.5073
```

Двадцать три. Почему интуиция промахивается так сильно: мы бессознательно считаем пары
«я и кто-то», а надо считать **все** пары. Среди 23 человек пар C(23,2) = 253 — вот это
число и близко к половине от 365.

```text
приближение:
ожидаемое число совпадающих пар ≈ C(k,2)/N = k(k−1)/(2N)
при k = 23, N = 365: 253/365 ≈ 0.69      — порядка единицы, совпадение вероятно
общая формула: P(коллизия) ≈ 1 − e^(−k²/(2N)), 50% при k ≈ 1.177·√N
```

## Часть 2. Переносим на хеши и id

Правило `k ≈ 1.177·√N` — универсальное. Подставим реальные пространства:

| Пространство | N | 50% коллизия около | Комментарий |
|---|---|---|---|
| 32-битный хеш | 4.3·10⁹ | 77 000 | ловится за секунды |
| 64-битный id | 1.8·10¹⁹ | 5.1·10⁹ | достижимо для крупного сервиса |
| 128-битный MD5 | 3.4·10³⁸ | 2.2·10¹⁹ | но MD5 сломан не перебором |
| UUIDv4 (122 бита) | 5.3·10³⁶ | 2.7·10¹⁸ | недостижимо |
| SHA-256 | 1.2·10⁷⁷ | 4.0·10³⁸ | недостижимо принципиально |

Отсюда практическое правило: **стойкость хеша к коллизиям равна половине его длины в
битах**. 256-битный хеш даёт 128 бит стойкости к коллизиям — именно поэтому SHA-256, а не
SHA-128.

## Часть 3. Доступность N реплик

Два разных вопроса, две разные формулы.

**Все компоненты нужны** (последовательная схема, микросервисная цепочка):

```text
P(система работает) = pⁿ
p = 0.999, n = 10:  0.999¹⁰ ≈ 0.990        — «три девятки» превратились в две
простой в месяц: (1 − 0.990)·730 ч ≈ 7.3 часа
```

**Достаточно одного** (реплики, резервирование):

```text
P(система работает) = 1 − (1−p)ⁿ
p = 0.99, n = 3:  1 − 0.01³ = 0.999999      — «две девятки» стали шестью
```

Резервирование даёт экспоненциальный выигрыш, последовательная зависимость — экспоненциальный
проигрыш. Отсюда главное архитектурное правило: **сокращайте число компонентов в критическом
пути и дублируйте те, что остались**.

Оговорка, без которой формулы врут: они предполагают **независимость** отказов. Три реплики
в одной стойке, на одном питании или с общим деплоем падают вместе — тогда реальная
доступность ближе к однократной p, чем к 1 − (1−p)³.

## Часть 4. Симуляция на Go

Аналитика хороша, но проверка убеждает лучше. Одна функция закрывает оба вопроса урока.

```go
import "math/rand/v2"

// Доля прогонов, в которых среди k случайных значений из space нашлось совпадение.
func birthday(space, k, trials int) float64 {
	hits := 0
	for range trials {
		seen := make(map[int]struct{}, k)
		for i := 0; i < k; i++ {
			v := rand.IntN(space)
			if _, dup := seen[v]; dup {
				hits++
				break
			}
			seen[v] = struct{}{}
		}
	}
	return float64(hits) / float64(trials)
}
// birthday(365, 23, 200_000) ≈ 0.507
```

Доступность:

```go
// mode "all" — нужны все n; mode "any" — достаточно одного.
func availability(p float64, n int, all bool, trials int) float64 {
	ok := 0
	for range trials {
		alive := 0
		for i := 0; i < n; i++ {
			if rand.Float64() < p {
				alive++
			}
		}
		if (all && alive == n) || (!all && alive > 0) {
			ok++
		}
	}
	return float64(ok) / float64(trials)
}
// availability(0.99, 3, false, 1_000_000) ≈ 0.999999
// availability(0.999, 10, true, 1_000_000) ≈ 0.990
```

Обратите внимание на точность симуляции: чтобы надёжно измерить вероятность 10⁻⁶, миллиона
прогонов уже мало — в среднем произойдёт всего один «плохой» исход. Правило: чтобы оценить
вероятность p, нужно порядка `100/p` прогонов. Это прямое следствие того, что относительная
погрешность Монте-Карло падает как 1/√(число событий).

## Итог

Два правила, которые стоит унести из урока. Первое: коллизии приходят на √N, потому что
растёт число пар, а не число значений; отсюда «стойкость хеша к коллизиям — половина длины в
битах». Второе: последовательные зависимости перемножают доступность и съедают девятки, а
резервирование перемножает **вероятности отказа** и девятки добавляет — но только при
независимости отказов, которая в одном дата-центре обычно фикция. И то и другое проверяется
симуляцией, но у симуляции есть предел: редкие события надо считать аналитически.
