# Урок 03 — Экспонента и логарифм в рабочих задачах

Теория к уроку: [`theory-2-functions-and-logarithms.md`](../theory-2-functions-and-logarithms.md).

Пять задач, которые встречаются в работе постоянно. Все пять — одна и та же пара
операций: **экспонента отвечает «сколько станет через n шагов», логарифм отвечает
«сколько шагов до этого значения»**.

## Задача 1. Время удвоения

Трафик растёт на 8% в месяц. Через сколько месяцев он удвоится?

Рост на 8% — это умножение на `1.08` каждый месяц, то есть `1.08ⁿ` после `n` месяцев.

```text
1.08ⁿ = 2               — хотим удвоение
n = log_1.08 2          — по определению логарифма
n = ln 2 / ln 1.08      — перешли к другому основанию
n = 0.6931 / 0.07696    — подставили значения
n ≈ 9.0                 — посчитали
```

Примерно девять месяцев. Отсюда же и «правило 70», которым удобно считать в уме: время
удвоения при росте `p` процентов за шаг примерно равно `70/p` шагов. Здесь `70/8 ≈ 8.75`,
что близко к точным 9.0. Работает правило потому, что `ln 2 ≈ 0.693`, а `ln(1 + x) ≈ x`
при малых `x`.

Проверка: `1.08⁹ = 1.999`. Действительно почти ровно два раза.

```drill

answer: "7"
```

## Задача 2. Полураспад и затухание TTL

Обратная сторона той же монеты. Кэш теряет актуальность: каждый час остаётся 90% ещё
годных записей. Через сколько часов останется меньше 10%?

```text
0.9ᵗ < 0.1              — доля годных записей через t часов
ln(0.9ᵗ) < ln 0.1       — взяли логарифм от обеих частей
t · ln 0.9 < ln 0.1     — по закону логарифма степени
t > ln 0.1 / ln 0.9     — разделили на ln 0.9, а это ОТРИЦАТЕЛЬНОЕ число: знак перевернулся
t > (−2.3026)/(−0.1054) — подставили значения
t > 21.85               — посчитали
t = 22                  — часы целые, округлили вверх
```

Здесь встретились сразу два сюжета модуля: закон `log(xⁿ) = n·log x` и переворот знака
неравенства при делении на отрицательное число. `ln 0.9` отрицателен, потому что `0.9`
меньше единицы — логарифм числа меньше 1 всегда отрицателен.

Проверка: `0.9²¹ = 0.109` (ещё больше 10%), `0.9²² = 0.098` (уже меньше). Граница
найдена верно.

## Задача 3. Сколько бит нужно для N значений

`b` бит дают `2ᵇ` различных комбинаций. Значит, чтобы закодировать `N` значений, нужно
наименьшее `b`, при котором `2ᵇ ≥ N`.

```text
2ᵇ ≥ N
b ≥ log₂ N              — по определению логарифма
b = ⌈log₂ N⌉            — b целое, округляем вверх
```

Запись `⌈x⌉` — «потолок», округление вверх до целого (подробнее в
[`01-numbers-and-arithmetic`](../../01-numbers-and-arithmetic/theory.md)).

Для `N = 1000`: `log₂ 1000 ≈ 9.97`, значит нужно `10` бит. Для `N = 1024` ровно
`log₂ 1024 = 10`, тоже 10 бит. А для `N = 1025` — уже 11: одно лишнее значение стоит
целого бита.

В коде лучше считать это целочисленно, без вещественной арифметики:

```go
package main

import (
	"fmt"
	"math/bits"
)

// bitsNeeded returns ceil(log2(n)) for n >= 1.
func bitsNeeded(n uint) int {
	if n <= 1 {
		return 0
	}
	return bits.Len(n - 1)
}

func main() {
	for _, n := range []uint{2, 1000, 1024, 1025} {
		fmt.Println(n, bitsNeeded(n))
	}
}
```

## Задача 4. Сколько шагов делает бинарный поиск

Каждый шаг бинарного поиска выбрасывает половину оставшегося диапазона: `n`, `n/2`,
`n/4`, ... Поиск заканчивается, когда осталось не больше одного элемента.

```text
n / 2ᵏ ≤ 1              — после k шагов осталось n/2ᵏ элементов
n ≤ 2ᵏ                  — умножили обе части на 2ᵏ, знак сохранился (2ᵏ > 0)
k ≥ log₂ n              — по определению логарифма
k = ⌈log₂ n⌉            — шаги целые
```

Та же формула, что и для битов, — и это не совпадение. Каждый шаг бинарного поиска даёт
один бит информации: «левее или правее». Чтобы различить `n` вариантов, нужно `⌈log₂ n⌉`
бит, значит и столько же вопросов.

Ощутить масштаб: для миллиона элементов `log₂ 1 000 000 ≈ 19.9`, то есть 20 шагов.
Для миллиарда — 30. Увеличили данные в тысячу раз, добавили десять шагов. Именно
поэтому логарифмическая сложность считается «практически бесплатной»; подробный разбор
классов роста — в
[`09-growth-and-calculus-intuition`](../../09-growth-and-calculus-intuition/index.md).

```drill

answer: "20"
check: exact
hint: "2¹⁰ ≈ 1000, значит 2²⁰ ≈ 1 000 000"
```

## Задача 5. Экспоненциальный retry backoff

Классическая схема повторов: задержка удваивается после каждой неудачи.

```text
delay(k) = base · 2ᵏ        — задержка перед попыткой номер k, считая с нуля
```

При `base = 100 мс` получаем `100, 200, 400, 800, 1600, 3200, ...` миллисекунд.
Суммарное ожидание после `k` попыток — `base · (2ᵏ − 1)`, потому что
`1 + 2 + 4 + ... + 2ᵏ⁻¹ = 2ᵏ − 1`.

Практический вопрос: сколько попыток поместится в бюджет 30 секунд при `base = 100 мс`?

```text
100 · (2ᵏ − 1) ≤ 30000
2ᵏ − 1 ≤ 300           — разделили обе части на 100
2ᵏ ≤ 301               — прибавили 1
k ≤ log₂ 301           — по определению логарифма
k ≤ 8.23               — посчитали
k = 8                  — попытки целые, округляем ВНИЗ: бюджет нельзя превысить
```

Обратите внимание на направление округления: в задаче про биты мы округляли вверх
(«надо хватить»), здесь — вниз («нельзя выйти за лимит»). Направление всегда диктует
смысл задачи, а не формула.

Обычно к такой схеме добавляют верхний потолок задержки и случайный разброс (jitter),
чтобы клиенты не приходили обратно одновременно, — но это уже про распределённые
системы, а не про алгебру.

```drill
type: free-form
prompt: "Задержка повторов растёт как 50 мс · 3ᵏ. Выведите формулу для числа попыток k, помещающихся в бюджет T миллисекунд, и посчитайте k для T = 20000. Объясните, почему здесь округление вниз."
answer: "Сумма задержек 50·(3ᵏ − 1)/2 ≤ T, отсюда 3ᵏ ≤ 2T/50 + 1 и k ≤ log₃(2T/50 + 1) = ln(2T/50 + 1)/ln 3. Для T = 20000: 2T/50 + 1 = 801, ln 801/ln 3 ≈ 6.69/1.0986 ≈ 6.08, значит k = 6. Округление вниз, потому что бюджет — верхняя граница: седьмая попытка уже не поместится."
check: manual
```

## Итог

- Экспонента отвечает «сколько станет через `n` шагов», логарифм — «сколько шагов до
  этого значения». Это взаимно обратные операции.
- Время удвоения при росте `p` процентов за шаг ≈ `70/p` шагов; точная формула —
  `ln 2 / ln(1 + p/100)`.
- Затухание — та же экспонента с основанием меньше единицы. Логарифм такого основания
  отрицателен, поэтому при делении на него **знак неравенства переворачивается**.
- «Сколько бит для `N` значений» и «сколько шагов у бинарного поиска» — одна формула
  `⌈log₂ N⌉`, потому что каждый шаг поиска даёт ровно один бит информации.
- В коде целочисленный `bits.Len(n-1)` надёжнее, чем `math.Ceil(math.Log2(...))`:
  у второго бывает ошибка округления на границах степеней двойки.
- Направление округления задаёт смысл задачи: «должно хватить» — вверх, «нельзя
  превысить бюджет» — вниз.
