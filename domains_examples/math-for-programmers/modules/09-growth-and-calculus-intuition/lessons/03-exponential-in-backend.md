# Урок 03 — Экспонента в бэкенде: backoff, EWMA, протухание, прогноз роста

## Разогрев

- **Рост**: `N(t) = N₀·e^(rt)`; **затухание**: `N(t) = N₀·e^(−λt)`.
- **Правило 70**: время удвоения ≈ `70 / процент роста за период`.
- **Half-life**: `T½ = ln 2 / λ`.
- **EWMA**: `avg ← α·x + (1 − α)·avg`, окно памяти ≈ `1/α`.

Теория — [`theory-2-calculus.md`](../theory-2-calculus.md), раздел
«Экспоненциальный рост и затухание».

## Новая тема: четыре места, где экспонента приходит сама

Экспонента появляется всегда, когда **скорость изменения пропорциональна текущему
значению**. В бэкенде это происходит чаще, чем кажется.

1. **Retry-политики.** Каждая неудачная попытка удваивает паузу — иначе клиенты
   добивают падающий сервис.
2. **Скользящие средние в мониторинге.** Load average, EWMA-латентность, скользящий
   error rate — все они «забывают» прошлое экспоненциально.
3. **Протухание значений.** TTL-кеш, decay скоринга в антифроде, «свежесть» поста в
   ленте — вес события падает как `e^(−λt)`.
4. **Планирование ёмкости.** «Растём на 8 % в месяц» — это не линия, это удвоение за
   девять месяцев.

Разберём каждое числом.

## Разобранные примеры

### Пример 1. Backoff: сколько ждём и сколько всего

`base = 100 мс`, `cap = 30 с`, попытки нумеруются с `k = 0`.

```text
k=0:  100·2⁰ = 100 мс
k=1:  100·2¹ = 200 мс
k=2:  100·2² = 400 мс
k=3:  800 мс
k=4:  1.6 с
k=5:  3.2 с
k=6:  6.4 с
k=7:  12.8 с
k=8:  25.6 с
k=9:  min(30, 51.2) = 30 с      — сработал cap
```

Суммарное ожидание за первые 8 попыток — сумма геометрической прогрессии:

```text
S = base·(2⁸ − 1)/(2 − 1)       — формула суммы геометрической прогрессии
  = 100 мс · 255                — 2⁸ = 256
  = 25.5 с                      — почти всё ожидание приходится на последние две попытки
```

Полезное правило: **суммарное время backoff примерно равно удвоенной последней паузе**.
Поэтому, если у вас дедлайн 10 секунд, ставить `maxRetries = 10` бессмысленно — до
десятой попытки дело всё равно не дойдёт.

С full jitter каждая пауза становится `random(0, delay)`, то есть в среднем вдвое
меньше, зато клиенты перестают ходить строем.

### Пример 2. EWMA: подбираем α под нужное окно

Хотим среднюю латентность «примерно за последние 100 запросов». Окно памяти EWMA ≈ `1/α`,
значит `α = 0.01`.

Посмотрим, как EWMA реагирует на скачок. Было стабильно 50 мс, сервис деградировал и все
последующие запросы идут по 200 мс:

```text
avg₀ = 50
avg₁ = 0.01·200 + 0.99·50   = 51.5
avg₂ = 0.01·200 + 0.99·51.5 = 53.0
...
отклонение падает как 0.99ᵏ·150     — экспоненциальное затухание разницы
половина пути пройдена при 0.99ᵏ = 0.5
k = ln 0.5 / ln 0.99 ≈ 69 запросов  — время «полуреакции»
```

Вывод, который стоит записать: **EWMA с α = 0.01 узнаёт о деградации только через
несколько десятков запросов**. Если алерт должен срабатывать быстро — нужен больший `α`
(и больше ложных срабатываний). Это честный компромисс «чувствительность против шума»,
и он выражается одним числом.

### Пример 3. Протухание скоринга

Правило: «подозрительность аккаунта уменьшается вдвое каждые 3 дня». Значит

```text
T½ = 3 дня
λ = ln 2 / 3 ≈ 0.231 (1/день)      — из формулы T½ = ln 2 / λ
score(t) = score₀ · e^(−0.231·t)
```

Сколько останется от 100 баллов через неделю?

```text
score(7) = 100 · e^(−0.231·7)      — подставили t = 7
         = 100 · e^(−1.617)        — перемножили
         ≈ 100 · 0.1985            — значение экспоненты
         ≈ 19.9 балла
```

Проверка здравым смыслом: 7 дней — это чуть больше двух периодов полураспада
(3 + 3 = 6), значит должно остаться чуть меньше `100/4 = 25`. Получили 19.9 — сходится.

Практический трюк: не пересчитывайте затухание по таймеру для каждого аккаунта. Храните
`score` и `updatedAt`, а при чтении домножайте на `e^(−λ·Δt)`. Это тот же результат, но
`O(1)` работы вместо фонового обхода всей таблицы.

### Пример 4. Прогноз роста и правило 70

Хранилище: сейчас 4 ТБ данных, лимит диска 20 ТБ, рост 8 % в месяц. Когда упрёмся?

```text
4·(1.08)^t = 20                    — условие «заполнили диск»
(1.08)^t = 5                       — поделили на 4
t·ln 1.08 = ln 5                   — взяли ln от обеих частей
t = ln 5 / ln 1.08                 — выразили t
  = 1.6094 / 0.07696               — значения логарифмов
  ≈ 20.9 месяца
```

Быстрая прикидка правилом 70: удвоение за `70/8 ≈ 8.75` месяца. Нужно вырасти в 5 раз,
то есть чуть больше двух удвоений (в 4 раза) — примерно `2.3 · 8.75 ≈ 20` месяцев. Тот
же ответ за пятнадцать секунд без калькулятора.

### Пример 5. Всё вместе в Go

```go
// Затухание скора «по требованию»: считаем на момент чтения, а не по таймеру.
func decayedScore(score float64, updatedAt time.Time, halfLife time.Duration) float64 {
	lambda := math.Ln2 / halfLife.Hours()
	dt := time.Since(updatedAt).Hours()
	return score * math.Exp(-lambda*dt)
}

// Время до заполнения диска при экспоненциальном росте.
func monthsUntilFull(current, limit, monthlyRate float64) float64 {
	return math.Log(limit/current) / math.Log(1+monthlyRate)
}

// monthsUntilFull(4, 20, 0.08) → 20.91
```

## Итог

Экспонента — рабочий инструмент, а не абстракция. Backoff: `min(cap, base·2^k)`, и
суммарное ожидание примерно вдвое больше последней паузы. EWMA: `α` — единственная
ручка, она одновременно задаёт окно памяти `1/α` и скорость реакции. Протухание: держите
`value` и `updatedAt`, домножайте на `e^(−λΔt)` при чтении, `λ = ln 2 / T½`. Планирование
роста: `t = ln(во сколько раз) / ln(1 + процент)`, а для прикидки в голове хватает
правила 70. Во всех четырёх случаях математика одна и та же — меняются только имена
переменных в тикете.
