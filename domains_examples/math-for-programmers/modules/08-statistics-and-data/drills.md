## Объяснить своими словами

```drill
type: free-form
prompt: "Объясните, почему средняя латентность — плохая метрика для алертов, и что стоит использовать вместо неё."
answer: "Латентность скошена вправо: подавляющее большинство запросов быстрые, а хвост длинный. Среднее лежит между медианой и хвостом и не описывает ни типичного пользователя, ни пострадавшего; рост p99 в тридцать раз может поднять среднее лишь вдвое и не пробить порог алерта. Использовать надо перцентили (p50 для типичного случая, p95/p99 для хвоста), считая их из гистограмм, а также следить за долей запросов, превысивших SLO."
check: manual
```

```drill
type: free-form
prompt: "Команда запустила A/B-тест, на третий день увидела p = 0.04 и остановила эксперимент, объявив победу. Перечислите проблемы этого решения."
answer: "Во-первых, подглядывание: ежедневная проверка с остановкой при первом p < 0.05 раздувает долю ложных срабатываний с 5% до 20–30%, потому что даёт много попыток поймать случайное отклонение. Во-вторых, размер выборки, скорее всего, не рассчитывался заранее, значит мощность теста неизвестна. В-третьих, значимость не равна размеру эффекта: надо смотреть доверительный интервал разницы и оценивать, окупает ли нижняя граница интервала стоимость изменения. Правильный порядок — заранее задать MDE, посчитать n, дождаться его и только потом анализировать, либо применить последовательный тест с корректным alpha spending."
check: manual
```

```drill
type: free-form
prompt: "Нагрузочный тест показывает отличный p99, но пользователи жалуются на таймауты. Назовите две статистические причины такого расхождения."
answer: "Первая — ошибка выжившего: запросы, упавшие по таймауту, не попали в гистограмму латентности, поэтому она описывает только успешные и выглядит тем лучше, чем больше отказов. Вторая — coordinated omission: генератор нагрузки ждёт ответа перед отправкой следующего запроса, поэтому во время затыка он просто не отправляет запросы и не измеряет самое плохое время; реальная очередь на стороне пользователя при этом растёт. Лечится измерением по расписанию отправки, а не по факту ответа, и обязательным учётом ошибок и таймаутов как замеров с максимальным временем."
check: manual
```

```drill
type: free-form
prompt: "Объясните на пальцах, почему для уточнения оценки вдвое нужно вчетверо больше данных, и какой практический вывод из этого следует для сбора метрик."
answer: "Стандартная ошибка равна s/√n, то есть падает как корень из объёма выборки. Чтобы разделить её на 2, нужно увеличить √n вдвое, а значит n — вчетверо. Практический вывод: точность дорожает квадратично, поэтому нет смысла собирать больше данных ради косметического уточнения; выгоднее уменьшать s (снижать разброс самих измерений, разделять разнородные сегменты) или заранее решать, какая точность действительно нужна, и не платить за большую."
check: manual
```
