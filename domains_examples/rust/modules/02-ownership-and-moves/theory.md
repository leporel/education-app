# Владение и перемещения

## Проблема, которую решает владение

Любой язык должен ответить на вопрос: **когда освобождать память?** Три исторических ответа:

1. **Вручную** (C): ты сам зовёшь `free`. Мощно и быстро, но ошибиться легко: забыл —
   утечка; освободил дважды — крэш; держишь указатель на освобождённое — use-after-free.
2. **Сборщик мусора** (Go, Java): рантайм сам находит мусор и убирает. Безопасно, но есть
   паузы, накладные расходы и непредсказуемость момента освобождения.
3. **Владение** (Rust): компилятор по правилам владения **сам вставляет освобождение** в
   нужную точку, и доказывает на компиляции, что ошибок памяти нет. Ни ручного `free`, ни
   GC. Это третий путь, и он — фундамент всего Rust.

## Правила владения

Их три, и они короткие:

1. У каждого значения есть **владелец** (переменная).
2. В каждый момент времени владелец **ровно один**.
3. Когда владелец выходит из **области видимости** (scope), значение **сбрасывается**
   (drop) — память освобождается.

```rust
fn main() {
    let s = String::from("hello");   // s — владелец строки в куче
    // ... пользуемся s ...
}                                    // s выходит из scope → строка освобождается ЗДЕСЬ
```

Никто не звал `free`, никакой GC не пробегал. Компилятор **на этапе компиляции** знал, что
в конце блока `s` умирает, и вставил вызов освобождения. Это называется **RAII** (resource
acquisition is initialization, привет из C++): ресурс живёт ровно столько, сколько его
владелец.

> **Аналогия с Go.** Самое близкое в Go — `defer file.Close()`: ты привязываешь очистку
> к области видимости. Разница в том, что в Rust это **автоматически для всего** (память,
> файлы, сокеты, мьютексы), без ручного `defer`, и гарантировано компилятором. Освобождение
> детерминировано: ты точно знаешь, в какой точке оно произойдёт, в отличие от «когда-нибудь
> придёт GC».

## Стек и куча — простыми словами

Дальше будет много «на стеке» и «в куче». В Go это можно было не знать (компилятор решал
сам), в Rust — нельзя. Разберёмся один раз и по-человечески.

**Стек (stack)** — блокнот, в который пишут только с конца. Когда функция вызывается, она
получает на стеке кадр (frame) под свои локальные переменные; когда возвращается — кадр
просто отрезается. Отсюда свойства: работа со стеком почти бесплатна (сдвинуть указатель),
но **размер каждого значения должен быть известен на компиляции**, и данные живут ровно
столько, сколько живёт вызов функции.

**Куча (heap)** — большой склад, у которого есть кладовщик (аллокатор). Просишь: «дай мне
место на 40 байт» — он ищет свободный кусок, помечает занятым и отдаёт **адрес**. Отсюда
свойства: размер может быть любым и вычисляться в рантайме, данные живут независимо от
кадров функций, но каждая аллокация — это работа, а обращение — прыжок по указателю (и,
скорее всего, промах кэша).

Ключевое: **владеющие типы вроде `String` и `Vec<T>` живут в обоих местах сразу.** На стеке
— маленький «паспорт» фиксированного размера (указатель на данные, длина, ёмкость), в куче
— сами байты:

```text
        s (на стеке, 24 байта)          куча (аллокация)
      ┌───────────┬─────┐            ┌───┬───┬───┬───┬───┐
      │ ptr       │ ────────────────►│ h │ e │ l │ l │ o │
      │ len = 5   │                  └───┴───┴───┴───┴───┘
      │ cap = 5   │
      └───────────┴─────┘
```

Почему это важно именно в Rust — четыре следствия, которые объясняют весь модуль:

- **Move двигает паспорт, а не склад.** Перемещение `String` — копирование трёх слов со
  стека. Дёшево. Байты в куче не шевелятся.
- **`Copy` возможен только у «стек-онли» типов.** Нет указателей в кучу — побайтовая копия
  честна и безвредна. Отсюда `i32` — `Copy`, а `String` — нет.
- **`Drop` нужен только тому, кто владеет кучей.** `i32` умирает бесплатно (кадр отрезали),
  а `String` обязана сказать аллокатору «верни кусок обратно» — этим и занимается drop.
- **Ссылка (`&T`) — это просто адрес.** Поэтому вопрос «а не умрут ли данные раньше
  ссылки?» вообще имеет смысл, и решает его borrow checker (модуль 03).

> **Как это было в Go.** Ты писал `x := &Foo{}` и не думал, где `Foo` окажется: компилятор
> делал escape analysis (убежала переменная из функции или нет), а GC потом убирал. То есть
> размещение выбирал компилятор, а судьбу памяти — рантайм. В Rust размещение выбираешь ты
> (`String`/`Vec`/`Box::new` — куча, обычные значения — стек), а освобождение
> детерминировано и следует из владения. Меньше магии, больше предсказуемости.

### Где живёт строковый литерал

Отдельный случай, который путает всех: `"hello"` — это **не** `String`. Литерал вшит в
бинарник и имеет тип `&'static str` — ссылку на данные, которые живут всё время работы
программы (поэтому её никто не освобождает и её нельзя менять). А `String::from("hello")`
берёт эти байты и **копирует их в кучу**, создавая владеющую и растущую строку.

```rust
let a: &str = "hello";                 // ссылка в бинарник, ноль аллокаций
let b: String = String::from("hello"); // аллокация в куче, b владеет данными
let c: String = "hello".to_string();   // то же самое, другой синтаксис
```

## Move: почему присваивание забирает значение

Вот сюрприз из модуля 01:

```rust
let s1 = String::from("hello");
let s2 = s1;          // НЕ копия! Владение перемещено: s1 теперь невалиден
// println!("{s1}"); // ❌ error[E0382]: borrow of moved value: `s1`
```

Чтобы понять, посмотрим, что такое `String` внутри. Это три слова **на стеке**: указатель
на данные в куче, длина, ёмкость. Сами байты `"hello"` лежат **в куче**.

```text
        s1 (на стеке)              куча
      ┌───────────┬─────┐       ┌───┬───┬───┬───┬───┐
      │ ptr       │ ──────────► │ h │ e │ l │ l │ o │
      │ len = 5   │             └───┴───┴───┴───┴───┘
      │ cap = 5   │
      └───────────┴─────┘
```

Если бы `let s2 = s1;` просто скопировало три слова со стека, у тебя было бы **два
указателя на одну кучу**. И когда оба выйдут из scope, оба попытаются освободить одну и ту
же память — **double free**, классическая дыра. Go решает это через GC (он знает, что
ссылок несколько). Rust решает иначе: после `let s2 = s1;` он **инвалидирует** `s1` —
владелец теперь один, `s2`. Освобождение произойдёт ровно один раз. Поэтому это называется
не «копия», а **move** (перемещение): данные в куче не трогаются, но право владения и
ответственность за освобождение переходят к `s2`.

> **Go-параллель и почему это непривычно.** В Go `s2 := s1` для строки копирует заголовок
> (ptr/len), и обе переменные валидны — строки в Go неизменяемы, шарить заголовок безопасно,
> а память подберёт GC. В Rust нет GC, который «посчитает ссылки», поэтому язык требует:
> один владелец. Привычка «присвоил — у меня две независимые переменные» здесь не работает
> для владеющих типов.

## Copy: когда присваивание всё-таки копирует

Не всё перемещается. Простые значения фиксированного размера, целиком лежащие на стеке,
реализуют трейт `Copy`, и для них `=` **копирует**, оставляя оригинал валидным:

```rust
let x = 5;
let y = x;            // i32 — Copy: x скопирован, ОБА валидны
println!("{x} {y}");  // ок: 5 5
```

`Copy` есть у: всех целых и дробных чисел (`i32`, `u64`, `f64`...), `bool`, `char`,
кортежей и массивов **из Copy-типов** (`(i32, bool)` — Copy; `(i32, String)` — нет).
Правило интуитивно: если тип **не владеет ничем в куче** и его дешево скопировать
побайтово — он может быть `Copy`. Как только появляется владение ресурсом (`String`,
`Vec`, `Box`, файловый дескриптор) — `Copy` исчезает, остаётся move.

| Категория | Поведение `=` | Примеры |
|---|---|---|
| `Copy`-типы (целиком на стеке) | копирование, оригинал валиден | `i32`, `f64`, `bool`, `char`, `(i32, i32)` |
| не-`Copy` (владеют ресурсом) | move, оригинал инвалидируется | `String`, `Vec<T>`, `Box<T>`, своя `struct` без `derive(Copy)` |

> **Почему так, а не «всегда копируй»?** Копия `String` = новая аллокация + дублирование
> байт. Делать это неявно на каждом `=` — дорого и обычно не то, что ты хотел. Move
> бесплатен (двигаются только три слова на стеке) и выражает реальное намерение: «теперь
> этим владеет вот эта переменная».

## Clone: явная глубокая копия

Хочешь именно независимую копию владеющего типа — проси явно:

```rust
let s1 = String::from("hello");
let s2 = s1.clone();    // ГЛУБОКАЯ копия: новая аллокация, свои байты в куче
println!("{s1} {s2}");  // оба валидны
```

`clone()` виден в коде — и это фича, а не баг: аллокации в Rust **не прячутся**. Если в
горячем цикле висит `.clone()`, ты это видишь и можешь решить, нужен ли он. В Go копии и
аллокации часто незаметны; здесь — на виду.

> ⚠️ **`clone()` как «затыкание» borrow checker.** Новички, упёршись в ошибку move,
> рефлекторно лепят `.clone()`, чтобы «компилятор замолчал». Иногда это правильно, но
> часто настоящий ответ — **одолжить ссылку** (`&`, модуль 03), а не копировать. Клонируй,
> когда тебе действительно нужна вторая независимая копия данных, а не просто почитать.

## Частичное перемещение: можно вынести одно поле

Move работает не только на переменную целиком, но и на **отдельное поле**:

```rust
struct User { name: String, age: u32 }

fn main() {
    let u = User { name: String::from("Ann"), age: 30 };
    let name = u.name;             // частичный move: вынесли name из u
    println!("{name} {}", u.age);  // ок: age на месте (u32 — Copy)
    // println!("{}", u.name);     // ❌ поле name уже перемещено
    // let u2 = u;                 // ❌ нельзя двигать структуру целиком: часть уже вынесли
}
```

Компилятор ведёт учёт **по полям** и говорит прямо:

```text
error[E0382]: use of partially moved value: `u`
  |
  = note: partial move occurs because `u.name` has type `String`,
          which does not implement the `Copy` trait
```

Это удобно: структуру можно «разобрать на детали», ничего не клонируя. Но после частичного
перемещения структура как целое непригодна. Хочешь разобрать её полностью — сделай это одним
движением через деструктуризацию:

```rust
let User { name, age } = u;   // забрали оба поля сразу, u больше не нужен
```

## Drop: что происходит при выходе из scope

Когда владелец умирает, Rust вызывает «деструктор» — метод трейта `Drop`. Для `String` он
освобождает кучу; для файла — закрывает дескриптор; для мьютекса — снимает блокировку.
Можно реализовать `Drop` и для своего типа:

```rust
struct Guard(&'static str);

impl Drop for Guard {
    fn drop(&mut self) {
        println!("освобождаю {}", self.0);
    }
}

fn main() {
    let _a = Guard("A");
    let _b = Guard("B");
    println!("конец main");
}   // порядок drop — ОБРАТНЫЙ объявлению: сначала B, потом A
// вывод:
// конец main
// освобождаю B
// освобождаю A
```

> **Это «автоматический `defer`».** В Go ты пишешь `defer f.Close()` руками у каждого
> ресурса, и порядок — LIFO. В Rust очистка привязана к владению и вызывается сама, тоже в
> обратном порядке. Забыть нельзя — компилятор не даёт «потерять» владельца без drop.

## Move при передаче в функцию и возврате

Передача аргумента подчиняется тем же правилам: для не-`Copy` типа аргумент **перемещается**
внутрь функции.

```rust
fn consume(s: String) {        // s стал владельцем
    println!("{s}");
}                              // здесь s дропается

fn main() {
    let name = String::from("Rust");
    consume(name);             // владение ушло в функцию
    // println!("{name}");     // ❌ name перемещён, использовать нельзя
}
```

Если хочешь и отдать значение, и продолжить им пользоваться — варианты: вернуть его
обратно (`fn consume(s: String) -> String { ...; s }`), клонировать, или — самое частое и
правильное — **передать ссылку** (`fn read(s: &String)`), не отдавая владение. Это уже
тема модуля 03, но именно здесь становится ясно, **зачем** нужен заём: чтобы дать функции
почитать данные, не вручая ей владение и не делая копию.

## Глоссарий модуля

- **Владелец (owner)** — переменная, отвечающая за значение и за его освобождение.
- **Область видимости (scope)** — блок `{ ... }`, в конце которого владельцы умирают.
- **Move (перемещение)** — передача владения при `=`, передаче в функцию или возврате;
  исходная переменная становится непригодной.
- **`Copy`** — маркерный трейт «меня можно честно скопировать побайтово»; бывает только у
  типов, не владеющих кучей.
- **`Clone`** — трейт с методом `.clone()`: явная (обычно глубокая) копия, часто с аллокацией.
- **`Drop`** — трейт с методом `drop(&mut self)`: что сделать при смерти владельца.
  Вызывается автоматически; чтобы освободить досрочно, есть функция `drop(x)`, которая просто
  забирает значение и даёт ему умереть.
- **RAII** — приём «время жизни ресурса = время жизни владельца» (пришёл из C++).
- **Стек / куча** — кадры фиксированного размера vs аллокации у аллокатора (см. раздел выше).
- **Аллокация** — запрос памяти у аллокатора; в Rust она всегда видна в коде.
- **Частичное перемещение (partial move)** — вынос отдельного поля структуры.
- **`&'static str`** — тип строкового литерала: ссылка на данные внутри бинарника, живущие
  всё время работы программы.
- **`E0382`** — «use / borrow of moved value»: обратился к тому, что уже переехало.
- **`E0204`** — «the trait `Copy` cannot be implemented for this type»: среди полей есть
  не-`Copy`.

## Типичные ошибки и заблуждения

- **«Присваивание копирует».** Только для `Copy`-типов. Для `String`/`Vec`/своих структур
  это **move**, оригинал инвалидируется (`E0382`).
- **«`clone()` — это бесплатно / так и надо всегда».** `clone()` владеющего типа — это
  аллокация и копирование. Часто настоящий ответ — ссылка (`&`), а не клон.
- **«Без GC придётся звать `free` руками».** Нет: drop вызывается автоматически на выходе
  из scope. Детерминированно и без утечек, но без сборщика.
- **«Раз `i32` копируется, то и `String` тоже».** Разница в том, владеет ли тип ресурсом в
  куче. Стек-онли и дешёвое → `Copy`; владеет кучей → move.
- **«Move физически копирует кучу».** Нет, move двигает только заголовок на стеке (ptr/len/cap);
  байты в куче не трогаются. Это дёшево.
- **«Передал в функцию — у меня осталась переменная».** Для не-`Copy` типа она перемещена
  в функцию; верни её, клонируй или передавай по ссылке.
- **«`"hello"` — это `String`».** Нет: литерал имеет тип `&'static str` — ссылку на данные в
  бинарнике. `String` появляется только там, где есть аллокация: `String::from("hello")`,
  `"hello".to_string()`.
- **«Вынес одно поле — структура целой осталась».** Это частичное перемещение: после него
  структуру нельзя двигать и использовать как целое (`use of partially moved value`).
- **«Drop можно позвать руками: `x.drop()`».** Нельзя (компилятор запретит — иначе был бы
  двойной drop). Для досрочного освобождения есть функция `drop(x)`, которая забирает
  значение себе.
