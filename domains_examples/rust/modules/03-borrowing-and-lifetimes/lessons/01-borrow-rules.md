# Урок 01 — Правило заёма на практике

Цель: прочувствовать «много читателей ИЛИ один писатель», прочитать `E0502`/`E0499` и
понять, как NLL спасает «выглядящий нарушением» код.

## Разогрев

- Сколько `&T` можно держать одновременно? А `&mut T`?
- Почему нельзя `&` и `&mut` вместе?
- Что такое NLL?

## Шаг 1. Много читателей — ок

```rust
fn main() {
    let v = vec![1, 2, 3];
    let a = &v;
    let b = &v;
    let c = &v;
    println!("{a:?} {b:?} {c:?}");   // три неизменяемых заёма — без проблем
}
```

Читателей сколько угодно: никто ничего не меняет, конфликта нет.

## Шаг 2. Один писатель — ок, но единственный

```rust
fn main() {
    let mut v = vec![1, 2, 3];
    let m = &mut v;
    m.push(4);
    println!("{m:?}");               // [1, 2, 3, 4]
}
```

А вот два `&mut` сразу — нельзя:

```rust
fn main() {
    let mut v = vec![1, 2, 3];
    let m1 = &mut v;
    let m2 = &mut v;                 // ❌
    m1.push(4);
    println!("{m2:?}");
}
```

```text
error[E0499]: cannot borrow `v` as mutable more than once at a time
  |
3 |     let m1 = &mut v;
  |              ------ first mutable borrow occurs here
4 |     let m2 = &mut v;
  |              ^^^^^^ second mutable borrow occurs here
5 |     m1.push(4);
  |     -- first borrow later used here
```

`E0499` — «изменяемый заём больше одного раза». Логика прежняя: два писателя = гонка.

## Шаг 3. Смешали & и &mut — главный конфликт

```rust
fn main() {
    let mut v = vec![1, 2, 3];
    let r = &v;                      // читатель
    v.push(4);                       // ❌ пишем, пока r жив
    println!("{r:?}");
}
```

```text
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
  |
3 |     let r = &v;
  |             -- immutable borrow occurs here
4 |     v.push(4);
  |     ^^^^^^^^^ mutable borrow occurs here
5 |     println!("{r:?}");
  |               - immutable borrow later used here
```

`push` — это `&mut self` под капотом, и он конфликтует с живым `&v`. Если бы Rust
пропустил это, `push` мог бы перевыделить буфер, и `r` стал бы висячим.

## Шаг 4. NLL: тот же код, но читатель «отжил»

Переставим использование `r` ДО мутации:

```rust
fn main() {
    let mut v = vec![1, 2, 3];
    let r = &v;
    println!("{r:?}");               // последнее использование r — здесь
    v.push(4);                       // теперь ок: r уже не нужен
    println!("{v:?}");               // [1, 2, 3, 4]
}
```

Компилируется! Borrow checker видит, что после `println!("{r:?}")` ссылка `r` больше не
используется, и считает заём завершённым. Это non-lexical lifetimes — заём живёт до
последнего использования, а не до `}`.

> **Практический вывод.** Когда ловишь `E0502`/`E0499`, частая починка — **сузить область
> жизни ссылки**: использовать её раньше, или завести меньший блок `{ ... }`, чтобы заём
> закончился до мутации. Не рефлекс `clone()`, а «дай читателю отжить».

## Итог

Правило заёма — «много читателей ИЛИ один писатель» — это весь модуль в одной фразе. Оно
ловит гонки и висячие ссылки на компиляции. А NLL делает его терпимым: ссылка живёт до
последнего использования, поэтому большинство «конфликтов» лечится переупорядочиванием или
сужением области, а не клонированием. Дальше — что делать, когда ссылку надо **вернуть**
из функции: lifetimes.
