# Умные указатели и внутренняя изменяемость

## Зачем вообще «умные указатели»

Правила владения строги: один владелец, заём по правилам, всё проверяется на компиляции.
В 95% случаев этого хватает. Но есть законные сценарии, где строгой схемы мало:

- значение надо положить **в кучу** явно (большой объект, рекурсивный тип неизвестного
  размера) → `Box<T>`;
- у данных должно быть **несколько владельцев** (граф, дерево с общими узлами) → `Rc<T>` /
  `Arc<T>`;
- надо **изменить** данные, имея лишь `&` (неизменяемую ссылку) → `Cell<T>` / `RefCell<T>`.

Умные указатели — это типы, которые ведут себя как указатель (можно разыменовать), но несут
дополнительную логику (счётчик ссылок, проверку заёма) и реализуют `Drop` (освобождают
ресурс). Это «клапаны давления»: они дают гибкость, перенося часть проверок в рантайм или
добавляя накладные расходы — но честно и под контролем.

## `Box<T>` — значение в куче

`Box<T>` — простейший умный указатель: владеющий указатель на значение в куче.

```rust
let b = Box::new(5);        // 5 лежит в куче, b владеет им
println!("{b}");            // 5 — Box разыменовывается прозрачно (Deref)
```

Зачем класть `i32` в кучу? Обычно незачем. Реальные применения `Box`:

1. **Рекурсивные типы** — без `Box` компилятор не знает их размер:

```rust
enum List {
    Cons(i32, Box<List>),   // без Box: «recursive type has infinite size» (E0072)
    Nil,
}
```

Здесь `Box` разрывает бесконечность: размер `Cons` — это `i32` + размер указателя
(фиксированный), а не «`i32` + целый `List` + …». Это как `*Node` в связном списке Go,
только с владением.

2. **Trait objects** — `Box<dyn Trait>` (модуль 06): хранить значение неизвестного размера
   за указателем.

> **Go-параллель.** В Go ты редко думаешь о куче явно — escape analysis сам решает, где
> разместить. `Box::new` — это явное «положи в кучу», ближайшее к `new(T)`/`&T{}` в Go.
> Разница: `Box` — единоличный владелец с детерминированным освобождением.

## `Rc<T>` — несколько владельцев (один поток)

Иногда у данных нет одного естественного владельца — например, узел графа, на который
ссылаются несколько других. `Rc<T>` (reference counted) разрешает **разделённое владение**:
данные живут, пока на них есть хоть один `Rc`; счётчик растёт на `clone` и падает на `drop`.

```rust
use std::rc::Rc;

let a = Rc::new(String::from("shared"));
let b = Rc::clone(&a);            // НЕ копия строки! +1 к счётчику, b делит данные с a
let c = Rc::clone(&a);
println!("счётчик: {}", Rc::strong_count(&a));   // 3
// когда a, b, c все дропнутся — строка освободится ровно один раз
```

`Rc::clone` дёшев — он копирует указатель и инкрементит счётчик, **не дублируя данные**
(в отличие от `data.clone()`). По соглашению пишут `Rc::clone(&a)`, а не `a.clone()`, чтобы
было видно: это разделение, не глубокая копия.

Важно: `Rc<T>` даёт только **неизменяемый** доступ (несколько владельцев читают), и он
**не потокобезопасен** — счётчик не атомарный. Для одного потока.

## `Arc<T>` — потокобезопасный Rc (мост в модуль 09)

`Arc<T>` (atomic reference counted) — то же, что `Rc`, но счётчик меняется **атомарно**,
поэтому `Arc` можно делить **между потоками**. Чуть дороже `Rc` (атомарные операции), зато
безопасен для конкурентности.

```rust
use std::sync::Arc;
let data = Arc::new(vec![1, 2, 3]);
let data2 = Arc::clone(&data);       // можно отправить data2 в другой поток
```

> **Запомни связку.** `Rc` = один поток, дёшево. `Arc` = много потоков, атомарный счётчик.
> Компилятор не даст случайно отправить `Rc` в другой поток (он не `Send` — модуль 09).
> Именно поэтому `Arc` стоит здесь, рядом с `Rc`: в модуле 09 он станет основным способом
> делить данные между потоками (`Arc<Mutex<T>>`).

> **Простыми словами: что такое «внутренняя изменяемость».** Обычно в Rust изменяемость —
> свойство **доступа**: есть `&mut` — меняй, есть только `&` — не смей. Внутренняя
> изменяемость переворачивает это. Тип говорит: «внутри меня есть комнатка, которую я разрешаю
> менять даже тем, у кого на руках только `&`, — но за порядком в ней следю я сам». `Cell`
> следит простейшим способом (меняем значение только целиком, ссылок внутрь не выдаём);
> `RefCell` ведёт счётчик выданных заёмов и паникует при нарушении; `Mutex` (модуль 09) ставит
> настоящий замок. Правило «один писатель ИЛИ много читателей» никуда не исчезает — меняется
> только **момент проверки**: с компиляции на рантайм.

## Внутренняя изменяемость: `Cell` и `RefCell`

Тупик: `Rc<T>` даёт нескольких владельцев, но только для **чтения**. А если общий узел надо
**менять**? Правило «`&mut` эксклюзивен» этого не позволяет напрямую. Выход — **внутренняя
изменяемость** (interior mutability): тип, который разрешает менять содержимое через `&`,
взяв на себя проверку правил заёма.

- **`Cell<T>`** — для `Copy`-типов: `get`/`set` значения целиком, без ссылок внутрь. Просто
  и без накладных расходов.
- **`RefCell<T>`** — для любых типов: выдаёт `borrow()` (`Ref<T>`, как `&`) и `borrow_mut()`
  (`RefMut<T>`, как `&mut`), но проверяет правило заёма **в рантайме**. Нарушил («два
  `borrow_mut` сразу») — **паника** `already borrowed: BorrowMutError`, а не ошибка
  компиляции.

```rust
use std::cell::RefCell;

let cell = RefCell::new(5);
*cell.borrow_mut() += 1;          // взяли изменяемый заём в рантайме, поменяли
println!("{}", cell.borrow());    // 6

// ❌ это паникует в рантайме:
let a = cell.borrow_mut();
let b = cell.borrow_mut();        // panic: already borrowed: BorrowMutError
```

> **Ключевой компромисс.** Обычный заём проверяется на компиляции (надёжно, бесплатно).
> `RefCell` **переносит ту же проверку в рантайм** — гибче (можно то, что статически не
> докажешь), но нарушение превращается из ошибки компиляции в панику. Это осознанная сделка,
> а не лазейка: правило «один писатель ИЛИ много читателей» по-прежнему действует, просто
> контролируется динамически.

### Глобальное состояние без `static mut`: `OnceLock`

Обещанный в модуле 04 сюжет. Ленивая инициализация «один раз на всю программу» делается
типами из std, а не `static mut`:

```rust
use std::sync::OnceLock;

static CONFIG: OnceLock<String> = OnceLock::new();

fn config() -> &'static str {
    CONFIG.get_or_init(|| std::env::var("APP_MODE").unwrap_or_else(|_| "dev".into()))
}
```

`OnceLock` гарантирует, что замыкание инициализации выполнится **ровно один раз**, даже если в
`config()` одновременно войдут несколько потоков. Это прямая замена паттерну `sync.Once` из
Go, только результат хранится внутри и отдаётся ссылкой (и её `'static` — тот самый второй
смысл из модуля 03). Если нужна «глобальная изменяемая» вещь, берут `static X: Mutex<T>`
(модуль 09) — но сначала стоит спросить себя, нельзя ли просто передать состояние аргументом.

## Паттерн `Rc<RefCell<T>>` — общий изменяемый узел

Сложив две вещи, получаем «несколько владельцев + изменяемость»: `Rc<RefCell<T>>`. Это
рабочая лошадка для деревьев/графов/наблюдаемого состояния в однопоточном коде.

```rust
use std::rc::Rc;
use std::cell::RefCell;

let shared = Rc::new(RefCell::new(vec![1, 2, 3]));
let alias = Rc::clone(&shared);          // второй владелец того же вектора

shared.borrow_mut().push(4);             // меняем через первого
println!("{:?}", alias.borrow());        // [1, 2, 3, 4] — видно через второго
```

`Rc` даёт совладельцев, `RefCell` — изменяемость через `&`. В многопоточном коде аналог —
`Arc<Mutex<T>>` (модуль 09): `Arc` вместо `Rc`, `Mutex` вместо `RefCell` (блокировка вместо
рантайм-проверки заёма).

> **Go-параллель.** `Rc<RefCell<T>>` ≈ общий `*T` в Go, который несколько структур держат и
> мутируют. Разница: Go полагается на GC и на тебя (гонки ловит race-детектор в рантайме,
> если повезёт), а Rust в однопоточном `RefCell` всё равно проверяет «один писатель» —
> просто в рантайме, с честной паникой вместо тихой порчи данных.

## `Deref`: почему умные указатели «прозрачны»

`Box`, `Rc`, `RefCell`'s `Ref` ведут себя как обычные ссылки благодаря трейту `Deref`
(associated type из модуля 06): он определяет, во что разыменовывается тип. Поэтому
`b.len()` для `b: Box<String>` работает — компилятор автоматически разыменует `Box` до
`String` (deref coercion). Это не магия, а трейт, который ты тоже можешь реализовать.

## Шпаргалка: что брать в каком случае

| Ситуация | Инструмент | Цена |
|---|---|---|
| Один владелец, обычные данные | просто значение (`String`, `Vec<T>`) | ноль |
| Нужен фиксированный размер (рекурсия, `dyn`) | `Box<T>` | аллокация + разыменование |
| Несколько владельцев, только чтение, один поток | `Rc<T>` | счётчик ссылок |
| Несколько владельцев, несколько потоков | `Arc<T>` | атомарный счётчик |
| Менять `Copy`-поле, имея только `&` | `Cell<T>` | ноль (только get/set целиком) |
| Менять любые данные через `&`, один поток | `RefCell<T>` | рантайм-проверка + риск паники |
| Общий изменяемый узел, один поток | `Rc<RefCell<T>>` | сумма двух предыдущих |
| Общее изменяемое состояние, много потоков | `Arc<Mutex<T>>` (модуль 09) | атомарность + блокировка |
| Обратная ссылка (ребёнок → родитель) | `Weak<T>` | не удерживает данные живыми |

Читай таблицу сверху вниз: **каждая строка дороже предыдущей**, и спускаться стоит только
тогда, когда вариант выше действительно не подходит. Типичная ошибка новичка — начать снизу:
завернуть всё в `Rc<RefCell<T>>`, «чтобы не воевать с borrow checker», и построить на этом всю
программу. Так вместо ошибок компиляции получаются паники в рантайме — обмен, который редко
бывает выгодным. 90% данных в нормальном Rust-коде живут с одним владельцем.

## Циклы `Rc` и утечки: `Weak<T>`

У подсчёта ссылок есть классическая болезнь — **циклы**. Если `a` держит `Rc` на `b`, а `b`
— `Rc` на `a`, их счётчики никогда не дойдут до нуля, и память **утечёт** (даже в Rust!).
Это один из немногих способов словить утечку в безопасном Rust.

Лечение — `Weak<T>`: «слабая» ссылка, которая **не** удерживает данные живыми (не считается
в strong-счётчике). Типичная схема: родитель держит `Rc` на детей (владеет), дети держат
`Weak` на родителя (ссылаются, но не владеют). `Weak::upgrade()` даёт `Option<Rc<T>>` —
`None`, если данные уже умерли.

```rust
use std::rc::{Rc, Weak};
use std::cell::RefCell;

struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,     // Weak: не держим родителя живым → нет цикла
    children: RefCell<Vec<Rc<Node>>>,// Rc: владеем детьми
}
```

## Глоссарий модуля

- **Умный указатель** — тип, который ведёт себя как указатель (реализует `Deref`), но несёт
  дополнительную логику и освобождает ресурс в `Drop`.
- **`Box<T>`** — единоличный владеющий указатель на значение в куче.
- **`Rc<T>` / `Arc<T>`** — разделённое владение с подсчётом ссылок: неатомарным (один поток) и
  атомарным (много потоков).
- **strong count / weak count** — счётчики сильных и слабых ссылок; данные живут, пока
  strong > 0.
- **`Weak<T>`** — слабая ссылка: не удерживает данные живыми; `Rc::downgrade` создаёт её,
  `upgrade()` возвращает `Option<Rc<T>>`.
- **Внутренняя изменяемость (interior mutability)** — возможность менять содержимое через `&`,
  с проверкой правил в рантайме.
- **`Cell<T>`** — внутренняя изменяемость для `Copy`-типов: только `get`/`set` целиком.
- **`RefCell<T>`** — внутренняя изменяемость для любых типов: `borrow()` / `borrow_mut()` с
  рантайм-проверкой.
- **`Ref` / `RefMut`** — guard-объекты, возвращаемые `borrow()` / `borrow_mut()`; заём жив,
  пока жив guard.
- **`BorrowMutError`** — паника при нарушении правила заёма в `RefCell`.
- **`Deref` / deref coercion** — трейт разыменования и автоматическое приведение
  (`&Box<String>` → `&String` → `&str`), из-за которого умные указатели «прозрачны».
- **Тип неизвестного размера (DST / unsized)** — тип, размер которого неизвестен на компиляции
  (`dyn Trait`, `[T]`, `str`); хранится только за указателем.
- **Цикл ссылок** — взаимные `Rc`, из-за которых счётчики не доходят до нуля; лечится `Weak`.
- **`OnceLock`** — ячейка «инициализируется один раз», замена `sync.Once` из Go.

## Типичные ошибки и заблуждения

- **«`Box` нужен для всего в куче».** Нет: коллекции (`Vec`, `String`) уже в куче. `Box`
  нужен для рекурсивных типов и trait objects, иногда для очень больших значений.
- **«`Rc::clone` копирует данные».** Нет: он копирует указатель и инкрементит счётчик,
  данные общие. Глубокая копия — это `(*rc).clone()` на самих данных.
- **«`Rc` можно слать между потоками».** Нельзя — он не `Send` (счётчик неатомарный). Для
  потоков — `Arc`. Компилятор это проверит.
- **«`RefCell` отключает borrow checker».** Нет: он переносит проверку «писатель/читатели» в
  рантайм. Нарушение — паника `BorrowMutError`, а не тихая гонка.
- **«В Rust утечек памяти не бывает».** Бывают: цикл `Rc<->Rc` течёт. Лечится `Weak`.
  Безопасность памяти ≠ отсутствие утечек (утечка не является «небезопасностью»).
- **«`Rc<RefCell<T>>` — это для многопоточности».** Нет, это однопоточный паттерн. Для
  потоков — `Arc<Mutex<T>>` (модуль 09).
- **«Заверну всё в `Rc<RefCell<T>>` — и borrow checker отстанет».** Отстанет компилятор, а
  придут паники `BorrowMutError` в рантайме. Спускайся по шпаргалке сверху вниз, а не наоборот.
- **«Для глобальной переменной нужен `static mut`».** Нет: `OnceLock` для «инициализировать
  один раз», `static X: Mutex<T>` для изменяемого состояния. `static mut` требует `unsafe` и в
  нормальном коде не встречается.
- **«`Weak` — это просто более слабый `Rc`, можно им пользоваться напрямую».** Нельзя: сначала
  `upgrade()` → `Option<Rc<T>>`, и `None` здесь — законный ответ «данных уже нет».
