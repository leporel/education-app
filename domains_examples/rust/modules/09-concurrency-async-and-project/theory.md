# Конкурентность, async и сквозной проект

## Два разных вопроса: потоки и async

Сразу разведём, потому что новички их путают:

- **Потоки (`std::thread`)** — про **параллелизм**: несколько OS-потоков реально бегут на
  разных ядрах. Хороши для CPU-тяжёлой работы.
- **`async`/`await`** — про **конкурентность с масштабируемым I/O**: десятки тысяч задач,
  которые большую часть времени **ждут** (сеть, диск), на небольшом пуле потоков. Хорош
  для серверов/клиентов с массой одновременных соединений.

Go сливает это в одну абстракцию — горутину (планировщик сам мультиплексирует на потоки).
Rust разделяет: потоки — в std, async — отдельная модель плюс **внешний рантайм**. Это
больше контроля и нюансов, но меньше «магии под капотом».

## Потоки и «бесстрашная конкурентность»

```rust
use std::thread;

fn main() {
    let handle = thread::spawn(|| {        // запускаем OS-поток
        for i in 1..=3 { println!("из потока: {i}"); }
    });
    println!("из main");
    handle.join().unwrap();                 // ждём завершения (как WaitGroup на один поток)
}
```

`thread::spawn` берёт `move`-замыкание (модуль 07): данные, которые поток использует,
должны **переехать** в него — иначе они могли бы умереть раньше потока. Вот тут начинается
магия безопасности:

```rust
fn main() {
    let data = vec![1, 2, 3];
    let handle = std::thread::spawn(move || {   // move: data переехала в поток
        println!("{data:?}");
    });
    // println!("{data:?}");   // ❌ data перемещена в поток, в main её больше нет
    handle.join().unwrap();
}
```

### `Send` и `Sync` — почему гонки невозможны на компиляции

Два маркерных трейта, на которых стоит вся потокобезопасность Rust:

- **`Send`** — тип можно **переместить** в другой поток (передать владение). Почти все
  типы `Send`; не-`Send` — например, `Rc<T>` (неатомарный счётчик).
- **`Sync`** — на тип можно **ссылаться** из нескольких потоков (`&T` можно слать в потоки).

Компилятор **проверяет** эти трейты при `spawn`. Поэтому:

```rust
use std::rc::Rc;
fn main() {
    let rc = Rc::new(5);
    std::thread::spawn(move || {
        println!("{rc}");        // ❌ компилятор не пустит
    });
}
```

```text
error[E0277]: `Rc<i32>` cannot be sent between threads safely
  = help: the trait `Send` is not implemented for `Rc<i32>`
  = note: required because it appears within the type ...
```

`Rc` не `Send` — его счётчик неатомарный, и гонка по нему испортила бы подсчёт. Компилятор
ловит это **до запуска**. Возьми `Arc` (атомарный, `Send + Sync`) — и всё ок. Вот что
значит «**fearless concurrency**»: целый класс гонок данных невозможен по построению.

> **Контраст с Go.** В Go ты можешь зашарить любой указатель между горутинами, и компилятор
> промолчит; гонку, может быть, поймает `-race` детектор **в рантайме** (и только если она
> проявится на тесте). В Rust «нельзя безопасно расшарить» — это **ошибка компиляции**.
> Меньше свободы выстрелить себе в ногу.

### Делим изменяемое состояние: `Arc<Mutex<T>>`

Несколько потоков, общий счётчик. В модуле 08 для одного потока был `Rc<RefCell<T>>`; для
потоков — его близнец `Arc<Mutex<T>>`:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));     // Arc: совладение между потоками; Mutex: эксклюзивный доступ
    let mut handles = vec![];

    for _ in 0..10 {
        let c = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            let mut n = c.lock().unwrap();      // блокируемся, берём эксклюзивный доступ
            *n += 1;
        }));                                    // n дропается → mutex разблокируется (RAII!)
    }
    for h in handles { h.join().unwrap(); }
    println!("итог: {}", *counter.lock().unwrap());   // 10
}
```

- `Arc` — несколько владельцев между потоками (`Rc` не пустит — не `Send`).
- `Mutex<T>` — данные **внутри** замка; `lock()` даёт guard с эксклюзивным доступом.
- Замок **снимается автоматически**, когда guard выходит из scope (тот же RAII/`Drop`).
  Забыть `unlock` нельзя — в отличие от ручных мьютексов.

> **Go-параллель.** В Go `sync.Mutex` отдельно от данных, и ничто не мешает обратиться к
> данным, забыв `Lock()`. В Rust данные **живут внутри** `Mutex<T>`: добраться до них можно
> **только** через `lock()`. «Защита данных замком» гарантирована типом, а не дисциплиной.

### Почему `lock()` возвращает `Result`: отравление мьютекса

Ты наверняка заметил `.unwrap()` после каждого `lock()` — это не небрежность. `lock()`
возвращает `Result`, потому что мьютекс может быть **отравлен** (poisoned): так помечается
замок, который держал поток, когда он запаниковал. Данные внутри могли остаться
полуизменёнными, и Rust честно предупреждает об этом всех следующих желающих.

- `lock().unwrap()` — политика «если кто-то умер с замком в руках, то и мне продолжать
  незачем». Разумный вариант по умолчанию.
- Если состояние всё-таки пригодно, отравление можно осознанно проигнорировать:
  `let guard = m.lock().unwrap_or_else(|e| e.into_inner());`.

В Go такой концепции нет вовсе: паника в горутине с захваченным `sync.Mutex` либо оставит
замок захваченным навсегда, либо (при `defer mu.Unlock()`) отпустит его, ничего не сказав о
целостности данных.

### `thread::scope`: потоки без `Arc`

`thread::spawn` требует `'static` (модуль 03), потому что поток может пережить того, кто его
создал. Отсюда `move` и `Arc` — даже для данных, которые никуда не денутся. Но если потоки
гарантированно завершатся до конца блока, обёртки не нужны: для этого есть **scoped-потоки**.

```rust
let data = vec![1, 2, 3];

std::thread::scope(|s| {
    s.spawn(|| println!("читаю: {data:?}"));            // просто заём, без Arc и без move
    s.spawn(|| println!("тоже читаю: {}", data.len())); // и второй читатель — можно
});   // выход из scope ЖДЁТ все порождённые потоки — поэтому заём безопасен

println!("{data:?} всё ещё моё");
```

Компилятор знает: `scope` не вернётся, пока живы потоки, — значит, ссылки внутри не переживут
данные. Это самый простой способ распараллелить «посчитать по кускам массива». По смыслу —
`WaitGroup`/`errgroup` из Go, только гарантия обеспечена типами, а не дисциплиной.

### `RwLock` и атомики — когда `Mutex` слишком груб

- **`RwLock<T>`** — тот же `Mutex`, но с раздельными `read()` (много читателей) и `write()`
  (один писатель). Полезен, когда читают часто, а пишут редко; прямой аналог `sync.RWMutex`.
  Заметь: это буквально правило заёма из модуля 03, только проверяемое в рантайме.
- **Атомики** (`AtomicUsize`, `AtomicBool` из `std::sync::atomic`) — счётчики и флаги без
  блокировок: `counter.fetch_add(1, Ordering::Relaxed)`. Аналог пакета `sync/atomic` в Go.
  Порядки памяти (`Ordering`) — глубокая отдельная тема; для счётчика статистики достаточно
  `Relaxed`, для флага «пора останавливаться» берут `SeqCst` и не умничают.

### Каналы — CSP, как в Go

Альтернатива общей памяти — передача сообщений. Rust's `std::sync::mpsc` (multi-producer,
single-consumer) — это привычный по Go паттерн «не общайся через память, делись через
каналы»:

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    thread::spawn(move || {
        for i in 0..3 { tx.send(i).unwrap(); }    // отправитель владеет tx (move)
    });
    for received in rx {                          // итерируемся по каналу, пока отправители живы
        println!("получил: {received}");
    }
}
```

Похоже на каналы Go, с нюансами: владение **отправленного значения переходит** получателю
(никакого общего доступа после `send` — снова никаких гонок), и `mpsc` по умолчанию — много
отправителей, один получатель (для многих получателей берут крейты типа `crossbeam`).

## `async`/`await`: масштабируемый I/O

### `Future` ленив, и ему нужен рантайм

`async fn` не запускает работу — он возвращает **`Future`**: описание вычисления, которое
**ничего не делает, пока его не «поллят»**. Кто-то должен его исполнить — это **рантайм
(executor)**. В std рантайма нет: Rust не навязывает один. Стандарт де-факто — **Tokio**.

```rust
// async fn возвращает Future<Output = u32>; тело НЕ выполнится само
async fn fetch_score() -> u32 {
    // ... await-точки внутри ...
    42
}

#[tokio::main]                      // макрос разворачивает main в запуск Tokio-рантайма
async fn main() {
    let score = fetch_score().await;   // .await — «жди готовности, отдав управление другим задачам»
    println!("{score}");
}
```

`.await` — точка, где задача может **уступить** исполнителю, пока ждёт (например, ответа
сети). Пока она ждёт, рантайм крутит другие задачи на том же потоке. Так один поток
обслуживает тысячи «ждущих» соединений.

> **Главное отличие от goroutines.** Горутина в Go — «зелёный поток» со встроенным
> планировщиком: написал `go f()` — оно поехало, рантайм уже в языке. В Rust:
> 1. `Future` **ленив** — без `.await`/рантайма не исполнится (забыл `.await` — компилятор
>    предупредит: future должен быть использован).
> 2. Рантайм **внешний** и выбираемый (Tokio, smol). `async-std` уже мёртв; для 99% задач
>    берут Tokio.
> 3. Это даёт контроль (какой рантайм, сколько потоков, как планировать), ценой явности:
>    надо подключить рантайм и понимать, что «async само по себе не параллельно».

> **Простыми словами: рантайм, executor и «поллинг».** `Future` — это не запущенная работа, а
> **машина состояний в коробке**: объект, у которого есть один метод «попробуй продвинуться»
> (`poll`). Он отвечает либо «готово, вот результат», либо «пока не готов, разбуди меня, когда
> придут данные». Тот, кто в цикле дёргает эту ручку у тысяч коробок, и есть **executor**
> (исполнитель); вместе с таймерами и системным опросом сокетов он образует **рантайм**
> (Tokio). Твой `.await` — это буквально «здесь я возвращаю управление исполнителю и прошу
> разбудить меня, когда мой сосед-`Future` ответит „готово“». Отсюда сразу два вывода:
> без исполнителя ничего не крутится, а если ты внутри задачи ушёл в долгий синхронный цикл и
> не вернул управление — исполнитель стоит вместе с тобой.

### Конкурентность внутри async

`.await` по очереди — это последовательно. Чтобы ждать несколько вещей **одновременно**:

```rust
// обе задачи прогрессируют конкурентно, ждём обе
let (a, b) = tokio::join!(fetch_score(), fetch_score());

// настоящий параллелизм (на пуле потоков рантайма) — spawn задачи
let handle = tokio::spawn(async { fetch_score().await });
let v = handle.await.unwrap();

// гонка: кто первый — тот и ответ
tokio::select! {
    x = fetch_score() => println!("первым пришёл {x}"),
    _ = tokio::time::sleep(std::time::Duration::from_secs(1)) => println!("таймаут"),
}
```

- `join!` — ждать несколько futures конкурентно (как `errgroup`/`sync.WaitGroup` по смыслу).
- `tokio::spawn` — отдать задачу рантайму (ближайший аналог `go f()`); задача должна быть
  `Send + 'static`.
- `select!` — кто первый завершится (как `select` по каналам в Go, но по futures).

### «Не блокируй executor» — главный async-грабль

Async-задачи кооперативны: они отдают управление **только** на `.await`. Если внутри
async-функции ты делаешь **блокирующий** или долгий **синхронный** вызов (тяжёлый цикл,
`std::thread::sleep`, блокирующее чтение файла), он «затыкает» поток исполнителя — и **все
остальные задачи на нём стоят**.

```rust
async fn bad() {
    std::thread::sleep(std::time::Duration::from_secs(5));   // ❌ блокирует весь executor-поток
}
async fn good() {
    tokio::time::sleep(std::time::Duration::from_secs(5)).await;  // ✅ уступает, ждёт асинхронно
}
```

Тяжёлую CPU-работу выносят на `tokio::task::spawn_blocking` или в обычные потоки. В Go об
этом не думаешь — рантайм вытесняюще планирует горутины; в Rust планирование кооперативное,
и ответственность «уступать на await» — на тебе.

### Что нужно знать про `spawn`, отмену и дедлоки

**`Send + 'static` у задач.** `tokio::spawn` (как и `thread::spawn`) требует от задачи
`Send + 'static`: она может уехать на другой поток пула и пережить того, кто её породил.
Отсюда `move`-блоки и `Arc` вместо ссылок — те же два ограничения, что и у потоков.

**Отмена — это drop.** Сигнала «стоп» у async-задачи нет, как нет его и у горутины. Зато есть
то, чего в Go нет вовсе: **уронишь future — вычисление прекратится**. На этом построены
таймауты:

```rust
use tokio::time::{timeout, Duration};

match timeout(Duration::from_secs(2), fetch_score()).await {
    Ok(v)  => println!("успели: {v}"),
    Err(_) => println!("не дождались: future отменён и уничтожен"),
}
```

`select!` работает так же — проигравшие ветки просто дропаются, а `JoinHandle::abort()`
отменяет уже запущенную задачу. Обратная сторона: задачу могут отменить **в любой точке
`.await`**, поэтому не оставляй инварианты «полуобновлёнными» между двумя `await` (например,
списал деньги — и до зачисления ушёл в `await`). В Go горутину без её согласия остановить
нельзя вообще (нужен `ctx.Done()`), здесь — наоборот, отменяют легко и молча.

**Дедлоки Rust не ловит.** «Fearless concurrency» — это про **гонки данных**, а не про
взаимные блокировки. Два потока, берущие два мьютекса в разном порядке, спокойно
скомпилируются и повиснут. Правила профилактики те же, что и в Go: единый порядок захвата,
держать замок как можно короче, не звать чужой код под замком.

И один async-специфичный совет: **не держи `std::sync::MutexGuard` через `.await`**. Задача
может уехать на другой поток, а guard этого не переживёт; на практике компилятор обычно
ловит это как «future is not `Send`». Если замок действительно нужен через `await` — бери
`tokio::sync::Mutex` (он для этого и сделан, но медленнее — сначала подумай, нельзя ли
взять и отпустить обычный замок между `await`'ами).

### Async-трейты (актуальное на 2026)

Раньше `async fn` в трейтах требовал костылей (`async-trait`-крейт). Сейчас **нативный
`async fn` в трейтах стабилен** (через RPITIT) — можно писать прямо:

```rust
trait Fetcher {
    async fn fetch(&self, id: u32) -> u32;   // нативно, без внешнего крейта
}
```

Оговорка: для **trait objects** (`dyn Fetcher`) с async-методами всё ещё есть ограничения,
и там иногда по-прежнему берут `async-trait`. Для статической диспетчеризации (дженерики/
`impl Trait`) нативные async-методы работают.

## Глоссарий модуля

- **Параллелизм** — задачи реально выполняются одновременно на разных ядрах.
  **Конкурентность** — задачи перемежаются на одном ядре; выигрыш там, где они ждут.
- **Поток (thread)** — поток операционной системы; `thread::spawn` создаёт настоящий OS-поток.
- **`Send`** — тип можно переместить в другой поток. **`Sync`** — на тип можно ссылаться из
  нескольких потоков. Оба — маркерные трейты, проверяются компилятором.
- **Гонка данных (data race)** — одновременный доступ к одним данным, где хотя бы один пишет;
  в безопасном Rust невозможна.
- **Дедлок (deadlock)** — взаимная блокировка. Rust её **не** предотвращает.
- **Guard** — объект, возвращаемый `lock()`; пока он жив, замок держится, при `drop` снимается.
- **Отравление (poisoning)** — пометка мьютекса, чей владелец запаниковал; поэтому `lock()`
  возвращает `Result`.
- **Scoped-потоки (`thread::scope`)** — потоки, гарантированно завершающиеся до конца блока,
  поэтому им можно давать обычные ссылки.
- **`mpsc`** — канал «много отправителей, один получатель»; закрывается, когда умирает
  последний `tx`.
- **`Future`** — машина состояний с методом `poll`: «продвинься, если можешь». Ленив.
- **Executor / рантайм** — тот, кто дёргает `poll` у задач (плюс таймеры и опрос сокетов);
  в std его нет, берут Tokio.
- **Задача (task)** — future, отданная рантайму через `spawn`; единица планирования.
- **Кооперативное планирование** — задача уступает управление только на `.await`; отсюда
  правило «не блокируй executor».
- **`spawn_blocking`** — отправить блокирующую/CPU-тяжёлую работу в отдельный пул потоков.
- **Отмена (cancellation)** — уничтожение future (`timeout`, проигравшая ветка `select!`,
  `abort()`); работа просто прекращается.
- **`Send + 'static`** — требование к задачам `spawn`: могут уехать на другой поток и пережить
  породившего.

## Типичные ошибки и заблуждения

- **«async = параллельно, как горутины».** Нет: `async` сам по себе — конкурентность на
  ожидании. Параллелизм даёт многопоточный рантайм + `spawn`. И `Future` ленив: без
  `.await`/рантайма ничего не произойдёт.
- **«Можно расшарить `Rc`/обычные данные между потоками».** Нет: компилятор требует `Send`/
  `Sync`. `Rc` не `Send` — бери `Arc`. Это и есть fearless concurrency.
- **«`Mutex` отдельно от данных, как в Go».** В Rust данные **внутри** `Mutex<T>`, доступ
  только через `lock()`; замок снимается автоматически (RAII). Забыть нельзя.
- **«Блокирующий вызов в async — ничего страшного».** Он затыкает поток executor'а и
  морозит другие задачи. Используй async-аналоги (`tokio::time::sleep`) или `spawn_blocking`.
- **«Нужен async-trait-крейт для async-методов».** Уже нет для статической диспетчеризации —
  нативный `async fn` в трейтах стабилен. Крейт остаётся для некоторых `dyn`-случаев.
- **«Какой рантайм — неважно».** Стандарт — Tokio (экосистема, axum, tower). `async-std`
  мёртв; `smol` — нишевый. Выбор рантайма влияет на доступные библиотеки.
- **«Rust защищает и от дедлоков».** Нет: гарантия только про гонки данных. Взаимная
  блокировка двух мьютексов прекрасно компилируется и вешает программу.
- **«`.unwrap()` после `lock()` — просто ленивый код».** `lock()` возвращает `Result` из-за
  отравления мьютекса (кто-то запаниковал с замком). `unwrap()` здесь — осознанная политика.
- **«Для потоков всегда нужен `Arc`».** Не всегда: `thread::scope` даёт потокам обычные
  ссылки, потому что гарантирует их завершение до конца блока.
- **«Отменить async-задачу нельзя, как и горутину».** Наоборот: drop future = отмена
  (`timeout`, `select!`, `abort()`). Помни, что отмена случается на любом `.await`, и не
  оставляй между ними полуобновлённое состояние.
- **«Замок можно держать через `.await`».** `std::sync::MutexGuard` не `Send`: задача не
  соберётся или сломается при переезде на другой поток. Нужен замок через `await` —
  `tokio::sync::Mutex`.
