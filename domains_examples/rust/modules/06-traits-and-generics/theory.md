# Трейты и дженерики

## Трейт — это контракт поведения (близкий родственник интерфейса Go)

**Трейт** описывает набор методов, которые тип обязуется предоставить. Это очень похоже на
интерфейс Go:

```rust
trait Greet {
    fn hello(&self) -> String;          // обязательный метод

    fn shout(&self) -> String {          // метод с реализацией по умолчанию
        format!("{}!!!", self.hello())
    }
}
```

Реализуем трейт для типа — **явно** (в отличие от Go, где реализация интерфейса неявная):

```rust
struct Dog;
struct Robot;

impl Greet for Dog {
    fn hello(&self) -> String { "гав".to_string() }
}

impl Greet for Robot {
    fn hello(&self) -> String { "beep".to_string() }
    fn shout(&self) -> String { "BEEP BEEP".to_string() }   // переопределили дефолт
}
```

> **Главные отличия от интерфейсов Go:**
> 1. **Явная реализация.** В Go тип реализует интерфейс автоматически, если совпадают
>    сигнатуры (структурно). В Rust ты пишешь `impl Trait for Type` явно — компилятор и
>    читатель точно знают, что тип «подписался» на контракт. Случайное совпадение методов
>    не сделает тип реализацией.
> 2. **Методы по умолчанию.** Трейт может нести реализацию по умолчанию (`shout`), которую
>    тип переопределяет по желанию. В интерфейсе Go тел методов нет.
> 3. **Можно реализовать ЧУЖОЙ трейт для СВОЕГО типа и СВОЙ трейт для ЧУЖОГО типа.**
>    (С правилом сиротства: хотя бы трейт **или** тип должен быть твой.) Можно, например,
>    реализовать `Display` для своей структуры или свой трейт `Summary` для `Vec<T>`.

## Дженерики и trait bounds

Дженерики Rust — это параметрический полиморфизм с ограничениями. «Этот код работает для
любого `T`, **который умеет X**», где «умеет X» — это trait bound:

```rust
use std::fmt::Display;

// T должен реализовывать Display, иначе {} не напечатать
fn announce<T: Display>(item: T) {
    println!(">> {item}");
}

// несколько bound через + ; читаемее — через where
fn largest<T>(list: &[T]) -> &T
where
    T: PartialOrd,        // тип должен поддерживать сравнение
{
    let mut max = &list[0];
    for x in list {
        if x > max { max = x; }
    }
    max
}
```

> **Go-параллель.** До дженериков Go использовал `interface{}` (теперь `any`) и приведения
> в рантайме. С Go 1.18 появились дженерики с **constraints** — и это очень близко к trait
> bounds: `func Largest[T constraints.Ordered](s []T) T`. Разница в реализации (ниже:
> мономорфизация vs словари) и в богатстве системы трейтов.

> **Простыми словами: мономорфизация и vtable.** Представь обобщённую функцию `largest<T>`.
> Компилятору надо выпустить машинный код, который умеет сравнивать «что угодно». Честных
> способов ровно два.
> **(а) Размножить.** Увидев в программе `largest::<i32>` и `largest::<String>`, выпустить
> **две** функции, каждую под свой тип, с прямыми вызовами внутри. Это и есть
> **мономорфизация** («сведение к одной форме»): максимально быстро, всё инлайнится, но кода
> в бинарнике больше.
> **(б) Приложить справочник.** Сделать одну функцию, которая получает данные **и таблицу
> „где лежат методы этого типа“** — это **vtable** (virtual method table). Вызов метода
> превращается в «загляни в таблицу по нужному смещению и прыгни по адресу». Медленнее и не
> инлайнится, зато функция одна и типы можно смешивать.
> Rust даёт выбрать: дженерики / `impl Trait` → (а), `dyn Trait` → (б). Go для интерфейсов
> всегда использует (б): интерфейс-значение в Go — это буквально «данные + таблица методов».

### Мономорфизация: дженерики бесплатны

Когда ты вызываешь `announce::<i32>` и `announce::<String>`, компилятор **генерирует две
отдельные специализированные функции** под `i32` и под `String` — как если бы ты написал их
руками. Это **мономорфизация**. Итог: никакого боксинга, никаких рантайм-приведений,
никаких виртуальных вызовов — дженерик-код по скорости равен написанному вручную. Это и
есть «zero-cost abstractions». Платишь только размером бинарника (копии кода).

> **Контраст с Go.** `any`-подход Go боксирует значение и теряет тип до рантайма; даже
> дженерики Go частично используют словари методов (GC-shape stenciling) и не всегда
> мономорфизируют. Rust мономорфизирует всегда — быстрее в рантайме, дороже по компиляции и
> размеру.

## Дженерики не только у функций: структуры, enum'ы и `impl`-блоки

Параметр типа можно повесить почти на что угодно:

```rust
struct Wrapper<T> {              // структура, параметризованная типом
    inner: T,
    label: String,
}

// impl<T> — методы для ЛЮБОГО T
impl<T> Wrapper<T> {
    fn new(inner: T, label: &str) -> Self {
        Self { inner, label: label.to_string() }
    }
    fn inner(&self) -> &T { &self.inner }
}

// impl с bound — методы, которые появляются только если T что-то умеет
impl<T: std::fmt::Display> Wrapper<T> {
    fn describe(&self) -> String { format!("{}: {}", self.label, self.inner) }
}

// impl для КОНКРЕТНОГО T — метод есть только у Wrapper<u32>
impl Wrapper<u32> {
    fn doubled(&self) -> u32 { self.inner * 2 }
}
```

Три `impl`-блока для одного типа — обычная практика: API «дорастает» по мере того, как тип
что-то умеет. Стандартная библиотека устроена ровно так: у `Option<T>` есть методы для любого
`T`, а есть только для `Option<&T>` (`copied`, `cloned`) или только для `Option<Option<T>>`
(`flatten`). В Go такой «условной части API» нет вовсе: метод либо есть у типа, либо нет.

Кстати, `Option<T>` и `Result<T, E>`, которыми ты уже пользовался, — это просто дженерик-enum'ы
из std, никакой особой поддержки в языке у них не спрятано.

> **Турбофиш.** Когда компилятор не может вывести тип-параметр, его указывают явно
> «рыбкой»: `"42".parse::<i32>()`, `Vec::<u8>::new()`, `iter.collect::<Vec<_>>()`.
> Символ `_` внутри означает «а вот это выведи сам».

## Трейт как тип: статическая vs динамическая диспетчеризация

Трейт можно использовать не только как ограничение, но и как **тип значения** — двумя
способами, и выбор важен.

### Статическая: `impl Trait` / дженерик-параметр

```rust
fn make_greeter() -> impl Greet {     // «возвращаю НЕКИЙ конкретный тип, реализующий Greet»
    Dog
}

fn greet_all(g: &impl Greet) {        // == fn greet_all<T: Greet>(g: &T)
    println!("{}", g.hello());
}
```

`impl Trait` — это всё ещё мономорфизация: конкретный тип известен на компиляции, вызов
метода прямой (static dispatch). Быстро, но: коллекция `Vec<impl Greet>` не может смешивать
разные типы — все элементы должны быть одного конкретного типа.

### Динамическая: `dyn Trait` (trait object)

Когда нужно хранить **разные** типы за одним интерфейсом (гетерогенный список), берут
**trait object** `dyn Trait`, обычно за указателем (`&dyn`, `Box<dyn>`):

```rust
let zoo: Vec<Box<dyn Greet>> = vec![
    Box::new(Dog),
    Box::new(Robot),     // разные типы — ок, объединены трейтом
];

for animal in &zoo {
    println!("{}", animal.hello());   // вызов через vtable (dynamic dispatch)
}
```

`dyn Greet` — это «жирный указатель»: данные + указатель на **vtable** (таблицу методов).
Вызов метода — косвенный (через vtable), как интерфейс-значение в Go. Гибко, но: чуть
медленнее (нет инлайнинга), и нужен указатель (`Box`/`&`), потому что размер типа неизвестен.

| | `impl Trait` / дженерик | `dyn Trait` |
|---|---|---|
| Диспетчеризация | статическая (прямой вызов) | динамическая (vtable) |
| Производительность | максимум (инлайнинг) | чуть ниже (косвенный вызов) |
| Тип элементов | один конкретный | разные за общим трейтом |
| Аналог в Go | дженерик с constraint | интерфейс-значение |
| Когда брать | по умолчанию, перф-критично | гетерогенные коллекции, плагины |

> **Правило по умолчанию:** бери дженерики/`impl Trait` (статика, бесплатно). Переходи на
> `dyn` осознанно — когда реально нужно хранить разнородные типы за одним трейтом или
> уменьшить размер бинарника/время компиляции.

## `derive`: трейты бесплатно

Многие стандартные трейты реализуются механически, и компилятор сгенерирует их за тебя по
аннотации `#[derive(...)]`:

```rust
#[derive(Debug, Clone, PartialEq, Eq, Hash, Default)]
struct Point { x: i32, y: i32 }
```

- `Debug` — отладочный вывод `{:?}` (почти всегда нужен).
- `Clone` — метод `.clone()`; `Copy` — побитовое копирование (только для простых типов).
- `PartialEq`/`Eq` — сравнение `==`. `PartialOrd`/`Ord` — упорядочивание `<`.
- `Hash` — чтобы класть в `HashMap`/`HashSet`. `Default` — `Point::default()`.

> Это похоже на то, как Go генерирует поведение для некоторых вещей сам (сравнение
> сравнимых структур, `%+v` форматирование), но в Rust это явный, расширяемый механизм:
> `derive` — это макрос, и крейты добавляют свои (`Serialize` из serde, `Error` из thiserror).

## Стандартные трейты как общий язык библиотек

Половина практического «знания Rust» — это знание десятка трейтов из std: все крейты
разговаривают друг с другом через них. Минимальный набор, который стоит узнавать в лицо:

| Трейт | Зачем нужен | Как получить |
|---|---|---|
| `Debug` | отладочная печать `{:?}` | `#[derive(Debug)]` |
| `Display` | человеческая печать `{}`, плюс `.to_string()` | писать руками |
| `Clone` / `Copy` | копирование значения | `derive` |
| `PartialEq` / `Eq` | оператор `==` | `derive` |
| `PartialOrd` / `Ord` | `<`, `sort()` | `derive` |
| `Hash` | ключ в `HashMap` / `HashSet` | `derive` (нужен вместе с `Eq`) |
| `Default` | `T::default()` | `derive` |
| `From` / `Into` | конверсия типов; на ней работает `?` | писать `From`, `Into` придёт само |
| `Iterator` | цикл `for` и адаптеры (модуль 07) | реализуют `next()` |
| `Deref` | «прозрачные» умные указатели (модуль 08) | руками, редко |

### Свой `Display` и свой `From`

Это два трейта, которые пишут руками чаще всего.

```rust
use std::fmt;

struct Money { cents: u64 }

impl fmt::Display for Money {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "{}.{:02}", self.cents / 100, self.cents % 100)
    }
}

println!("{}", Money { cents: 12345 });            // 123.45
let s: String = Money { cents: 50 }.to_string();   // "0.50" — и это мы не писали!

impl From<u64> for Money {
    fn from(cents: u64) -> Self { Money { cents } }
}

let a = Money::from(500u64);
let b: Money = 500u64.into();     // .into() тоже появился сам
```

Обрати внимание на подарки: реализовав `Display`, ты бесплатно получил `to_string()`, а
реализовав `From` — метод `.into()`. Это **blanket implementation** — реализация «для всех
типов, удовлетворяющих условию», записанная в std один раз: «для любого `T: Display`
реализовать `ToString`». В Go такого механизма нет: там каждый метод пишут вручную для
каждого типа.

### Почему «Partial»: `PartialEq` vs `Eq`, `PartialOrd` vs `Ord`

Странность, о которую спотыкаются все. Виновата плавающая точка: `f64::NAN != f64::NAN`, а
для `NaN` не определены ни `<`, ни `>`. То есть равенство и порядок у `f64` **частичные**
(partial) — определены не для всех значений.

- `PartialEq` — «`==` есть, но не обязательно ведёт себя как математическое равенство»
  (`f64` реализует только его).
- `Eq` — маркер без методов: «равенство настоящее» (`i32`, `String` реализуют).
- `PartialOrd` — сравнение может ответить «несравнимы»: `partial_cmp` → `Option<Ordering>`.
- `Ord` — полный порядок, ответ есть всегда: `cmp` → `Ordering`.

Практические следствия, с которыми столкнёшься в модуле 07: ключом `HashMap` может быть
`String` или `i32` (они `Eq + Hash`), а `f64` — не может. `v.sort()` требует `Ord`, поэтому
вектор `f64` сортируют через `v.sort_by(f64::total_cmp)`. Это не бюрократия, а честность:
язык отказывается делать вид, что `NaN` ведёт себя нормально.

## Associated types: «выходной тип» трейта

Иногда трейту нужен связанный тип, а не параметр. Канонический пример — `Iterator`:

```rust
trait Iterator {
    type Item;                          // associated type — что выдаёт итератор
    fn next(&mut self) -> Option<Self::Item>;
}
```

`type Item` задаётся реализацией один раз (для `Counter` — `u32`, для строкового итератора
— `char`). Это чище, чем тащить `Iterator<Item>` параметром повсюду. Стандартные трейты
(`Iterator`, `Deref`, `Add`) построены на associated types — мы встретим их в модулях 07–08.

## Глоссарий модуля

- **Трейт (trait)** — контракт поведения: набор методов, которые тип обязуется предоставить.
- **Реализация (`impl Trait for Type`)** — явное «этот тип подписывается на контракт».
- **Trait bound** — требование к дженерик-параметру (`T: Display`); длинный список выносят
  в `where`.
- **Мономорфизация** — генерация отдельной копии кода под каждый конкретный тип.
- **Static dispatch** — вызов метода известен на компиляции (дженерики, `impl Trait`).
- **Dynamic dispatch** — вызов через таблицу методов в рантайме (`dyn Trait`).
- **Trait object (`dyn Trait`)** — значение неизвестного типа за указателем, вместе с vtable.
- **vtable** — таблица адресов методов конкретного типа.
- **Жирный указатель (fat pointer)** — указатель + дополнительное слово (для `dyn Trait` это
  vtable, для `&[T]` — длина).
- **`impl Trait`** — «некий конкретный тип, реализующий трейт»: в аргументе — сахар над
  дженериком, в возвращаемом типе — «не хочу называть тип, но он один».
- **Associated type** — тип, задаваемый реализацией трейта один раз (`Iterator::Item`).
- **`derive`** — генерация реализации трейта макросом на этапе компиляции.
- **Blanket implementation** — реализация для всех типов с некоторым свойством (`impl<T: Display> ToString for T`).
- **Marker trait** — трейт без методов, несущий только гарантию (`Copy`, `Send`, `Sync`, `Eq`).
- **Правило сиротства (orphan rule)** — реализовать трейт можно, если твой либо трейт, либо тип.
- **Newtype** — обёртка `struct My(Their)`, чтобы обойти правило сиротства и/или добавить смысл.
- **Турбофиш (`::<>`)** — явное указание типа-параметра: `parse::<i32>()`.
- **dyn-совместимость (object safety)** — набор условий, при которых трейт можно превратить в
  `dyn Trait` (нет дженерик-методов, нет методов, возвращающих `Self`, и т.п.).

## Типичные ошибки и заблуждения

- **«Трейт = интерфейс Go один в один».** Близко, но: реализация явная, есть методы по
  умолчанию, можно реализовать для чужих типов, по умолчанию — статическая диспетчеризация.
- **«Дженерики медленные / боксируют, как `any`».** Наоборот: мономорфизация делает их
  бесплатными в рантайме. Боксинг — только у `dyn`.
- **«`dyn` и `impl Trait` — одно и то же».** Нет: `impl Trait` — статика (один конкретный
  тип, прямой вызов), `dyn` — динамика (vtable, разные типы). Разный перф и разные
  возможности.
- **«`Vec<impl Trait>` хранит разные типы».** Нет: `impl Trait` — это один конкретный тип.
  Для разнородных — `Vec<Box<dyn Trait>>`.
- **«Можно реализовать любой трейт для любого типа».** Правило сиротства: трейт **или** тип
  должен быть твоим. Нельзя реализовать чужой трейт для чужого типа (обходят через
  newtype-обёртку).
- **«`derive` — это рефлексия в рантайме».** Нет, это генерация кода на компиляции (макрос),
  zero-cost.
- **«`Display` тоже можно `derive`».** Нельзя: как именно показывать тип человеку — решение
  автора, компилятор его не угадает. `Debug` — `derive`, `Display` — руками.
- **«Любой трейт можно превратить в `dyn Trait`».** Нет, нужна dyn-совместимость: трейт с
  дженерик-методами или методами, возвращающими `Self`, объектом не сделать (ошибка «the trait
  cannot be made into an object»). Обход — отдельный «объектный» трейт-фасад.
- **«`f64` можно положить ключом в `HashMap` / просто позвать `v.sort()`».** Нет: `f64` не
  `Eq` и не `Ord` из-за `NaN`. Для сортировки — `v.sort_by(f64::total_cmp)`.
- **«Дженерики — это про экономию строк».** В первую очередь это про **гарантии**: bound
  доказывает, что нужное поведение у типа есть, ещё до запуска.
