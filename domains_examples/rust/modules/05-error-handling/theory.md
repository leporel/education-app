# Обработка ошибок

## Ошибки — это значения (как в Go), но иначе упакованные

Rust и Go согласны в главном: **ошибки — обычные значения**, а не выбрасываемые исключения,
которые летят сквозь стек. Это делает поток управления честным и видимым. Но упаковка
разная.

В Go функция возвращает **два** значения — результат и ошибку — и ты по соглашению
проверяешь второе:

```go
// Go
f, err := os.Open("file.txt")
if err != nil {
    return err
}
// ...используем f
```

Тонкость: при `err != nil` значение `f` обычно «нулевое», но язык **не мешает** тебе
обратиться к нему, забыв проверку. В Rust результат и ошибка — это **один** тип-сумма
`Result<T, E>`, где есть **либо** успех, **либо** ошибка, но не оба:

```rust
enum Result<T, E> {   // обычный enum из прелюдии
    Ok(T),
    Err(E),
}
```

```rust
use std::fs::File;

fn open() -> Result<File, std::io::Error> {
    let f = File::open("file.txt")?;   // см. оператор ? ниже
    Ok(f)
}
```

Поскольку `Ok` и `Err` — разные варианты, добраться до значения, не разобрав ошибку,
**невозможно** — ровно как с `Option`. Это закрывает Go-граблю «использовал результат,
забыв проверить `err`».

## Оператор `?` — проброс ошибки без бойлерплейта

Главная эргономическая разница. В Go проброс ошибки — это ритуал `if err != nil { return
err }`, повторённый на каждом шаге. В Rust есть `?`:

```rust
use std::fs;

fn read_config() -> Result<String, std::io::Error> {
    let text = fs::read_to_string("config.toml")?;   // если Err — вернуть его из функции
    Ok(text)                                          // если Ok — развернуть и продолжить
}
```

`expr?` означает: «если `expr` — это `Ok(v)`, дай мне `v` и иди дальше; если `Err(e)` —
немедленно `return Err(e)` из текущей функции». Один символ вместо четырёх строк. Сравни
цепочку:

```rust
fn load() -> Result<Config, MyError> {
    let raw = fs::read_to_string("c.toml")?;   // io error пробросится
    let cfg = parse(&raw)?;                     // parse error пробросится
    validate(&cfg)?;                            // validation error пробросится
    Ok(cfg)
}
```

В Go это были бы три блока `if err != nil`. `?` не прячет ошибки (как исключения) — поток
по-прежнему явный, просто без ручного повторения.

> **Важная деталь: `?` конвертирует ошибку.** Если тип ошибки выражения не совпадает с
> типом ошибки функции, `?` попробует привести его через трейт `From`. Поэтому разные
> ошибки (`io::Error`, `ParseIntError`) можно пробрасывать в общий `MyError`, если для него
> реализован `From`. Крейты `thiserror`/`anyhow` (ниже) делают это за тебя.

## `?` работает и на `Option`

`?` на `Option` пробрасывает `None`:

```rust
fn first_char_upper(s: &str) -> Option<char> {
    let c = s.chars().next()?;       // None → функция вернёт None
    Some(c.to_ascii_uppercase())
}
```

Конвертация между мирами:

```rust
// Option → Result: дать ошибку на месте None
let name: Result<String, MyError> = maybe_name.ok_or(MyError::Missing);

// Result → Option: выбросить причину ошибки
let opt: Option<String> = some_result.ok();
```

## `panic!` vs возврат ошибки — где граница

Это ключевое разделение, которое надо уложить.

- **`Result` / `Option`** — для **ожидаемых, восстановимых** ситуаций: файла нет, ввод
  кривой, сеть отвалилась, пользователь не найден. Вызывающий **может и должен** их обработать.
- **`panic!`** — для **невосстановимых** ситуаций и **нарушенных инвариантов**: «такого не
  может быть, а если случилось — программа в неконсистентном состоянии, продолжать опасно».
  Паника разворачивает стек (или аборт), печатает сообщение и роняет поток.

```rust
fn divide(a: i32, b: i32) -> Result<i32, String> {
    if b == 0 {
        return Err("деление на ноль".to_string());   // ОЖИДАЕМАЯ ошибка → Result
    }
    Ok(a / b)
}

fn get(v: &[i32], i: usize) -> i32 {
    v[i]      // если i вне границ — это panic (нарушен инвариант вызывающего)
}
```

`unwrap()` / `expect("msg")` на `Result`/`Option` — это **запрос паники**: «дай значение
или паникуй». Уместно в тестах, прототипах и там, где `Err`/`None` действительно
невозможен по логике (и `expect` документирует, почему). В прод-коде по умолчанию —
возвращать `Result` и пробрасывать `?`.

> **Go-параллель.** `panic` в Go — тоже «невосстановимо/баг», и в идиоматичном Go его
> избегают в библиотеках, возвращая `error`. Та же философия: ожидаемое — значение
> (`Result`/`error`), катастрофа — паника. Разница в эргономике (`?` против `if err`) и в
> том, что Rust не даёт проигнорировать `Result` (есть предупреждение `#[must_use]`).

## `main`, возвращающий `Result`

`main` может вернуть `Result`, чтобы пользоваться `?` прямо в нём:

```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let text = std::fs::read_to_string("config.toml")?;
    println!("{text}");
    Ok(())
}
```

`Box<dyn std::error::Error>` — «любая ошибка, реализующая стандартный трейт `Error`»
(динамический тип ошибки; `dyn` разберём в модуле 06). Если `main` вернёт `Err`, программа
завершится с ненулевым кодом и напечатает ошибку.

## Не только пробрасывать: как ошибку обработать на месте

`?` — это про «наверх». Но иногда решение принимается здесь и сейчас, и для этого есть свои
инструменты.

**Разобрать по причине.** У `io::Error` есть `kind()` — перечисление, по которому удобно
матчить. Это прямой аналог `errors.Is(err, os.ErrNotExist)` из Go:

```rust
use std::fs;
use std::io::ErrorKind;

fn read_or_default(path: &str) -> String {
    match fs::read_to_string(path) {
        Ok(s) => s,
        // файла нет — это нормальная ситуация, у нас есть дефолт
        Err(e) if e.kind() == ErrorKind::NotFound => String::from("<default>"),
        // всё остальное (нет прав, диск отвалился) обрабатывать здесь нечем
        Err(e) => panic!("не смог прочитать {path}: {e}"),
    }
}
```

Для своего enum-типа ошибки всё ещё проще: `match err { AppError::NotFound => ..., ... }` —
обычный исчерпывающий разбор, как с любым enum. Именно поэтому библиотеки описывают ошибки
через `thiserror`: у вызывающего появляется возможность **различать** случаи, а не только
печатать текст.

**Комбинаторы на `Result`** — когда ветвление избыточно:

```rust
let a: i32 = "42".parse().unwrap_or(0);              // дефолт вместо ошибки
let b: i32 = "oops".parse().unwrap_or_default();     // «нуль своего типа» (для i32 — 0)
let cfg = load().unwrap_or_else(|e| {                 // дефолт + лог
    eprintln!("warning: {e}");
    Config::default()
});

// map_err — заменить или обогатить ошибку перед пробросом
let port: u16 = raw.parse().map_err(|_| AppError::Invalid(raw.to_string()))?;

// and_then — «если получилось, сделай следующее, которое тоже может упасть»
let value = read_file(path).and_then(|s| parse(&s));
```

**Цепочка причин.** Трейт `std::error::Error` умеет отдавать причину через `source()`, и
`anyhow`/`thiserror` этим пользуются: при печати получается не одна строка, а «что и почему»:

```text
Error: не смог прочитать c.toml

Caused by:
    0: No such file or directory (os error 2)
```

Это ровно то, за чем в Go оборачивают ошибки через `fmt.Errorf("...: %w", err)`. Разница в
том, что здесь цепочка выстраивается сама, а `.context("...")` из `anyhow` добавляет к ней
человеческий слой.

> Мелочь, которая пригодится сразу: **тест тоже может возвращать `Result`**, и тогда внутри
> него можно писать `?` вместо гирлянды `unwrap()`:
> `#[test] fn parses() -> Result<(), Box<dyn std::error::Error>> { let n: i32 = "42".parse()?; assert_eq!(n, 42); Ok(()) }`

## Что физически происходит при панике

Стоит знать, чтобы `panic!` не выглядел чёрным ящиком.

1. Печатается сообщение и место: `thread 'main' panicked at src/main.rs:12:5`.
2. Начинается **раскрутка стека** (unwinding): Rust идёт по кадрам вверх и **вызывает `drop`
   у всех живых значений** — файлы закрываются, мьютексы освобождаются. Это не «выход в
   никуда», ресурсы подчищаются.
3. Умирает **паникующий поток**. Если это `main` — процесс завершается с кодом 101. Если
   паникует рабочий поток, программа живёт дальше, а `handle.join()` вернёт `Err` (модуль 09).

Полезные ручки:

- `RUST_BACKTRACE=1 cargo run` — напечатает стек вызовов паники. Первое, что делают, увидев
  панику в логе.
- В `Cargo.toml` можно попросить не раскручивать стек, а падать сразу:
  `[profile.release] panic = "abort"`. Бинарник меньше и чуть быстрее, но `drop`'ы не
  вызываются и панику нельзя перехватить.
- Перехват существует (`std::panic::catch_unwind`), но это инструмент для границ FFI и
  серверов-надзирателей, а не замена обработке ошибок. `panic` — не исключение, и притворяться,
  что это `try/catch`, — плохая идея.

> **Go-параллель.** `recover()` в Go применяют примерно за тем же: не дать одному запросу
> уронить сервер. В Rust ту же роль обычно играет не `catch_unwind`, а изоляция по
> потокам/задачам (упавшая задача возвращает `Err` в `join`/`await`) — плюс общий принцип
> «ожидаемое → `Result`, а не паника».

## Свои ошибки: `thiserror` и `anyhow`

Для своего типа ошибки обычно берут `enum`:

```rust
enum ConfigError {
    NotFound,
    Invalid(String),
}
```

Но чтобы он хорошо работал с `?` и печатался, нужно реализовать трейты `Display`,
`std::error::Error` и `From` для конвертаций — это много ручного кода. Экосистема решила
это двумя крейтами:

- **`thiserror`** — для **библиотек**: derive-макрос, который генерирует `Display`/`Error`/
  `From` по аннотациям. Ты объявляешь точный, типизированный enum ошибок для своего API.

  ```rust
  use thiserror::Error;

  #[derive(Debug, Error)]
  enum ConfigError {
      #[error("файл не найден")]
      NotFound,
      #[error("неверный формат: {0}")]
      Invalid(String),
      #[error(transparent)]
      Io(#[from] std::io::Error),   // авто-From: io::Error -> ConfigError
  }
  ```

- **`anyhow`** — для **приложений** (бинарей): один тип `anyhow::Error`, который проглотит
  любую ошибку, плюс удобный `Context` для добавления пояснений. Не нужно описывать каждый
  вариант — когда тебе важно «сообщить и упасть», а не различать ошибки программно.

  ```rust
  use anyhow::{Context, Result};

  fn load() -> Result<String> {                      // anyhow::Result<String>
      let s = std::fs::read_to_string("c.toml")
          .context("не смог прочитать c.toml")?;     // добавили контекст
      Ok(s)
  }
  ```

> **Правило большого пальца.** Пишешь **библиотеку** — типизированные ошибки через
> `thiserror` (пусть вызывающий различает случаи). Пишешь **приложение** — `anyhow` (тебе
> важно собрать причину и показать). Это де-факто стандарт экосистемы на 2026 год. Оба —
> внешние крейты, ставятся `cargo add thiserror` / `cargo add anyhow`.

## Глоссарий модуля

- **`Result<T, E>`** — enum `Ok(T)` / `Err(E)`: успех или ошибка, но не оба сразу.
- **`?`** — оператор проброса: разворачивает `Ok`/`Some`, а на `Err`/`None` делает ранний
  возврат (с конверсией через `From` при необходимости).
- **`From` / `Into`** — трейты конверсии; на них держится автоматическое приведение ошибок в `?`.
- **`#[must_use]`** — атрибут «результат нельзя молча выбросить»; висит на `Result`, `Option`
  и итераторах.
- **`unwrap()` / `expect("...")`** — «дай значение или паникуй»; `expect` ещё и документирует,
  почему `Err`/`None` здесь невозможен.
- **`panic!`** — невосстановимая ошибка/нарушенный инвариант: раскрутка стека и смерть потока.
- **Unwinding (раскрутка)** — проход по кадрам стека с вызовом `drop`; альтернатива —
  `panic = "abort"`.
- **Backtrace** — стек вызовов паники, включается переменной окружения `RUST_BACKTRACE=1`.
- **`Box<dyn std::error::Error>`** — «любая ошибка, реализующая стандартный трейт `Error`»
  (динамический тип; удобно в `main` и прототипах).
- **`source()`** — метод трейта `Error`, отдающий причину; из него складывается цепочка
  `Caused by`.
- **`ErrorKind`** — enum-классификация ошибок ввода-вывода (`NotFound`, `PermissionDenied`, ...).
- **`thiserror`** — derive для типизированных ошибок библиотеки; **`anyhow`** — универсальный
  тип ошибки для приложений, с `.context()` и макросом `bail!`.

## Типичные ошибки и заблуждения

- **«`?` — это как исключения / try-catch».** Нет: поток остаётся явным, `?` просто
  заменяет ручной `return Err(e)`. Никакого невидимого «прыжка через стек».
- **«`unwrap()` везде — это нормально».** `unwrap()` паникует; в проде это краш. Используй
  `?`/`match`, а `unwrap`/`expect` — только где `Err`/`None` логически невозможен.
- **«`panic!` — способ вернуть ошибку».** Паника — для невосстановимого/багов. Ожидаемые
  ошибки — `Result`, который вызывающий обработает.
- **«Надо всегда писать свой enum ошибок руками».** Для библиотек используй `thiserror`,
  для приложений — `anyhow`; ручная реализация `Error`/`From` почти не нужна.
- **«`Result` можно проигнорировать, как в Go можно забыть err».** `Result` помечен
  `#[must_use]` — игнор даёт предупреждение компилятора. Забыть труднее.
- **«`?` сам приведёт любую ошибку к моему типу».** Только если есть `From`-конверсия.
  `thiserror`'s `#[from]` или `anyhow` обеспечивают её.
- **«Паника — это как исключение, её надо ловить».** `catch_unwind` существует, но это не
  `try/catch`: панику не «обрабатывают», а не допускают. Ожидаемое — `Result`.
- **«При панике ресурсы текут».** Нет: при раскрутке стека вызываются `drop`'ы (кроме режима
  `panic = "abort"`). Файлы и замки освобождаются.
- **«Обработка ошибки — это только `?` наверх».** Ещё есть разбор по причине
  (`e.kind()`, `match` по своему enum) и комбинаторы (`unwrap_or`, `unwrap_or_else`,
  `map_err`, `and_then`).
