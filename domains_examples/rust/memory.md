## Слабые места

Прогнозируемые зоны риска для опытного Go-разработчика (проверить на практике, не
постулировать заранее):
- **Борьба с borrow checker.** Привычка из Go «беру указатель и передаю куда угодно»
  ломается о правила заёма (один `&mut` ИЛИ много `&`). Лечится чтением ошибок, а не угадыванием.
- **Move вместо копии.** После `let b = a;` (если тип не `Copy`) `a` больше нельзя
  использовать. В Go присваивание копирует — здесь перемещает владение.
- **Lifetimes как явная вещь.** В Go «указатель жив, пока жив объект» — забота GC. Здесь
  компилятор требует доказать, что ссылка не переживёт данные.
- **Нет `nil`.** Вместо «забыл проверить на nil → паника в проде» — `Option<T>`, который
  обязывает обработать `None`. Перестроиться с `if x != nil`.
- **`Result` вместо `if err != nil`.** Оператор `?` вместо ручного проброса; `panic!` —
  не «верни ошибку», а «программа сломана».
- **Трейты ≠ интерфейсы один-в-один.** Можно реализовать чужой трейт для своего типа;
  static dispatch по умолчанию (мономорфизация), `dyn` — отдельный осознанный выбор.
- **Async ≠ goroutines.** Нет встроенного планировщика: нужен рантайм (Tokio). `Future`
  ленив (ничего не делает, пока его не поллят). Блокирующий вызов в async «затыкает» исполнитель.
